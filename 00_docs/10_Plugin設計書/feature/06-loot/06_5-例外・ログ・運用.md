# 06_5-例外・ログ・運用

## 1. 方針

`loot` は API から構築した不変 snapshot を原子的に公開する。全件 prepare 失敗時は直前 snapshot を維持し、単体 fallback 失敗時は `null` で利用側へ返す。

## 2. 主なログポイント

- `LootService`
  - snapshot 公開: `LogId.I_5300`
  - 詳細 cache 登録: `LogId.D_5301`
  - 全件・単体ロード失敗: `LogId.E_5301`
- `LootRepository`
  - 個別取得成功: `LogId.D_5300`
  - 個別 404: `LogId.W_5300`
  - HTTP・変換失敗: `LogId.E_5300`

## 3. 例外境界

- `LootRepository`
  - HTTP 異常は `LogId.E_5300` を記録して例外化する。
  - `InterruptedException` は interrupt flag を再設定して `RuntimeException` 化する。
- `LootService.loadSnapshot`
  - repository 例外を呼び出し元へ伝播し、公開 cache を変更しない。
- `LootService.loadAll`
  - 全件例外を捕捉し、`LogId.E_5301` を記録して `0` を返す。
- `LootService.getLoadedOrFetch`
  - 単体例外を捕捉し、`LogId.E_5301` を記録して `null` を返す。

## 4. thread と snapshot

- 起動時 `loadAll` は非同期セットアップで実行する。
- `loadedLoots` は `volatile Map`、公開値は copy 済みの変更不能 `LinkedHashMap` とする。
- 全件・単体追加・clear は map の中身を変更せず、`cacheLock` 内で新 snapshot へ参照置換する。
- reader は更新前または更新後の完全な snapshot だけを参照する。
- `getLoadedOrFetch` 自体は同期 HTTP を含むため、item 側からメインスレッドで cache miss した場合の改善は [[04_9-未決事項]] を正本とする。

## 5. 利用側表示

- loot feature 単独のプレイヤーメッセージやコマンドは定義しない。
- bundle Lore の解決失敗は item feature が `◆ ルート情報: <lootTableId> (未取得)` と表示する。
- bundle 開封の解決失敗は item feature がエラーを通知し、bundle を消費しない。
