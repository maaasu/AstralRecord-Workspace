# 33_5-例外・ログ・運用

## 配置順

`server_metrics`メッセージの互換性を保つため、更新時はAstralRecordProxyを先に配置してVelocityを再起動し、その後にAstralRecordLobbyと各RPGサーバーのAstralRecordを更新する。一括停止して全成果物を同時配置する場合はこの順序を問わない。

## 配置前提

- 外部公開ポートはVelocityだけとし、Lobby・ch1・ch2・devのbackendポートはループバックまたはホスト内firewallで直接接続を拒否する。
- Velocityはオンライン認証を有効にし、Paper backendはVelocity modern forwardingと共通secretを有効にする。
- Velocity本体へ`lobby`、`ch1`、`ch2`、`dev`を登録し、`AstralRecordProxy`の同名設定と一致させる。
- `AstralRecordLobby.jar`とDiscordSRVはLobbyだけへ置く。RPGには`AstralRecord.jar`を置き、DiscordSRVを置かない。
- Proxy、Lobby、APIの`apiKey`は同じ有効値を設定し、サンプル値`your_api_key`のまま起動しない。
- ProxyとLobbyの`api.baseUrl`は実際にAPIが待ち受けるURLへ変更する。初期値の`http://127.0.0.1:5261`はAPIの開発用HTTP profileに合わせている。同一PCのHTTP URLからHTTPSへリダイレクトされる構成にもクライアントは追従するが、本番ではAPI証明書を検証できるHTTPS URLを使用する。
- ProxyとLobbyの`api.allowInsecureTls`は既定値`false`とする。開発環境で自己署名証明書を使う場合に限り`true`を許可し、有効時は証明書チェーンとホスト名の検証を無効化して起動ログへ警告を出す。本番では検証を無効化しない。
- Proxyの`serverCapacities.<serverId>`は`maxPlayers`、`donorExtraPlayers`、`adminExtraPlayers`を持つ。旧形式の単一数値も基本上限として読み込むが、その場合の追加枠は0とする。
- ch1、ch2、devは同一ワールドファイルを同時に開かず、サーバーごとに独立したworldディレクトリを使用する。共有するのはAPI/DB上のプレイヤーデータだけとする。

## 起動順

1. SQL ServerとAstralRecord API
2. Lobby、ch1、ch2、devの各Paperサーバー
3. Velocity Proxy

APIの所在・チャット状態はメモリ管理のため、APIだけを再起動した場合も30秒以内に所在は再構築される。チャット中継cursorはsequence巻き戻りを検出して再開する。

## 障害時動作

- Lobby admissionでAPIへ接続できない場合はfail closedで接続を拒否する。
- 所在heartbeat失敗はMinecraft接続を切断せず、次回周期で再送する。
- Discordチャットpoll失敗はログを出して次回周期で再試行する。
- RPGの保存が失敗した場合はロビー転送せず切断する。プレイヤーへ再接続を案内し、Proxyの初期接続規則によりLobbyへ戻す。
- 接続先backendが停止中または満員の場合はProxyが接続を拒否し、Lobbyに残す。
- Lobbyのサーバー状態API取得に失敗した場合はGUIを開いたまま人数情報を利用不可とし、接続要求を送らない。
