# 33_5-例外・ログ・運用

## 配置順

ネットワーク管理導入時はManagementDBスキーマ、API、Proxy、RPG/Webの順で配置する。APIはadmissionでも新しい表を参照するため、スキーマ確認が終わるまで配置しない。Proxyの初回取り込みが成功するまで旧config.ymlをバックアップとして保持する。以後はWeb管理値が正本で、YAMLを書き換えて再起動しても上書きしない。

### ManagementDBの明示移行

既存3DB用db-migrateはManagementDBを扱わない。運用SQL接続先を明示し、既存DBのバックアップ後に以下を実行する。`$networkSqlServer`には配置先設定と照合した接続先を指定する。例はWindows統合認証であり、パスワードをコマンド本文へ記載しない。

```powershell
sqlcmd -S $networkSqlServer -E -b -i '00_docs/40_Database設計書/table-definitions/ManagementDB/migrations/20260916_managed_network_and_bans.sql'
if ($LASTEXITCODE -ne 0) { throw 'ManagementDB migration failed; do not deploy API.' }
sqlcmd -S $networkSqlServer -E -b -d ManagementDB -Q "IF OBJECT_ID(N'dbo.network_settings', N'U') IS NULL OR OBJECT_ID(N'dbo.network_ban', N'U') IS NULL OR OBJECT_ID(N'dbo.network_management_audit', N'U') IS NULL THROW 51020, 'Network schema missing.', 1; SELECT migration_id FROM dbo.schema_migration WHERE migration_id = N'20260916_managed_network_and_bans';"
if ($LASTEXITCODE -ne 0) { throw 'ManagementDB schema verification failed.' }
```

新規DBは`ManagementDB/init.sql`を先に適用する。既存playerの件数・UUID・web_admin・公開状態が保持されることを確認する。migrationはトランザクション、専用アプリケーションロック、適用台帳で直列化・冪等化する。ゲームDB再構築ツールをManagementDBへ向けない。

### 初回設定取り込みと切替

1. APIに`Network:AuthoritySyncKey`と`Network:ModerationKey`を設定する。いずれも共通APIキーと異なる秘密値を使う。
2. Proxyの`api.authoritySyncKey`を一致させて起動する。`GET /api/network/settings`が404なら旧YAMLの非API値をbootstrapへ送る。Webで先に初期作成した場合はWeb設定をそのまま使用する。
3. WebAdminの`/Admin/Network`で表示名・定員・周期・全体権限・Discord通知を旧設定と照合する。RPG側で使っていたdebug/whitelistを必要なチャンネルへMCIDで登録し、ホワイトリストを有効化する。
4. RPGの`api.networkModerationKey`をAPIと一致させ、`network.channelName`を管理チャンネルIDへ合わせて配置する。Lobby GUIの接続先IDとVelocity登録名も一致させる。名前変更だけでVelocity/Lobbyの定義を自動変更しない。
5. APIキー類はWeb画面にもManagementDB設定JSONにも含めない。Proxy設定GET、入場、Web保存、BANの期限表示を検証する。実プレイヤーへの試験BANは行わず専用検証ユーザーを用いる。

## 配置前提

- 外部公開ポートはVelocityだけとし、Lobby・ch1・ch2・devのbackendポートはループバックまたはホスト内firewallで直接接続を拒否する。
- Velocityはオンライン認証を有効にし、Paper backendはVelocity modern forwardingと共通secretを有効にする。
- Velocity本体へ`lobby`、`ch1`、`ch2`、`dev`を登録し、`AstralRecordProxy`の同名設定と一致させる。
- `AstralRecordLobby.jar`とDiscordSRVはLobbyだけへ置く。RPGには`AstralRecord.jar`を置き、`discord.enabled: false`としてDiscordSRVを置かない。この設定ではAstralRecordの起動・whitelist切替・停止処理からDiscordSRVのクラスを参照しない。
- Proxy、Lobby、APIの`apiKey`は同じ有効値を設定し、サンプル値`your_api_key`のまま起動しない。
- Proxyの`api.authoritySyncKey`とAPIの`Network:AuthoritySyncKey`は同じ専用値へ設定し、通常backendへ配布しない。bootstrapと移行前authorities PUTで要求する。RPG `/ban`は別の`api.networkModerationKey` / `Network:ModerationKey`を使用する。共通APIキーと同値・空値では更新を拒否する。
- ProxyとLobbyの`api.baseUrl`は実際にAPIが待ち受けるURLへ変更する。初期値の`http://127.0.0.1:5261`はAPIの開発用HTTP profileに合わせている。同一PCのHTTP URLからHTTPSへリダイレクトされる構成にもクライアントは追従するが、本番ではAPI証明書を検証できるHTTPS URLを使用する。
- ProxyとLobbyの`api.allowInsecureTls`は既定値`false`とする。開発環境で自己署名証明書を使う場合に限り`true`を許可し、有効時は証明書チェーンとホスト名の検証を無効化して起動ログへ警告を出す。本番では検証を無効化しない。
- 管理チャンネルは`maxPlayers`、`donorExtraPlayers`、`adminExtraPlayers`を持つ。初回移行時は旧`serverCapacities.<serverId>`の単一数値も基本上限として読み込み、その場合の追加枠は0とする。非負intの合計はProxy側でint最大値へ飽和させる。
- Proxyの`discord.excludedSourceServers`にbackend IDを指定すると、そのサーバーのMinecraft全体チャットはProxy内へ配信するが、Network APIへ登録せず、LobbyからDiscordへ中継しない。未設定または空リストでは全backendをDiscord中継対象とする。
- 同じ除外backendはDiscord接続通知にも適用し、除外backendへの切替、除外backendからの切替、除外backend上での実切断を通知しない。
- 旧`serverAuthorityUsers`は初回取り込みだけに使用する。Webでの追加はゲームDBに登録されたMCID候補から選択しUUIDを保存する。Proxyは既定5秒周期（API通信設定`api.settingsRefreshSeconds`）で管理設定を取得するため、通常の変更反映に再起動を要しない。
- 在席通知間隔は既定10秒を推奨する。旧設定互換のため長い間隔も保存可能だが、30秒以上では次のheartbeatまでに所在TTLを超える。負の容量・クールタイム、1秒未満の周期は拒否する。
- ch1、ch2、devは同一ワールドファイルを同時に開かず、サーバーごとに独立したworldディレクトリを使用する。共有するのはAPI/DB上のプレイヤーデータだけとする。

## 起動順

1. SQL ServerとAstralRecord API
2. Lobby、ch1、ch2、devの各Paperサーバー
3. Velocity Proxy

APIの所在・チャット状態はメモリ管理のため、APIだけを再起動した場合も30秒以内に所在は再構築される。チャット中継cursorはsequence巻き戻りを検出して再開する。
管理設定・最高権限・BANはDBに保持され、API再起動では失われない。

## 障害時動作

- Lobby admissionでAPIへ接続できない場合はfail closedで接続を拒否する。
- 所在heartbeat失敗はMinecraft接続を切断せず、次回周期で再送する。
- Discordチャットpoll失敗はログを出して次回周期で再試行する。
- Proxyの設定更新失敗は最後の正常スナップショットを保持し、次回再試行する。ただし接続・転送admissionの失敗は接続拒否とする。RPGの接続前channel-accessも失敗・未知チャンネルを拒否し、ローカル設定へ戻さない。オンラインのチャンネルロールcacheは5秒TTL、旧全体権限cacheは30秒TTLとし、失敗が続いた場合にローカルdebugへ昇格させない。
- RPGの player-state または Quest state 保存が失敗した場合はロビー転送要求を送らない。無敵化と操作凍結を解除し、プレイヤーを現在チャンネルに残して保存失敗メッセージを表示する。
- 接続先backendが停止中または満員の場合はProxyが接続を拒否し、Lobbyに残す。
- Lobbyのサーバー状態API取得に失敗した場合はGUIを開いたまま人数情報を利用不可とし、接続要求を送らない。
