# 26_3-サービス

## 1. 最寄り入口検索

クラス名: `BossChallengeService`
物理名: `findNearestChallengeEntry`

引数: Bukkit `Player`

結果: `BossEntryHit?`

処理内容:

1. ロード済み `MobCategory.BOSS` ID を走査し、template と challenge があるものだけ対象にする。
2. `entryLocation.worldId` を WorldMasterData、解決できなければ Bukkit world 名としてロード済み world へ解決する。
3. プレイヤーと同一 world かつ `entryRadius` 内の入口を候補にする。
4. 実距離が最小の候補を返す。同距離は boss ID の辞書順で決める。対象なしは `null` を返す。

副作用とプレイヤーメッセージは発生させない。

## 2. 最寄り挑戦受付

クラス名: `BossChallengeService`
物理名: `acceptNearestChallenge`

引数:

- `player`: 受付対象
- `notifyMissing`: 入口がない場合に `P_6500` を送るか。1引数 overload は `true`

結果:

- 入口が見つかり受付処理を呼んだ場合、または missing 通知を送った場合は `true`
- 入口なし・通知なしは `false`

## 3. ボス挑戦受付

クラス名: `BossChallengeService`
物理名: `acceptChallenge`

引数: Bukkit `Player`, boss master ID

処理内容:

1. `AstPlayer` が存在し gameplay mode であることを確認する。
2. boss template が存在し、category `BOSS`、challenge ありであることを確認する。
3. プレイヤーが challenge の入口円内にいることを再確認する。
4. ソロは本人、party は現在の member を参加予定者とし、人数が `partyMin..partyMax` 内か確認する。party leader であることは要求しない。
6. party key を `solo:<uuid>` または `party:<partyId>` とし、Dungeon／Boss 共通の party key・参加者UUID予約を原子的に取得する。競合時は保持中の挑戦表示名を `P_6505` の `{0}` へ渡して拒否する。
7. `boss.hubWorldId` の WorldMasterData と実 world、`fieldWorldId` の WorldMasterData を確認する。
8. field が `BOSS_FIELD` かつ instance 有効であることを確認する。
9. `BossChallengeInstance` を cache へ登録し、`I_6500` を記録する。
10. 現在 party の全 member へ `P_6508` を送り、受付実行者だけをハブ spawn へ非同期転送する。各 member のハブ転送成功時、まだハブへ到着していない current member へ到着 member 名・ボス名を含む `P_6535`（待機ハブで待機中です）と通知音を送る。
11. 現在 party の全 member がハブへ到着するまで `PREPARING` のメンバー待機を継続する。各 member が受付地点でスニークした場合だけ、その member をハブへ転送する。各 member の転送成功から約2秒間はハブ初期スポーンの待機離脱入力を抑止する。待機中の Sidebar は `P_6713` の状態を表示し、ハブ未到着メンバー名を灰色にする。ハブ初期スポーンから待機離脱した `waitingAbsent` 本人には Sidebar を表示しない。
12. 全 member がオンライン・通常プレイモード・ハブ滞在を満たした時点で、現在のリーダーと member 一覧を確定して `InstanceCreationQueue` へ登録する。枠を取得した callback でフィールド準備を開始する。待機列中の Sidebar は `P_6714` の状態を表示し、title は空、subtitle だけへ `P_6534` の順番・待機人数を表示する。
13. 列中のハブ初期スポーン離脱は確認 GUI 後に ticket を取り消してメンバー待機へ戻す。party 構成変更は PartyService 通知で同期し、全員が揃い直した場合は列の最後尾へ登録する。待機中の current member が一人も Hub にいなくなった場合は、他挑戦との予約競合中でも待機を終了して共通予約を解放する。待機中は拠点帰還を許可し、フィールド未生成で終了する場合はHub外のparty memberを受付位置へ転送しない。`waitingAbsent` 本人は expected participant に残すが、Sidebar からは除外する。作成開始後は固定参加者として扱い、party の招待・承認を拒否する。

各拒否条件のメッセージは [[26_5-例外・ログ・運用]] を正本とする。

## 4. フィールド準備完了と入場

クラス名: `BossChallengeService`
物理名: `finishFieldPreparation`, `startField`, `finishFieldStartAfterTransfers`

内部処理:

1. `BossFieldInstanceService.createFieldAsync` の完了をメインスレッドで受ける。
2. 例外または field なしは `E_6500` と `P_6509` を出し、`FIELD_PREPARE_FAILED` で終了する。
3. 成功時は field を challenge に設定し、40 tick 後に `startField` を呼ぶ。
4. `startField` はオンライン、受付時 party 所属、ハブまたは既に当該 field 滞在を満たす参加者を確定する。
5. `partyMin` 未満は `PARTICIPANT_REQUIREMENT_NOT_MET` とする。
6. 全実参加者を `playerSpawnLocation` へ非同期転送する。
7. 例外または1件でも `false` なら `P_6521` を送り、`TRANSFER_FAILED` とする。
8. 全員成功時は20 tick周期の10秒カウントダウンを開始し、各秒に `P_6529` / `P_6530` title とカウント音を送る。この段階ではボスを生成しない。
9. フィールド内の実参加者が開始条件を満たしたまま10秒経過した場合、`P_6531` / `P_6532` title と開始音を送り、その後にだけボスを生成して [[26_3-サービス]].BOSS Mob の参加人数補正 を適用する。
10. challenge／boss Mob の index と中止 controller を登録し、`markStarted` 後に実参加者のリセット対象バフと短命なスキル runtime を解除してから、`I_6501`、`P_6510` を実行する。ボス生成完了時、フィールド内の実参加者へ3秒間の無敵を付与する。
11. 成否を問わず開始用 chunk ticket を解除する。終了・Plugin停止時はカウントダウン task も cancel する。

## 5. BOSS Mob の参加人数補正

共通クラス名: `BossMobScalingService`
物理名: `apply`

引数: 生成済み `MobInstance`, 補正に使用する参加者数

処理内容:

1. `MobCategory.BOSS` 以外は変更しない。
2. `extraPlayers = max(0, participantCount - 1)` とし、HP倍率 `1 + extraPlayers * 0.50`、シールド倍率 `1 + extraPlayers * 0.30` を計算する。
3. 最大 HP と現在 HP を同じ倍率で補正する（生成直後は補正後最大値となる）。
4. 現在のシールド値・表示容量へシールド倍率を適用し、以後の Mob シールド再充填量にも同じ倍率を適用する。

`BossChallengeService` は生成直後のボスへこの共通処理を呼び出す。DungeonService は Dungeon 内で生成した Mob へ、開始時に確定した `originalParticipants.size()` を渡して呼び出す（現行の BOSS 部屋を含む）。BossChallenge の package-private `applyParticipantScaling` は共通処理の後、`BossChallengeConfig.scaling.enabled` が有効な場合だけ既存の `attackPerExtraPlayer` を `outgoingDamageMultiplier` へ設定する。`BossChallengeServiceTest` と `DungeonServiceRoomLifecycleTest` で両生成経路を検証する。

## 6. ボス判定とダメージ記録

クラス名: `BossChallengeService`
物理名: `isBossMob`, `recordBossDamage`

処理内容:

- `isBossMob`: Mob instance ID が稼働中 challenge の boss index にあるか返す。
- `recordBossDamage`: boss index、challenge の `IN_PROGRESS`、攻撃者が実参加者、amount 正数をすべて満たす場合だけ参加者別 damage へ加算する。

`DamageService` は HP に実反映した damage と Shield damage の合計を渡す。

## 7. 報酬対象解決

クラス名: `BossChallengeService`
物理名: `resolveRewardRecipients`

引数: boss Mob instance ID

結果: immutable な `List<AstPlayer>`

処理内容:

1. index から `IN_PROGRESS` challenge と field を取得する。取得不能は空リストを返す。
2. 実参加者のうち、オンラインかつ討伐時に field world と同一 world にいるプレイヤーだけを対象にする。
3. `AstPlayerCache` で解決できた対象だけを返す。

この固定受取人一覧を `MobCombatService.handleDeath(mob, recipients)` へ渡す。専用 `BossRewardService` は存在しない。

## 8. 参加者死亡

クラス名: `BossChallengeService`
物理名: `handleParticipantDeath`

引数: `AstPlayer`, 死亡地点

結果: ボス挑戦死亡として対象だった場合 `true`、対象外は `false`

処理内容:

1. 実参加者の `IN_PROGRESS` challenge を検索し、死亡地点が field world か確認する。
2. 既に `PlayerDeathService` の死亡状態なら重複開始せず `true` を返す。
3. 個人／共有死亡回数を加算する。
4. 経験値ペナルティなし、`reviveDelaySeconds`、field 復帰 callback を指定して死亡状態を開始する。
5. 共有回数が `deathLimit` を超えた場合だけ `P_6525` を送り `DEATH_LIMIT` で終了する。固有通知済みのため汎用失敗通知を重ねない。
6. 許容回数以内なら本人へ `P_6524` を送る。
7. callback 時点で挑戦継続中・field あり・本人オンラインなら全回復後の本人を `playerSpawnLocation` へ転送する。失敗は `TRANSFER_FAILED` とする。

## 9. ボス討伐

クラス名: `BossChallengeService`
物理名: `handleBossDefeated`

処理内容:

1. boss Mob index から challenge を取得する。
2. `IN_PROGRESS` の場合だけ、`startedAtMs` から討伐処理時刻までの表示用経過秒数を確定して `RESULT_WAITING` にし、終了時刻を現在時刻＋15秒へ設定する。
3. 入場時に保存した固定参加者の識別情報が全員分ある場合、`challengeId` をイベントIDとして、ボスID・表示名、ミリ秒精度の開始・討伐時刻、個人の実効ダメージと死亡回数を `PlayerActivityHistoryService` の `bossClears` へ渡す。履歴の生成失敗は討伐の成否に影響しない。
4. `I_6502(DEFEATED)` を記録し、boss index を解除する。
5. `P_6511`（ボス表示名・討伐時間）を送り、死亡地点の上2.4 blockへ確定した討伐時間と与ダメージ・被ダメージ・ヒール量それぞれの順位を含む動的 result TextDisplay を生成する。同じ順位・実量・構成比・死亡回数を、フィールド内の参加者へ `PlayerMessageService` 経由でチャット送信する。
6. 15秒後に `DEFEATED` の終了処理を開始する task を保持する。

戦績は `IN_PROGRESS` の固定参加者について挑戦ごとに集計する。与ダメージはボスへの実HP被害（過剰ダメージを除く）と実消費シールド量の合計で、ペットの攻撃は主人に帰属する。シールドだけを削った一撃も加算する。被ダメージは同一フィールドの参加者が受けた実HP・シールド被害で、肩代わりや状態異常も共通のダメージ適用経路で記録する。ヒール量は同じ挑戦内の味方・自分へ `recoverHp` で実際に増加したHPを回復者へ加算する。上限超過、自然回復の通知なし経路、死亡復帰・NPC等の `restoreAll` 全回復は含めない。待機中・討伐後の値を加算せず、被ダメージ・ヒール量は今回の表示用メモリ集計とし管理用API履歴の契約は変更しない。

## 10. 終了・退場・回収

クラス名: `BossChallengeService`
物理名: `endChallenge`, `beginChallengeCompletion`, `exitParticipantsAndCleanup`

処理内容:

1. `ENDING` / `ENDED` の重複終了を無視する。`DEFEATED` は [[26_3-サービス]].ボス討伐 へ接続する。
2. 準備中作成と開始カウントダウンを cancel し、状態を `ENDING` にして controller、結果 task、結果 display を破棄する。
3. 実参加者未確定なら、その時点の入場可能者で確定する。
4. 失敗終了は `I_6502` と理由別メッセージを出す。残存 boss Mob を破棄する。
5. 表示対象参加者の死亡状態を `recoverNow` で回収する。
6. Hub待機中に終了した場合はHub内の表示対象だけを入口へ転送する。フィールド生成済みなら実参加者全員を入口へ非同期転送し、失敗時は安全な別 world spawn へ fallback する。
7. 全員退場できなければ5秒後に再試行する。
8. 退場成功後に `destroyFieldAsync` を呼び、失敗時は5秒後に退場から再試行する。
9. field 破棄成功後、状態を `ENDED` として party key／challenge cache から削除する。

## 11. Sidebar 情報

クラス名: `BossChallengeService`
物理名: `findSidebarInfo`

`PREPARING` または `IN_PROGRESS` で表示対象 participant に含まれる最初の challenge から、ボス名／level、共有死亡回数／上限、経過秒／制限秒、参加者表示名を返す。待機ハブから離脱した `waitingAbsent` 本人は表示対象から除外し、対象なしは `null` を返す。待機ハブ到着通知は到着した member 名・ボス名を未到着 member へ送り、通知音を再生する。

## 12. 中止操作

クラス名: `BossChallengeService`
物理名: `findCancelableChallengeId`, `isChallengeLeader`, `stopChallengeForLeader`, `resolveCancelInteraction`, `findNearbyCancelController`

- 中止可能 state は `PREPARING` / `IN_PROGRESS`。
- solo の leader は受付者、party の leader は操作時点の `PartyService` 判定を使う。
- `stopChallengeForLeader` は `STOPPED` / `NO_CHALLENGE` / `NOT_LEADER` を返し、成功時は `ADMIN_STOP` で終了する。
- controller Interaction entity は UUID index、drop 操作は同一 world かつ中心から3.5 block以内で解決する。

## 13. 管理表示・停止

クラス名: `BossChallengeService`
物理名: `describeActive`, `stopChallenge`

- `describeActive`: challenge ID、party key、boss ID、状態日本語、表示参加者数、world、経過秒、残り秒を1行ずつ返す。
- `stopChallenge`: 完全 party key、`party:` を省略した party ID、challenge UUID prefix の順で検索し、最初に見つかった挑戦を `ADMIN_STOP` で終了する。対象なしは `false`。

## 14. フィールド作成

クラス名: `BossFieldInstanceService`
物理名: `createFieldAsync`

結果: `CompletableFuture<BossFieldInstance>`

処理内容:

1. 呼出メインスレッドで world container を取得し、challenge ごとの cancel flag を登録する。
2. 非同期 task で instance root 作成、target 逸脱／重複、base directory／`level.dat` を検証する。
3. `uid.dat` / `session.lock` を除外して非同期コピーする。
4. cancel または plugin disable を確認後、メインスレッドの安全な world load 処理へ接続する。
5. world tick 中または全体ロード枠使用中は1 tick後に再試行し、同じ tick 内では再実行しない。
6. world 名を予約し `Bukkit.createWorld`、runtime 登録、RPG gamerule 適用を行う。ロード枠は最低1 tick後に解放する。
7. player／boss spawn の重複しない chunk を `getChunkAtAsync(..., generate=true, urgent=false)` で準備し、各完了時に plugin ticket を保持する。
8. 全 chunk 成功時だけ Future を正常完了する。失敗／cancel は ticket 解放、unload、非同期削除が完了するまで回収を再試行してから例外完了する。

## 15. 準備 cancel・chunk ticket 解放

クラス名: `BossFieldInstanceService`
物理名: `cancelPendingCreations`, `cancelPendingCreation`, `releaseStartupChunkTickets`

- 全 challenge または指定 challenge の cancel flag を立てる。コピー先削除、ロード済み world の unload、folder 削除が完了して作成 Future が終端になるまで、Boss 側は作成枠を保持する。
- ticket 解放は challenge ID の保持 chunk を index から除き、全 chunk の plugin ticket を削除する。

## 16. 起動時残存フィールド掃除

クラス名: `BossFieldInstanceService`
物理名: `cleanupStaleFieldsAsync`

結果: 削除成功した directory 数の Future

処理内容:

1. `BOSS_FIELD` かつ instance 有効な全 `instanceRootPath` を取得する。
2. 各 root 直下の directory だけを候補とし、root 配下であることを正規化確認する。
3. load 済み world は player がいない場合だけ同期 unload する。player あり／unload 失敗は `E_6503` を出し候補から外す。
4. 残りを非同期再帰削除し、成功数を返す。個別削除失敗は `E_6502` を出す。

## 17. フィールド破棄

クラス名: `BossFieldInstanceService`
物理名: `destroyField`, `destroyFieldAsync`

- `destroyField` は async API を fire-and-forget で呼ぶ。
- `destroyFieldAsync` は world tick 外のメインスレッドで ticket 解放と unload を行い、成功後に folder を非同期削除する。Boss 側の作成枠 ticket はフィールド破棄 Future の成功後にだけ release する。
- unload 失敗または plugin 停止中に削除 task を予約できない場合は `false`、folder 削除まで成功した場合だけ `true` を完了する。

## 18. ボス固有ギミック

クラス名: `BossMechanicService`

Lv20の希少なWITCH型ボス `empusa_witch` は `EmpusaSpellController` で多地点魔法とHP65%・30%の三波儀式、`EmpusaHazardController` で並行する地走波と召喚魔女の一時防御結界を管理する。戦闘、BE向け予兆、Display回収、報酬の契約は [[26_3-エンプーサ]] を参照する。

`vesperala_manor_keeper`「幽翠の館主・ヴェスパーラ」はWITCH型のLv20ダンジョンボスとし、`VesperalaEncounterController`を5 tick周期で実行する。通常攻撃とMob skillはマスタへ定義せず、専用コントローラがすべての攻撃を制御する。歩行可能な半径16ブロックの会場と上方空間を必要とし、確定参加者の生存・同一world・上下3ブロック・水平16ブロック以内を判定する。会場外のPlayerやペット所有者からの攻撃は共通ダメージgateで拒否し、跳躍だけでは水平命中域から離脱しない。ダンジョンでは既存の部屋単位damage gateも維持する。通常AIでボスが会場外へ退避した場合は、場内の有効な参加者がいるときだけ予兆・浮遊・無敵を復元してから、保存した開始地点の歩行可能な床へ戻して再開する。HP境界と未発動儀式波は保持し、CC・無参加者・別world・安全床の配置不能時には強制移動しない。

通常は、前方全角70度・半径10の扇（40 tick予兆、倍率0.70）、開始時の対象足元へ固定する半径3.2の棘円（45 tick、0.74）、固定方向へ前後16・半幅1.4の廊道（35 tick、0.76）を順に使用する。扇は側面・背面へ、棘円は円外へ、廊道は横へ退避する。すべて魔法・無属性の一波一撃で、予兆・発動表示・命中判定は同じ固定形状を使い、壁越しの命中と表示を除く。通常攻撃後の間隔はHP段階ごとに40 / 30 / 20 tickとする。

HP70%の三波儀式は、外周危険・半径5.5の内円安全、内円危険・外側安全、半幅1.5の十字危険・斜め安全を順に使用する。HP35%は、半幅2の安全通路、安全通路の方向から45度回転した十字、対象足元の棘円を順に使用する。最初の波を70 tick、後続波を45 tick予兆し、各波の倍率は0.90とする。HP境界はキューとして記憶し、一撃で70%・35%を跨いでも、70%儀式と反撃窓が完了してから35%儀式を開始する。命中処理より先に波の完了を記録し、中断後は次の未発動波から完全な予兆を再開する。

導入と各儀式第1波の開始時だけ40 tick浮上・無敵になり、40 tick後は元座標・重力・開始前の無敵設定を復元する。導入後と各儀式最終波の後は60 tick（3秒）、通常AIと攻撃を停止して反撃できる時間を保証する。初期無敵設定がfalseのマスタを使用する。Shieldが正値から0へ遷移した場合は現在の波の完了後に60 tickの露出を置き、`TemporarySkillEffectService`の被ダメージ倍率1.35を適用する。露出中に新しい攻撃を予約しない。

安全地点は固定対象から会場内の候補を探索し、非危険な半径0.7の円、床のsolid、頭上2m、液体・接触ダメージの除外、0.5m間隔の左右0.35mを含む歩行経路を確認する。別階や穴を使わず、成立しない波は20 tick後へ延期する。予兆は10 tick周期で最大96点の危険面・176点の輪郭・最大109点の白い安全輪・安全通路を共通`ParticleDisplayService`で表示する。最低密度でも一点一粒を残し、OFF設定は尊重する。トウヒ・苔片の非永続BlockDisplayは各波最大8個で、BEでDisplayが見えなくても粒子とBossBarで回避できる。会場境界は淡い青灰の半径16m円を20 tick周期・2層128地点で表示し、範囲外から攻撃できない境界を示す。実Mobを召喚せず、Dungeonの部屋討伐計数に影響しない。

状態異常によるAI停止・skill禁止、拘束、参加者喪失では現在の予兆・Display・BossBar・浮遊・無敵・一時倍率・行動ロックを回収し、未発動の儀式波を保持する。待機・leash帰還、死亡、Mob破棄、アンロード、service停止では遭遇状態も回収する。Lv20最高難度を目標とするが、戦闘時間・安全地点の視認性・BEの最低粒子密度・複数人・連続HP境界・中断復帰の実機評価は未確認であり、既存ボスより難しいと実測確認したことを意味しない。基礎値と試算の正本は戦闘バランス設計書とMobマスタとする。

共通ローテーションの対象とHP境界は `BossMechanicProfile` のBoss ID別定義を正とし、専用コントローラを持つエンプーサの65% / 30%境界は `EmpusaSpellController` で管理する。`twilight_colossus` と `forgotten_alda_colossus` は70% / 35%の3段階、`great_tree_guardian_granbal` は60% / 30%の3段階、`midgard_savanna_sunbird` は30%境界の2段階とする。段階上昇時のShield再展開はボス固有ギミックの契約に従い、サンバードは30%境界のバードメテオ開始時にShieldを増加・再展開しない。ボス消滅またはservice停止時に召喚Mob、未発動予兆、演出用Displayを回収する。

攻撃は点・線・円・扇形の予兆を先に表示し、予兆終了時の範囲にいる管理対象Playerへ `DamageService` の `SKILL` damageを適用する。発動瞬間にも同じ実効範囲を `ParticleDisplayService` で再表示し、危険な命中面の内部へ最大96地点の爆発を表示する。安全円や壁で切られた範囲外は爆発させず、表示密度は既存のプレイヤー設定に従う。サンバードの境界外への周期ダメージは、対象Playerの位置へ爆発を表示する。周囲32ブロックに管理対象Playerがいない間は新しい攻撃を予約せず、既存の予兆も取り消す。共通ローテーションの行動、予兆時間、段階は [[04-レベル帯コンテンツ設計#16. ボスギミック]]、エンプーサは [[26_3-エンプーサ]] を正本とする。

`ConditionService.canRunAi` が `false` の状態異常中は、対象Bossの予約済み通常ギミックを予兆・専用行動状態ごと取り消し、HP段階遷移、Shield破壊時処理、サンバードの境界処理・陽炎転移、通常ローテーションの予約を進行しない。状態異常中に到達した通常のHP境界は解除後のtickで処理する。ただし、サンバードのHP30%到達時に1回だけ開始するバードメテオ系の必殺は例外とし、状態異常中でも30%到達を検出してチャージを開始し、チャージ、予兆、発動までを中断・取消ししない。

`twilight_colossus` の交差ルーンは中心から前後左右の各方向を、壁への衝突地点または32ブロックの安全上限まで延長する。予兆表示・発動瞬間の表示・命中判定は、各方向で同じ壁制限後の長さを使用する。

`forgotten_alda_colossus` はフェーズ1の `BossMechanicProfile` ローテーションを空にし、`mob_clay_guard_leap` をMobスキル側から実行する。半径8ブロック、攻撃力倍率150%、30 tick詠唱、160 tick cooldownの跳躍中は、着地点の周囲へDEEPSLATE_BRICKSのBlockDisplayを10個表示し、14 tickの跳躍完了、Mob破棄、中断、Plugin停止のいずれでも回収する。

同BossのShieldが0へ遷移したことは5 tick周期で検出する。検出時は未発動のボス予兆を取り消し、60 tickだけ通常AIを停止して発光させ、IRON_BLOCKのBlockDisplayを8個回転表示する。`TemporarySkillEffectService` へ被ダメージ倍率1.50を登録し、露出中のパーティクルと効果終了時の表示・倍率・発光を解除する。Mob破棄時またはservice停止時も同じ回収処理を行う。

HP70%以下のフェーズ2では105 tick間隔で `ALDA_RUIN_SHOCKWAVE` を予約する。30 tickの予兆後、ボスを中心に前後左右4方向へ、壁で区切られた最大22ブロック長・半幅1.25ブロックの範囲を攻撃し、近接・無属性の攻撃力倍率0.68とノックバック0.65を適用する。予兆中はPOLISHED_DEEPSLATEのBlockDisplayを16個、伸長する4方向へ移動させる。

HP35%以下のフェーズ3では90 tick間隔で `ALDA_PRIMORDIAL_COLLAPSE` を予約する。一次地点と二次地点を最低16ブロック離して選び、それぞれ内半径2.8ブロック・外半径7ブロックの円を表示する。一次地点は40 tick予兆、発動後に二次地点を10 tick予兆で繰り越し、各地点へ近接・無属性の攻撃力倍率0.95とノックバック0.70を適用する。CRYING_OBSIDIANのBlockDisplayとパーティクルは各予兆の完了・中断時に回収し、これらの攻撃は地形ブロックを変更しない。

`great_tree_guardian_granbal` は古代の種から目覚めたSNIFFER型の守護獣とし、アルダの巨神兵と同じ巨像外見・十字衝撃波・二地点崩落を使用しない。フェーズ1で105 tick、フェーズ2で90 tick、フェーズ3で75 tick間隔のローテーションを使う。フェーズ1は `GRANBAL_ROOT_FAN`、フェーズ2は根の扇払いと `GRANBAL_PETAL_BURST`、フェーズ3は花形攻撃の発動回数を増やす。

`GRANBAL_ROOT_FAN` は発動時の対象方向へ全角70度・長さ16ブロックの扇形を固定し、30 tickの予兆後に近接・無属性の攻撃力倍率0.60とノックバック0.45を適用する。予兆は扇形の境界、内部の放射線、外周弧を根色particleで表示する。発動時はダメージ判定と同じ扇形の面全体へ爆発particleを配置し、実際の当たり判定範囲を表示する。

`GRANBAL_PETAL_BURST` は詠唱開始時の対象位置を花芯とし、水平4.5ブロック離れた6地点へ花弁中心を配置する。花芯と各花弁は半径2.4ブロックの円で36 tick予兆し、いずれかの円内にいるPlayerへ魔法・無属性の攻撃力倍率0.75とノックバック0.45を1回だけ適用する。重なった円にいても多段命中させない。発動時は7つの円盤内へ爆発particleを配置し、命中面全体を表示する。未発動予兆は既存のボス回収処理で破棄する。

`charon_ferryman` はBOGGED型のLv20ボスで、主手の櫂と魂灯、装飾したネザライト防具を使う。HP50%・25%で3段階へ移り、通常ローテーションの間隔は105・90・75 tick。基礎HPは192000（従来64000の3倍、アルダの88160の約2.18倍）、シールドは120（アルダの60の2倍）とする。攻撃1391・防御1603・経験値6000は維持する。通常AIの単体攻撃は設定射程4.2・30 tick間隔、接近の基準距離は3.5。通常攻撃の実距離判定には共通AIの距離二乗への許容値4が加わる。挑戦用フィールドは `vanaheim_boss_charon_field` を使用する。挑戦・ダンジョンでは共通の確定参加人数補正がさらに掛かり、基礎HPへ `1 + 0.50 × (人数 - 1)`、シールドへ `1 + 0.30 × (人数 - 1)` を適用する。シールド中は共通ダメージ処理によりHPが減らず、HP増加はシールドダメージ換算の分母にも反映される。自動リチャージは設定しない。

`CHARON_RIVER` はカロンの位置から対象方向と左右28度へ、長さ22・半幅2.8ブロックの3河道を固定する。40 tickの予兆後、いずれかの河道内へ魔法・無属性の倍率0.68とノックバック0.35を1回適用する。交点でも多段命中させない。3河道の中央線と両側境界をまとめて表示し、発動時の爆発面も同じ方向・幅の判定から生成する。

`CHARON_TOLL` は開始時の最寄り対象を含む最大4人の足元と、最寄り対象の左右7ブロックの地点へ、最大6個の半径4.8ブロックの円を固定する。45 tick後に倍率0.62の魔法・無属性ダメージを1回適用し、その時点の対象位置を再捕捉して `CHARON_TOLL_ECHO` を35 tickの新しい予兆付きで予約する。追撃の円も予約後は追尾しない。各波は複数の円が重なっても1人へ1回だけ命中し、全円の48点の円周と縮む魂炎の輪を表示する。広がった円盤の発動面へ均等に爆発を配置する。渡し賃は戦闘演出と確定ドロップの名称であり、所持ゴールドを徴収しない。

`CHARON_LANTERN` は詠唱開始時の対象位置を中心に半径20ブロックの危険円と半径2.5ブロックの魂炎の安全円を70 tick表示する。危険境界は96点で描く。対象は開始時に安全円内にいるため、ソロでも到達できる。詠唱中に位置が変わっても円は追尾せず、仲間は灯の下へ集まれる。発動時に安全円の外側かつ危険円の内側へ魔法・無属性の攻撃力倍率1.0を1回適用する。詠唱中と発動後40 tickは `scriptedAction` で通常AIと攻撃を停止し、反撃時間を保証する。3技と渡し賃の追撃は中心上空の縮む魂炎の輪で残り予兆時間を示し、範囲境界と命中判定に同じ数値を使う。

`CharonRitualController` は通常3技に加え、持続する魂柱とHP境界儀式を管理する。戦闘開始100 tick以降、通常技の予兆と専用行動が残っていないときに魂柱召喚を開始する。召喚時の人数は、ボス挑戦では `BossChallengeService.participantCountForBossMob` の確定参加人数、ダンジョンでは `DungeonService.participantCountForMob` の攻略開始時に確定した人数を使用する。直接召喚では現在の攻撃対象のパーティー人数（未所属なら1人）を使い、1〜6人へ丸める。希望本数は6〜11本、HP50%以下では8〜13本。床不足時は1本ずつ減らして最低4本を試し、4本も確保できなければ100 tick後へ延期する。柱は周囲の読み込み済みchunk内で床・頭上6ブロックの空間を確保し、互いに6ブロック以上離す。石柱・冠・魂灯のBlockDisplayを各3個表示する。カロンは最大4ブロック浮遊し、60 tickだけ無敵・通常AI停止となる。召喚終了時に元位置・重力・開始前の無敵設定を復元する。

魂柱は召喚終了後600 tick残る。初回の予兆は召喚終了20 tick後から、以降65 tick間隔で、隣接する辺と対角の2本、HP50%以下では追加の対角を含む3本を同時予兆する。35 tickの予兆後、半幅1.1ブロック・床から上3ブロックの帯へ魔法・無属性の倍率0.65を1回適用する。交点でも1斉射につき各Playerへ1回だけ命中する。壁で切った同じ線分を描画・命中判定へ使う。通常AI停止中はビームを取り消して延期し、カロンが柱中心から水平32ブロック以上離れた場合も回収する。次回予約は召喚開始から `760 - 40 × (人数 - 1)` tick以降（1〜6人で38 / 36 / 34 / 32 / 30 / 28秒）だが、残柱がないことも条件とするため、召喚60 tick＋寿命600 tickの660 tick（33秒）より早く柱を重複生成しない。

HP50%では個体ごとに1回「冥河の大渡航」を開始する。通常の未発動予兆・魂柱・前の儀式を回収し、最初の40 tickだけ浮遊・無敵でチャージする。その後は無敵を解除して元位置へ戻り、通常AI停止を維持する。開始位置と対象方向を基準に、6波それぞれ2本の全長40・半幅3.2ブロックの河道を固定する。各波は基準方向を30度ずつ回転させ、左右の中心を `shift - 6` / `shift + 6` とする。`shift` は波ごとに0 / 4 / -4ブロックを繰り返し、中央の安全帯と片側へ退避する帯を切り替える。70 tick後から50 tick間隔で、現波のいずれかの河道へ倍率1.0の魔法・無属性ダメージを1回適用する。2本が重なっても多段命中させない。各河道へ2隻ずつ、計24隻の魂灯付き冥舟（各3個のBlockDisplay）を召喚し、予兆・命中・舟の移動は開始時の同一線分一覧を参照する。現波は紫、次波は別色の粒子バッチで示し、各波のBossBarは発動時に空になる。

HP25%では個体ごとに1回「五魂灯の裁定」を開始する。40 tickの浮遊・無敵チャージ後に無敵を解除し、通常AI停止を維持する。最寄り対象の足元を最初の安全灯と危険範囲の中心に固定する。後続4灯は直前の灯から約6ブロック先、高さ差1ブロック以内の歩ける床とする。経路は0.5ブロック以下の間隔で中心・左右0.35ブロックの足元と頭上空間を確認し、壁・穴・液体・危険床・高さ1ブロックを超す段差を除外する。配置不能時は直前灯を維持する。危険円は半径30、安全円は半径2.8ブロック。70 tick後から55 tick間隔の5波で安全灯を切り替え、危険円内かつ現在の安全円外へ倍率1.10 / 1.20 / 1.30 / 1.40 / 1.50の魔法・無属性ダメージを各1回適用する。円周上は安全とする。現在灯を青く強調し、次灯までの経路と切替先の輪も示す。同位置の灯は円を重複描画しない。魂灯5個、回転する黒曜石片8個、爆発particle、各波のBossBarを表示する。

裁定の初期床は対象の足元Yから下1.5・上0.05ブロック以内へ限定し、頭上の別階を採用しない。後続床は直前灯から上下1ブロック以内、経路も連続する歩行面から上下1ブロック以内へ限定する。対象の足元に床がなければ対象位置を維持し、そこから渡れない別階へ灯を移さない。

両儀式は最終発動の10 tick後に表示を回収し、60 tickの反撃時間へ移る。その後通常AIと通常ローテーションへ戻る。魂柱の次回召喚は反撃終了180 tick以降とし、大技中にビームを重ねない。一撃でHP50%・25%を跨いでも、大渡航と反撃時間の終了後に裁定を開始する。粒子は10 tick周期・1バッチ512地点以内で共通の表示密度設定を使う。現波と次波を別バッチにし、表示上限による後半河道の欠落を防ぐ。通常の渡し賃は各地点から近傍閲覧者を一括解決し、離れた参加者の予兆も表示する。表示物は一時Displayで、地形ブロックは変更しない。

カロンが追跡状態を失った場合、対象がいない場合、AIを妨げる状態異常・拘束、Mobの死亡・破棄・アンロード、service停止時は予約予兆、魂柱、儀式Display、BossBarと専用行動を解除する。浮遊中なら元位置・重力・無敵設定を復元する。魂灯・儀式の反撃時間中も追跡喪失を検出し、leash帰還を妨げない。開始済みのHP境界儀式は中断後に再発動しない。

`midgard_savanna_sunbird` は各6行動の先頭で天陽崩落を1回発動し、残る5行動に太陽フレア、対象地点へ固定するサンストライク、ソーラービームを配置する。通常段階は60 tick、30%以下は46 tick（従来値の約0.7倍）の間隔で次の行動を予約する。天陽崩落は通常AIを停止して発動時の位置から移動せず、60 tickの予兆後に半径12ブロックへ攻撃力145%の火属性ダメージを与える。命中判定には一撃だけ命中補正25ポイントを加算する。予兆円は内側4ブロック・中間8ブロック・外周12ブロックをそれぞれ36・48・64地点で表示し、詠唱中は黄金のBlockDisplay 12個を回転・収束させる。

戦闘中は `MobInstance.spawnLocation` から水平18ブロックの境界を、中心高さより上方向へ0.5ブロック間隔の8層、下方向へ2層の合計10層、各円周64地点へ水平方向±0.12ブロック・垂直方向±0.04ブロックのランダムな位置揺らぎを加え、1秒周期の赤色particleで表示し、境界外の管理対象Playerへ同周期で攻撃力18%の火属性ダメージを与える。サンバード自身が境界外へ出た場合は、境界内の最寄り管理対象Playerへ10 tickの直線予兆を表示して帰還タックルを行い、攻撃力100%の火属性近接ダメージを与えて水平9ブロック以内へ戻る。境界内に管理対象Playerがいない場合はタックルを予約しない。

戦闘中は12秒ごとに「陽炎転移」を使い、`MobInstance.spawnLocation` から水平7ブロック離れた6地点を順番に巡回する。必殺技、帰還タックルなどの専用行動中と周囲32ブロックに管理対象Playerがいない間は転移を延期する。転移前後は太陽色の粒子だけで消失・出現を表示する。

30%到達時は個体ごとに1回だけ通常AIと他のボスギミックを停止し、`MobInstance.spawnLocation` からY方向へ5ブロック高い地点へ移動して100 tick（5秒）のチャージを行う。チャージ中はボスを無敵・静止状態にし、太陽粒子と炎粒子をボス位置へ収束させる。チャージ中は通常攻撃、境界外への継続ダメージ、BossBar、安全地帯表示を開始しない。チャージ完了後のバードメテオ予兆・発動中は赤色particleの境界を表示し、境界外への継続ダメージを継続する。チャージ完了時に `MobInstance.spawnLocation` へ戻り、同地点を攻撃範囲の中心として80 tick（4秒）の「バードメテオ」を開始し、詠唱時間に合わせて空になる専用BossBarを周囲32ブロックの管理対象Playerへ表示する。`MobInstance.spawnLocation` を中心とする半径15ブロック以内からランダムに選んだ地点へ、半径3ブロック・高さ2.5ブロックのEND_RODパーティクル円柱を継続表示し、安全判定は高さを問わず、その円柱の中心からX/Zの水平距離が半径3ブロック以内を安全地帯とする。完了時は安全地帯を除く半径18ブロックの境界内へ攻撃力3000%の火属性即死級ダメージを与え、命中判定にはこの一撃だけ命中補正1000ポイントを加算して必ず命中させ、同じ範囲へ爆発パーティクルを表示する。詠唱完了後はボスの無敵と専用行動状態を解除する。専用モデルアニメーションとBlockDisplayは使用しない。

地形破壊は次をすべて満たす場合だけ行う。

- 対象Boss IDに固有profileがある。
- `DungeonService.isDungeonWorld` がfalseである。
- 対象がpolicyで許可した自然地形である。
- 1回のギミックで36ブロック以内である。

破壊は `Block#setType(AIR, false)` を使い、アイテムを落とさない。コンテナ、機能ブロック、基盤ブロック、未許可素材は変更しない。Dungeonではdamage・予兆・召喚を継続し、ブロック変更だけを行わない。
