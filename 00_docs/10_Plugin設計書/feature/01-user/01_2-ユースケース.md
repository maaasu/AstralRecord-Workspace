# 01_2-ユースケース

## 1. 初回ログイン時にユーザーを登録する

アクター:

- プレイヤー（初回参加）
- サーバー（user/account 管理）

事前条件:

- `user` が未登録である

主シナリオ:

1. プレイヤーがサーバーへ接続する
2. ログイン前イベントでプレイヤー情報を取得する
3. user 未登録を検知する
4. user を作成する
5. 初期 account を作成する
6. user の選択アカウントを更新する
7. 登録完了ログを出力する

事後条件:

- `user` と初期 `account` が作成済み
- `user.account_id` が初期 account を参照する

## 2. 既存プレイヤーのログイン情報を更新する

アクター:

- プレイヤー（既存参加者）
- サーバー

事前条件:

- `user` が登録済みである

主シナリオ:

1. プレイヤーがサーバーへ接続する
2. ログイン前イベントでプレイヤー情報を取得する
3. user 登録済みを検知する
4. 選択アカウントを解決する
5. 最終参加日時・IP・選択アカウントを更新する

代替シナリオ:

- 選択アカウントが解決できない場合は更新を行わず終了する

事後条件:

- 条件を満たす場合、`lastJoinDate/globalIp/accountId` が更新される

## 3. 管理者が権限レベルを変更する

アクター:

- 管理者プレイヤーまたはコンソール
- デバッグユーザー（`plugin.debugUsers` に UUID が設定されたプレイヤー）

事前条件:

- 実行者が権限条件を満たしている
  - プレイヤー時は `permission >= 99`
  - または `config.yml` の `plugin.debugUsers` に実行者 UUID が含まれている

主シナリオ:

1. 実行者が `/user permission <permission> [<player|uuid>]` を実行する
2. 対象ユーザーと permission 値を検証する
3. permission を更新する
4. 更新後ユーザーを再取得する
5. 対象がオンラインならキャッシュへ再反映する
6. 実行者へ結果を通知する

事後条件:

- `user.permission` が更新される
- オンライン対象は反映済み状態になる

## 4. 管理者がプレイヤーを BAN する

アクター:

- `permission = 99` の管理者プレイヤーまたはコンソール

事前条件:

- 対象 MCID が `dbo.user` に登録されている
- プレイヤー実行時は `UserPermission.ADMIN` を持っている

主シナリオ:

1. 実行者が `/ban <mcid> <indefinite|temporary> [days]` を実行する
2. 第1引数を API の参加履歴ユーザー検索で検証する
3. `indefinite` は `banIndefinite = true` / `banDate = null`、`temporary` は正の整数日数から終了日時を計算して更新する
4. API の更新結果を監査ログへ記録する
5. 対象がオンラインなら接続拒否と同じ BAN メッセージでキックする
6. 実行者へ完了を通知する

代替シナリオ:

- 対象 MCID が見つからない場合は DB ユーザー未検出を通知し、更新しない
- 対象が有期限 BAN 中に再度 BAN された場合は、指定値で上書きする

事後条件:

- `dbo.user.ban_indefinite` / `dbo.user.ban_date` が指定値へ更新される
- 有効 BAN の対象者は次回接続時に参加できない
