# 12_2-ユースケース

## 1. テンプレートをロードする

アクター:

- サーバー管理者（`/mob load`）または `MobService` の遅延ロード

事前条件:

- AstralRecord API が稼働している

主シナリオ:

1. 呼び出し側が [[12_3-サービス]].テンプレート全件ロード を呼ぶ
2. サービスが [[12_3-リポジトリ]].Mob 一覧取得 を呼ぶ
3. 取得した summary 一覧を `templates` キャッシュへ登録する
4. 件数を返す

代替シナリオ:

- API が 5xx を返した場合は例外を呼び出し元へ伝播し、キャッシュは更新しない

事後条件:

- 既存キャッシュは新しい一覧で完全置換される

## 2. テンプレート ID を解決する

アクター:

- `MobService.spawn`、コマンド、その他の呼び出し側

主シナリオ:

1. 呼び出し側が [[12_3-サービス]].テンプレート取得 を呼ぶ
2. キャッシュにあれば即返却
3. 未ヒットなら [[12_3-リポジトリ]].Mob 取得 を呼び、結果をキャッシュへ登録して返す

代替シナリオ:

- API が `404` を返した場合は `null` を返す

事後条件:

- 取得成功時はキャッシュに該当テンプレートが入る

## 3. Mob をスポーンする

アクター:

- `MobCommand`（`/mob spawn <mobId>`）または外部呼び出し側

事前条件:

- テンプレート ID を指定する場合は、指定 `mobId` のテンプレートが API 上に存在する
- feature が実行時 `MobTemplate` を直接渡す場合は、API・テンプレートキャッシュを前提としない
- 呼び出し側がスポーン座標を持っている

主シナリオ:

1. 呼び出し側が [[12_3-サービス]].Mob スポーン を呼ぶ
2. テンプレートを取得する（未ロードなら遅延ロード）
3. インスタンス ID を採番する
4. [[12_1-モデル定義]].Mob インスタンス を生成し、初期 HP・状態・脅威値を設定する
5. [[12_3-実体Mob制御]].実体 Mob 生成 を呼び、Bukkit/Paper の実体 Mob を生成する
6. 生成直後に vanilla goal を全削除し、PDC と Pathfinder 設定を反映する
7. インスタンスを `instances` / `instanceByEntity` / `viewers` キャッシュへ登録する
8. 生成したインスタンスを返す

代替シナリオ:

- テンプレートが見つからない場合は `null` を返す

事後条件:

- ワールド上に該当インスタンスが存在し、範囲内プレイヤーに表示される
- AI tick タスクが該当インスタンスを処理対象にする

## 4. AI を tick 駆動する

アクター:

- `MobAiService`（`BukkitScheduler` 1 tick 周期）

主シナリオ:

1. tick タスクが [[12_3-サービス]].全インスタンス取得 で対象一覧を取得する
2. 各インスタンスについて以下を実行する
   1. `state == DEAD` ならスキップして死亡処理キューへ
   2. `LEASHED` 判定（`distance(spawnLocation, currentLocation) > leashRange`）→ `LEASHED` 遷移
   3. 状態に応じて以下を駆動
      | 状態 | 駆動 |
      |---|---|
      | `IDLE` | [[12_3-サービス]].待機行動駆動。`aggroRange` 内のプレイヤーがいれば `AGGRO` 遷移 |
      | `AGGRO` | [[12_3-戦闘]].ターゲット選定 を呼んでターゲットを更新。次に使用するスキルの共通発動距離内に入れば `COMBAT` 遷移。上下照準を許可するスキルは三次元射程、その他は水平射程と高低差1.25 block以内で判定する |
      | `COMBAT` | 次に使用するスキルの共通発動距離内なら攻撃し、射程外なら `AGGRO` へ戻る。上下照準を許可するスキルが高低差だけで通常の地上戦範囲を超える場合は、現在地でPathfinderを停止して発動する。その他の`RANGED` / `MAGIC`は近すぎる場合に後退し、`preferredRange`付近を維持できている場合は左右へ移動する |
      | `LEASHED` | Paper Pathfinder でスポーン地点へ移動。到達で `IDLE` 復帰 |
3. 死亡処理キューを処理（[[12_3-戦闘]].致死処理 経由）

事後条件:

- 各インスタンスの `state` と `currentLocation` が更新される
- ターゲット・脅威値テーブルが必要に応じて更新される

## 5. Mob がプレイヤーを攻撃する

アクター:

- `MobCombatService`（`MobAiService` から呼ばれる）

事前条件:

- `state == COMBAT`
- `normalAttack` を持つ場合は `currentTick - lastAttackTick >= normalAttack.intervalTicks`
- ターゲット `AstPlayer` が範囲内

主シナリオ:

1. `skills` を持つ場合は Mob 専用スキルの詠唱・発動を試み、使用できなければ [[12_3-戦闘]].攻撃 tick を呼ぶ
2. `combat.style` に応じて使用ステータスを決定する
3. 命中判定（`ACCURACY` vs ターゲットの `EVASION`）
4. ダメージ計算
5. 通常会心判定（Mob 攻撃では超星会心を判定しない）
6. プレイヤーへダメージ適用（プレイヤー側 feature の API 経由）
7. プレイヤーへノックバック送出（[[12_3-戦闘]].ノックバック適用）
8. `lastAttackTick = 現在 tick`

代替シナリオ:

- 命中判定で外れた場合はダメージ・ノックバックなし
- 回避された場合は HUD 通知のみ

事後条件:

- プレイヤーの HP が更新される
- 必要に応じてプレイヤーへノックバックが送出される

## 6. プレイヤーが Mob を攻撃する

アクター:

- 外部呼び出し側（戦闘イベント、スキル発動など）

主シナリオ:

1. 外部呼び出し側が [[12_3-戦闘]].被ダメージ を呼ぶ
2. ダメージ計算（防御力反映）
3. `currentHealth -= 確定ダメージ`
4. ヘイト加算（[[12_3-戦闘]].脅威値加算）
5. ノックバック送出（[[12_3-戦闘]].ノックバック適用）
6. `nonLethal=false` かつ `currentHealth <= 0` なら `state = DEAD` に遷移して死亡キューへ。`nonLethal=true` の場合は combat 側で HP 1 を下限とし、死亡キューへ進めない

事後条件:

- インスタンスの HP が更新される
- 必要に応じて死亡処理が予約される
- ヘイトテーブルにプレイヤーが登録／加算される

## 7. Mob が死亡する

アクター:

- `MobCombatService`（致死判定後）

事前条件:

- `currentHealth <= 0` かつ `state == DEAD`

主シナリオ:

1. [[12_3-戦闘]].致死処理 を呼ぶ
2. キラー（最後に致死ダメージを与えたプレイヤー）を特定する
3. [[12_3-戦闘]].ドロップ確定 を呼ぶ
   - `drops.items` の各エントリを抽選
   - `drops.lootTable` の抽選（参照解決後）
   - `drops.exp`, `drops.money` を加算
4. ドロップ結果をプレイヤーへ配布する（item / inventory feature の API 経由）
5. [[12_3-サービス]].個別 Mob 破棄 を呼び、実体 Mob を remove する
6. `instances` / `instanceByEntity` / `viewers` キャッシュからインスタンスを削除する

事後条件:

- インスタンスが完全に消滅する
- キラーがドロップ・経験値・金銭を受け取る

## 8. 頭上表示の viewer を更新する

アクター:

- `MobAiService`（tick 駆動）

主シナリオ:

1. 各インスタンスについて、頭上表示距離（既定 64.0 ブロック）内のオンラインかつ生存しているプレイヤーを判定する
2. 範囲内プレイヤー UUID を `viewers` に登録する
3. 範囲外・オフライン・死亡中のプレイヤー UUID を `viewers` から削除する
4. Mob 本体の表示は Bukkit/Paper の entity tracking に任せる

事後条件:

- `OverheadDisplayService` が頭上 HP 表示の spawn / teleport / destroy を差分実行できる
- Mob 本体は通常の実体 Entity としてサーバに同期される

## 9. すべての Mob を破棄する

アクター:

- プラグイン終了処理、または管理者コマンド

主シナリオ:

1. [[12_3-サービス]].全 Mob 破棄 を呼ぶ
2. 各インスタンスの実体 Mob を remove する
3. `instances` / `instanceByEntity` / `viewers` キャッシュをクリアする

事後条件:

- ワールド上から実体 Mob が消える
- メモリリークなくセッションが終了する

## 10. 採集 object を採集する

アクター:

- gameplay mode のプレイヤー

主シナリオ:

1. `GatheringInteractionEventHandler.resolve` がメインハンド左クリックについて、視線 5.5 block 以内で最も近い採集 object を副作用なしで解決する。
2. `player-interaction` が可視性を再検証し、採集候補を勝者に選んだ場合だけ `GatheringService.startMining` を実行する。
3. service が gameplay mode、tool tag、対象、既存 session、ツールの耐久値切れを検証し、初回 damage を即時適用する。
4. object が残った場合は 8 tick 間隔の session を開始し、同じ対象・同じ tool signature・視線・tool tag が維持される間だけ採集 damage を続ける。
5. HP が 0 になると hit / break sound を切り替え、`displayBlock` 材質のブロック破壊パーティクルを表示する。メインハンド TOOL の `durability.consume` を1回消費し、Mob と共有する drop 経路で item / exp / money を抽選・付与する。`exp` はアカウント経験値とクラス経験値へ反映する。
6. 報酬受取人が解決でき、drop presentation が利用可能な場合は `QuestService.recordGathering` へ gathering ID を通知する。
7. session と packet-only 表示を除去し、instance を破棄する。

代替シナリオ:

- target、gameplay mode、tool tag、またはツール耐久値のいずれかを満たさない場合は入力を受理しない。既存 session がある場合は停止して object HP を全回復する。
- 同じ player が同じ対象を同じ tool で追加クリックしても、8 tick 間隔を迂回する追加 damage は与えない。
- 別 player が同じ object を開始した場合は旧 player の session を終了し、新しい player を owner とする。

## 11. 採集スポナーから採集 object を出現させる

アクター:

- `GatheringSpawnerService` の 20 tick task

主シナリオ:

1. spawner ごとの `spawnIntervalTicks` と world time window を検証する。
2. 半径内の gameplay player を数え、最大 6 人分の `spawnPerPlayer` と `maxAlivePerSpawner` から目標 alive 数を決める。
3. 当該配置由来の追跡 instance と、他配置由来を含む周辺採集 object 数を検証する。
4. `spawnGatherings` を weight 抽選し、半径内で最大 24 回、足元 block 条件と空間条件を満たす位置を探索する。
5. `GatheringService.spawn` で instance を生成し、配置単位の追跡集合へ登録する。

事後条件:

- gameplay player が周辺にいない場合は新規生成しない。
- 採集完了で instance が消えた後、次回判定時に追跡集合を cleanup して再出現枠を空ける。

## 12. 採集スポナーを配置・管理する

アクター:

- 管理権限を持つプレイヤー

主シナリオ:

1. `/gathering spawner item <id> [amount]` で PDC `gathering_spawner_id` を持つ設置 item を取得する。
2. block place / break または `AccountMode.ADMIN` 向け packet display の左クリックを `GatheringSpawnerBlockEventHandler` が input candidate に変換する。
3. 勝者 executor が `hasAdminPermission()` を再検証し、配置 cache を登録・削除する。
4. dirty 配置は 60 秒間隔または service stop 時に `gathering_spawners.yml` へ保存する。

代替シナリオ:

- 未ロード ID、同一 block 座標、権限不足は登録しない。
- packet-only spawner 表示は `AccountMode.ADMIN` の viewer だけに見せる。設置・削除権限の判定とは別契約とする。
