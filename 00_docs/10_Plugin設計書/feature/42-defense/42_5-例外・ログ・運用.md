# 42_5-例外・ログ・運用

## 開始前の確認

運営はWebで対象チャンネル、JSTの日次時刻、有効/無効、[[42_9-未決事項]] の必須設定を入力する。APIの `missingSettings` が空であり、登録済みの適格ENEMY Mobが存在することを確認する。Plugin側では `api.serverId` と `defense.runtimeKey` を設定し、APIの `Defense:RuntimeKey` と一致させる。通常のAPIキーも必要で、runtime専用キーをWeb管理キーと共用しない。未設定時はPluginの監視を開始せず、APIは503を返す。

設定する`worldName`は既存のチャンネル内ワールドで、中央・入場・召喚地点が安全に立てる座標であることを確認する。使用範囲のチャンクも事前に生成し、部外者が滞在していない状態にする。Pluginは既存ワールドの解決と位置検証を行い、mapを生成しない。地形の設置・破壊、爆発、通常Mobスポーンは設定済みの専用ワールドで開催外も抑止する。進軍経路とチャンク保持範囲は実機で確認する。

## 障害と回収

設定・ワールド・適格Mob・入場が不成立なら `ABORTED` を報告する。通信障害はoutboxに残し、次回の5秒pollで再送する。ローカルの `defense_runtime.json` に帰還先、未送信報告、active runを保存するため、このファイルを稼働中に消さない。journalが破損した場合は上書きせず処理を停止する。調査時は原本を保全し、帰還先と未送信報酬の整合を確認する。

停止・再起動では戦闘を再開せず、ABORTED報告と帰還・残存実体回収を行う。確定済み報酬のoutboxは旧開催の終端後でもAPIへ再送可能である。APIは報酬を開催・アカウント・段階で冪等化し、既存メールへ期限なしで配送する。メール保存後の配送失敗はAPI側の再試行対象である。

ログ本文は `logger.properties`、プレイヤー向け文言は `player.properties` を正本とする。通信失敗は `E_7900`、journal失敗は `E_7901`、ゲーム処理失敗は `E_7902` で調査する。運用者はチャンネル、runId、起動世代、Webの直近結果、journalのoutboxを照合する。

## 検証境界

文書・コードの静的検証では、本番ワールドの進軍、30人時の処理負荷、実SQL Serverの永続化、Webの実認可、サーバー再起動後の実メール受取までは保証できない。実サーバー、Web、API、DBを結んだ開催・再接続・再起動・メール重複防止の検証結果を運用投入前に記録する。
