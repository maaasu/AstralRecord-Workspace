# 04_2-ユースケース

## 1. 起動時にアイテムマスタを一括ロードする

アクター:

- サーバー起動処理

事前条件:

- `ItemService` と `ItemRepository` が初期化済みである

主シナリオ:

1. 非同期セットアップが `ItemService.loadAll` を呼ぶ
2. `ItemRepository.findAll` で全 `ItemSummary` を取得する
3. summary ごとに `findById(id, category)` で詳細を取得し、ID key の snapshot へ登録する
4. 組み込み通貨定義を追加し、準備済み snapshot で master cache を置換する
5. 合計ロード件数を返す

代替シナリオ:

- 一覧・詳細取得中の例外は `LogId.E_5202` を記録し、それまで構築した snapshot と組み込み通貨を公開する
- ゴールド系7額面と `astrald` の組み込み通貨定義もマスタ snapshot に含める

事後条件:

- 取得できた全アイテムが正規化 ID key の共有キャッシュに保持される

## 2. 管理者が単一アイテムをリロードする

アクター:

- 管理者（コマンド実行者）
- アイテム付与対象プレイヤー（実行者自身または指定したオンラインプレイヤー）

事前条件:

- 対象アイテム ID が API 側に存在する

主シナリオ:

1. 実行者が `/item load <itemId>` を実行する
2. 詳細 API で対象アイテムを取得する
3. 取得結果を該当カテゴリの共有キャッシュへ上書き登録する
4. 実行者へロード結果を通知する

代替シナリオ:

- 対象アイテムが見つからない場合はエラーメッセージを返して終了する

事後条件:

- 指定アイテムの共有キャッシュが最新の API 状態に同期される

## 3. プレイヤーが指定アイテムを受け取る

アクター:

- 管理者プレイヤー（コマンド実行者）

事前条件:

- 対象アイテムが起動時ロードまたは `/item load` によりキャッシュ済みである

主シナリオ:

1. 実行者が `/item get <itemId> [amount] [player]` を実行する
2. 対象プレイヤーを解決する。対象省略時は実行者自身、コンソール実行時は対象指定を必須とする
3. `ItemService.findLoadedById` でロード済みキャッシュを確認する
4. 対象プレイヤーのインベントリサービスへ付与を委譲する
5. 通貨カテゴリは GUI を再描画しない。その他のカテゴリは対象プレイヤーの通常インベントリ GUI を再描画する
6. 実行者へ付与結果を通知し、対象が別プレイヤーなら対象にも通知する

代替シナリオ:

- 対象がオンラインでない、または `AstPlayerCache` に未登録の場合は `PlayerMsgId.P_5814` を返して終了する
- ロード済みキャッシュに対象アイテムがない場合は `PlayerMsgId.P_5213` を返して終了する。`/item get` 自体は API を呼ばない
- 対象アイテムがゴールド系7額面または `astrald` の場合は Plugin 組み込みマスタを使用し、filebase 由来の item 定義には依存しない
- インベントリ空きがない場合は `PlayerMsgId.P_5241` を返して終了する

事後条件:

- 対象プレイヤーの該当インベントリにアイテムが追加される

## 4. プレイヤーが AstralRecord アイテムのバニラ操作を試みる

アクター:

- プレイヤー（PLAYER モード）

事前条件:

- プレイヤーが AstralRecord アイテムを所持・装着している

主シナリオ:

1. プレイヤーがクリック・消費・攻撃などのバニラ動作を行う
2. クリック入力は`PlayerInteractionGatewayEventHandler`が受け付け、item resolverがプレイヤーの[[02_1-モデル定義]].アカウントモード と手持ちitemを副作用なしで評価する
3. world interactionなど上位候補が成立した場合、item候補は実行しない
4. item候補が勝者の場合だけexecutorへ委譲し、`InputClaimPolicy`に従って対象eventを抑止する

事後条件:

- バニラの食事消費・ブロック使用・エンティティ攻撃などの効果は発生しない

## 4.1 ポーションを右クリックで使用する

アクター:

- プレイヤー

契機:

- PLAYER モードのプレイヤーが `CONSUMABLE` カテゴリの AstralRecord アイテムを右クリックする

主シナリオ:

1. 右クリックgatewayが入力を正規化し、item resolverが`CONSUMABLE`カテゴリのitem use候補を返す
2. [[28_3-サービス]].勝者選択 でitem use候補が勝った場合だけ`PotionUseService.use`へ委譲する
3. `consumable.onUse.useTimeTicks` の間、移動キャンセル可能な待機を開始し、`consumable.onUse.usingSound`（未指定時は `entity.generic.drink`）、タイトル、BossBar、パーティクルで使用中の進捗と残り秒数を表示する
4. 待機中に移動または持ち替えを検知した場合、ポーション使用をキャンセルし、タイトルと BossBar を片付けてキャンセル通知を表示する
5. 待機完了後、使用開始時と同じアイテムを保持している場合だけ `ItemConsumable.effects` の `rate` 判定に成功した効果を適用する
6. `RECOVER` 効果は `status` に応じて HP / MP / EN を回復する。`isPercent=true` の場合は対応する最大値に対する割合として扱う
7. `BUFF` 効果は `buffId` を `StatusService.applyBuff` へ渡し、バフ付与とステータス再計算を行う
8. 効果が 1 件以上適用された場合、`InventoryService.consumeHotbarItemInHand` で使用した手のホットバーアイテムを消費し、`consumable.onUse.sound` を再生する
9. バフが新規獲得・再付与された場合、プレイヤー視界のより右下へバフ表示情報を数秒だけ表示し、表示中の残り時間を更新する

事後条件:

- バニラ消費イベントは発生せず、AstralRecord 側の効果適用とホットバー消費だけが行われる
- 同一入力からNPC操作、テレポーター、アクションリングなど別のトップレベルactionは実行されない
- 待機中は使用中であることと完了までの残り時間がタイトルと BossBar で分かる
- バフ獲得通知はプレイヤーごとに 1 件だけ表示し、別バフ獲得時は既存通知を差し替える

## 4.2 bundle を右クリックで開封する

アクター:

- プレイヤー（PLAYER mode）

主シナリオ:

1. 右クリック gateway の item use 候補が勝者になった場合だけ `BundleUseService.beginBundleUse` を呼ぶ
2. `bundle.lootTableId` を `LootService.getLoadedOrFetch` で解決する
3. `bundle.openTimeTicks`（省略時 `20 tick`）の移動キャンセル可能待機を開始し、subtitle と BossBar で item 名と進捗を表示する
4. 待機完了時にも開始時と同じ bundle を同じ手に保持していることを確認する
5. `LootRollService.roll` で報酬を抽選し、bundle を 1 個消費する
6. 報酬 item はロード済みキャッシュを優先し、未ロードなら `ItemService.loadItem` で単体取得する
7. 解決できた報酬を統合 inventory へ付与し、付与できた種類数・合計数と各 item 名・個数を表示する
8. 付与できた報酬に対して ItemDisplay の落下・回収演出、filebase 定義の sound / particle を再生する

キャンセル条件:

- 移動、hotbar 持ち替え、退出、別の bundle 開始
- キャンセル時は title / BossBar を片付け、bundle 消費と報酬付与を行わない

終了条件:

- bundle 拡張または loot table ID がない、loot table を解決できない場合は `P_5242` を返す
- 完了時に同じ bundle を保持していない場合は消費・報酬付与を行わない
- bundle 消費に失敗した場合は `P_5245` を返す
- 現実装は統合 inventory に収容できなかった報酬を生成せず破棄する。改善方針は [[04_9-未決事項]] で管理する

Lore 表示:

- `ItemStackFactory.appendBundleLootLore` は `LootService.getLoadedOrFetch` で解決を試みる
- 候補は item 表示名、数量範囲（全角 `～`）、100% 未満の場合だけ確率を表示する
- 解決失敗時は `◆ ルート情報: <lootTableId> (未取得)` を表示する

## 4.3 フックショットを装填して発射する

アクター:

- プレイヤー（PLAYER mode）

契機:

- crossbow iconのmain hand `HOOKSHOT` tag `TOOL` を左クリックすると、従来どおり装填または発射する
- 未装填の同じフックショットを右クリックすると、発射せず装填だけを行う

主シナリオ:

1. 未装填の左クリックgatewayは、同じ主手equipment instanceと装備条件を副作用なしで確認できる場合に従来どおり装填の `WORLD_INTERACTION` 候補を収集する。未装填の右クリックgatewayも装填のみの `WORLD_INTERACTION` 候補を収集し、どちらも `stableOrder=80`（既存独自world操作の `10`～`70` の後、generic vanilla block の `90` の前）で仲裁する。左クリック・右クリックの装填はアンカー照準を必要としない。loadedまたは装填中の右クリックはhookshot候補を返さず、発射も行わない。
2. 勝者executorは1.5秒（30 tick）の装填を開始し、専用の transient movement modifier で移動速度を50%低下させる。`PlayerHudService` の primary ActionBar には残り時間と進捗を表示する。開始・中断では素材も耐久も消費しない。
3. 完了時だけ `hook` materialを1個消費し、同じinventory state lockで当該equipment entryの `metadataJson.hookshot.loaded=true` を保存する。この状態は持ち替え・収納・再ログイン後にも残り、取り外し操作は提供しない。左クリック装填で保存に成功し、現在の照準に有効な固体アンカーがあれば、その完了処理から直ちに発射へ進む。右クリック装填は発射せず、loaded状態を保持する。
4. 左クリック装填の自動発射では、同一主手instanceと最大24 block先の最初の固体アンカーを再確認する。アンカーが無効なら装填済み状態を保持し、次の左クリックで発射できる。
5. 発射では耐久が足りる場合だけ `durability.consume` を1回消費し、loaded状態を外す。metadata更新が失敗した場合は耐久を補償して発射しない。照準失敗・耐久不足ではloaded状態と耐久を保持する。
6. ブロックを変更せず、アンカー位置へ短命の金属格子型 `BlockDisplay` と着弾particleを表示する。`hook` のアイコンは `TRIPWIRE_HOOK` であり、BlockDisplayには使用しない。
7. 最長44 tick、現在velocityのアンカー方向成分を保持し横方向だけを減衰しながら、距離比例の加速度を加えて最大速度2.05で `Player#setVelocity` を適用する。2 tickごとにプレイヤーとアンカーの間を最大12地点のtether particleでまとめて描画する。

終了・取消条件:

- 装填中に持ち替え、死亡、退出、world変更、外部teleport、skill詠唱開始が起きた場合は、移動低下・ActionBar・taskだけを回収して未装填のまま終了する。完成済みloaded状態は除去しない。
- アンカーまで1.15 block以内、44 tick経過、持ち替え、死亡、退出、world変更、外部teleport、または表示entityの無効化で牽引を終了し、taskとBlockDisplayを回収する。
- 装填完了時の照準が空中・非固体block・射程外、または耐久不足の場合は発射・牽引を行わず、フック消費済みの装填済み状態を保持する。装填完了時にフック不足ならloaded状態を作らない。
- プレイヤー座標の直接変更、`Player#teleport`、重力停止、落下ダメージのリセットは行わない。衝突・重力はBukkit/Paperの物理処理に従う。

## 5. サーバーがクライアントへアイテムパケットを送信する

アクター:

- サーバー（ProtocolLib リスナー）
- クライアント

主シナリオ:

1. サーバが `SET_SLOT`、`WINDOW_ITEMS` または `ENTITY_EQUIPMENT` パケットを送信する
2. `SET_SLOT` と `WINDOW_ITEMS` は、アダプタがパケット内 `ItemStack` の PDC を読み取り、AstralRecord アイテムだけ icon Material / customModelData を送信コピーへ書き換えて元パケットを送信する。装填済みフックショットは `CrossbowMeta` の charged projectile を送信コピーへ設定してチャージ済みクロスボウアイコンを表示する。`ACTION_RING_HOLD_SELECT=true` の受信者本人では、選択中 hotbar slot の主武器だけをクライアント専用 `TRIDENT` として送る。ホットバースロット切り替え時は選択 slot cache を更新して inventory を再送する
3. `ENTITY_EQUIPMENT` は、各装備 slot の送信コピーへ同じ書き換えと `ARMOR_DISPLAY` に応じた `EQUIPPABLE` component の除去が必要か判定する。受信者本人のエンティティ向けメインハンドだけは、選択中 hotbar slot の主武器ならクライアント専用 `TRIDENT` を再適用する
4. `ENTITY_EQUIPMENT` に変更が不要なら、元パケットをそのまま送信する
5. 変更が必要なら、元パケットを cancel し、Bukkit メインスレッドで対象 `LivingEntity` を解決する
6. 退避した全装備 slot を Paper API の `Player#sendEquipmentChange` で受信者へ再送し、packet 符号化は Paper に委譲する
7. 再送された装備更新は再送識別によりそのまま通過させる

代替シナリオ:

- AstralRecord アイテムでない場合は何もせず元のパケットを通過させる
- icon Material 解決に失敗した場合は警告ログを記録し、当該 ItemStack の書き換えをスキップする
- 仮想トライデントは選択中 hotbar slot 以外、他エンティティの `ENTITY_EQUIPMENT`、他プレイヤーの inventory には適用せず、サーバー側の `PAPER` ItemStack は常に維持する。受信者本人の `ENTITY_EQUIPMENT` メインハンドだけは inventory 同期と同じ選択 slot 条件で適用する。選択 slot の変更、設定変更、インベントリ同期時に本人の表示を再計算する

事後条件:

- 本人の inventory と、他プレイヤーの手持ち品には icon 適用済みの ItemStack が表示される
- 防具レイヤーは受信者自身の `ARMOR_DISPLAY` に従い、本人と他プレイヤーで同じ表示・非表示方針になる

## 6. 装備インスタンスを生成する

アクター:

- サーバー（ルート抽選・コマンド・GUI など）

主シナリオ:

1. 呼び出し側が `ItemService.createEquipmentInstance(equipmentId, accountId, source, createdBy)` を呼ぶ
2. リポジトリが `POST /api/equipment/instances` を発行する
3. API がステータスロールを解決し、作成済み装備インスタンスを返す
4. サービスが結果を呼び出し側へ返却する

代替シナリオ:

- 例外発生時はエラーログを記録し、`null` を返す

事後条件:

- API 側に新規装備インスタンスが作成され、呼び出し側はインスタンス ID を含む結果を取得する

## 8. ItemStack の lore を生成する

アクター:

- サーバー（インベントリ表示、GUI 表示、コマンド付与）

主シナリオ:

1. `ItemStackFactory` が `ItemModel` または装備インスタンスから表示用 ItemStack を生成する。ルーンは `ItemModel` の固定値だけを表示する
2. 通貨カテゴリ以外かつ `unSellable=false` の lore に `saleValue` を売値として `売値: <saleValue> ゴールド` の形式で表示する。通貨カテゴリでは売値と売却不可表示を出さず、`unSellable=true` のアイテムでは売値を出さずに売却不可表示を出す
3. skill gem は「左クリックで習得」と消費注意を表示する
4. sigil はスキルマネージャーで合成することと、装着後に取り外せないことを表示する
5. equipment にセット効果が設定されている場合、セット名、2セット・4セットなどの発動必要数、各ステータス補正を Lore に表示する。定義を取得できない場合は内部 ID を表示しない

事後条件:

- 通貨カテゴリ以外かつ売却可能なアイテムでは、プレイヤーは lore から売却時に得る予定のゴールド量を確認できる

## 8.1. 所持アイテムをチャット共有する

アクター:

- プレイヤー

主シナリオ:

1. プレイヤーが通常の所持品画面で AstralRecord item に Shift+Q を入力する、または `/showitem <itemName>` / `/si <itemName>` を実行する。
2. `ItemChatShareService` が現在の所持品から対象 item を解決し、アイテムを消費・移動せず clone を作る。
3. 管理全体チャットの本文へ、先頭の `◆` 装飾を除いた item 表示名を送信する。
4. 受信者が本文を hover すると、インベントリ表示専用のクリック操作案内を除いた clone の表示名と lore を含む item tooltip を確認できる。本文のクリックでは `◆` と装飾コードを含まない表示名をクリップボードへコピーできる。

代替シナリオ:

- Shift+Q の対象が AstralRecord item でない場合は通常のドロップ操作を維持する。
- コマンド指定名が現在の所持品に存在しない場合は `P_5949` を送信して終了する。

事後条件:

- アイテム本体、所持数、所持品配置は変化しない。

## 9. オーブで装備を更新する

アクター:

- プレイヤー（PLAYERモード）

主シナリオ:

1. 通常プレイヤーインベントリ内のオーブをクリックし、そのオーブで現在実行可能な装備一覧を開く。
2. 装備中を先頭、その後に BAG / HOTBAR の候補を表示する。強化・修理・エンチャントは候補を選択し、状態変化は候補選択後に27枠の確認画面を開く。確認画面の2行目には対象装備（slot 11）・消費アイテム一覧（slot 13）・実行（slot 15）を配置し、戻るは最下段中央（slot 22）とする。消費アイテム一覧は54枠のページ付き画面で素材とゴールドを表示する。ルーン装着・脱着は27枠で、対象装備（slot 10）、ルーン選択（slot 13）、完成形（slot 16）、対象装備一覧へ戻る（slot 22）を表示する。装着画面ではBAG表示slotのルーンを選択し、選択済みのslot 13を再クリックすると選択を解除する。下段のスクロールとHOTBAR slotは共通インベントリ操作へ委譲する。脱着候補が1件なら自動選択し、複数なら27枠・18件単位のページ付き選択画面を開き、選択画面のslot 22で脱着確認画面へ戻る。
3. 実行直前にオーブentry、対象instance、所有account、rank・slot・耐久・エンチャント枠を再検証する。
4. 成立した操作はオーブを必ず1個消費し、装備を更新する。強化失敗も成立した試行として1個消費する。
5. API操作と正本照合中は対象slotへ時計アイコンを一度だけ表示し、すべてのクリックを拒否する。ルーン装着・脱着は完成形のslot 16へ時計を表示する。固定フレーム演出・反復サウンド・確定後の追加待機は行わない。
6. 正本照合が完了した同じtickで全候補を再計算して結果音を鳴らす。オーブが残っていなければ閉じ、状態変化とルーン装着・脱着は残数にかかわらず閉じる。

代替シナリオ:

- `FILL_ALL_EMPTY` は全空き枠を非復元抽選で埋めるが、消費するオーブは1個です。異なる候補が不足する場合は全体を変更せず消費もしません。
- 同じ `effectId` は既存を含めて重複させません。付与可能候補がない場合は、その旨をプレイヤーへ通知します。
- 通信失敗時も支払いをローカル推測で補償しません。同一 `operationId` を保持し、API台帳のterminal結果と影響entryの正本照合が完了するまで同一accountの後続保存を待機させます。
