# 04_2.00-ユースケース

## 1. 起動時にアイテムマスタを一括ロードする

アクター:

- サーバー起動処理

事前条件:

- `ItemService` と `ItemRepository` が初期化済みである

主シナリオ:

1. 非同期セットアップが `ItemService.loadAll` を呼ぶ
2. `ItemRepository.findAll` で全 `ItemSummary` を取得する
3. summary ごとに `findById(id, category)` で詳細を取得し、ID key の snapshot へ登録する
4. 組み込み通貨定義を追加し、準備済み snapshot で master cache を置換する
5. 合計ロード件数を返す

代替シナリオ:

- 一覧・詳細取得中の例外は `LogId.E_5202` を記録し、それまで構築した snapshot と組み込み通貨を公開する
- ゴールド系7額面と `astrald` の組み込み通貨定義もマスタ snapshot に含める

事後条件:

- 取得できた全アイテムが正規化 ID key の共有キャッシュに保持される

## 2. 管理者が単一アイテムをリロードする

アクター:

- 管理者プレイヤー（コマンド実行者）

事前条件:

- 対象アイテム ID が API 側に存在する

主シナリオ:

1. 実行者が `/item load <itemId>` を実行する
2. 詳細 API で対象アイテムを取得する
3. 取得結果を該当カテゴリの共有キャッシュへ上書き登録する
4. 実行者へロード結果を通知する

代替シナリオ:

- 対象アイテムが見つからない場合はエラーメッセージを返して終了する

事後条件:

- 指定アイテムの共有キャッシュが最新の API 状態に同期される

## 3. プレイヤーが指定アイテムを受け取る

アクター:

- 管理者プレイヤー（コマンド実行者）

事前条件:

- 対象アイテムが起動時ロードまたは `/item load` によりキャッシュ済みである

主シナリオ:

1. 実行者が `/item get <itemId> [amount]` を実行する
2. `ItemService.findLoadedById` でロード済みキャッシュを確認する
3. インベントリサービスへ付与を委譲する
4. 通貨カテゴリは GUI を再描画しない。その他のカテゴリは通常インベントリ GUI を再描画する
5. 実行者へ付与結果を通知する

代替シナリオ:

- ロード済みキャッシュに対象がない場合は `PlayerMsgId.P_5213` を返して終了する。`/item get` 自体は API を呼ばない
- 対象アイテムがゴールド系7額面または `astrald` の場合は Plugin 組み込みマスタを使用し、filebase 由来の item 定義には依存しない
- インベントリ空きがない場合はエラーメッセージを返して終了する

事後条件:

- 対象プレイヤーの該当インベントリにアイテムが追加される

## 4. プレイヤーが AstralRecord アイテムのバニラ操作を試みる

アクター:

- プレイヤー（PLAYER モード）

事前条件:

- プレイヤーが AstralRecord アイテムを所持・装着している

主シナリオ:

1. プレイヤーがクリック・消費・攻撃などのバニラ動作を行う
2. クリック入力は`PlayerInteractionGatewayEventHandler`が受け付け、item resolverがプレイヤーの[[02_1.00-モデル定義]].アカウントモード と手持ちitemを副作用なしで評価する
3. world interactionなど上位候補が成立した場合、item候補は実行しない
4. item候補が勝者の場合だけexecutorへ委譲し、`InputClaimPolicy`に従って対象eventを抑止する

事後条件:

- バニラの食事消費・ブロック使用・エンティティ攻撃などの効果は発生しない

## 4.1 ポーションを右クリックで使用する

アクター:

- プレイヤー

契機:

- PLAYER モードのプレイヤーが `CONSUMABLE` カテゴリの AstralRecord アイテムを右クリックする

主シナリオ:

1. 右クリックgatewayが入力を正規化し、item resolverが`CONSUMABLE`カテゴリのitem use候補を返す
2. [[28_3.02-サービス]].勝者選択 でitem use候補が勝った場合だけ`PotionUseService.use`へ委譲する
3. `consumable.onUse.useTimeTicks` の間、移動キャンセル可能な待機を開始し、タイトル、BossBar、サウンド、パーティクルで使用中の進捗と残り秒数を表示する
4. 待機中に移動または持ち替えを検知した場合、ポーション使用をキャンセルし、タイトルと BossBar を片付けてキャンセル通知を表示する
5. 待機完了後、使用開始時と同じアイテムを保持している場合だけ `ItemConsumable.effects` の `rate` 判定に成功した効果を適用する
6. `RECOVER` 効果は `status` に応じて HP / MP / EN を回復する。`isPercent=true` の場合は対応する最大値に対する割合として扱う
7. `BUFF` 効果は `buffId` を `StatusService.applyBuff` へ渡し、バフ付与とステータス再計算を行う
8. 効果が 1 件以上適用された場合、`InventoryService.consumeHotbarItemInHand` で使用した手のホットバーアイテムを消費する
9. バフが新規獲得・再付与された場合、プレイヤー視界のより右下へバフ表示情報を数秒だけ表示し、表示中の残り時間を更新する

事後条件:

- バニラ消費イベントは発生せず、AstralRecord 側の効果適用とホットバー消費だけが行われる
- 同一入力からNPC操作、テレポーター、アクションリングなど別のトップレベルactionは実行されない
- 待機中は使用中であることと完了までの残り時間がタイトルと BossBar で分かる
- バフ獲得通知はプレイヤーごとに 1 件だけ表示し、別バフ獲得時は既存通知を差し替える

## 4.2 bundle を右クリックで開封する

アクター:

- プレイヤー（PLAYER mode）

主シナリオ:

1. 右クリック gateway の item use 候補が勝者になった場合だけ `BundleUseService.beginBundleUse` を呼ぶ
2. `bundle.lootTableId` を `LootService.getLoadedOrFetch` で解決する
3. `60 tick` の移動キャンセル可能待機を開始し、subtitle と BossBar で item 名と進捗を表示する
4. 待機完了時にも開始時と同じ bundle を同じ手に保持していることを確認する
5. `LootRollService.roll` で報酬を抽選し、bundle を 1 個消費する
6. 報酬 item はロード済みキャッシュを優先し、未ロードなら `ItemService.loadItem` で単体取得する
7. 解決できた報酬を統合 inventory へ付与し、付与できた種類数・合計数と各 item 名・個数を表示する
8. 付与できた報酬に対して ItemDisplay の落下・回収演出、filebase 定義の sound / particle を再生する

キャンセル条件:

- 移動、hotbar 持ち替え、退出、別の bundle 開始
- キャンセル時は title / BossBar を片付け、bundle 消費と報酬付与を行わない

終了条件:

- bundle 拡張または loot table ID がない、loot table を解決できない場合は `P_5242` を返す
- 完了時に同じ bundle を保持していない場合は消費・報酬付与を行わない
- bundle 消費に失敗した場合は `P_5245` を返す
- 現実装は統合 inventory に収容できなかった報酬を生成せず破棄する。改善方針は [[04_9.00-未決事項]] で管理する

Lore 表示:

- `ItemStackFactory.appendBundleLootLore` は `LootService.getLoadedOrFetch` で解決を試みる
- 候補は item 表示名、数量範囲（全角 `～`）、100% 未満の場合だけ確率を表示する
- 解決失敗時は `◆ ルート情報: <lootTableId> (未取得)` を表示する

## 5. サーバーがクライアントへアイテムパケットを送信する

アクター:

- サーバー（ProtocolLib リスナー）
- クライアント

主シナリオ:

1. サーバが `SET_SLOT` または `WINDOW_ITEMS` パケットを送信する
2. アダプタがパケット内 `ItemStack` の PDC を読み取る
3. AstralRecord アイテムであれば icon Material / customModelData を解決して書き換える
4. 書き換え結果でパケットを差し戻す

代替シナリオ:

- AstralRecord アイテムでない場合は何もせず元のパケットを通過させる
- icon Material 解決に失敗した場合は警告ログを記録し、当該 ItemStack の書き換えをスキップする

事後条件:

- クライアントには icon 適用済みの ItemStack が表示される

## 6. 装備インスタンスを生成する

アクター:

- サーバー（ルート抽選・コマンド・GUI など）

主シナリオ:

1. 呼び出し側が `ItemService.createEquipmentInstance(equipmentId, accountId, source, createdBy)` を呼ぶ
2. リポジトリが `POST /api/equipment/instances` を発行する
3. API がステータスロールを解決し、作成済み装備インスタンスを返す
4. サービスが結果を呼び出し側へ返却する

代替シナリオ:

- 例外発生時はエラーログを記録し、`null` を返す

事後条件:

- API 側に新規装備インスタンスが作成され、呼び出し側はインスタンス ID を含む結果を取得する

## 8. ItemStack の lore を生成する

アクター:

- サーバー（インベントリ表示、GUI 表示、コマンド付与）

主シナリオ:

1. `ItemStackFactory` が `ItemModel` / 装備インスタンス / ルーンインスタンスから表示用 ItemStack を生成する
2. 通貨カテゴリ以外の lore に `saleValue` を売値として `売値: <saleValue> ゴールド` の形式で表示する。通貨カテゴリでは売値と売却不可表示を出さない
3. 装備の追加スキルは見出しを `スキル` として表示する
4. `equipment.onUse.leftClickSkillId` / `rightClickSkillId` に紐づく通常攻撃・特殊攻撃の built-in スキルは、装備 lore のスキル一覧には表示しない

事後条件:

- 通貨カテゴリ以外では、プレイヤーは lore から売却時に得る予定のゴールド量を確認できる
