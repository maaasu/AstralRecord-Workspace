# 04_3-サービス

## 1. アイテムマスタロード

### 全アイテムロード

クラス名: `ItemService`
物理名: `loadAll`

処理内容:

1. [[04_3-サービス]].アイテムマスタスナップショット構築 を実行する
2. [[04_3-サービス]].アイテムマスタスナップショット置換 を実行する
3. snapshot 件数を返す

### アイテムマスタスナップショット構築

クラス名: `ItemService`
物理名: `loadMasterDataSnapshot`

処理内容:

1. `ItemRepository.findAll` で全 summary を取得する
2. summary ごとに `ItemRepository.findById(id, category)` で詳細を取得する
3. 未検出詳細は `LogId.W_5200` を記録し、snapshot 構築を失敗させる
4. 取得 item を正規化 ID key の一時 map へ登録する
5. Gold 7 額面と `99a00008`（旧ID `astrald`）の組み込み通貨を追加する
6. ENCHANT オーブが参照する全 `enchantMasterId` を重複排除し、`ItemRepository.findEnchantMasterById` で共通マスタを全件解決する
7. カテゴリ件数を `LogId.I_5202`、合計を `LogId.I_5203` で記録し、item と共通エンチャントマスタを含む不変 `MasterDataSnapshot` を返す

例外時挙動:

- item 詳細または参照する共通エンチャントマスタが1件でも取得できない場合は例外を伝播し、準備途中の snapshot を公開しない

### アイテムマスタスナップショット置換

クラス名: `ItemService`
物理名: `replaceMasterDataSnapshot`

入力:

- 準備済み `MasterDataSnapshot`

処理内容:

1. item と共通エンチャントマスタを同じ immutable snapshot として原子的に置換し、set-effect cache をクリアする
2. 共通エンチャントマスタ参照は置換後 snapshot だけを通信なしで参照する
3. equipment instance cache と dirty durability は保持する

### アイテムマスタキャッシュクリア

クラス名: `ItemService`
物理名: `clearMasterDataCache`

処理内容:

1. master item cache と set-effect cache だけをクリアする
2. runtime equipment state は保持する。ルーンは item マスタの通常スタック定義として次回ロード結果を使用する

### カテゴリ単位ロード

クラス名: `ItemService`
物理名: `loadAllByCategory`

処理内容:

1. category を trim・小文字化し、空なら `0` を返す
2. `ItemRepository.findAllByCategory` の結果が参照する共通エンチャントマスタを先に全件取得する
3. currency category の場合は組み込み通貨も追加する
4. item と解決済み共通エンチャントマスタを単一 snapshot として一度に公開し、成功件数を返す

例外時挙動:

- item または参照マスタ取得に失敗した場合は旧 snapshot を維持し、`LogId.E_5202` を記録して `0` を返す

### 個別アイテムロード

クラス名: `ItemService`
物理名: `loadItem`

入力:

- overload 1: item ID
- overload 2: item ID と category

処理内容:

1. ID を正規化し、空なら `null` を返す
2. 組み込み通貨 ID なら組み立てて cache へ登録する
3. category 未指定時は一覧 API で一致 summary を検索する
4. `ItemRepository.findById` で詳細を取得する
5. ENCHANT オーブなら参照する共通エンチャントマスタを先に取得し、item と同じ snapshot 世代で原子的に公開する

例外時挙動:

- category 未指定経路の例外は `LogId.E_5202` を記録して `null` を返す
- category 指定経路の repository 例外は呼び出し元へ伝播する

## 3. 所有インスタンス

### 装備インスタンス作成・取得

クラス名: `ItemService`
物理名: `createLocalEquipmentInstance` / `findEquipmentInstanceById`

入力:

- 作成: equipment `ItemModel`、account ID
- 取得: instance ID

処理内容:

1. 作成はAPI通信を行わず、UUID、ルーンslot数、耐久値、stat rollを一度だけ確定する
2. 新規instanceを正規化ID keyでcacheし、`pendingEquipmentCreations`とdirty集合へ登録する
3. 取得はcacheを優先し、未登録の場合だけ詳細APIを呼ぶ
4. player-state snapshotは新規instanceへ`isNew=true`とitem ID・stat rollsを付け、inventory entryと同じtransactionで保存する

例外時挙動:

- ローカル生成または取得に失敗した場合は`LogId.E_5202`を記録して`null`を返す

### ローカル装備状態の保存

クラス名: `ItemService`
物理名: `applyLocalEquipmentInstance` / `snapshotDirtyEquipmentState` / `acknowledgeEquipmentState`

処理内容:

1. 強化・修理・エンチャント・ルーン・状態変化の完成した `EquipmentInstance` は API command を送らず、Plugin cache と装備全体の dirty 集合へ反映する。耐久値だけの更新も同じ dirty 集合へ含める
2. player-state snapshotのcaptureはinventory state lock中にinventoryとdirty equipmentを同時に取得する。新規個体は`itemId`、`statRolls`、`isNew=true`も送る。既存個体の`statRolls`は作成時確定の不変値であり、可変フィールド、エンチャント、ルーンを保存する。耐久未設定のcache値は`durabilityMax=0` / `durabilityValue=0`として保持し、snapshot APIへは両方を`null`で送る。耐久ありはraw値のまま送る
3. snapshot 保存の ACK は capture と同じ装備状態だけを dirty から除去する。capture 後に再更新された個体は dirty を維持する
4. ACK の `updatedAtById` は capture 世代が古くても現在 cache の同一個体へ反映し、次回 snapshot の optimistic concurrency 基準を API 確定値へ更新する
5. 装備の未送信状態や操作 command を Plugin data folder へ保存しない。通常変更はメモリ上の dirty state、重要操作は即時 SQL ACK と補償で管理する

### 共通エンチャントマスタ取得

クラス名: `ItemService`
物理名: `findEnchantMasterById`

処理内容:

1. 正規化した ID で公開済み `MasterDataSnapshot` の共通エンチャントマスタを通信なしで確認する
2. 未登録時は `null` を返し、この参照メソッドから追加API通信やsnapshot変更は行わない

### 装備インスタンスのローカル破棄

クラス名: `ItemService`
物理名: `evictEquipmentInstanceFromCache`

処理内容:

1. 保存前に生成を取り消す個体、または外部取引APIで削除・譲渡済みと確定した個体を、通信せずinstance cacheから除去する。
2. durability dirty、完成スナップショット用dirty、新規作成集合も同じ排他境界で除去し、後続保存で復活させない。

## 4. 装備耐久値

### 耐久値キャッシュ更新

クラス名: `ItemService`
物理名: `updateEquipmentDurability`

処理内容:

1. equipment instance を cache 優先で解決する
2. durability を `0..durabilityMax` に clamp した新 instance を cache へ反映する。ローカル表示時刻を `updatedAt` へ書かず、APIが最後に確定したbase timestampを次回snapshotの`expectedUpdatedAt`として保持する
3. account ID・updatedBy と共に dirty update を登録する
4. 戦闘中の同期 HTTP は行わない

### dirty耐久値照会・snapshot・破棄

クラス名: `ItemService`
物理名: `hasDirtyEquipmentDurability` / `snapshotDirtyEquipmentState` / `acknowledgeEquipmentState` / `clearDirtyEquipmentDurability`

処理内容:

1. account ID 単位で未保存 update を照会し、最新の装備個体全体を完成スナップショットへ渡す。
2. snapshot ACKは送信時と同じrevisionだけをdirtyから除去し、送信後に発生した耐久値変更を保持する。
3. APIが返した`updatedAt`を次回snapshotの楽観ロック基準へ反映する。
4. 個別の耐久値POSTは呼ばない。clearは保存成功後のstate破棄境界で当該accountのdirtyを削除する。

### 戦闘耐久値消費

クラス名: `EquipmentDurabilityService`
物理名: `canUseMainHandWeapon` / `consumeOnAttackHit` / `consumeOnDamageTaken` / `isBroken`

処理内容:

1. 最大耐久値が正で現在値 0 以下の instance を破損と判定する
2. 破損した main-hand weapon は攻撃へ使用できない
3. 実 HP damage または shield damage が発生した命中だけを消費抽選対象にする
4. 攻撃側は weapon と攻撃寄与 accessory、被ダメージ側は armor と反応 accessory を対象にする
5. 同一 instance を 1 hit 内で二重消費しない
6. weapon の耐久値が減少して 5%、4%、3%、2%、1% の各閾値以下になる場合、該当する閾値ごとに `P_5282` を5%から1%の順で1回送信する。1回の消費で複数閾値を跨いだ場合はすべて送信し、耐久値が0になった場合は破損通知だけを送信する

### 装備中防具・アクセサリの破損通知

クラス名: `EquipmentDurabilityService` / `EquipmentDurabilityReminderTask`
物理名: `getDamagedArmorAndAccessoryDisplayNames` / `start` / `stop`

処理内容:

1. Bukkit の頭・胴・脚・足スロットと仮想アクセサリスロットを、メインスレッドの同期 timer から走査する
2. 最大耐久値が正で現在耐久値が最大値未満の装備個体を破損対象とする。耐久値0も対象に含める
3. 武器・補助装備・道具、最大耐久値を持たない装備は対象外とし、同一装備個体は1回だけ通知対象にする
4. 対象名をプレイヤー単位で結合し、3分（3600 tick）ごとに `PlayerMsgId.P_5283` を1通送信する。対象がない周期は送信しない
5. plugin disable 時に timer を停止する

### 採集耐久値消費

クラス名: `EquipmentDurabilityService`
物理名: `canUseMainHandTool` / `consumeOnGathering`

処理内容:

1. 最大耐久値が正で現在値 0 以下の main-hand TOOL は採集に使用できない
2. 採集 object の破壊完了時に、main-hand TOOL の `durability.consume` を1回消費する
3. 耐久値または装備 instance が未設定の場合は耐久値を変更しない

## 5. ItemStack生成

装備マスタおよび所有インスタンスの Lore には装備部位を表示する。`slot=ACCESSORY` かつ共有タグが解決できる場合は、アミュレット、タリスマン、チャーム、コア、レリックの種類別表示名を `アクセサリ枠` として追加する。未登録タグの内部 ID はプレイヤー表示へ出さない。

マスタ ItemStack と所有インスタンス ItemStack の共通 Lore ヘッダーには、カテゴリ表示の右へ ` | <item ID>` を追加する。カテゴリは灰色、区切り文字と item ID は濃い灰色で表示する。

### マスタItemStack生成

クラス名: `ItemStackFactory`
物理名: `create`

入力:

- `ItemModel`、任意の amount

処理内容:

1. model 内容から template を構築または cache から clone する
2. amount を `1..maxStack` に clamp する
3. 表示名、Lore、icon、customModelData、item ID、category 等を PDC へ格納する。`icon: PLAYER_HEAD` かつ `iconTexture` が非空なら Base64 textures 値も格納する
4. equipment のステータス名は既存の `StatusType` カテゴリー色で表示し、ステータス値は `値～値` 形式で表示する。値と `～` の左右に空白を入れない
5. equipment の `min` / `max` に個別の乱数範囲がある場合は、主値の次行へ灰色の `└2-3～4-5` として表示する。強化値注釈がないマスタ表示でも乱数幅を表示し、乱数幅へ強化加算を行わない
6. equipment に `setId` があり、セット効果を解決できる場合は、セット名、必要装備数、各ステータス補正を Lore へ表示する。セット効果を解決できない場合は内部 ID を表示しない
7. bundle Lore は `LootService.getLoadedOrFetch` で候補を解決する
8. rune は `❖ ルーン効果` の下に対象スロット、対象装備タグ（指定時）、必要強化（`requiredEnhanceLevel > 0` の場合）、ステータス補正を表示する。対象スロットは `ANY` を含む場合は「全スロット」、未登録値を「不明な装備枠」へ変換し、対象装備タグの未登録値は「不明な装備種別」へ変換して内部 ID を表示しない
9. rune のステータス補正は equipment と同じ `StatusType` の表示名、補正方式、数値書式を使用し、固定値のため乱数幅注釈は表示しない。解決できないステータスは内部IDを表示せず「未登録のステータス」とする

### 所有インスタンスItemStack生成

クラス名: `ItemStackFactory`
物理名: `create`

入力:

- equipment overload: `ItemModel`, `EquipmentInstance`, amount
- equipment metadata overload: `ItemModel`, `EquipmentInstance`, amount, `InventoryEntryModel.metadataJson`

処理内容:

1. 装備 instance ID と確定 roll、強化、状態変化、enchant、装着 rune、耐久値を Lore / PDC へ反映する。装着 rune はルーン名に続けて item マスタの固定ステータス補正を表示する
2. 装備マスタの `min` / `max` に個別の乱数範囲があるステータスは、主値の次行へ元範囲を灰色の `└2-3～4-5` として表示し、乱数幅へ強化加算を行わない。強化加算値がある場合は、主値の右側へ黄色の `[+値]`（範囲の場合は `[+下限～+上限]`）として表示する
3. ステータス範囲および強化加算範囲は `値～値` / `+下限～+上限` 形式で表示し、値と `～` の左右に空白を入れない
4. 状態変化 rank が 1 以上の場合は、状態変化名の後ろに灰色で `(ランクN)` を表示する。rank 0 の状態変化行は表示しない
5. `HOOKSHOT` tool の `metadataJson.hookshot.loaded=true` は Lore に `フック装填済み` を追加し、送信側でチャージ済みアイコンへ変換するための PDC を付与する
6. `equipment` の `setId` に対応するセット効果を解決できる場合は、マスタ ItemStack と同じセット名・必要装備数・各ステータス補正を Lore へ表示する。装備欄・仮想アクセサリ・現在保持中の主手・オフハンドへ表示する場合だけ、現在の有効セット数に応じて各 `{n}セット効果` の右へ発動中 `+` / 未発動 `-` を付け、未発動効果の文字列全体を灰色で表示する
7. マスタ、BAG、非選択 HOTBAR の表示は従来どおり静的なセット効果表示とし、発動状態記号・灰色化を適用しない
8. instance 固有のため template cache は使用しない

### display・shop ItemStack生成

クラス名: `ItemStackFactory`
物理名: `createDisplay` / `createShopDisplay` / `asDisplayStack`

処理内容:

1. `createDisplay` / `asDisplayStack` は PDC を保った clone へ icon の見た目を適用する。鍛冶型 icon は元 Material を維持して `ITEM_MODEL` だけを差し替え、クライアント固有の鍛冶型説明を出さない。それ以外は clone の Material を icon へ置換する。`PLAYER_HEAD` は iconTexture が非空の場合だけ SkullMeta の textures property を設定する
2. `BUNDLE` の表示では `DataComponentTypes.BUNDLE_CONTENTS` を非表示にし、バニラの内容量表示を出さない
3. `createShopDisplay` は未確定 equipment 等を `min～max` の範囲で表示する

### 耐久表示反映

クラス名: `ItemStackFactory`
物理名: `applyDurabilityVisual`

処理内容:

1. PDC の最大・現在耐久値を読み、vanilla damage bar へ比率を反映する
2. 装備 Lore の耐久バーは、耐久率 `75%以上` を濃い緑、`50%以上75%未満` を緑（ライムではない緑）、`25%以上50%未満` を黄色、`25%未満` を赤で表示し、未充填部分は灰色とする
3. 対象 PDC または `Damageable` meta がない場合は `false` を返す

### ItemStack PDC参照・外観反映

クラス名: `ItemStackFactory`
物理名: `getAstralItemId` / `getIconName` / `getCustomModelData` / `getAppearanceColor` / `getPotionType` / `getCategory` / `getEquipmentInstanceId` / `applyAppearance`

処理内容:

1. 各 getter は対応 PDC、未設定なら `null` を返す。`getEquipmentSlot` と `isWeapon` は `astralrecord:equipment_slot` を参照し、仮想トライデント対象を主武器だけへ限定する
2. `applyAppearance` は color / potion PDC を Bukkit meta へ適用できた場合に `true` を返す

### ItemStack template cache管理

クラス名: `ItemStackFactory`
物理名: `clearCache` / `cacheSize`

処理内容:

1. clear 時は全 prototype を破棄し `LogId.D_5210` を記録する
2. `cacheSize` は現在の template 件数を返す

### フックショット表示状態

クラス名: `ItemStackFactory` / `ItemStackPacketAdapter`
物理名: `create` metadata overload / `isHookshotLoaded` / `applyHookshotChargedIcon`

処理内容:

1. inventory entry metadata の `hookshot.loaded=true` を、該当する equipment instance の Lore に `フック装填済み` として表示する
2. `ItemStackPacketAdapter` は装填済み marker と `CROSSBOW` icon を検出した場合、送信コピーの `CrossbowMeta` に arrow 1個を charged projectile として設定し、バニラのチャージ済みクロスボウアイコンを表示する
3. サーバー側の base `PAPER` ItemStack と metadata 正本は変更せず、未装填時は通常のクロスボウアイコンを表示する

## 6. 使用待機

### bundle開封開始・取消

クラス名: `BundleUseService`
物理名: `beginBundleUse` / `cancelPendingOpen`

処理内容:

1. bundle 拡張と loot table ID を検証し、`LootService.getLoadedOrFetch` で開封前に解決する
2. 同一プレイヤーの既存待機を通知なしで取消し、`bundle.openTimeTicks`（省略時 `20 tick`）の移動キャンセル可能待機を開始する
3. subtitle / BossBar を表示し、完了時に同一手の同一 item を再確認する
4. `LootRollService.roll`、bundle 消費、報酬 item 解決、inventory 付与、演出・結果表示を行う
5. `AstPlayer` overload の cancel は必要に応じて取消通知し、UUID overload は退出用に通知なしで破棄する

戻り値:

- 開始・取消対象が成立した場合 `true`

### potion使用開始・取消

クラス名: `PotionUseService`
物理名: `use` / `cancelPendingUse`

処理内容:

1. consumable 拡張を検証し、`onUse.useTimeTicks` の移動キャンセル可能待機を開始する。待機中は `onUse.usingSound`（未指定時は `entity.generic.drink`）を再生する
2. 完了時に RECOVER / BUFF effect の rate 判定を行う
3. RECOVER は HP / MP / ENG の固定値または最大値比率、BUFF は `StatusService.applyBuff` へ委譲する
4. 1 件以上適用した場合だけ元 item を 1 個消費し、`onUse.sound` を使用完了後のサウンドとして再生する
5. 取消 overload の通知方針は bundle と同じとする
6. 使用完了時の消費は `executeResponsivePlayerMutation` でローカル確定する。回復効果・成功表示・cooldownはその結果直後に反映し、先行保存やSQL ACKを待たない。完成状態の非同期保存失敗を理由に消費を戻さない。外部取引境界・保存競合でローカル変更を拒否した場合は効果を適用しない

## 7. 補助サービス

### フックショット

#### 装填状態と発射耐久

クラス名: `HookshotLoadState`, `HookshotCostService`
物理名: `setLoaded` / `consumeDurabilityForFire` / `rollbackDurability`

処理内容:

1. 装填済みの正本は、equipment instanceではなく主手 `InventoryEntryModel.metadataJson` の namespaced object `hookshot.loaded` とする。通常のhotbar / bag / loadout移動、storageの格納・取出し、logout保存、market / trade transferでmetadataを保持する。storage格納時は既存metadataへ `acquiredAt` をmergeする。
2. 未装填の左クリックまたは右クリック開始時は、素材・耐久・metadataを変更せず、開始前に`10a00057` 1個の所持を確認する。不足時は装填taskを開始せず、`フックがありません。`のエラーを表示する。所持している場合は30 tickの装填完了時だけ、`HookshotLoadState.setLoaded(..., true)` で作ったmetadataと `10a00057` 1個の消費を `InventoryService.consumeNormalItemAndUpdateHotbarEquipmentMetadata` の同じstate lockで確定する。左クリック装填は従来どおり有効アンカーがあれば自動発射し、右クリック装填は装填だけで完了してloaded状態を保持する。
3. metadataが不正、主手instanceの持ち替え、metadata競合、素材不足のいずれかでは装填完了を確定せず、loaded状態を作らない。
4. 左クリック発射および左クリック装填完了後の自動発射はloaded状態と固体アンカーを再確認してから、主手equipment instanceとmasterの `durability.consume` を再解決する。現在耐久が消費値未満、最大耐久未設定、またはinstance未解決ならloaded状態を保持して無変更で終了する。右クリック装填完了では発射判定を行わない。
5. 発射直前に `ItemService.updateEquipmentDurability` で耐久だけを減らし、`InventoryService.updateHotbarEquipmentMetadata` でloaded状態を外す。後者が失敗した場合は `rollbackDurability` で元耐久へ戻し、発射しない。
6. 装填済みフックを外す業務操作は提供しない。loaded状態は有効発射成功時だけ外す。

#### 装填、照準・牽引

クラス名: `HookshotUseService`
物理名: `startLoading` / `fire` / `calculatePullVelocity` / `cancel` / `cancelLoading` / `shutdown`

処理内容:

1. crossbow iconを持つmain handの `slot=TOOL` かつ共有tag `HOOKSHOT` の同一equipment instanceだけを対象にする。装填中の一時状態はメモリtaskだけに保持し、完了済み状態はmetadataだけを正本にする。
2. `startLoading(player, fireOnCompletion)` は左クリックまたは右クリックで呼び出され、未装填・PLAYER mode・非skill詠唱・非牽引の主手toolで、`10a00057` 1個を所持している場合だけ30 tickのtaskを開始する。不足時はtaskを開始せずエラーを表示する。専用の transient `Attribute.MOVEMENT_SPEED` modifier（`MULTIPLY_SCALAR_1 = -0.5`）だけを付与し、終了時にそのmodifierだけを除去する。左クリックは `fireOnCompletion=true`、右クリックは `false` とする。
3. 装填中は `PlayerHudService.setPrimaryActionBarRenderer` で残り時間と進捗バーを毎tick再描画する。完了・中断時は自分のrendererだけを解除して通常HUDを再描画する。skill詠唱が始まった場合はそのrendererを上書き・解除しない。
4. `fire` は左クリックまたは左クリック装填完了時の自動処理から、最大24 blockの独自ray traceで最初の固体blockへ命中したloaded状態だけを発射する。snapshotの8 block rayは発射判定に使用しない。無効照準ではloaded状態を保持し、タイトルを空欄にした灰色subtitle `フックが命中しませんでした。`を表示する。耐久不足ではloaded状態を保持する。右クリック装填完了では `fire` を呼び出さない。
5. 成功時はblockを置換せず、命中面に金属格子型 `BlockDisplay` を表示し、`ParticleDisplayService`経由で着弾・tether particleを表示する。tether表示は2 tick間隔、最大12地点に制限する。
6. 毎tick、現在velocityのアンカー方向成分を88%保持し、横方向成分を68%へ減衰しながら、距離比例で0.16～0.27のアンカー方向加速度を加える。合成velocityは最大2.05に制限して `Player#setVelocity` を呼ぶ。位置座標、gravity、fall distanceは変更しない。
7. アンカー到達・44 tick時間切れ・持ち替え・死亡・退出・world変更・外部teleport・表示無効化でtaskとBlockDisplayを必ず回収する。装填中は同じライフサイクルとskill詠唱開始でmodifier・ActionBar・taskだけを回収し、completed loaded metadataは変更しない。

### デバッグ釣り竿仮想キャスト

クラス名: `DebugFishingRodUseService`
物理名: `cast` / `retract` / `moveHook` / `cancel` / `shutdown`

処理内容:

1. `slot=TOOL` かつ共有tag `FISHING_ROD` のmain-hand equipment instanceだけを対象にし、`StatusService.getStatus(player).rollValue(StatusType.CAST_DISTANCE)` を最大距離としてキャスト開始時に保持する。1は1 block（1m）。ステータス値は有限かつ正であれば採用し、別の固定上限は設けない。障害物のない水平キャストで35m指定なら35mに届くよう重力補償した初速を設定する。
2. 竿先は毎tick、eye locationと視線基底の右・上・前方オフセットから再計算する。投擲・落下・沈下の次位置は、現在の竿先を中心とする `CAST_DISTANCE` の球内に制限する。空中の範囲外候補は球内へ投影し、外向きの速度だけを除いて範囲内で落下を継続する。水中沈下の範囲外候補は移動線分と球面の交点で止め、水平位置を変えない。プレイヤー移動・視線変更で既存の針が上限外になった場合はキャストを終了する。
3. バニラの `FishHook` は生成しない。針は `TRIPWIRE_HOOK` の `BlockDisplay`、糸はサイズ0.15の黒色 `DUST`。糸は両端から毎tick再計算した21個の表示ノードを結ぶ浅い放物線とする。中央のたるみは0.35 block以下・水平距離の5%以下・距離上限の余裕の半分以下とし、描画曲線の総長も上限内に収める。糸自体は衝突・重力・慣性・張力を持たず、針を動かさない。
4. 糸dustは約0.15 block間隔、各区間最大4点（全20区間で最大80点）をユーザー指定の1tick間隔で描画する。長さゼロの区間は描画せず、viewerのいないworldでは生成を省略する。`ParticleDisplayService` の一括送信で竿先64 block以内のviewerへ密度設定に従って送る。糸dustの共通定義は統合版 viewer への送信を抑制し、Java版 viewer にだけ表示する。針には1tickの移動補間を設定する。
5. 針の移動は最大2 blockずつの掃引で固体・水面を調べる。探索予算を使い切った場合は未検査区間の手前でそのtickの移動を止め、固定状態にせず次tickに探索を続ける。最初の固体接触で `GROUNDED` へ移行し、位置と速度を固定する。地面・壁・水底が対象で、回収まで再び重力を適用しない。着水は `SINKING` へ移行し、X/Zを保持したまま0.08 block/tickで沈む。以前に飛んだ距離に制限せず、設定キャスト距離まで沈下を許可する。距離上限では沈下を停止し、上限に余裕ができれば再開する。標準4 blockキャストの同期衝突探索は1tickあたり128回以内とする。
6. 再右クリックで `RETRACTING` へ移行し、固体固定を解除して2 block/tickで竿先へ直接戻す。回収中の表示は固体を通過でき、到着後に表示とtaskを削除して再キャスト可能にする。回収中の再入力で音や処理を再開しない。`moveHook` は同worldの有限な目標へ初速を変更できるが、固体固定後は拒否する。移動にも距離上限と衝突を適用する。
7. 投擲・回収開始時に `ENTITY_FISHING_BOBBER_THROW` / `ENTITY_FISHING_BOBBER_RETRIEVE` を1回再生する。着水位置で `ENTITY_FISHING_BOBBER_SPLASH` と `FISHING_ROD_SPLASH` を1回再生する。player quit / death / world変更 / 外部teleport / 持ち替え / plugin停止 / 距離上限超過でtaskと針のBlockDisplayを削除し、糸dustの更新を停止する。魚の食いつき・釣果処理は追加しない。

### 装備条件判定

クラス名: `EquipmentRequirementService`
物理名: `check` / `checkAndNotify`

処理内容:

1. equipment の level / class 条件を `AstPlayer` と照合する
2. `check` は失敗種別と必要値を `Result` で返す
3. `checkAndNotify` は失敗時に対応メッセージを送り、利用可否を boolean で返す

### 武器左クリック処理

クラス名: `ItemWeaponAttackService`
物理名: `handleLeftClick` / `hasLeftClickAction` / `hasUsableMainHandWeapon`

処理内容:

1. main-hand weapon の `SWORD` / `HAMMER` / `SPEAR` / `BOW` / `SHORTBOW` / `LONGBOW` / `WAND` / `STAFF` tagから組み込み通常攻撃を解決する
2. 装備条件・耐久値を確認して system skill 実行へ委譲する
3. `hasLeftClickAction` は副作用なしで候補成立可否を返す
4. `hasUsableMainHandWeapon` は主手が weapon であり、プレイヤーレベル・クラス・クラスレベルの装備条件を満たし、耐久値切れでない場合だけ true を返し、action ring と左クリック bind の発動前判定に共通利用する
5. 全武器種の待機判定は共通 cooldown key `weapon_normal_attack` を参照し、発動成功時は `10 / 22 / 14 / 12 / 7 / 17 / 9 / 14` tick のタグ別基本値で同じkeyを開始する

### キャストディスク

クラス名: `CastDiskUseService`、`CastDiskGui`

1. `SKILL_CAST_DISK` と `DODGE_CAST_DISK` の `slot=TOOL` equipment instance は、ホットバー主手からだけ使用する。両方とも個体耐久を最大200、成功使用ごとに1消費する。
2. スキルキャストディスクの metadata はアクションスロット番号（1～6）と武器ホットバー番号（1～9）だけを保持する。スキルIDは保存せず、設定GUIを開いた時点の選択プリセットの6枠を上段に表示し、発動時もその時点の同じ番号の枠を再解決する。個体の通常表示Loreには、この2つの現在設定を未設定状態を含めて表示する。
3. 設定GUIは3行で、上段の6枠がアクションスロット選択、下段の9枠が武器ホットバー選択である。右クリックは常にGUIを開く。未設定のディスクを左クリックした場合もGUIを開く。
4. 設定済みディスクの左クリックは、指定ホットバー枠に装備条件と残耐久を満たすWEAPONがある場合だけ、その武器を発動中の主手として扱い、主手切替後に `StatusService` でステータスを再計算してからアクションスロットを実行する。発動後は元の主手へ戻し、ステータスも再計算する。一時武器の最大値クランプで失われた現在HP/MP/ENG/Shieldは復元し、実際に確定したスキル消費だけを保持する。武器がない場合は `P_7170` を表示し、ディスク耐久を消費しない。スキル発動成功時だけディスク耐久を消費する。
5. ドッジキャストディスクは、右クリック時の位置と同一instanceを予約し、5tick（0.25秒）後に自動で通常ドッジを試行する。callback時点の現在座標を終点とし、右クリック時の始点から終点へのXZベクトルを使う。スニーク入力は使用しない。同一playerの再右クリックは前の予約を取消し、持ち替え・破棄・logout・account切替で同一instanceを確認できない予約は不発にする。地上でない場合は予約も発動もせず、メッセージを表示しない。成功時だけ耐久を消費し、プレイヤー単位で3秒の共有クールダウンを開始する。

### 報酬落下回収演出

クラス名: `ItemDropAnimationService`
物理名: `playCollectingDrop`

処理内容:

1. icon Material の `ItemDisplay` を起点から落下させ、対象プレイヤーへ回収する演出を再生する

### オーブ装備操作

クラス名: `OrbService`

処理内容:

1. 通常プレイヤーインベントリのオーブ entry クリックからオーブ item IDを特定して候補一覧を開く。クリックしたentry IDは消費元として固定せず、操作確定時にitem IDの通常アイテム共通消費順（BAG優先、後方slot優先、slot未指定は後、同slotは`inventoryEntryId`昇順）で消費元entryを再解決する
2. BAG / HOTBAR と装備中を走査し、強化可能、耐久減少中、即時次ランクへ状態変化可能、エンチャント可能のいずれかを満たす装備だけを表示する。装備中を先にし、同一 instance は重複させない
3. 対象クリック時にオーブ item IDから消費元entryを通常アイテム共通消費順で再解決し、対象 instance、所有 account、ランク・装備種・空き枠等を state 正本から再検証する
4. 強化の `successRate` 抽選と失敗時の `NONE` / `SET_LEVEL` / `DECREASE_ONE` 適用、修理、エンチャント抽選、ルーン装着・脱着、即時次ランクへの状態変化は、ロード済みitem snapshot と現在の player state を使ってPluginが操作直前に計算する。使用数を設定した場合（最大10個、所持数以下）も、各回は現在値に対して即時処理する
5. 修理は `repairAmount` 分または最大耐久まで回復する。追加費用は消費しない。使用数を設定した場合は、修理可能な耐久値が残る間だけ単一操作を逐次実行する
6. 状態変化は immediate next rank だけを対象とし、27枠の専用確認画面で名称・必要素材・通貨・不足を表示する。確認画面の2行目には対象装備（slot 11）、54枠のページ付き消費アイテム一覧への導線（slot 13）、実行（slot 15）を配置し、確認画面の戻るは最下段中央（slot 22）、一覧画面の戻るは最下段中央（slot 49）とする。不足時は実行不可とする
7. エンチャントは共通マスタを使い、同一 `effectId` を重複させない。候補不足は無変更・無消費としてプレイヤーへ通知し、使用数を設定した場合は次の候補がなくなるまで単一操作を逐次実行する
8. 成立した単一操作は成功・強化失敗を問わずオーブを必ず1個だけ消費する。`FILL_ALL_EMPTY` も1個とする。複数回適用では各回にこの支払い規則を適用し、途中で対象条件またはオーブがなくなれば未実行分を消費せず終了する
9. Pluginはオーブ、状態変化素材・通貨を予約した後、`executeResponsivePlayerMutation` 内の同一state lockで `commitLocalOrbOperationPayment` を実行し、実消費、装備完成状態の反映、ルーン脱着時の返却を一体確定する。外部 market / trade 境界中は開始しない
10. 先行dirty保存とSQL ACKは待たない。ローカル検証・適用の失敗時だけ inventory と equipment cache の部分変更を戻す。確定した完成状態は非同期snapshot保存へ渡し、通信失敗で消費・結果を補償しない
11. ローカル確定直後に画面・装備表示・ステータス・成功音・成功メッセージを反映する。送信中のsnapshotは不変のまま保持し、次のローカル変更はACK後の次便へ保存する
12. 複数回適用は各回のローカル確定後に次の回を少なくとも1tick後に開始し、SQL ACKを待たない。最後に使用数・成功数・失敗数・残数を集計通知する。途中のローカル検証失敗以降の回は開始せず、未実行分を消費しない
13. mutation中の手動closeは同じsession tokenのGUIを次tickに再表示し、結果確定まで入力ロックを維持する。quitは表示だけをdetachし、保存 lane は開始済み操作の確定・補償を継続する
14. 通常インベントリから最初にオーブGUIを開く場合は `GuiSound.OPEN`、オーブGUI内で別のオーブ画面へ遷移する場合は `GuiSound.SELECT` を再生する。オーブGUIの手動終了確定時は共通セッション基盤が `GuiSound.CLOSE` を一度だけ再生し、画面遷移中の古いcloseイベントとquitでは再生しない
15. ルーン装着画面の下段ではスクロール制御とHOTBAR slotを共通クリック処理へ先に委譲し、BAG表示slotだけをルーン選択に使用する。選択済みルーンのslot 13を再クリックすると未選択へ戻す。装着・脱着確認画面はslot 22で対象装備一覧へ戻す。複数ルーンの脱着選択画面はslot 18/26でページ移動し、slot 22の共通戻るボタンで脱着確認画面へ戻す
16. `SIGIL_ATTACH` / `SIGIL_DETACH` は装備候補収集へ入れず、`SkillSigilOrbService`へ委譲する。習得済み個体を45件/pageで表示し、27枠GUIで所持シジルitem IDまたは装着行UUIDを選択する。装着時は操作確定時に対応するオーブと選択シジルitem IDを通常アイテム共通消費順でentryへ解決して各1個消費し、脱着時は対応するオーブを同じ順で解決して1個消費する。素材、習得個体、返却を一つの重要操作 snapshot で保存する。
