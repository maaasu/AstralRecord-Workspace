# 31_5-例外・ログ・運用

## 1. 読み込み時の扱い

- `training-dummies.yml` が存在しない場合は配置なしとして起動する。
- `id` または `world` が空の行は読み飛ばす。数値・boolean の不正値は [[31_1-モデル定義]] のフォールバックと下限制約を適用する。
- 定義先ワールドが未ロードの場合は定義を残し、20 tick 周期で実体生成を再試行する。
- ワールド解決後の実体生成に失敗した場合は、同じ読み込み状態で毎周期の再試行を行わない。原因修正後に `/dummy reload`、再配置、または設定更新を行って再試行する。
- reload は現在のカカシ実体をすべて破棄してから読み直すため、YAML の欠落・不正行はその時点の出現対象から外れる。

## 2. 保存失敗

data folder を作成できない場合、または `training-dummies.yml` を保存できない場合は `IllegalStateException` を送出する。

現行処理はメモリ変更と実体破棄を保存前状態へロールバックしない。

- `place` / GUI 更新の失敗ではメモリ定義だけが新しい値となり、実体再生成まで進まない場合がある。
- `remove` の失敗ではメモリ定義と実体は削除済みだが、ディスクには削除前の定義が残る場合がある。
- 保存失敗後は data folder の権限・空き容量を確認し、YAML と出現状態を確認してから reload または再操作する。

## 3. ログとプレイヤーメッセージ

本 feature 固有の `LogId`、`PlayerMsgId`、properties 定義はない。コマンドは引数不備時の共通 usage だけを表示し、成功件数、存在しない ID、reload 結果を通知しない。実体生成では Mob 基盤の既存ログが発生する場合がある。

## 4. 権限と共有範囲

- `/dummy` は player-only かつ `UserPermission.ADMIN` 必須とし、コンソールと権限不足プレイヤーから実行できない。
- Drop キー経由の GUI は権限を検証しない。配置済みカカシを視認できる全プレイヤーが同じ定義を編集する。
- 変更はプレイヤー別セッションではなく直ちに全体へ保存・再生成される。同時操作のロックや楽観的競合検出は行わないため、後から処理された更新を正とする。

## 5. 運用手順

- 通常は `/dummy place <id>` と GUI で管理し、ID は小文字で統一する。
- YAML を手編集する場合は Plugin 停止中にバックアップを取得するか、編集後に `/dummy reload` を実行する。
- 手編集では `world` にロード可能な Bukkit ワールド名を指定し、重複 ID、大文字小文字の混在、不正な回復間隔を避ける。
- 同じ ID の `place` は座標だけでなく検証ステータスも既定値へ戻すため、既存設定を保持した移設には使用しない。
