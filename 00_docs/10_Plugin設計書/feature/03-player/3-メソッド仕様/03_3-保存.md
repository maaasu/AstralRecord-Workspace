# 03_3-保存

## 1. save メソッド仕様

### ローカル状態と完成スナップショット

プレイ中の状態決定者はPluginとする。装備操作、習得スキル、シジル、バインド、スキルツリー、経験値・クラス進行・モードの通常変更はAPIの業務判定を待たずローカルで確定する。素材と通貨を伴う変更は `InventoryService.executeLocalPlayerMutation` または `commitLocalOrbOperationPayment` により `PlayerInventoryState` の同一monitor内で行う。計算・所持数検証・実消費・変更の順とし、不足時には一部分だけを適用しない。表示だけ数量を隠す予約は確定済み消費の代わりにしない。

保存は `InventorySaveCoordinator` のアカウント別laneへ集約する。`InventoryPersistence` が有効な全inventory entry、loadout slot、dirty装備、登録された `PlayerStateSection` を同じstateロック下で捕捉し、`POST /api/player-state/snapshots` へ非同期送信する。Goldは独立残高でなくCURRENCY inventoryのentryとして同じ保存に含める。プロファイルの識別・権限・BANなどを進行状態のスナップショットに混ぜない。位置・表示など別の保存が進行の期待版を更新しないよう、APIの進行版は独立させる。

送信中のスナップショットは不変とし、`snapshotId` と内容を再送時も維持する。同一アカウントの先行送信が未受領なら後続を追い越させない。送信後のローカル変更はdirtyとしてまとめ、先行ACK後に最新の完成状態を捕捉する。APIは素材を再消費したり強化を再抽選したりせず、所有権・期待版・構造を検証して全セクションを一つのDB transactionで保存する。

ACKはsnapshotIdと保存済み版情報のみを返す。inventory数量・装備強化値・スキル内容を応答で置き換えない。送信時点より先のローカル変更がある場合も期待版のmetadataは進め、dirty解除は捕捉した世代に限定する。異なるsnapshotId、欠落したACK要素は成功扱いにしない。

`saveNow` の成功は対象の送信内容が受領されたことを意味し、捕捉後に生じた後続dirtyがあってもfalseへ変換しない。後続dirtyは保存queueへ再登録する。外部取引の開始には成功結果に加えて未保存変更がないことを別途確認する。再起動時の再送も通常時と同じ本文基準のACK検証（account、全明細、section revisionと保存版）を通った後だけファイルを削除する。

### ローカルファイルと再送

所持品dirtyがない経験値・スキル設定・耐久値だけの保存ではinventory/loadout全文を送らない。所持品dirtyがある場合はinventory間移動・削除を同時確定するため、有効なinventoryとloadoutの完成状態を同梱する。

各inventoryの `expectedEntries` は最終受領時の有効entry UUIDとAPI更新日時の全組とする。現在の完成状態に存在しない削除対象もこの集合に含め、APIは集合と各版を確認する。ローカル操作日時でAPI期待版を更新しない。外部取引後は正本照合と同時に期待集合・版を更新する。

`PendingStateStore` は所有者UUIDごとに未受領の送信内容を圧縮バイナリへ保存する。保存・読込・圧縮・削除は非同期保存処理で行い、クリック処理で全プレイヤーのファイルを再書込みしたりディスク同期を待ったりしない。表示文字列・マスタ・応答全文は保持せず、APIが受領した送信内容だけを削除する。他アカウントの未受領データは削除しない。

ファイルは不変の送信中本文と、合流した後続の最新完成状態の最大二世代を保持する。API laneとは独立したローカルI/O laneで後続を書き込み、連打時も履歴を無制限に蓄積しない。先行ACK後は後続の期待版だけを進め、数量・強化値・UUIDを再計算しない。先行受領・後続未送信の状態を次便POSTより先に耐久化する。

既存ファイルはAPIへ同じsnapshotIdで順番に再送した後に通常ロードする。ファイル所有accountと両世代のaccountを送信前に照合する。読込不正や再送失敗時に空状態でログインを継続しない。旧単一snapshot形式も復元可能とする。プロセス内の最新dirty変更と、非同期にファイルへ書込済みの送信内容は別であり、メモリ受付直後・ファイル保存前の強制終了や停電に対する耐久性保証は対象外とする。

正常停止では新規変更の受付停止後、API応答とは独立して最終ローカル書込完了を待つ。API待機の時間切れ後も後続を保持する。停止用ファイルを凍結した後の遅延ACKは、破棄済みcacheから再捕捉せず、ファイル内の後続と期待版を引き継ぐ。

クエスト完了・報酬claimも同じ原則で、`QuestPlayerStateRepository` が完成状態を専用の圧縮ローカルファイルへ先に書き込む。API保存が成功した場合だけ削除し、通信断・正常停止・受領不明では次回ログイン時にローカル状態を先に復元して再送する。これによりinventory報酬だけが保存されてQuest完了状態が旧API値へ戻る経路を作らない。

通常参加・account切替の双方で、account/習得スキルの初期値を適用する前に復元を完了する。account識別のために先に取得した値は、復元があった場合に再取得し、復元前の経験値・進行版をセッションへ適用しない。

通信の一時障害は最大30秒までの指数バックオフで再送し、ローカル確定済み操作の失敗・素材返却としてプレイヤーへ通知しない。401/403・契約不一致など確定的な4xx、または200でも不正・不完全なACKでは対象スナップショットを保持して同期を停止し、対象アカウントの追加経済変更を拒否する。waystone ACKも文字列配列の順序・要素を含む完全一致で検証する。409を根拠にAPI状態でローカル全体を上書きしない。保存失敗は `W_5252` に記録する。

### 共有更新とライフサイクルの境界

マーケット・トレードなど別所有者または外部台帳を更新する操作は、従来の `executeExclusiveAfterSave` 境界を使う。先行のローカル完成状態を保存後に外部操作を開始し、API側正本の照合が済むまで新しい装備・スキル・経済変更を保留する。照合したAPI entry集合を次のスナップショットの期待集合へ反映し、外部操作中の許可済みローカル差分は既存の三者マージで維持する。

設定はアカウントでなくユーザー所有とする。`userId + settingKey` の最新希望値をローカルで反映し、独立した非同期保存で版情報だけをACKする。退出や再ログインで古いセッションの応答を新しい希望値へ上書きしない。

旧 `pending-mutations.bin` は移行用の未完了操作として保持し、新方式の操作を追加しない。旧操作が残るアカウントだけ新規経済変更を保留して旧台帳へ順次再送する。再送待ちの操作を後続が追い越さず、受領済み分だけを削除する。

### プレイヤー保存実行

クラス名: `PlayerSaveCoordinator`
物理名: `save`

処理内容:

1. 登録済み保存タスクを順に実行する
2. 個別タスクで例外が発生しても後続タスクは継続する
3. 例外時は `LogId.W_5071` を記録する

	| 項目 | 内容 |
	|---|---|
	| ID | `LogId.W_5071` |
	| レベル | `WARN` |
	| テンプレート | `プレイヤーデータ保存に失敗しました: タスク=%s, 契機=%s, プレイヤー=%s, 理由=%s` |
	| 出力条件 | 保存タスクで例外発生時 |
	| 引数 | タスク名, 保存契機, プレイヤー名, 例外メッセージ |
