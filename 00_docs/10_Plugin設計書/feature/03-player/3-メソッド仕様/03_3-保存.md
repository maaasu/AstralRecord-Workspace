# 03_3-保存

## 1. save メソッド仕様

### ローカル状態と完成スナップショット

プレイ中は Plugin のメモリ状態で計算し、耐久化済みの正本は AstralRecord API が保存する SQL Server とする。inventory、loadout、equipment、習得スキル、バインド、スキルツリー、経験値・クラス進行・mode、waystone の保存待ち情報を Plugin data folder へ書き出さない。ログイン時は API から読み、プロセス終了後に復元するローカル player-data ファイルは持たない。

素材と通貨を伴う計算は `PlayerInventoryState` の同一 monitor 内で検証・消費・状態変更する。途中で検証が失敗した場合は部分適用しない。Gold は独立残高ではなく CURRENCY inventory の entry として扱う。

## 通常変更の統合スナップショット

`InventorySaveCoordinator` は account 別 lane で保存を直列化する。経験値、耐久値、通常の inventory 変更など連続しやすい変更は 200ms の debounce 中に一件へまとめる。プレイヤー操作はメモリ計算の完了を待つだけとし、通常保存の HTTP I/O は非同期 executor で行う。

`InventoryPersistence` は dirty な inventory、loadout、equipment と登録済み `PlayerStateSection` を同じ state lock で捕捉し、`POST /api/player-state/snapshots` へ送る。送信中 payload と `snapshotId` は不変である。捕捉後に増えた変更は同じ payload へ混ぜず、先行 ACK 後の次便へ残す。

各 inventory の `expectedEntries` は最終 ACK 時の有効 entry UUID と API 更新日時の全組である。ローカル操作時刻で API の期待版を進めない。inventory 間移動・削除を含む場合は関係する完成配置を同じ snapshot に含め、API が所有権、期待版、集合一致を検証して一つの SQL transaction で適用する。

## 重要操作のACKと補償

強化、修理、スキル習得・強化、購入、取引など、消費と結果が不可分な操作は account lane の `executeCriticalMutation` を使う。

1. 操作前の通常 dirty を snapshot 保存し、SQL ACK を補償点とする。
2. Plugin が state lock 内で所持数検証、乱数・数値計算、消費、完成状態反映を行う。
3. 消費後の inventory と結果を一つの player-state snapshot として即時保存する。
4. 完成 snapshot の SQL ACK 後だけ成功 callback、成功メッセージ、GUI 遷移を実行する。
5. 保存失敗が確定した場合は、同じ排他境界内で inventory、equipment、skill を操作前のメモリ状態へ戻し、失敗メッセージを表示する。失敗した完成 payload は後から自動送信しない。

操作受付後に ACK 待機が長引く場合は GUI を処理中として閉じられるが、同じ account の競合操作は結果確定まで受け付けない。プレイヤーへ成功を先に表示しない。

マーケットやトレードなど API が独自の原子 transaction を持つ操作は `executeExclusiveAfterSave` を使う。先行 player-state の ACK 後に API 操作を開始し、同じ operation ID の結果照会と影響 entry の正本照合が終わるまで account lane を解放しない。

## ACK検証と失敗処理

ACK は `snapshotId`、`accountId`、送信した全 core 行、全 optional section の revision と保存版を検証する。inventory 数量や装備・スキルの内容を ACK 本文で置き換えない。捕捉後に state revision が進んでいる場合は保存版 metadata だけを進め、後続 dirty は解除しない。不正・不完全な 200 応答は成功扱いにせず、その account の追加変更をブロックする。

POST が I/O 例外または 408 / 425 / 429 / 5xx で結果不明になった場合、Plugin は同じ `snapshotId` と `accountId` を `GET /api/player-state/snapshots/{snapshotId}` で照会する。`COMPLETED` と完全な ACK を取得できた場合は成功とする。GET の 404 は、最初の POST がまだ commit 前である可能性があるため失敗確定に使わず、同じ payload と `snapshotId` で POST を一度だけ再送して再照会する。それでも確定を確認できない場合だけ保存失敗として扱う。401 / 403、構造不正、競合など確定的な応答は再計算や別 ID での再送を行わない。

通常保存失敗では dirty state を現在プロセスのメモリに保持して再試行する。重要操作では前項の補償を行う。どちらもローカルファイルへ退避しない。保存失敗は `W_5252` に記録する。

## player-state snapshot

チャンネル移動では Bukkit 状態を現在セッションへ反映した後、debounce 待ちを即時 flush し、捕捉中に増えた差分がなくなるまで最大三回 snapshot 保存する。player-state と Quest state の両 ACK が成功するまで Proxy 接続要求を送らず、feature runtime と cache を解放しない。チャンネル移動とアカウント切替はプレイヤー単位の共通セッション遷移ゲートを先に取得し、一方の完了または失敗まで他方を開始しない。失敗時は移動を中止し、無敵化と操作凍結を解除して現在チャンネルに残す。

正常 logout と Plugin 停止では新規受付を止め、account lane の登録済み保存を drain する。時間内に保存できなかった状態は SQL 未確定であり、プロセス終了後の復元保証はしない。

player setting は user 所有のまま、選択中 account の保存 lane から player-state snapshot の `playerSettings` optional section として保存する。最新希望値と retry state はプロセス内だけに保持し、ACK の version が現在世代と一致する場合だけ dirty を解除する。

### プレイヤー保存実行

クラス名: `PlayerSaveCoordinator`
物理名: `save`

処理内容:

1. 登録済み保存タスクを順に実行する
2. 個別タスクで例外が発生しても後続タスクは継続する
3. 例外時は `LogId.W_5071` を記録する

	| 項目 | 内容 |
	|---|---|
	| ID | `LogId.W_5071` |
	| レベル | `WARN` |
	| テンプレート | `プレイヤーデータ保存に失敗しました: タスク=%s, 契機=%s, プレイヤー=%s, 理由=%s` |
	| 出力条件 | 保存タスクで例外発生時 |
	| 引数 | タスク名, 保存契機, プレイヤー名, 例外メッセージ |
