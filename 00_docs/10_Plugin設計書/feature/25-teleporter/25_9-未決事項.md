# 25_9-未決事項

## 1. プレイヤー単位とアカウント単位の扱い

現行 API / DB は `account_waystone_unlock` として選択中アカウント単位で解除状態を保持する。
ユーザー依頼上は「プレイヤー単位」と表現されているため、Minecraft ユーザー内の複数アカウントで解除状態を共有するか、選択中アカウントごとに分けるかは最終確認が必要である。

本設計の仮決定:

- 実装上は既存 API / DB 契約に合わせ、選択中アカウント単位とする。
- ゲーム内表示上は「プレイヤーが解除したウェイストーン」と表現してよい。

## 2. ウェイストーン ID 生成規則

現行実装では `/teleporter set` 実行時に Plugin が `ws-<UTC yyyyMMddHHmmss>-<name slug>` 形式で内部 ID を生成し、同一 ID が発生した場合は `-2` 以降の連番を付ける。全体は最大 100 文字に収める。
将来的に管理者が安定した ID を指定したい場合、`/teleporter set <id> <name> <lockEnabled> <unlockGold> [icon]` へ拡張する。

## 3. ゴールド消費と API 登録の原子性

現行設計では `CurrencyService` と `account-waystone` API の間で完全な分散トランザクションを持たない。
そのため、ゴールド消費後に API 登録へ失敗した場合は返金で補償する。

今後、通貨消費と解除登録を同一 API トランザクションで扱う必要が出た場合、API 側に `unlock with cost` エンドポイントを追加する。

## 4. packet-only 表示とクリック精度

packet-onlyのBlockDisplay / TextDisplayはサーバー側Entityとして存在しないため、クリック判定はhitbox ray traceで代替する。他featureやvanilla操作対象との競合は[[28_0-概要]]の共通ray snapshot、入口`hitDistance`、遮蔽距離、勝者一件実行で解消済みとする。

残る未決事項は実サーバーでのhitbox寸法と見た目に対するクリック感度の調整である。精度調整だけで解消できない場合は不可視`Interaction` entityを置く方式を検討するが、feature間の排他制御をlistener順へ戻す理由にはしない。

## 5. 表示デザインの最終ブロック構成

本設計では Waystones 系 mod をモチーフにした石碑状の BlockDisplay 構成を指定している。
最終的な Material、スケール、回転、発光、TextDisplay の高さは、実サーバー上で見た目を確認して微調整する。

## 6. 同一座標の重複登録

現行実装は `/teleporter set` で同一座標に複数定義を登録できる。表示と入力候補が重複するため、座標単位で拒否するか、明示的な置換操作を導入するかを決定してから検証を追加する。
