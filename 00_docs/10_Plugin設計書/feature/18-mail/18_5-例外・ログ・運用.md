# 18_5-例外・ログ・運用

## 例外方針

- 一覧 repository は非期待 status／通信失敗を runtime exception とする。
- service は非同期境界で例外を捕捉し、main thread callback の `false`／failure に変換する。
- 報酬、equipment、既読状態を同じplayer-state snapshotへ含め、一部だけのSQL確定を許さない。削除も個別更新 API を使わず `mailDelete` section で確定する。
- SQL失敗、version競合、結果照会後も確定できない通信失敗では、受取処理のinventoryとequipment cacheを操作前へ戻し、削除処理の対象メールを表示に残す。
- 保存失敗時の受取callbackは`success=false`／`rewardReceived=false`とし、成功通知を出さない。

## ログ・メッセージ

| ID | 用途 |
|:--|:--|
| `LogId.E_5190` | mail API operation、path、failure reason |
| `LogId.E_5601` | mail GUI click／drag／close の安全実行失敗。player と `mail_gui_click`／`mail_gui_drag`／`mail_gui_close` を記録 |
| `P_5620` | 報酬受取成功 |
| `P_5621` | 削除結果 |
| `P_5622` | メール未存在／削除失敗 |
| `P_5623` | 報酬準備・付与失敗 |
| `P_5624` | 未読件数通知 |
| `P_5625` | 報酬・既読状態の重要保存失敗 |

## 運用

- mail ID は master／個別配送を通して一意となる安定 ID を使う。
- `publishFrom`／`publishTo` とアカウント別可視性は API の正本とし、plugin で再実装しない。
- `P_5625`または共通player-state保存ログが連続する場合は、snapshot IDの結果照会、API稼働状況、version競合を確認する。
- SQL ACK時にplayerがofflineの場合、受取成功listenerはログイン完了後へ保留し、`notifyPendingMailReceived`で一度だけ再送する。
- welcome mail の有無は API／master data を監査し、plugin の起動・ログイン処理へ暗黙に追加しない。
