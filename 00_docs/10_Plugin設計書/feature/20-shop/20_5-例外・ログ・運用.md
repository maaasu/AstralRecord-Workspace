# 20_5-例外・ログ・運用

## 例外方針

- master load 失敗時は不完全な cache を公開しない。
- 業務上の購入不可は `preview.canPurchase=false` または `purchase=false` で返す。
- payment／grant mutation 後の失敗は `InventoryStateSnapshot` を復元する。
- restore 自体が失敗した場合は自動で再試行せず warning を残す。

## ログ・メッセージ

- GUI click／drag 例外は `LogId.E_5601` に player と `shop_gui_click`／`shop_gui_drag` を渡す。
- 購入補償は `LogId.W_6300` を使う。現在の実装は resource 上の `shopId` 位置へ `entry.id()` を渡しているため、運用上は第 2 値を entry ID として読む。
- command の shop 未存在／非公開は `PlayerMsgId.P_5930`。

## 運用

- shop ID は一意、entry ID は shop 内で一意にする。
- explicit slot と row／column が GUI 範囲内か master review で確認する。
- `recipeId` が未解決の場合は direct cost のみで販売されるため、参照整合性を事前検証する。
- stock／販売上限は未実装である。YAML に未知 field を加えるだけでは制限にならない。
- `W_6300` の第 2 field 名を shop ID にするか entry ID にするかは、log resource と purchase API を同時に整理して統一する。
