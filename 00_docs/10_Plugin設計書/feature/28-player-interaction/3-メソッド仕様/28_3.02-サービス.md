# 28_3.02-サービス

## 1. プレイヤー入力調停

クラス名: `PlayerInputDispatcher`

物理名: `dispatch`

1. `PlayerInputContext`と対応する入力tokenを受け取る。
2. 登録された全`PlayerInputResolver`へ候補収集を依頼する。対象familyを扱わないresolverは空を返す。
3. `PlayerInputCandidate`の生成時検証を通った候補を集約し、同じ`id` / `targetKey`の重複候補は構成不備として拒否する。遮蔽物より遠い候補を返さない責務は各空間resolverが持つ。
4. [[28_3.02-サービス]].勝者選択で勝者を最大一件に確定する。
5. 候補がない場合はwinnerなしの`PlayerInputDispatchResult.passThrough()`を返し、元eventの状態を変更しない。
6. 勝者が存在する場合、gatewayから渡された実行直前処理がpolicyに従ってtokenのclaimとevent cancelを反映する。
7. 勝者の`executeIfValid()`を一回だけ呼ぶ。`executionGuard`が`true`の場合だけexecutorを実行し、`false`の場合は見送る。
8. guard不成立、executorの拒否・失敗・例外のいずれでも次候補を実行しない。
9. 勝者は変えず、`PlayerInputDispatchResult.selected(winner)`を返す。

既にclaim済みのtokenをdispatchへ再投入しない責務はgatewayと`PlayerInputSequenceLedger`が持つ。

## 2. 候補解決

クラス名: `PlayerInputResolver`

物理名: `resolve`

1. contextのfamily、player状態、source snapshot、必要な空間情報を読み取る。
2. feature固有の候補成立条件を読み取りだけで判定する。
3. executorへ渡す対象は安定IDで保持し、候補収集中に業務副作用を実行しない。
4. 遅延実行までに変化し得る対象・手持ちitem・player状態は、`PlayerInteractionSnapshot.refresh()`で現在のray・遮蔽状態を取得する`executionGuard`でも再検証する。refresh結果はguard判定だけに使い、候補の再収集には使わない。
5. 候補がなければ空を返す。

候補提供責務:

| family | resolver責務 |
|:--|:--|
| `RIGHT_CLICK` | NPC、ウェイストーン、vanilla操作対象、item使用、open ring、new ring |
| `LEFT_CLICK` | NPC、ウェイストーン、skilltree、gathering、spawner、open ring、weapon / combat |
| `BLOCK_MUTATION` | skilltree管理操作、Mob spawner、Gathering spawner |
| `DROP_ITEM` | input lock、boss cancel、menu craft shortcut、player-mode normal drop guard |
| `HOTBAR_SLOT` | input lock、skilltree setup、displayed action ring guard |
| `SNEAK` | input lock、boss entry、base / overworld spawn action、wall-cling / dodge player control |

## 3. family別候補契約

| family / 候補 | tier | `stableOrder` | policy | executor |
|:--|:--|--:|:--|:--|
| `DROP_ITEM` / input lock | `INPUT_LOCK` | `0` | `CLAIM_AND_CANCEL` | 入力ロック |
| `DROP_ITEM` / boss cancel | `WORLD_INTERACTION` | `10` | `CLAIM_AND_CANCEL` | boss中止GUI表示 |
| `DROP_ITEM` / menu craft shortcut | `ITEM_USE` | `90` | `CLAIM_AND_CANCEL` | 生成済みitem entityのremove |
| `DROP_ITEM` / player-mode normal drop guard | `FALLBACK` | `500` | `CLAIM_AND_CANCEL` | mode規則による通常ドロップ拒否 |
| `HOTBAR_SLOT` / input lock | `INPUT_LOCK` | `0` | `CLAIM_AND_CANCEL` | 入力ロック |
| `HOTBAR_SLOT` / skilltree setup | `EXCLUSIVE_CONTEXT` | `30` | `CLAIM_AND_CANCEL` | 変更前slotの復元 |
| `HOTBAR_SLOT` / displayed action ring guard | `FALLBACK` | `100` | `CLAIM_AND_CANCEL` | slot変更を抑止してring sessionを維持 |
| `SNEAK` / input lock | `INPUT_LOCK` | `0` | `CLAIM_AND_CANCEL` | 入力ロック |
| `SNEAK` / boss entry | `WORLD_INTERACTION` | `10` | 処理成立時`CLAIM` | boss challenge受付 |
| `SNEAK` / base / overworld spawn | `WORLD_INTERACTION` | `15` | 処理成立時`CLAIM` | GUI表示またはworld帰還 |
| `SNEAK` / wall-cling / dodge | `FALLBACK` | `500` | 処理成立時`CLAIM` | player control |

DROP_ITEMとHOTBAR_SLOTの非空間候補は`hitDistance = 0`を返す。SNEAKのworld interaction候補は3D実距離を返し、距離比較後のtie-breakにだけ`stableOrder`を使う。world spawn actionは水平半径で成立可否を判定するが、成立後の`hitDistance`には高低差を含める。

クリック系resolver内で同じ入口距離の対象が複数ある場合は、waystone ID、skilltree position ID、gathering / Mob instance UUID、Mob spawner location keyの昇順で対象を一件に決定する。Mob entity NPCはrayの太さで拡張した全entity AABBを走査し、block NPCのAABB候補と共通の入口距離で比較する。Paperの単発entity ray結果やcollection走査順は選択根拠にしない。

## 4. 勝者選択

クラス名: `PlayerInputDispatcher`

物理名: `select`

1. family別に定義された`InteractionTier`の高い候補を優先する。
2. 同一tierでは`hitDistance`の短い候補を優先する。
3. 距離が同じ場合は`stableOrder`の小さい候補を優先する。
4. `targetKey`を比較する。
5. 最後に候補`id`を比較し、必ず決定的な結果にする。
6. 候補が空なら勝者なしを返す。

SNEAKのboss入口とworldスポーン地点が同時成立する場合、まず近い地点が勝つ。距離も同一の場合だけboss `10`、world `15`の順になる。

## 5. 入力token相関

クラス名: `PlayerInputSequenceLedger`

物理名: `correlate` / `claim(PlayerInputToken)` / `claim(PlayerInputToken, boolean)` / `isClaimed(PlayerInputToken)` / `isCancelRequested(PlayerInputToken)` / `observeSemanticInput(PlayerInputToken)` / `hasSemanticInput(PlayerInputToken)`

1. `correlate`はplayer UUID、server tick、family、sourceの相関情報から`PlayerInputToken`を取得または生成する。
2. main/offhand、entity向け/汎用eventは同じ物理入力かつ同じserver tickなら同じsequenceへ正規化する。同tickの独立入力は異なるsequenceで区別する。前tickentryはarm swingのnext-tick pending参照用に保持するだけで、`correlate`の相関比較には使用しない。
3. semantic event受信時は`observeSemanticInput(PlayerInputToken)`でその入力sequenceを記録し、arm swingの次tickfallback前に`hasSemanticInput(PlayerInputToken)`で同じtokenの重複有無を確認する。player / tick全体を一括で抑止せず、同tickの別sequenceは独立入力として扱う。
4. `claim(PlayerInputToken)`は`claim(token, false)`へ委譲する。gatewayの実行直前処理は、勝者policyがclaimを要求する場合に`claim(token, winner.claimPolicy().isCancelRequested())`を呼び、`claimed`と`cancelRequested`をtoken単位で保存する。`cancelRequested`は論理和で保持し、同じentryに記録済みの`true`を後続呼び出しで失わない。
5. 同じtokenがclaim済みなら、後続ingress eventではresolver・dispatcher・executorを再実行しない。gatewayは`isCancelRequested(token)`が`true`の場合だけ後続の元eventをcancelし、`CLAIM`で記録された`false`の場合はcancelしない。dispatch結果自体はledgerへ保存しない。
6. resolver選択、実行直前処理、executorのいずれかで例外が発生した場合は`claim(token, true)`として入力を確定し、共通event例外処理へ渡す。同期ingressの処理中なら現在の元eventもcancelする。次tickのarm swing executor例外では既に受信処理を終えた元eventを再操作しない。いずれも敗者候補は実行しない。
7. `correlate`は`serverTick < currentTick - 1`のentryを破棄し、current tickと前tickだけを保持する。ただし新規ingressの相関比較はcurrent tickのentryだけを対象とする。前tickentryはarm swingのnext-tick fallbackにおけるclaim・semantic観測状態の参照専用とし、次tickの独立入力を同じtokenへ結合しない。

## 6. 非競合observer境界

status、equipment、item表示更新など、HOTBAR_SLOTの結果を反映するだけの処理はresolverではなくobserverとする。

- observerは候補を返さず、勝者選択へ参加しない。
- `PlayerItemHeldEvent`がcancel済みなら実処理しない。
- 未cancelの通常slot変更だけを、新しいslotの表示・status同期へ反映する。
- observer同士の表示更新順は業務上必要な依存で定め、入力所有権の優先度として扱わない。

## 7. プレイヤー入力状態破棄

クラス名: `PlayerInputSequenceLedger`

物理名: `clear`

1. 指定player UUIDの入力tokenとpending arm swingを破棄する。
2. quit後に遅延fallbackを実行しない。

## 8. feature executor境界

勝者確定後のexecutorは、対象featureの既存業務サービスへ委譲する。

- NPC: 選択されたNPCの左右クリックaction一覧
- teleporter: ロック解除またはGUI表示
- skilltree: node解放・再ロック、管理用位置・接続操作、setup中のslot復元
- item: bundle開封開始、potion使用開始、weapon攻撃
- action ring: 表示、終了、選択skill発動
- weapon / combat: 通常攻撃またはentity combat
- gathering: 採集session開始
- spawner: 座標登録・削除
- menu: craft shortcutのdrop item entity削除
- boss: challenge受付またはdrop拒否
- world: overworld転送GUI表示またはbase帰還
- player: mode drop guard、wall-cling、dodge

executor開始前に`executionGuard`が対象やplayer状態の失効を検出した場合はexecutorを見送る。guard通過後に拒否・失敗・例外となった場合を含め、別候補へfallbackしない。
