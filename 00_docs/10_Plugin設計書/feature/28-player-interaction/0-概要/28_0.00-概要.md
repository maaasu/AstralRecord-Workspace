# 28_0.00-概要

## 1. 目的

`player-interaction` は、一回の物理入力から複数のイベントや feature 候補が観測されても、トップレベルの AstralRecord アクションを一件だけ実行する共通調停機能である。

イベントの cancel 状態や Bukkit/Paper の listener 登録順を feature 間の排他ロックにせず、全候補を副作用なしで収集してから勝者を確定する。

## 2. 対象入力 family

| `InputFamily` | ingress event | 主な候補 |
|:--|:--|:--|
| `RIGHT_CLICK` | `PlayerInteractEvent` / `PlayerInteractEntityEvent` / `PlayerInteractAtEntityEvent` | NPC、ウェイストーン、vanilla操作対象、item使用、表示中リング操作、新規リング表示 |
| `LEFT_CLICK` | `PlayerInteractEvent` / `PrePlayerAttackEntityEvent` / `PlayerArmSwingEvent` | NPC、ウェイストーン、skilltree、gathering、spawner、表示中リング操作、武器・combat |
| `BLOCK_MUTATION` | `BlockPlaceEvent` / `BlockBreakEvent` | skilltree管理操作、Mob spawner、Gathering spawner |
| `DROP_ITEM` | `PlayerDropItemEvent` | 入力ロック、boss中抑止、menuクラフトショートカット、player mode通常ドロップguard |
| `HOTBAR_SLOT` | `PlayerItemHeldEvent` | 入力ロック、skilltree設定中抑止、表示中action ringのslot変更guard |
| `SNEAK` | `PlayerToggleSneakEvent` | 入力ロック、boss入口、base / overworldスポーン地点操作、壁張り付き・回避 |

`PlayerArmSwingEvent` は左クリックの意味が確定していない補助 ingress とする。同一 tick に `PlayerInteractEvent` または `PrePlayerAttackEntityEvent` が観測されなかった場合だけ、次 tick に fallback 入力として解決する。

## 3. family別の優先順位

異なるfamily間では候補を比較しない。同じfamily内で、次の上から順に最初の成立tierを優先する。

| family | 高い順の候補 |
|:--|:--|
| `RIGHT_CLICK` / `LEFT_CLICK` | `INPUT_LOCK` → `EXCLUSIVE_CONTEXT` → world interaction → item use → fallback内のopen action ring → weapon / combat → new action ring |
| `BLOCK_MUTATION` | `INPUT_LOCK` → `EXCLUSIVE_CONTEXT` → world interaction |
| `DROP_ITEM` | `INPUT_LOCK` → boss cancel controller (`WORLD_INTERACTION`) → menu craft shortcut (`ITEM_USE`) → player-mode normal drop guard (`FALLBACK`) |
| `HOTBAR_SLOT` | `INPUT_LOCK` → skilltree setup (`EXCLUSIVE_CONTEXT`) → displayed action ring guard (`FALLBACK`) |
| `SNEAK` | `INPUT_LOCK` → boss / world spawn action (`WORLD_INTERACTION`) → wall-cling / dodge player control (`FALLBACK`) |

同じtierでは`hitDistance`の短い候補を優先し、その後に`stableOrder`、安定した`targetKey`を比較する。open action ring、weapon / combat、new action ringは同じ`FALLBACK`内で、それぞれ`stableOrder`を使って順序付ける。クリック系の等距離候補はwaystone ID、skilltree position ID、gathering / Mob instance ID、Mob spawner location keyなどの安定IDで決着する。SNEAKのworld interaction同士は各入口・スポーン地点までの3D実距離を返すため、近い対象が先に勝つ。距離も同じ場合はboss entryの`stableOrder = 10`、base / overworld spawn actionの`stableOrder = 15`で決定する。player controlは`stableOrder = 500`とする。

## 4. claimとvanilla動作

- `CLAIM_AND_CANCEL`: 入力をclaimし、元eventをcancelする。
- `CLAIM`: 入力をclaimするが、元eventはcancelしない。
- `PASS_THROUGH`: 入力をclaimもcancelもせず、vanillaへ委譲する候補である。
- 候補が一件もなければdispatcherは未処理を返し、gatewayは元eventを変更しない。

DROP_ITEMの各抑止候補、HOTBAR_SLOTの各候補、SNEAKの入力ロック候補は`CLAIM_AND_CANCEL`を使用する。SNEAKのboss・world・player-control業務候補は、処理成立時に`CLAIM`を使用してスニーク姿勢そのものをcancelしない。

## 5. 排他不変条件

- resolver は候補収集時に GUI 表示、通貨消費、状態変更、メッセージ送信などの副作用を発生させない。
- dispatcher は全 resolver の候補を比較し、勝者を最大一件だけ確定する。
- executor を呼べるのは勝者だけとし、実行直前に勝者の`executionGuard`を再評価する。
- 遅延中に対象・手持ちitem・player状態などが失効して`executionGuard`が`false`になった場合はexecutorを見送る。勝者選択と入力claimは確定済みのため、敗者候補へfallbackしない。
- 勝者の実行が拒否、失敗、例外のいずれで終了しても、敗者候補へ fallback しない。
- event cancel は勝者確定後にvanilla動作を抑止する目的だけで適用し、候補間の連携には使用しない。
- worldまたはbossのSNEAK候補が勝った場合、wall-cling・dodgeなどplayer controlは実行しない。
- 設定上、一件の NPC 候補が複数の `message` / `gui` / `command` action を順番に実行することは、選択済みユースケース内部の処理として許可する。

## 6. vanilla操作と非競合observer

- `PlayerInteractEvent#useInteractedBlock()`が`DENY`でないvanilla blockと、通常のvanilla entityはworld interactionの`PASS_THROUGH`候補として扱う。
- DROP_ITEMで候補がなければ通常ドロップを変更しない。
- HOTBAR_SLOTで候補がなければ通常の選択スロット変更を変更しない。
- SNEAKで候補がなければ通常のスニーク姿勢変更を変更しない。
- status・equipment・item表示更新などのHOTBAR_SLOT observerは候補を返さない。eventがcancel済みなら実処理せず、未cancelの通常変更だけを反映する。

## 7. 対象外

次のイベントは本dispatcherへ統合しない。

- `PlayerInputEvent` の jump 状態
- join / quit / world change / teleport / move のライフサイクル・表示同期
- GUI 内 `InventoryClickEvent` / `InventoryDragEvent`
- player 以外を起点とする combat event

ただし、quit 時は保持中の短期入力 token を破棄する。
