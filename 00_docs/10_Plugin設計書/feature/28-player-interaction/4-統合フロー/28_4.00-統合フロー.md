# 28_4.00-統合フロー

## 1. 右クリック調停

1. `PlayerInteractionGatewayEventHandler`が右クリックingressを受信する。
2. `PlayerInputSequenceLedger.correlate`がplayer UUID、server tick、`RIGHT_CLICK`、sourceから`PlayerInputToken`を解決する。
3. gatewayが直接entity、ray snapshot、遮蔽距離を`PlayerInputContext`へ設定する。
4. dispatcherがNPC、ウェイストーン、vanilla操作対象、item使用、open ring、new ringの候補を収集する。
5. tier、`hitDistance`、`stableOrder`、`targetKey`、候補`id`の順で勝者を一件に確定する。
6. 勝者policyがclaimを要求する場合、gatewayはexecutor直前に`claim(token, winner.claimPolicy().isCancelRequested())`を記録し、勝者executorだけを一回実行する。元eventはpolicyのcancel要求に従ってcancelまたはpass-throughする。
7. 同じtokenへ相関したoffhandや別ingress eventはresolver・dispatcher・executorを再実行しない。ledgerの`isCancelRequested(token)`が`true`の場合だけその後続eventもcancelし、`CLAIM`由来の`false`ならvanilla eventをcancelしない。

## 2. 左クリック調停

1. `PlayerInteractEvent`または`PrePlayerAttackEntityEvent`をsemantic ingressとして`LEFT_CLICK` tokenを確定する。
2. dispatcherがNPC、ウェイストーン、skilltree、gathering、spawner、open ring、weapon / combat候補を収集する。skilltreeの通常プレイヤー操作は視線がノードに命中した場合だけ候補となり、未命中時はNPCやaction ringなど他の候補へ入力を渡す。
3. world interaction同士は実命中距離で最も近い候補を選ぶ。
4. world interactionまたはopen ringが勝った場合、weapon / combatを実行しない。
5. weapon / combatが勝った場合だけ攻撃処理へ委譲する。

`PlayerArmSwingEvent`しか観測されない場合は、受信tickでpending tokenだけを保持する。同じplayer・hand・tickに入力familyを問わずsemantic ingressが来なかった場合だけ次tickに一度dispatchし、完了後にtokenを破棄する。block設置や右クリックに伴うarm swingは独立した左クリックとして実行しない。

次tickでは受信時に選択した勝者の`executeIfValid()`を呼ぶ。guardは`PlayerInteractionSnapshot.refresh()`で現在のray・遮蔽状態を再生成し、NPC / waystone / gathering / skilltree / Mob spawnerの同一target、weaponの現在手持ちitemなどを再検証する。staleならexecutorを見送り、候補の再収集と敗者へのfallbackは行わない。

## 3. block mutation調停

1. gatewayが`BlockPlaceEvent`または`BlockBreakEvent`を`BLOCK_MUTATION`へ正規化する。
2. skilltree、Mob spawner、Gathering spawnerのresolverが対象block候補を返す。
3. dispatcherが勝者を一件に確定する。
4. 勝者だけが登録・削除・通知を実行する。Mob / Gathering spawnerの設置勝者は`CLAIM_AND_CANCEL`で実blockの設置とvanillaのitem消費を抑止し、専用itemを保持する。
5. 同一座標に複数featureの定義が存在しても、一回のeventで複数定義を変更しない。

## 4. DROP_ITEM調停

1. gatewayの`onPlayerDropItem`が`PlayerDropItemEvent`を`DROP_ITEM`へ正規化する。
2. dispatcherがinput lock、boss cancel、menu craft shortcut、player-mode normal drop guardの候補を収集する。
3. `INPUT_LOCK` → `WORLD_INTERACTION` → `ITEM_USE` → `FALLBACK`の順で勝者を一件選ぶ。
4. 勝者は`CLAIM_AND_CANCEL`で元eventをcancelする。
5. menu craft shortcutが勝った場合だけ、そのexecutorが生成済みitem entityをremoveする。bossまたはplayer-modeが勝った場合、menu executorは実行しない。
6. 候補がなければ未処理を返し、通常ドロップを変更しない。

## 5. HOTBAR_SLOT調停

1. gatewayの`onPlayerItemHeld`が`PlayerItemHeldEvent`の変更前slotと変更要求先slotを`HOTBAR_SLOT`へ正規化する。
2. dispatcherがinput lock、displayed action ring guardの候補を収集する。
3. `INPUT_LOCK` → `FALLBACK`の順で勝者を一件選ぶ。
4. displayed action ring guardが勝った場合は`CLAIM_AND_CANCEL`してslot変更を抑止し、既存ring sessionを維持する。ringを新規表示しない。
5. 候補がなければ未処理を返し、通常slot変更を変更しない。
6. status・equipment・item表示observerは、cancel済みeventでは実処理せず、未cancelの通常変更だけを反映する。

## 6. SNEAK調停

1. gatewayの`onPlayerToggleSneak`が`PlayerToggleSneakEvent`と変更後sneaking状態を`SNEAK`へ正規化する。
2. dispatcherがinput lock、boss entry、base / overworld spawn action、wall-cling / dodge player controlの候補を収集する。
3. `INPUT_LOCK` → `WORLD_INTERACTION` → `FALLBACK`の順で比較する。
4. world interaction同士は対象地点までの3D実距離が短い候補を優先する。world spawn actionは水平2メートル以内を成立条件とするが、順位には高低差を含む距離を使う。距離も同じならboss entry `stableOrder = 10`、world spawn action `stableOrder = 15`の順で決定する。
5. bossまたはworldが勝った場合はplayer controlを実行しない。player controlは上位候補がない場合だけ`stableOrder = 500`のfallbackとして実行する。
6. 成立した業務勝者は`CLAIM`するが元eventをcancelせず、vanillaのスニーク姿勢変更を維持する。input lockはロック方針に従う。
7. 候補がなければ未処理を返し、vanilla動作を変更しない。

## 7. 拒否・失敗・例外

1. 遅延実行直前に対象・手持ちitem・player状態が選択時snapshotと一致しなければ、`executionGuard = false`としてexecutorを見送る。
2. 対象発見後の権限不足、通貨不足、state未準備、必要tool不足は、guard通過後の選択済み候補の拒否結果として扱う。
3. guard不成立または拒否時も、敗者候補を実行しない。
4. resolver選択、実行直前処理、executorの例外時は`claim(token, true)`として入力とcancel要求を記録し、共通event例外処理でログを記録する。同期ingressなら現在の元eventもcancelする。次tickのarm swing executor例外では受信済みeventを再操作せず、敗者候補も実行しない。
5. gateway到達前の外部cancelはevent種別ごとに正規化する。`PlayerInteractEvent`はblock useとitem useがともに`DENY`の場合だけ入力全体のcancelとし、AIR由来のblock `DENY` / item `DEFAULT`は処理する。`PlayerInteractEntityEvent` / `PlayerInteractAtEntityEvent`は直接対象がserver-side `Interaction` entityなら初期cancel済みでも処理対象とする。`PrePlayerAttackEntityEvent`は`willAttack = false`の初期cancelを処理対象とし、`willAttack = true`かつcancel済みの場合だけ追加処理せず維持する。その他の`Cancellable` eventはcancel済みなら追加処理しない。

## 8. 初期化・終了

1. plugin初期化で各featureのresolverを明示的なstable order付きでdispatcherへ登録する。
2. `PlayerInteractionGatewayEventHandler`だけを対象ingressの共通入口として登録する。
3. player quit時に`PlayerInputSequenceLedger.clear`でtokenとclaim状態を破棄する。
4. plugin disable時に全token、claim状態、pending fallbackを破棄する。
