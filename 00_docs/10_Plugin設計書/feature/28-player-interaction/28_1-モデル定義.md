# 28_1-モデル定義

## 1. 入力 family

物理名: `InputFamily`

同じ排他制御へ参加する論理入力の区分。異なるfamily間で候補を競合させない。

| 定数 | 論理入力 |
|:--|:--|
| `RIGHT_CLICK` | 右クリック |
| `LEFT_CLICK` | 左クリック |
| `BLOCK_MUTATION` | block設置・破壊 |
| `DROP_ITEM` | itemドロップ |
| `HOTBAR_SLOT` | 選択ホットバースロット変更 |
| `SNEAK` | スニーク開始・解除 |

## 2. 入力 source

物理名: `InputSource`

Bukkit/Paperのingress eventを識別するenum。gatewayはeventを対応する定数へ正規化し、event固有の読み取り情報は`PlayerInteractionSnapshot`へ保持する。

- `PLAYER_INTERACT`: `PlayerInteractEvent`由来
- `PLAYER_INTERACT_ENTITY`: `PlayerInteractEntityEvent`由来
- `PLAYER_INTERACT_AT_ENTITY`: `PlayerInteractAtEntityEvent`由来
- `PLAYER_ARM_SWING`: `PlayerArmSwingEvent`由来
- `PRE_PLAYER_ATTACK_ENTITY`: `PrePlayerAttackEntityEvent`由来
- `PLAYER_DROP_ITEM`: `PlayerDropItemEvent`由来
- `PLAYER_ITEM_HELD`: `PlayerItemHeldEvent`由来
- `PLAYER_TOGGLE_SNEAK`: `PlayerToggleSneakEvent`由来
- `BLOCK_BREAK`: `BlockBreakEvent`由来
- `BLOCK_PLACE`: `BlockPlaceEvent`由来
- `SYNTHETIC`: testまたはgateway内で合成した入力

`PlayerInteractionSnapshot`は元event、player、hand、interact action、直接対象entity / block、block face、attack成立可否、ray等を保持する。resolverはDROP_ITEMのitem entity、HOTBAR_SLOTの変更前・変更要求先slot、SNEAKの変更後sneaking状態をsnapshotの元eventから読み取る。`PlayerInteractAtEntityEvent`のentity内クリック位置は保持しない。将来の扱いは [[28_9-未決事項]] とする。

sourceは入力tokenを分断するキーではない。同一tickに配送されたmain/offhandやentity向け/汎用eventは、異なるsourceでも同じ論理入力へ相関できる。

## 3. プレイヤー入力コンテキスト

物理名: `PlayerInputContext`

一つの論理入力をresolverへ渡す読み取り専用コンテキスト。

| 項目 | 説明 |
|:--|:--|
| playerId | 入力元player UUID |
| inputSequence | gatewayが付与した入力系列番号 |
| family | `InputFamily`で表す排他区分 |
| source | `InputSource`へ正規化したingress情報 |
| inputSnapshot | gateway固有の不変入力snapshot。本gatewayでは`PlayerInteractionSnapshot` |

`PlayerInteractionSnapshot`はplayer、元event、hand、interact action、直接対象entity / block、block face、attack成立可否、共通ray、遮蔽距離を保持する。コンテキスト生成後に各resolverが個別に視線方向やスロット状態を取り直さず、同一入力では同じsnapshotを使用する。

`PlayerInteractionSnapshot.refresh()`はplayer、元event、hand、action、直接対象などの入力メタデータを維持したまま、playerの現在位置・視線・遮蔽状態からray情報を再生成する。遅延実行のguardだけが現在状態の再検証に使用し、最初の候補収集・勝者選択結果を置き換えない。

共通 ray の生成条件と sphere / axis-aligned bounding box への入口距離契約は、[[28_3-サービス]]の「ray entry distance」を正本とする。

## 4. 入力 token

物理名: `PlayerInputToken`

同一物理入力を識別する不変record。

| accessor | 説明 |
|:--|:--|
| `playerId` | 入力元player UUID |
| `serverTick` | ingressを受信したserver tick |
| `sequence` | 同じplayer・tick・family内の独立入力を区別するsequence |
| `family` | `InputFamily`で表す排他区分 |

`PlayerInputSequenceLedger`がsource情報を相関してtokenを発行する。handやingress event種別は直接tokenを分断するキーにせず、同じ物理入力なら同じsequenceへ正規化する。

- main hand / off hand の重複配送を同じ論理入力として扱う。
- entity向けeventと汎用interact eventの重複配送を同じ論理入力として扱う。
- 左クリックのsemantic eventと`PlayerArmSwingEvent`を相関できる場合は同じtokenとして扱い、semantic観測状態は正確なinput sequence単位で保持する。同じplayer・tickの別sequenceをまとめてfallback抑止しない。
- DROP_ITEM、HOTBAR_SLOT、SNEAKは各Bukkit event一件を一つの論理入力として扱う。
- tokenとclaim結果は同一tickと次tickfallbackに必要な最小期間だけ保持し、wall-clock期限を使用しない。`correlate`実行時はarm swingのnext-tick pendingが前tick tokenを参照できるよう`currentTick - 1`以降のentryを残すが、相関候補として比較するのは`serverTick == currentTick`のentryだけとする。
- pending arm swingは次tickfallback完了時に破棄する。ledger entryはquit時の`clear`、または後続`correlate`時に`serverTick < currentTick - 1`となった時点で破棄し、次の独立入力を抑止しない。

ledger entryはtoken単位で`claimed`と`cancelRequested`を保持する。`CLAIM`の勝者は`claim(token, false)`、`CLAIM_AND_CANCEL`の勝者は`claim(token, true)`として記録し、後者のcancel要求は同じentryの存続中は失われない。同じtokenの後続ingressではresolver・dispatcher・executorを再実行せず、`isCancelRequested(token)`が`true`の場合だけ後続の元eventもcancelする。

## 5. プレイヤー入力候補

物理名: `PlayerInputCandidate`

resolverが返す、副作用をまだ実行していない候補。

| 項目 | 説明 |
|:--|:--|
| id | resolver内の候補種別を識別する安定ID |
| tier | [[28_1-モデル定義]].インタラクションtier |
| hitDistance | 空間候補の対象までの実距離。非空間候補は`0` |
| stableOrder | 同一tier・同一距離で使用する明示的なresolver順 |
| targetKey | tie-breakに使用するtarget種別と安定ID |
| claimPolicy | [[28_1-モデル定義]].入力claim方針 |
| executionGuard | 勝者確定後の実行直前に、現在状態と選択時snapshotの整合を再検証する`BooleanSupplier` |
| executor | 勝者確定後にだけ呼び出す業務処理 |

`hitDistance`は有限かつ0以上とする。RIGHT_CLICK / LEFT_CLICKはrayと対象形状の入口命中点までの距離を使う。Mob entity NPCはPaperの単発entity ray結果へ依存せず、rayの太さで拡張した全候補のAABB入口距離を比較し、block NPCはblock AABB入口距離を比較する。DROP_ITEM の検証用カカシ候補も対象実体の AABB 入口距離を使う。SNEAKのboss入口・worldスポーン地点候補はplayerから対象地点までの3D実距離を使う。worldスポーン地点候補の成立条件である水平半径判定と、順位比較に使う3D距離は区別する。距離を使わない DROP_ITEM 候補と HOTBAR_SLOT 候補は`0`を返す。

同じtier・同じ`hitDistance`・同じ`stableOrder`の候補は、次の安定した`targetKey`で決定する。

| 対象 | `targetKey` |
|:--|:--|
| waystone | waystone ID |
| skilltree | position ID。setup controlは操作種別prefixを付ける |
| gathering | gathering instance UUID |
| entity / block NPC | Mob instance UUID |
| training dummy | 配置 ID |
| Mob spawner | world UUIDとblock座標から成るlocation key |
| Dungeon報酬CHEST | session UUID、world UUID、block座標から成るlocation key |

一回のdispatchで`id`と`targetKey`がともに一致する候補は重複として拒否する。対象が存在するが業務条件を満たさない場合も拒否処理を行う候補として返してよく、勝者確定後の拒否から敗者へfallbackしない。

`executeIfValid()`は`executionGuard`を実行直前に一度評価し、`true`の場合だけexecutorを呼ぶ。`false`の場合はstale winnerとしてexecutorを見送るが、別候補を選び直さない。特に次tickへ遅延するarm swingでは、各featureのguardが`PlayerInteractionSnapshot.refresh()`で現在のray・遮蔽状態を取得し、NPC / waystone / gathering / skilltree / Mob spawnerの同一target、weaponの現在手持ちitemなどを再検証する。Dungeon報酬CHEST候補は同期実行時もsession eligibility、同一target key、CHEST Material、更新後のray・遮蔽を再検証する。同期実行する検証用カカシ候補は、選択した配置 ID の定義が実行直前にも存在することを検証する。

## 6. インタラクションtier

物理名: `InteractionTier`

候補の論理優先段階を表し、数値が大きいpriorityを先に選ぶ。一回のdispatchは一つのfamilyだけを対象とするため、異なるfamilyの候補同士は比較しない。各resolverは対象familyで有効なtierだけを返す。

| 論理名 | 主な対象 |
|:--|:--|
| `INPUT_LOCK` | 全入力を抑止するplayer状態 |
| `WORLD_INTERACTION` | plugin管理対象、vanilla操作対象、boss制御、world移動 |
| `EXCLUSIVE_CONTEXT` | skilltreeノード操作など、そのcontextだけが入力を所有する操作 |
| `ITEM_USE` | bundle、potion、menu craft shortcut等 |
| `FALLBACK` | action ring、武器・combat、player control等、上位候補がない場合の処理 |

familyごとの順序は次とする。

| family | 高い順 |
|:--|:--|
| `RIGHT_CLICK` / `LEFT_CLICK` | `INPUT_LOCK` → `EXCLUSIVE_CONTEXT` → `WORLD_INTERACTION` → `ITEM_USE` → `FALLBACK` |
| `BLOCK_MUTATION` | `INPUT_LOCK` → `EXCLUSIVE_CONTEXT` → `WORLD_INTERACTION` |
| `DROP_ITEM` | `INPUT_LOCK` → `WORLD_INTERACTION` → `ITEM_USE` → `FALLBACK` |
| `HOTBAR_SLOT` | `INPUT_LOCK` → `EXCLUSIVE_CONTEXT` → `FALLBACK` |
| `SNEAK` | `INPUT_LOCK` → `WORLD_INTERACTION` → `FALLBACK` |

enumの宣言順ではなく`tier.priority()`をdispatcherの共通comparatorで比較する。同じ`FALLBACK`内のopen action ring、weapon / combat、new action ring等は`stableOrder`で順序付け、呼び出し側やlistener登録順で比較しない。

## 7. 入力claim方針

物理名: `InputClaimPolicy`

| 定数 | claim | 元event cancel | 用途 |
|:--|:--:|:--:|:--|
| `CLAIM_AND_CANCEL` | する | する | pluginがvanilla入力を抑止して所有する |
| `CLAIM` | する | しない | plugin処理を一件に限定しつつvanilla姿勢等は維持する |
| `PASS_THROUGH` | しない | しない | 候補なし結果の既定方針。現行の明示候補では未使用 |

claim方針は候補収集中にeventへ反映せず、勝者確定後に`PlayerInputDispatchResult`を介してgatewayへ返す。候補が一件もない場合はwinnerなしの未処理結果を返し、`claimPolicy()`は`PASS_THROUGH`を返す。明示的なvanilla操作候補は、相関済み後続ingressでdispatcherを再実行しないため`CLAIM`を使い、元eventをcancelしない。

既にcancel済みでgatewayへ届いた入力は原則として追加処理しない。ただしAIR由来の`PlayerInteractEvent`、server-side `Interaction` entity、`willAttack=false`の`PrePlayerAttackEntityEvent`はBukkit/Paperの初期cancelを独自入力の拒否とみなさず、候補評価を続ける。

## 8. プレイヤー入力resolver

物理名: `PlayerInputResolver`

feature固有の状態から、指定contextで成立する候補を0件以上返す契約。

- 候補収集時は読み取りだけを行う。
- 同一feature内に複数対象がある場合も、実距離を保持した候補として返す。
- 空間候補は中心点距離ではなく、familyで定めた共通の`hitDistance`を返す。クリック系は対象形状のray入口、SNEAKは対象地点までの3D実距離とする。
- RIGHT_CLICK / LEFT_CLICKでは`blockingDistance`より遠い対象を返さない。
- DROP_ITEM / HOTBAR_SLOT / SNEAKでは、該当eventのsource snapshotだけを判定に使う。

## 9. プレイヤー入力dispatch結果

物理名: `PlayerInputDispatchResult`

gatewayへ返す一回の仲裁結果。`Optional<PlayerInputCandidate> winner`を保持し、`hasWinner`、`claimPolicy`、`isClaimed`、`isCancelRequested`で元eventへの反映方針を参照する。

候補なしは`passThrough()`によるwinnerなしの未処理結果を返す。勝者ありは`selected(winner)`を返す。勝者executorが拒否・失敗・例外となっても次候補の結果へ置き換えない。同一tokenの重複実行防止とcancel方針の再適用はdispatch結果の保存ではなく、`PlayerInputSequenceLedger`の`claimed` / `cancelRequested`状態で行う。

## 10. dispatcher

物理名: `PlayerInputDispatcher`

resolver一覧から候補を選択し、勝者を一回だけ実行する共通サービス。入力tokenとclaim状態の管理は`PlayerInputSequenceLedger`へ委譲する。

比較順は次で固定する。

1. 入力family内での`tier`の高い順
2. 同一tierでは`hitDistance`の短い順
3. 同一距離では`stableOrder`の小さい順
4. `targetKey`の昇順
5. 最後に`id`の昇順

resolver登録順、listener登録順、`HashMap`の走査順をtie-breakに使用しない。
