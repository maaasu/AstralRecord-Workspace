# 13_4.00-統合フロー

## 1. 起動時ロード

1. Plugin 起動処理が `SkillRegistry` に実行クラスを登録する
2. `AstralRecord` が `SkillService` を生成し、非同期で API 定義を取得して `implementationId` と実行クラスの対応を検証する
3. 検証成功分を immutable snapshot として完成させる
4. メインスレッドへ戻してレジストリ参照を一括交換する
5. レジストリ交換完了後に skilltree の名称・説明・表示アイテム cache を再構築する

## 2. プレイヤー発動

1. コマンド / GUI / ショートカットが `skillId` を決定する
2. `SkillService.canCast` が MP・レベル・cooldown を確認する
3. `SkillService.castSkill` が `SkillCastContext` を構築する
4. `SkillRegistry.getExecutor(implementationId)` で個別ロジックを解決する
5. 実行成功後に共通 MP 消費と cooldown を適用する

## 3. Mob 発動

1. 共通制御層は `SkillCaster` 抽象で Mob へ拡張できる構造を持つ
2. ただし Mob 用 `SkillCaster` 実装と AI からの接続は未実装
3. Mob 発動の実装時はプレイヤー発動と同じ `SkillService.castSkill` 経路へ接続する

## 4. skilltree・action ring入力仲裁

1. `PlayerInteractionGatewayEventHandler`がクリック、block mutation、hotbar slot変更を`PlayerInputContext`へ正規化する。
2. skilltree resolverは視線が命中したノード、gathering/spawnerとの競合対象、管理用設置・破壊操作を`EXCLUSIVE_CONTEXT`または`WORLD_INTERACTION`候補として返す。通常プレイヤーの視線がノードに命中しない場合はskilltree候補を返さず、NPCやaction ringなど他の候補を妨げない。複数位置のray入口距離が同じ場合はskilltree position IDの昇順で一件に決定する。
3. action ring resolverは表示中リングのクリック操作と未表示リングの新規表示を`FALLBACK`候補として返し、`stableOrder`で表示中ring、weapon / combat、新規ringの順にする。
4. `PlayerInputDispatcher`はtier、距離、`stableOrder`の順で勝者を一件選ぶ。
5. 勝者が表示中リング操作の場合だけリングを閉じるか選択skillを発動し、勝者が新規表示の場合だけリングを開く。
6. 候補収集時はring sessionやskilltree状態を変更せず、勝者executorが失敗しても別候補へfallbackしない。

`HOTBAR_SLOT`では次の順に処理する。

1. input lock候補を最優先する。
2. skilltree setup中なら`EXCLUSIVE_CONTEXT`候補が勝ち、eventをcancelして変更前slotを復元する。
3. skilltree setup候補がなくaction ring表示中なら`FALLBACK`のring guardが勝ち、eventをcancelして表示中ringを維持する。
4. 候補がなければ通常slot変更を許可する。status・equipment・item表示observerは未cancel時だけ反映する。

同一tickのhand/event相関、距離比較、event抑止の詳細は[[28_4.00-統合フロー]]を正本とする。
