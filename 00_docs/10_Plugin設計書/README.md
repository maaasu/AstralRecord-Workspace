# 設計書運用ルール（AstralRecord Plugin）

このファイルは `00_docs/10_Plugin設計書/` 配下の設計書構造と更新判断の正本です。
設計featureと実装packageの所有関係は [[FEATURE_CATALOG]] を正本とします。

## 1. 設計書の正本と状態

- 設計書は、原則として現在の `10_plugin/AstralRecord` で観測できる契約と挙動を現在形で記載する。
- 現行仕様、採用済みだが未実装の仕様、判断待ちの事項を混在させない。
- `0` から `6` の通常カテゴリには現行仕様だけを記載する。
- 採用済みだが未実装の仕様を独立して保持する必要がある場合は、任意カテゴリ `8-実装予定` に記載し、実装前であることと受入条件を明示する。
- 設計判断が残る事項だけを任意カテゴリ `9-未決事項` に記載する。未決事項がなくなったファイルは残さない。
- 未決事項では、判断対象を説明するために現行挙動を前提として併記してよいが、確定済み仕様や解決履歴だけの節は置かない。
- 解決済みの経緯はGit履歴を基本とし、長期的な判断根拠が必要な場合だけ `00_docs/99_資料/` のADR・資料へ残す。
- `追記`、日付見出し、実装同期メモのような時系列記録を本文へ継ぎ足さず、現在の正しい節へ統合する。
- 実装と設計書が食い違い、正しい側を一意に判断できない場合は、推測で統一せず未決事項として明示する。

## 2. featureの入口と所有関係

- featureディレクトリは `2桁採番-機能名` とする。例: `01-user`。
- feature番号は全featureで一意とし、既存番号を別featureへ再利用しない。
- 各featureには `<機能番号>_0-概要.md` を1件だけ必須とし、この概要をfeatureの入口とする。
- feature直下の `<機能番号>_README.md` は作成しない。
- 概要には、そのfeatureを理解するために必要な範囲で次を記載する。
  - 目的、責務、責務外
  - 主要な設計境界・不変条件
  - 依存featureと連携境界
  - 関連データ・設定・正本
  - 重要な関連設計書
  - feature固有の変更影響（必要な場合だけ）
- 実装package・resource・共有実装の所有パスは [[FEATURE_CATALOG]] に集約し、各概要へ一覧を複製しない。
- 一つの実装packageを複数featureが参照する場合も、主所有者は [[FEATURE_CATALOG]] で一意に決める。主所有者以外は利用する契約だけを記載する。
- 文書一覧を網羅する目次は必須としない。概要からは、読者が次に読む必要がある文書だけをリンクする。

## 3. カテゴリと配置

カテゴリ番号は読順と責務を示す安定した分類として使用する。

| 番号 | カテゴリ | 必須 |
|:--|:--|:--|
| `0` | 概要 | 必須 |
| `1` | モデル定義 | 内容がある場合 |
| `2` | ユースケース | 内容がある場合 |
| `3` | メソッド仕様・処理契約 | 内容がある場合 |
| `4` | 統合フロー | 内容がある場合 |
| `5` | 例外・ログ・運用 | 内容がある場合 |
| `6` | 開発・拡張ガイド | 必要時のみ |
| `8` | 採用済み・実装予定 | 必要時のみ |
| `9` | 未決事項 | 判断待ちがある場合のみ |

- 小規模featureへ不要なカテゴリ文書を作成しない。
- カテゴリのMarkdownが1ファイルだけの場合はfeature直下へ置き、カテゴリディレクトリを作らない。
- 同じカテゴリにMarkdownが複数ある場合だけ、`<カテゴリ番号>-<カテゴリ名>/` ディレクトリを作る。
- カテゴリディレクトリ内へ索引だけを目的としたファイルを必須にしない。複数文書の関係が名称だけで分からない場合に限り索引を置く。
- 空ディレクトリと、内容が「該当なし」だけの空文書は残さない。

例:

```text
feature/
  30-resource-pack/
    30_0-概要.md
    30_1-モデル定義.md
    30_2-ユースケース.md
    30_3-メソッド仕様.md
    30_4-統合フロー.md
    30_5-例外・ログ・運用.md
  01-user/
    01_0-概要.md
    01_1-モデル定義.md
    3-メソッド仕様/
      01_3-イベント.md
      01_3-サービス.md
      01_3-コマンド.md
      01_3-リポジトリ.md
```

## 4. ファイル名と見出し

- Markdownファイル名は `<機能番号>_<カテゴリ番号>-<意味のある名称>.md` とする。
  - 例: `30_0-概要.md`, `01_3-サービス.md`, `25_3-GUI・View.md`
- 並び順だけを目的とした `.00`, `.01`, `.02` などの詳細番号は使用しない。
- 同じカテゴリに同種文書が複数ある場合は、連番ではなく責務が分かる名称を使う。
  - 例: `01_3-ユーザーサービス.md`, `01_3-権限サービス.md`
- 順序自体が契約となる連作だけは、概要またはルールに理由を明記した上で名称へ連番を含めてよい。
- 全Markdownのファイル名は設計書ツリー内で一意にする。
- ファイル名に `[`、`]`、空白を使用しない。
- H1はファイル名の拡張子を除いた値と一致させる。

## 5. 編集ツールとリンク

- 設計書は標準MarkdownとしてGit、IDE、GitHub等から読める状態を維持する。
- Obsidianは推奨編集ツールとするが、必須にはしない。
- 設計書間参照は、Obsidian Wikiリンク `[[ファイル名]]` と相対Markdownリンクのどちらも使用できる。
- パスなしWikiリンクは、対象ファイル名が設計書ツリー内で一意に解決できる場合だけ使用する。
- 同名候補がある場合や設計書ツリー外を参照する場合は、相対Markdownリンクまたはリポジトリ相対パスを使用する。
- Wikiリンクで論理要素を示す場合は `[[ファイル名]].論理名` の既存形式を使用してよい。
- rename・移動と同じ変更で、参照元リンクとvalidatorを更新する。

## 6. メソッド仕様・処理契約

- `3`カテゴリは実装メソッドの全件台帳ではなく、実装やfeature間連携を判断するための処理契約を記載する。
- 次のうち設計上重要なものを具体的に記載する。
  - 入力、出力、前提条件、拒否条件
  - 重要な判定と委譲先
  - 状態遷移、永続化境界、キャッシュのライフサイクル
  - メインスレッド・非同期処理の境界
  - 例外、部分失敗、再試行、補償、冪等性
- クラス名、物理メソッド名、イベント物理名は、実装追跡に必要な場合だけ記載する。記載した物理名は現行実装と一致させる。
- 表、処理単位の節、複数メソッドをまとめた契約など、内容に適した形式を使用できる。定型ラベルの有無だけを完全性判定に使わない。
- 本文で別文書の処理やモデルを参照するときは、物理名だけでなく日本語の論理名または契約名を併記する。
- 実装に存在しない概念上の処理へ物理名を付けない。

## 7. ログとプレイヤーメッセージ

- 完全なメッセージ文言の正本が `logger.properties`、`player.properties` 等にある場合、設計書へ文言を複製しない。
- 設計書では必要に応じて次を記載する。
  - ID
  - レベルまたは表示種別
  - 出力・表示条件
  - 引数と意味
  - 利用者・運用者が取るべき対応
- 文言そのものが設計契約であり、設計書が正本となる場合だけテンプレート全文を記載する。
- ログやメッセージの説明は、発生する処理または運用項目の近くへ置く。形式だけをそろえるための重複表は作らない。

## 8. 統合フローと図

- `4`カテゴリは、複数コンポーネント、feature間連携、状態遷移、非同期処理、補償処理など、局所的な処理仕様だけでは理解しづらい流れを記載する。
- Mermaid図は、文章や表より関係を明瞭にできる場合に使用する。
- 複数participantの時系列が中心なら `sequenceDiagram`、状態遷移が中心なら `stateDiagram-v2`、分岐が中心なら `flowchart` を選ぶ。
- 単純な一方向処理では、文章または表だけでもよい。
- 図を使用する場合、図中のクラス名、メソッド名、APIパスなどの物理名は現行実装と一致させる。
- 図だけで例外、終了条件、永続化、スレッド境界が伝わらない場合は短い処理要点を補足する。

## 9. 設計書を更新する変更

次のいずれかが変わる場合は、同じ変更で関連設計書を更新する。

- 利用者から観測できる挙動、コマンド、GUI、メッセージ
- feature間または外部システムとの契約
- モデル、永続化、設定キー、filebase/API/DBの境界
- 状態遷移、失敗時挙動、補償、再試行、運用手順
- 重要なスレッド境界、ライフサイクル、責務分担
- 実装packageの追加・移動・統合・削除

次の変更だけで設計契約が変わらない場合、設計書更新は必須ではない。

- 内部リファクタリング
- テストのみの追加・整理
- フォーマット、コメント、局所的な命名変更
- 設計上観測できない実装詳細の変更

実装packageまたは設計featureを追加・移管した場合は、[[FEATURE_CATALOG]] と対象概要を同時に確認する。

## 10. 検証

変更後はリポジトリルートから次を実行する。

```powershell
python 00_docs/10_Plugin設計書/scripts/validate_plugin_docs.py
python .codex/skills/astralrecord-docs-review/scripts/docs_structure_audit.py 00_docs/10_Plugin設計書
```

検証では少なくとも次を確認する。

- feature採番と概要の一意性
- ファイル名、H1、カテゴリ配置
- 単一ファイルカテゴリの不要なディレクトリ化
- Wikiリンク・Markdownリンクの参照解決
- [[FEATURE_CATALOG]] のfeature・package所有関係
- READMEや旧詳細番号形式の残存
- 空の未決事項文書、時系列追記、曖昧な同名ファイル
