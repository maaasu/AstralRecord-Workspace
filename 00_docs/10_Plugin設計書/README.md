# 設計書運用ルール（AstralRecord）

このファイルは `00_docs/10_Plugin設計書/` 配下の設計書構造ルールです。
全 feature の設計書は本ルールに従って作成・改修します。

設計 feature と実装 package の所有関係は [[FEATURE_CATALOG]] を正本とする。

## 正本と記載状態

- 設計書は、原則として現在の `10_plugin/AstralRecord` で実行される挙動を記載する。
- 実装済み仕様と将来仕様を同じカテゴリの別ファイルへ並立させない。将来案、未実装案、判断待ちは `9-未決事項/` に集約する。
- 実装と設計書が食い違う場合は、利用中の契約、テスト、関連 feature への影響を確認して正しい側へ統一する。判断が一意でない場合は実装を推測で変更せず、未決事項として残す。
- `追記`、`YYYY-MM-DD 追加`、`実装同期メモ` のような時系列の差分記録を本文へ継ぎ足さない。内容を現在形へ直し、該当する既存の節へ統合する。
- クラス名、メソッド名、コマンド、設定キー、メッセージ ID、ログ ID は現行実装と一致させる。削除済みの物理名は履歴として残さない。

## 0. 編集ツールと参照記法

- 設計書の編集ツールは **Obsidian** を使用する。
- 別ファイル参照は原則 `[[参照]]`（Wikiリンク）を使用する。
- 通常の Markdown リンクより `[[参照]]` を優先する。
- 別ファイルを参照する場合は、原則としてパス付きではなくファイル名のみを使用する。
  - 例: `[[01_1.00-モデル定義]].ユーザモデル`
  - 非推奨: `[[../01-user/1-モデル定義/01_1.00-モデル定義]].ユーザモデル`

## 2. 採番ルール

- feature ディレクトリ名は `2桁採番-機能名`（例: `01-user`）
- feature 採番は `01`, `02`, `03`... の 1 単位
- feature 採番は全ディレクトリで一意とする。同じ番号または同じ Markdown ファイル名を複数 feature で使用しない。
- feature 直下の README ファイル名は `機能番号_README.md`（例: `01_README.md`）
- カテゴリ番号は 1 桁運用（必要に応じて `10` 以上を使用可）
  - `0`: 概要
  - `1`: モデル定義
  - `2`: ユースケース
  - `3`: メソッド仕様
  - `4`: 統合フロー
  - `5`: 例外・ログ・運用
  - `9`: 未決事項
- md ファイル名は以下形式
  - `機能番号_カテゴリ番号.詳細番号-名称.md`
  - 例: `01_0.00-概要.md`, `01_3.02-サービス.md`
- ファイル名に `[` `]` は使用しない
- ファイル名の区切りは空白ではなく `_` を使用する
- 詳細番号はカテゴリごとに `00` 始まりで `01`, `02`... と 1 ずつ増加
- ディレクトリ内にファイルが 1 つの場合、索引ファイルは作らない

## 3. feature README.md の必須項目

1. 対象実装パス
2. ドキュメント一覧（推奨順）
3. 依存 feature
4. 更新ルール（変更時に必ず更新する章）

## 4. メソッド仕様ルール

- 記載場所: `3-メソッド仕様/`
- 論理名（日本語）は「文章」ではなく「単語連結の名詞句（体言止め）」で記載する
  - 例: `ユーザ取得`, `権限更新`, `補完候補取得`（`ユーザを取得する` のような文章形は使わない）
- `物理名` は実装メソッド名と一致させる
  - 例: `onAsyncPreLogin`, `findByUuid`, `setPermission`
- クラスが分かるように `クラス名` を必ず記載する
- event の場合のみ `イベント物理名` も記載する
- 別ファイルで定義されたメソッド仕様を参照する場合は `[[ファイル名]].論理名` の形式で記載する
  - 例: `[[01_3.02-サービス]].権限更新`
- モデル定義では日本語の論理名と実装上の物理名を併記する
  - 例: `### ユーザモデル` の下に `物理名: UserModel`
- 別ファイルで定義されたモデルを参照する場合は `[[ファイル名]].モデル論理名` の形式で記載する
  - 例: `[[01_1.00-モデル定義]].ユーザモデル`
- 本文でモデルを参照する場合は、原則として `UserModel` などの物理名ではなく日本語のモデル論理名を使用する
- メソッド呼び出しを説明する場合、実装メソッド名ではなく論理名（日本語）を本文に使用する
- 処理内容は抽象表現だけで終わらせず、その番号内に判定条件・取得項目・委譲先・例外時挙動をまとめて記載する
  - 例: `3. ユーザ存在を検証する` の直下に `UUIDでAPI検索する`、`404は未登録扱い` などを記載する
- 1つの処理に含まれる検証内容を、別番号へ分離しない
- 実装に存在しない概念上のメソッドへ物理名を付けない。概念モデルや処理段階として説明する場合は、物理名欄を作らず、その旨を本文で明示する。

テンプレート（event）:

```text
<論理名>
イベント物理名: <EventClass>
クラス名: <HandlerClass>
物理名: <methodName>
```

テンプレート（service / command / repository）:

```text
<論理名>
クラス名: <ClassName>
物理名: <methodName>
```

## 5. メソッド仕様内のログ・メッセージ記載ルール

- 対象は `3-メソッド仕様/` の記載のみ
- ログIDだけで終わらせず、必ずメッセージ内容まで記載する
- ログやメッセージは、ログを出力する処理番号の直下にインデントして記載する
- `ログ/メッセージ:` のような独立見出しは作らない
- ログやメッセージは以下の表形式を使用する

```text
4. 例外時は runSafely で以下ログを記録する

    | 項目 | 内容 |
    |---|---|
    | ID | LogId.E_5000 |
    | レベル | ERROR |
    | テンプレート | ユーザーのログイン前処理に失敗しました: %s |
    | 出力条件 | runSafely で例外発生時 |
    | 引数 | プレイヤー名（event.getName()） |
```

- メッセージ（プレイヤー向け表示）も同じ形式で記載する
  - ID が無い場合は ID 欄を `-` とする

## 6. 統合フローの共通形式

- 対象は `4-統合フロー/` 配下の文書とする。
- 1 つの利用者操作、ライフサイクル、または連携処理を `## <連番>. <フロー名>` として分ける。
- 各フローは原則として次の順序で記載する。
  1. `### シーケンス`: コンポーネント間の呼び出しを Mermaid `sequenceDiagram` で示す。
  2. `### 処理要点`: 判定、状態更新、永続化、スレッド境界を番号付きリストで補足する。
  3. `### 例外・終了条件`: 正常系以外の終了条件がある場合だけ記載する。
- 状態遷移や分岐そのものが中心で、登場コンポーネントの時系列より明瞭になる場合に限り Mermaid `flowchart TD` または `stateDiagram-v2` を使用してよい。
- 図中の participant 名、クラス名、メソッド名、API パスは現行実装と一致させる。概念上の処理には日本語の論理名を使う。
- フロー文書を番号付き文章だけで構成しない。少なくとも 1 つの Mermaid 図を含める。

## 7. feature README の共通形式

- H1 はファイル名と同じ `# <機能番号>_README` とする。
- 冒頭に feature の責務を現在形で簡潔に記載する。
- 次の H2 をこの順序で置く。
  1. `対象実装パス`
  2. `ドキュメント一覧（推奨順）`
  3. `依存 feature`
  4. `更新ルール（変更時に必ず更新する章）`
- 対象実装パスは `10_plugin/AstralRecord/` から始まるリポジトリ相対パスで記載する。
- ドキュメント一覧は実在するファイルだけを推奨読順で列挙し、ファイル追加・削除・改名と同時に更新する。

## 8. 運用

- 実装変更 PR では対応する設計書も更新する
- `feature` package または設計 feature を追加・移管した場合は [[FEATURE_CATALOG]] と対象 README の実装パスを同時に更新する
- 未確定事項は `9-未決事項/` に集約する
- 変更後はリポジトリルートから次を実行し、採番、ファイル名、README、Wikiリンク、統合フロー、source package の設計所有者、feature カタログを検証する。

```powershell
python 00_docs/10_Plugin設計書/scripts/validate_plugin_docs.py
```
