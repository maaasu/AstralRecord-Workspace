### AR-CODE-001 [中] 遠隔取り出しでint上限を超える元数量が失われる
- 種別: `バグ/アルゴリズム`
- 対象: `10_plugin/AstralRecord/src/main/java/io/github/maaasu/astralRecord/feature/inventory/service/InventoryService.java:3105`
- 関連箇所: `10_plugin/AstralRecord/src/main/java/io/github/maaasu/astralRecord/feature/item/service/OrbService.java:806`
- 根拠: 新しい自動収納とAPIマーケット収納はlong型のSTORAGE stack数量を保持する。一方、withdrawStorageEntryのレビュー開始時の実装はentry.getQuantityをInteger.MAX_VALUEへ丸めたavailableQuantityを元数量として、availableQuantityとmovedAmountの比較でentryを削除し、残量もavailableQuantity - movedAmountで保存していた。
- 問題: STORAGEに2,147,483,648個あるオーブを左クリックで1個取り出すと、残量が正しい2,147,483,647ではなく2,147,483,646になる。取り出し可能数が丸め後数量に達する場合は、まだ残量があってもentryを削除する。
- 影響: 新規遠隔オーブ一覧の取り出し操作で、移動していない所有品が消失する。
- 修正方針: 要求数量のint制限は維持し、元entryのlong数量から実移動数を減算する。元long数量が実移動数以下の場合だけ削除する。
- 修正対象候補: `10_plugin/AstralRecord/src/main/java/io/github/maaasu/astralRecord/feature/inventory/service/InventoryService.java`
- 修正可否: `自動修正可`
- 確信度: `高`
- 修正状態: `修正済み`

### AR-CODE-002 [高] 初回STORAGEをPluginとAPIが別IDで作成すると購入回復が完了しない
- 種別: `バグ/アルゴリズム`
- 対象: `20_api/AstralRecordApi/AstralRecordApi/Repositories/MarketRepository.cs`
- 関連箇所: `10_plugin/AstralRecord/src/main/java/io/github/maaasu/astralRecord/feature/inventory/service/InventoryService.java:3810`
- 根拠: レビュー開始時のFindOrbStorageDestinationAsyncは未作成STORAGEのIDにGuid.NewGuidを使う。PluginのensureInventoryはstableStateIdで決定的IDを生成する。購入の事前容量検査はSTORAGEが未作成でもtrueを返すだけで親を作らない。ItemCommandの通常アイテム付与はAPI I/O中でも直接addItemToNormalInventoryを呼び出せる。新規親を取り込むreconcileは異なるIDの既存STORAGEがあればExternal storage inventory conflicts with local storageをthrowする。
- 問題: STORAGE未作成のトークン所持者が購入を開始し、API応答前に通常オーブ付与がローカルSTORAGEを作ると、APIが確定した購入先親IDと一致しない。同じprepared境界で再試行しても既存親は残り、毎回例外になる。
- 影響: Gold減算と購入はAPIで確定済みなのに、購入品のローカル反映と保存が回復待ちになり、通常操作も回復境界に阻まれる。
- 修正方針: 新規API STORAGEのIDをPluginの既存stableStateIdと同じUTF-8入力・UUID version 3・RFC variant・バイト順で生成する。既存親IDを変更しない。異なる同時entry追加が三者マージで保持されることも確認する。
- 修正対象候補: `20_api/AstralRecordApi/AstralRecordApi/Repositories/MarketRepository.cs`

### AR-CODE-003 [中] 右クリック半数の計算がint上限で1個へ溢れる
- 種別: `バグ/アルゴリズム`
- 対象: `10_plugin/AstralRecord/src/main/java/io/github/maaasu/astralRecord/feature/item/service/ItemTransferSupport.java:91`
- 関連箇所: `10_plugin/AstralRecord/src/main/java/io/github/maaasu/astralRecord/feature/item/service/OrbService.java:799`
- 根拠: 新しい遠隔取り出しはlongの元数量をInteger.MAX_VALUEまで丸めてresolveTransferAmountへ渡す。RIGHT分岐はint演算の(sourceAmount + 1) / 2を使う。
- 問題: 2,147,483,647個以上のSTORAGE stackではsourceAmount + 1が負数へ溢れ、Math.max(1, ...)によって要求数量が1個になる。
- 影響: 右クリックを半数として案内する新GUIで、取り出し可能なBAG空きがあっても1個しか移動しない。
- 修正方針: 共通RIGHT計算を1 + (sourceAmount - 1) / 2など、正のint上限でも溢れない切り上げ式へ変更する。
- 修正対象候補: `10_plugin/AstralRecord/src/main/java/io/github/maaasu/astralRecord/feature/item/service/ItemTransferSupport.java`

### AR-CODE-004 [高] 既存オーブ返却の事前容量判定が自動収納を誤って許可する
- 種別: `バグ/アルゴリズム`
- 対象: `10_plugin/AstralRecord/src/main/java/io/github/maaasu/astralRecord/feature/market/event/MarketGuiEventHandler.java:1979`
- 関連箇所: `10_plugin/AstralRecord/src/main/java/io/github/maaasu/astralRecord/feature/inventory/service/InventoryService.java`
- 根拠: canReturnListingToInventoryはcanAddItemToNormalInventoryを使う。今回、この容量検査はcanAutoStoreAcquiredOrbがtrueならBAG容量を調べずtrueを返すようになった。一方、取消後のreconcileExternalInventoryEntriesToOwnedInventoryは既存所有品を通常所持品へ返却し、STORAGEの自動収納を適用しない。専門レビュアーと公開呼出元・正規化処理を照合した。
- 問題: オーブ遠隔アクセストークン所持、BAG満杯、STORAGE空きありでオーブ出品取消を開始すると、事前容量検査は成功する。しかし取消がAPIで確定した後、BAGへの通常返却正規化に容量がなく、購入と同じ回復境界で再同期が失敗する。売却画面等の既存所有品返却にも同じ容量検査を流用すると同種の不一致が生じる。
- 影響: 完了済み取消のローカル反映が回復待ちに入り、既存所持品の返却が完了しない。
- 修正方針: 新規獲得の自動収納容量検査と、既存所有品の通常返却容量検査を分離する。Market取消とSell等の返却呼出元を通常返却検査へ変更し、新規購入の検査は自動収納対応を維持する。
- 修正対象候補: `複数`
- 修正可否: `自動修正可`
- 確信度: `高`
- 修正状態: `修正済み`

### AR-CODE-005 [中] 末尾1枠への同時新種獲得がSTORAGE容量を超過する
- 種別: `バグ/アルゴリズム`
- 対象: `10_plugin/AstralRecord/src/main/java/io/github/maaasu/astralRecord/feature/inventory/service/InventoryService.java`
- 関連箇所: `20_api/AstralRecordApi/AstralRecordApi/Repositories/MarketRepository.cs`
- 根拠: AR-CODE-002修正後はPluginとAPIの初回親IDが一致し、API I/O中のローカル追加も三者マージで保存できる。一方、API容量判定は保存済みDBのentry数を使い、ローカル付与は現在stateのentry数を使う。OrbInventoryThreeWayMergerはローカル追加を保持してAPI追加を反映し、normalizeExternallyReturnedOwnedEntriesはGAME/STORAGEの通常オーブを容量確認せずcontinueする。

### AR-CODE-006 [高] STORAGE受取の三者マージ後にslot重複が残り保存ACKに失敗する
- 種別: `バグ/アルゴリズム`
- 対象: `10_plugin/AstralRecord/src/main/java/io/github/maaasu/astralRecord/feature/inventory/service/InventoryService.java`
- 関連箇所: `10_plugin/AstralRecord/src/main/java/io/github/maaasu/astralRecord/feature/inventory/service/OrbInventoryThreeWayMerger.java:284`
- 根拠: 共有OrbStorageDestinationによりAPIはSTORAGE新規entryへ最大slot+1を付与する。三者マージの既存entryへの正のAPI差分はasNewEntryで別IDのentryを生成し、元のslotIndexを維持する。修正前normalizeAcquiredStorageOrbはentry数が実効容量以下ならearly returnする。PlayerStateSnapshotRepositoryの2074行はinventory内の非null slotIndex重複をHasDuplicatesで拒否する。
- 問題: 既存STORAGEのオーブ10個・slot1へAPIが5個加算すると、三者マージ結果に元の10個と新ID差分5個の2entryが同じslot1で残る。容量内なので同種統合もslot補正もされない。異種のローカル新規獲得とAPI新規受取が同じ末尾slotを使用した場合も、容量内なら同じ重複が残る。
- 影響: API取引は確定済みなのにplayer-state snapshotが構造拒否となり、保存ACKと取引回復を完了できない。
- 修正方針: 容量に関係なく、同種通常オーブをlong上限を超えない範囲で統合する。baselineにある既存IDを優先して既存予約・保存IDを維持し、baselineがない場合は受取IDを維持する。残る異種slot衝突は受取側だけ未使用の末尾slotへ補正する。新種で実効容量を超える場合のBAGフォールバックと全数量保全は維持する。
- 修正対象候補: `10_plugin/AstralRecord/src/main/java/io/github/maaasu/astralRecord/feature/inventory/service/InventoryService.java`
- 修正可否: `自動修正可`

### AR-CODE-007 [高] API作成のSTORAGE親が永続化済み集合へ登録されず保存ACKに失敗する
- 種別: `バグ/アルゴリズム`
- 対象: `10_plugin/AstralRecord/src/main/java/io/github/maaasu/astralRecord/feature/inventory/state/InventoryPersistence.java:476`
- 関連箇所: `10_plugin/AstralRecord/src/main/java/io/github/maaasu/astralRecord/feature/inventory/state/PlayerStateSnapshot.java:106`
- 根拠: APIが初回STORAGE親を作成した場合、InventoryServiceは所有者を確認してstateへ親を取り込む。APIと同じstableIDの親がローカル付与で先行しても親はstateに存在する。しかし修正前acknowledgeExternalEntryはentryの期待ID・versionだけを更新し、persistedInventoryIdsへ親IDを登録しない。PlayerStateSnapshotはpersistedInventoryIdsにない親をisNew=trueで送信し、PlayerStateSnapshotRepository191～197行は既存IDまたは同profile/typeの既存inventoryに対するisNew要求をNew inventory conflictsとして拒否する。
