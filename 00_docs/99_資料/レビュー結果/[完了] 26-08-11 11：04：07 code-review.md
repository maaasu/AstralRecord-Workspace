### AR-CODE-001 [高] オーブの部分消費でも BAG と HOTBAR のスロットを再採番する
- 種別: `バグ/アルゴリズム`
- 対象: `10_plugin/AstralRecord/src/main/java/io/github/maaasu/astralRecord/feature/inventory/service/InventoryService.java:1967`
- 関連箇所: `10_plugin/AstralRecord/src/main/java/io/github/maaasu/astralRecord/feature/inventory/service/OrbInventoryThreeWayMerger.java:255, 00_docs/10_Plugin設計書/feature/08-inventory/3-メソッド仕様/08_3-サービス.md:156`
- 根拠: `OrbInventoryThreeWayMerger.applyApiDeltaToRelocatedEntries` は API 差分で数量だけ減った entry の inventoryId も `changedInventoryIds` に追加し、`InventoryService.reconcileOrbOperationEntries` はその全 inventory に `compactMergedEntriesAfterRemoval` を適用して全 entry を 1 始まりの連番へ再採番する。一方、設計は全量削除時の BAG だけを詰め直し、部分移動は元 slot を維持し、HOTBAR は固定 slot のため詰め直さないとしている。
- 問題: オーブや追加素材の stack が部分消費されただけでも BAG の配置が移動し、HOTBAR の固定割当まで先頭へ詰め直される。HOTBAR の全量削除時にも同じ再採番が起きる。
- 影響: オーブ操作のたびにプレイヤーの配置が意図せず変わり、その誤った配置が保存される。HOTBAR の番号と実表示がずれ、次回操作対象を取り違える可能性がある。
- 修正方針: merge 結果で「数量変更」と「entry 全量削除」を区別し、全量削除が発生した BAG だけを compact する。HOTBAR は常に既存 slot を維持し、BAG/HOTBAR の部分消費と全量消費を恒久テストで固定する。
- 修正対象候補: `InventoryService.java, OrbInventoryThreeWayMerger.java, OrbInventoryThreeWayMergerTest.java, InventoryServiceTest.java`
- 修正可否: `自動修正可`

### AR-CODE-010 [高] Market Create の transient retry が出品確定を冪等に再生できない
- 種別: `バグ/アルゴリズム`
- 対象: `20_api/AstralRecordApi/AstralRecordApi/Repositories/MarketRepository.cs:91`
- 関連箇所: `20_api/AstralRecordApi/AstralRecordApi/Repositories/MarketRepository.cs:137, 20_api/AstralRecordApi/AstralRecordApi/Repositories/MarketRepository.cs:169, 20_api/AstralRecordApi/AstralRecordApi/Program.cs:35, 20_api/AstralRecordApi/AstralRecordApi/Models/MarketModels.cs:36`
- 根拠: AR-CODE-004 の修正で `CreateListingAsync` は `EnableRetryOnFailure` の execution strategy callback 内に手動 transaction を追加したが、`listingId` は callback の実行ごとに `Guid.NewGuid()` で作成し、callback 冒頭の確定済み結果照会も `ExecuteInTransactionAsync` の `verifySucceeded` も持たない。SQL Server が COMMIT を完了した直後に transient 接続障害を返すと、execution strategy は初回 commit の成否を確認できないまま callback 全体を再実行できる。
- 問題: 初回 transaction が実際には commit 済みの場合、個体出品の再試行は ACTIVE listing を見つけて `market.instance_already_listed` を返し、成功済みなのに API 応答が失敗になる。stack 出品は残量があれば同じ entry を再度減算し、別 listing ID で二重出品を確定でき、残量がなければ同様に成功済み出品を失敗応答にする。
- 影響: クライアントは失敗と認識したまま市場に出品が残り、stack では数量の二重予約と重複 listing が発生し得る。再送や手動再操作で経済データとプレイヤー所持数の不整合が拡大する。
- 修正方針: `listingId` を retry callback の外で一度だけ生成し、Serializable の `ExecuteInTransactionAsync` と `verifySucceeded` で同じ ID の確定を検証する。代替として callback 冒頭で同じ固定 ID の確定済み listing を読み、既存成功応答を再生する。COMMIT 結果不明を注入した instance/stack 双方の恒久テストを追加する。
- 修正対象候補: `20_api/AstralRecordApi/AstralRecordApi/Repositories/MarketRepository.cs, 20_api/AstralRecordApi/AstralRecordApi.Tests/Repositories/MarketRepositoryEquipmentListingTests.cs`
