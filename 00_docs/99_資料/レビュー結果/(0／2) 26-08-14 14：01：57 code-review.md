### AR-CODE-001 [中] シールド再充填方式の正本が関連設計書間で分裂している
- 種別: `仕様不整合`
- 対象: `00_docs/10_Plugin設計書/feature/14-combat/14_0-概要.md:36`
- 関連箇所: `10_plugin/AstralRecord/src/main/java/io/github/maaasu/astralRecord/feature/status/service/StatusService.java:362、00_docs/10_Plugin設計書/feature/07-status/07_1-モデル定義.md:187、00_docs/10_Plugin設計書/feature/07-status/3-メソッド仕様/07_3-タスク.md:57`
- 根拠: 今回の差分は `v1.administrator_shield_recharge.yml` の `rechargePercentPerSecond` を `10` から `2` へ変更し、Combat概要を「毎秒2%回復」へ更新しています。実装の `completeShieldRechargeIfReady` も configured recharge では `state.rechargeAmount` を加算し、最大値に達するまで state を保持します。既存の `StatusShieldRechargeTest` は `10%` 設定で `30` Shield に対し毎秒 `3`、次回 `6` となる挙動を検証しています。一方、Status設計書は `rechargeAmount` を「完了時に一括設定する値」と定義し、タスク・統合フローも完了時に一括回復して state を破棄すると記載しています。
- 問題: `administrator_shield_recharge` が8秒待機後に毎秒2%（最大Shield30なら0.6 Shield/秒）で段階回復するのか、従来どおり8秒後に最大値へ一括回復するのかが、関連する正本間で確定していません。今回の変更だけでは、実装・filebase・Combat概要とStatus設計書のどちらを採用すべきか判断できません。
- 影響: `rechargeAmount` の意味、完了時刻・状態保持、表示上限の扱いを設計入力から一意に決められず、将来の実装・テスト・HUD表示が相反する契約へ追従する可能性があります。特に `2` を「毎秒率」と解釈するか「完了時の回復量」と解釈するかで回復時間とゲームバランスが大きく変わります。
- 修正方針: 設計判断で回復方式を確定し、採用した方式に合わせて Status のモデル定義・タスク・統合フロー、Combat概要、filebase description、実装テストの `rechargeAmount` と state lifecycle の記述を一括同期します。段階回復を採用する場合は `rechargeAmount` を毎秒量として明記し、最大値到達まで state を保持する契約と、最大値を超えない表示・回復上限を明記します。
- 修正対象候補: `複数`
- 修正可否: `設計判断待ち`
- 確信度: `高`
- 修正状態: `未修正`

### AR-CODE-002 [低] filebase の回復率変更を実ランタイムへ結び付けるテストがない
- 種別: `テスト不足`
- 対象: `40_filebase/30.features.skill/v1.administrator_shield_recharge.yml:29`

- 根拠: YAMLの変更値は `AdministratorShieldRechargeSkillExecutor` が `rechargePercentPerSecond` として読み、`StatusService.configureShieldRecharge` へ渡します。しかし既存のシールドリチャージテストは YAML をロードせず、`configureShieldRecharge(player, 8.0D, 10.0D)` とテスト内の固定値を直接指定しています。今回の `2`、最大Shield `30` から導かれる実効回復量 `0.6` を検証するテストや、対象 master の params が executor へ到達する統合テストはありません。
- 問題: YAMLのキー名・ロード結果・対象masterの数値が変更されても、現在のテストは従来の固定値10%で通過します。filebase が実際のゲーム動作へ反映されない、または別の値で反映される回帰を検出できません。
- 影響: 管理者専用スキルの回復速度と、今回意図されたバランス変更が本番で未検証のままになります。AR-CODE-001の設計判断が段階回復の場合は、8秒待機後の増分、最大値到達時の state 解除、最大値超過防止まで一続きで確認できません。
- 修正方針: 採用する回復方式を確定したうえで、filebase の対象 master を実際にロードするテスト、または同じ loader 経路を通る fixture を追加し、`maxShield: 30`・`rechargePercentPerSecond: 2` が実効 `rechargeAmount: 0.6` へ反映されることと上限到達時の state lifecycle を検証します。
