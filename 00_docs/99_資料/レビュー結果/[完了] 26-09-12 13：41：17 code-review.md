### AR-CODE-001 [高] trade と snapshot のロック循環を組めていない
- 種別: `バグ/アルゴリズム`
- 対象: `20_api/AstralRecordApi/AstralRecordApi.Tests/Repositories/PlayerStateSnapshotDeadlockSqlServerDiagnosticTests.cs:75`
- 関連箇所: `20_api/AstralRecordApi/AstralRecordApi/Repositories/PlayerStateSnapshotRepository.cs:48`
- 根拠: trade は account の Serializable 読み取りで停止する一方、snapshot 保存は inventory を読む前に `FindAccountForUpdateAsync` で同じ account を `UPDLOCK, HOLDLOCK` 取得する。したがって trade を停止したままでは snapshot は account 取得で待機し、79行目の inventory 到達通知を発火できない。
- 問題: 79行目は10秒後に timeout し、意図した「snapshot が inventory lock を保持して trade の account lock を待つ」循環を作る前にテストが失敗する。現在の repository 呼出順とも XEL の snapshot×trade deadlock とも整合しない。
- 影響: SQL 1205 を再現できず、失敗理由を deadlock 修正の有無として判定できない。これを根拠に分離レベル・ロック順を決定すると誤った結論へ進む。
- 修正方針: 実際の SQL 実行順に従って両 transaction がそれぞれ保持する lock と次に待つ lock を確認し、その順序で同期点を置き直す。snapshot repository の account-first 順序で循環しないなら、この組合せを再現対象から外し、XEL の実際の statement 順序を再現する経路へ置き換える。
- 修正対象候補: `20_api/AstralRecordApi/AstralRecordApi.Tests/Repositories/PlayerStateSnapshotDeadlockSqlServerDiagnosticTests.cs`
- 修正可否: `要確認`
- 確信度: `高`
- 修正状態: `修正済み`

### AR-CODE-002 [中] snapshot 台帳の gap 分離が乱数依存
- 種別: `テスト不足`
- 対象: `20_api/AstralRecordApi/AstralRecordApi.Tests/Repositories/PlayerStateSnapshotDeadlockSqlServerDiagnosticTests.cs:380`
- 関連箇所: `20_api/AstralRecordApi/AstralRecordApi/Repositories/PlayerStateSnapshotRepository.cs:1527`
- 根拠: 各保存 request の `SnapshotId` と128件の台帳行の `SnapshotId` がすべて `Guid.NewGuid()` であり、`player_state_snapshot` の主キー検索は `UPDLOCK, HOLDLOCK` を使う。同じ主キー gap に2 request が入れば片方が quest/trade の同期点より前で待機するが、380行目以降はその配置を保証していない。
- 問題: コメントは台帳末尾gapでの直列化を除外するとするが、乱数行を追加しただけでは request ごとの異なる gap を保証できない。診断結果が、対象 deadlock ではなく snapshot 台帳 lock の衝突で timeout する実行に依存する。
- 影響: quest 型を含む両テストが非決定的になり、再現失敗を修正効果と区別できない。
- 修正方針: request の snapshot ID とそれぞれを隔離する前後の台帳キーを、SQL Server の uniqueidentifier 順序で決定的に用意する。または台帳 lock が先行しないことを DMVs 等で確認してから同期点へ進める。
- 修正対象候補: `20_api/AstralRecordApi/AstralRecordApi.Tests/Repositories/PlayerStateSnapshotDeadlockSqlServerDiagnosticTests.cs`
- 修正可否: `自動修正可`
- 確信度: `高`
- 修正状態: `修正済み`

- 関連箇所: `20_api/AstralRecordApi/AstralRecordApi.Tests/Repositories/PlayerStateSnapshotDeadlockSqlServerDiagnosticTests.cs:105`
- 根拠: 両テストは SQL 1205 を含む例外が1件以上あることだけを検証しており、もう一方の操作に timeout、接続失敗、または別の SQL 例外があっても成功する。例外内容は `output.WriteLine` に出すだけで assertion がない。
- 問題: 実行が1205だけで完結したことをテストが保証しないため、同期失敗や一時DBの異常を deadlock再現成功として扱う。

- 修正方針: 各結果について例外なし又は SQL 1205 のみを許容し、1205被害者がちょうど1件であることを assertion する。許容外の例外は assertion message に含める。

### Q-CODE-001
- 関連指摘: `AR-CODE-001`
- 確認事項: 指定 XEL の snapshot と trade の各 statement の実行順、被害者・生存側、および保有/待機 resource は何か。
- 判断が必要な理由: 提供されたUNC上の XEL/APIログはこの環境から参照できず、テストが再現すべき正確な lock cycle をソースだけでは確定できない。
