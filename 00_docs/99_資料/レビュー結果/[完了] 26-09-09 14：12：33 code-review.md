### AR-CODE-001 [中] 非同期再試行から Bukkit Player を参照している
- 種別: `コーディングルール違反`
- 対象: `10_plugin/AstralRecord/src/main/java/io/github/maaasu/astralRecord/feature/market/event/MarketGuiEventHandler.java:909`
- 関連箇所: `10_plugin/AstralRecord/src/main/java/io/github/maaasu/astralRecord/feature/market/event/MarketGuiEventHandler.java:923`
- 根拠: `runTaskLaterAsynchronously` の Runnable は 923〜925 行で `attemptCancelRecovery` を呼び、結果不明時は 836〜839 行で同じ `scheduleCancelRecovery` に戻る。その経路で 909 行および scheduler 登録失敗時の 933 行は `recovery.astPlayer().getBukkit().getUniqueId()` を実行する。`PLUGIN_GUIDE.md:44` は Bukkit / Paper API のスレッド制約遵守を要求している。
- 問題: 非同期 Runnable から `AstPlayer` 経由で Bukkit `Player` を取得しているため、Paper/Bukkit のスレッド制約に反する。
- 影響: 取消結果不明後の再試行中に、非同期 Bukkit API 参照による例外または非決定的な動作が起きる。復旧処理が止まれば prepared handle が残り、同一 account の保存・mutation が進行しない。
- 修正方針: prepared handle 作成時のメインスレッドで不変の player UUID を取得して `MarketCancelRecovery` に保持し、非同期経路では Bukkit `Player` を参照しない。プレイヤー通知だけを同期タスクで UUID から解決する。
- 修正対象候補: `10_plugin/AstralRecord/src/main/java/io/github/maaasu/astralRecord/feature/market/event/MarketGuiEventHandler.java`
- 修正可否: `自動修正可`
- 確信度: `高`
- 修正状態: `修正済み`

### AR-CODE-002 [中] 再試行の scheduler 登録失敗で prepared 取消が未解決のまま残る
- 種別: `バグ/アルゴリズム`
- 対象: `10_plugin/AstralRecord/src/main/java/io/github/maaasu/astralRecord/feature/market/event/MarketGuiEventHandler.java:927`
- 関連箇所: `10_plugin/AstralRecord/src/main/java/io/github/maaasu/astralRecord/feature/market/event/MarketGuiEventHandler.java:842`
- 根拠: 取消の結果不明時は 836〜839 行で再試行を予約する。scheduler が `RuntimeException` を送出すると 927〜936 行は scheduled flag を戻してログ出力するだけで、`cancelRecoveries` からの削除、`completePreparedExternalOperation`、`abandonPreparedExternalOperation`、completion の完了を行わない。`23_5-例外・ログ・運用.md:28` は receipt の再同期と保存が終わるまで prepared handle を維持し、応答喪失・5xx では結果照会・冪等再送を続けることを定める。
- 問題: scheduler が拒否するライフサイクル（停止開始を含む）では再照会経路が失われる一方、prepared handle と `cancelRecoveries` の登録が残る。
- 影響: プロセスが継続する scheduler 拒否では同一 account の保存・mutation が解除されない。停止・再起動をまたぐ場合にこの結果不明操作をどの永続情報で再照会し、操作前 inventory を上書きしないかも実装されていない。
- 修正方針: scheduler 登録不能時の取消復旧を明示的に扱う。通常稼働中の拒否では安全な再予約または失敗通知を行い、停止開始では idempotency key・listing ID・prepared state を永続化して次回起動/ログイン後に receipt 照会・再同期を再開するか、同等に stale state の保存を防ぐライフサイクルを実装する。
- 修正対象候補: `複数`
- 修正可否: `設計判断待ち`
- 確信度: `中`
- 修正状態: `修正済み`

### Q-CODE-001
- 関連指摘: `AR-CODE-002`
- 確認事項: scheduler が停止開始で新規タスクを拒否した取消結果不明操作について、次回起動/ログイン時に receipt を照会して inventory を再同期する永続 recovery の保管先と実行契機をどこに定めるか。
