### AR-CODE-001 [高] 既存の管理用インベントリ snapshot を migration が削除する
- 種別: `バグ/アルゴリズム`
- 対象: `00_docs/40_Database設計書/table-definitions/AstralRecord/migrations/20260801_remove_builder.sql:41`
- 関連箇所: `10_plugin/AstralRecord/src/main/java/io/github/maaasu/astralRecord/feature/inventory/service/InventoryService.java:802`
- 根拠: 旧 `InventoryService` は通常のツール用 snapshot を `metadata_json` の `builder` オブジェクトへ保存していた。migration は直形式（root に `format` と `contents` があるもの）だけを `admin` にラップしようとする一方、49-52 行で既存の `$.builder` を無条件に削除する。現行実装は `AccountMode.ADMIN` で `$.admin` だけを復元する。
- 問題: 一般的な旧保存形式である `{"builder": {"format": ..., "contents": ...}}` は 41-47 行の変換条件に一致せず、49-52 行で snapshot 本体だけが消える。さらに直形式でも `contents` の base64 文字列が 4,000 文字を超えると SQL Server の `JSON_VALUE` が `NULL` を返すため、46 行の条件を満たさず同じ削除経路に入る。
- 影響: migration 後に profile は `ADMIN` へ改名されても、既存管理者の Bukkit インベントリと保存済み GameMode を復元できず、空の管理用インベントリとして扱われる。データを失った後は再実行しても復旧できない。
- 修正方針: `builder` オブジェクトを `admin` へ安全にコピー（既存 `admin` がある場合の優先規則を明示）してから削除する。直形式の検出には長さ制限を受けない JSON 構造判定を用い、代表的な nested/直形式/既存 admin/再実行の各 fixture で migration 結果を検証する。
- 修正対象候補: `00_docs/40_Database設計書/table-definitions/AstralRecord/migrations/20260801_remove_builder.sql`
- 修正可否: `自動修正可`
- 確信度: `高`
- 修正状態: `修正済み`

### AR-CODE-002 [高] 未検証の既存 user.permission 値が migration 全体をロールバックする
- 種別: `バグ/アルゴリズム`
- 対象: `00_docs/40_Database設計書/table-definitions/AstralRecord/migrations/20260801_remove_builder.sql:25`
- 関連箇所: `00_docs/40_Database設計書/table-definitions/AstralRecord/migrations/20260801_remove_builder.sql:32; 20_api/AstralRecordApi/AstralRecordApi/Controllers/UserController.cs:83`
- 根拠: migration は `permission = 10` だけを `0` へ更新後、既存行を検証する `CK_user_permission IN (0, 99)` を追加する。変更前の `init.sql` には user.permission の CHECK 制約がなく、変更前の `UserController.Update` も任意の整数をそのまま更新できたため、既存 DB に `0` / `10` / `99` 以外の値が存在し得る。
- 問題: たとえば旧 API で保存された `permission = 7` または `100` が 1 件でも残ると、新 CHECK 制約の追加が失敗する。`SET XACT_ABORT ON` とトランザクションにより、mode/profile/snapshot を含む Builder 廃止 migration 全体がロールバックされる。
- 影響: デプロイ時に migration が完了せず、Builder 値の削除と新 API/Plugin/DB 契約への移行が全く適用されない。エラーは制約追加時にだけ現れるため、実データに依存してリリースが停止する。
- 修正方針: 制約追加前に `0` / `10` / `99` 以外の件数と値を明示して停止する事前検証、または採用済みの移行方針に従い安全な値へ正規化する。未知値を PLAYER/ADMIN のどちらへ移すかは既存運用上の意味を確認して決定する。
- 修正対象候補: `00_docs/40_Database設計書/table-definitions/AstralRecord/migrations/20260801_remove_builder.sql`
- 修正可否: `設計判断待ち`
- 確信度: `高`
- 修正状態: `修正済み`

### AR-CODE-003 [中] 将来の高位 user.permission に Mob spawner の視認・削除権限が誤付与される
- 種別: `バグ/アルゴリズム`
- 対象: `10_plugin/AstralRecord/src/main/java/io/github/maaasu/astralRecord/feature/spawner/service/MobSpawnerService.java:354`
- 関連箇所: `10_plugin/AstralRecord/src/main/java/io/github/maaasu/astralRecord/feature/player/model/AstPlayer.kt:252; 00_docs/10_Plugin設計書/feature/12-mob/12_1-モデル定義.md:Mob spawner 削除認可`
- 根拠: `AstPlayer.hasAdminPermission()` は `permission >= 99` を返す一方、Mob spawner の設計契約は `user.permission = 99` の場合だけ表示を許可し、削除はさらに `AccountMode.ADMIN` を要求する。
- 問題: 視認・削除判定が `hasAdminPermission()` をそのまま使うため、将来追加する `permission = 100` などが `ADMIN(99)` と同じ Mob spawner 権限を意図せず得る。
- 影響: 将来の権限追加時に、スポナーの管理対象表示や削除を許可しない権限へも、フィールド上のスポナー変更権が付与される。
- 修正方針: 視認と削除の user permission 判定を `UserPermission.ADMIN(99)` との等値へ分離し、削除は同じ等値判定と `AccountMode.ADMIN` の組合せを維持する。`permission = 100` で両方を拒否する回帰テストを追加する。
- 修正対象候補: `10_plugin/AstralRecord/src/main/java/io/github/maaasu/astralRecord/feature/spawner/service/MobSpawnerService.java, 10_plugin/AstralRecord/src/test/java/io/github/maaasu/astralRecord/feature/spawner/service/MobSpawnerVisualPermissionTest.java`
- 修正可否: `自動修正可`
- 確信度: `高`
- 修正状態: `修正済み`
