### AR-CODE-001 [高] 受取 entry が slot 未設定のまま保存・描画されない
- 種別: `バグ/アルゴリズム`
- 対象: `20_api/AstralRecordApi/AstralRecordApi/Repositories/TradeRepository.cs:186`
- 関連箇所: `20_api/AstralRecordApi/AstralRecordApi/Repositories/TradeRepository.cs:254, 10_plugin/AstralRecord/src/main/java/io/github/maaasu/astralRecord/feature/inventory/service/OrbInventoryThreeWayMerger.java:486, 10_plugin/AstralRecord/src/main/java/io/github/maaasu/astralRecord/feature/inventory/service/InventoryService.java:1597`
- 根拠: 新規の通常 item は `SlotIndex = null`、装備／ルーン entry の移管でも `source.SlotIndex = null` として API に保存される。一方、再同期 merger は追加 entry をそのまま state へ追加し、compaction 対象にするのは削除時だけである。BAG 描画は `slotIndex == null` の entry を明示的に skip する。
- 問題: 受取側に既存 stack がない通常 item、および移管した装備／ルーンは、API 正本には存在しても有効な BAG slot を持たないまま local state と DB に残る。
- 影響: 受取側では managed slot の filler 枠だけが見え、item が表示されない。ログアウト後も null slot のまま保存されるため、再ログイン時にも描画されず、今回報告された「枠だけ占有し、リログすると消える」症状を再現する。
- 修正方針: API 再同期で BAG へ追加・移管した entry に slot がなければ、受取側 state の容量規則に従い compaction して slot を割り当て、割当後 state を保存する。API 側で空き slot を推測せず、BAG 容量を持つ Plugin 側の three-way merger／再同期処理へ寄せる。
- 修正対象候補: `10_plugin/AstralRecord/src/main/java/io/github/maaasu/astralRecord/feature/inventory/service/OrbInventoryThreeWayMerger.java`

### AR-CODE-002 [高] API 確定後の再同期失敗を未確定として cancel できる
- 種別: `バグ/アルゴリズム`
- 対象: `10_plugin/AstralRecord/src/main/java/io/github/maaasu/astralRecord/feature/trade/service/TradeService.java:594`
- 関連箇所: `10_plugin/AstralRecord/src/main/java/io/github/maaasu/astralRecord/feature/trade/service/TradeService.java:629, 10_plugin/AstralRecord/src/main/java/io/github/maaasu/astralRecord/feature/trade/service/TradeService.java:647, 10_plugin/AstralRecord/src/main/java/io/github/maaasu/astralRecord/feature/inventory/service/InventorySaveCoordinator.java:230`
- 根拠: A lane は `repository.commit(...)` が成功した後に `apiResult.complete(result)` を実行する。続く B lane の `reconcileExternalInventoryEntries(...)` またはその保存が例外になると `playerBLock` は例外完了するが、`finishTradeCommit` は API 成功済みかを判別せず session を `OPEN` に戻す。`cancelTrade` は `OPEN` を中止可能として reservation を解除して session を破棄する。また、coordinator は operation 開始後の例外では unresolved 状態を解除しない。
- 問題: DB の item membership・個体 owner・Gold が確定済みでも、受取側の再同期失敗を通常の API failure として扱い、ユーザーに再提示・中止を許可する。
- 影響: DB 正本とメモリ session が分岐し、cancel 後に受取側の表示・保存が回復しないままになる。さらに失敗した account の save lane が unresolved のまま残り、後続の保存を停止する。
- 修正方針: API 応答を受け取った時点を remote commit 済みとして保持し、以後の再同期／保存失敗では `OPEN` に戻さず、同じ operation ID の replay による再同期完了まで cancel・再提示を拒否する。完了または明示的な復旧失敗状態まで coordinator の unresolved 境界を保ち、復旧時だけ解除する。
- 修正対象候補: `10_plugin/AstralRecord/src/main/java/io/github/maaasu/astralRecord/feature/trade/service/TradeService.java`

### AR-CODE-003 [中] 二つの save lane が executor worker をブロックして相互待機する
- 種別: `バグ/アルゴリズム`
- 対象: `10_plugin/AstralRecord/src/main/java/io/github/maaasu/astralRecord/feature/trade/service/TradeService.java:598`

- 根拠: B account の `executeExclusiveAfterSave` 内で `apiResult.join()` を実行し、B lane とその async executor worker を保持したまま A account の lane 実行を待つ。A lane は B の baseline 完了後に同じ coordinator executor へ enqueue される。single-thread executor または全 worker が同様の待機で占有された場合、A lane が開始できず commit future は永久に完了しない。設計書は「A/B の save lane は相互待機しない」と定めている。
- 問題: non-blocking な future 連結ではなく worker thread を `join()` で停止しており、executor の並列度を暗黙に要求する。
- 影響: 状況次第でトレードが `COMMITTING` のまま停止し、両プレイヤーの session と保存 lane を解放できない。
- 修正方針: B lane 内で A lane の結果を同期待機しない構成へ変更する。二 account の baseline 取得・API transaction・各 account の reconciliation を非ブロッキングに連結できる coordinator API、または順序を固定した cross-account exclusive operation を導入し、同一 executor の worker 枯渇でも進行することをテストする。
- 修正対象候補: `10_plugin/AstralRecord/src/main/java/io/github/maaasu/astralRecord/feature/trade/service/TradeService.java`

### AR-CODE-007 [高] 確定応答の通信喪失を未確定として保護せず cancel 可能にする
- 種別: `バグ/アルゴリズム`
- 対象: `10_plugin/AstralRecord/src/main/java/io/github/maaasu/astralRecord/feature/trade/service/TradeService.java:644`
- 関連箇所: `10_plugin/AstralRecord/src/main/java/io/github/maaasu/astralRecord/feature/trade/service/TradeService.java:651, 10_plugin/AstralRecord/src/main/java/io/github/maaasu/astralRecord/feature/trade/repository/TradeRepository.java:70, 00_docs/10_Plugin設計書/feature/22-trade/22_4-統合フロー.md:108`
- 根拠: `TradeRepository#commit` は HTTP 送信後に接続切断・応答読取失敗で例外になり得る。一方 API は `dbo.trade_commit` を transaction 内で保存しており、同じ operation ID の replay で確定結果を返す契約である。通信失敗は API transaction が未commit だったことを証明しない。
- 問題: `remoteCommitted` は `repository.commit(...)` が応答を返した後にしか true にならない。応答喪失時は recovery を作らず prepared operation を abandon し、`finishTradeCommit` は session を `OPEN` に戻すため、すでに DB で item・個体 owner・Gold が確定していても cancel できる。

- 修正方針: request を送信した後の transport / response-decode failure は確定不明として prepared operation と同じ operation ID を保持し、API replay で terminal 応答を取得するまで `COMMITTING` と未解決保存境界を維持する。明示的な 4xx 業務拒否だけを DB 未変更として `OPEN` へ戻す。応答喪失後の replay 回帰テストと設計書の「成功応答前の失敗」記述も更新する。
