### AR-CODE-001 [高] inventory間移動のロック順逆転
- 種別: `バグ/アルゴリズム`
- 対象: `20_api/AstralRecordApi/AstralRecordApi/Repositories/InventoryRepository.cs:248`
- 関連箇所: `00_docs/20_API設計書/feature/13-inventory/3-エンドポイント仕様/13_3.03-更新系.md:108`
- 根拠: API仕様は同一account内の既存entryを対象inventoryへ移動することを許可している。置換処理が対象inventoryの現在entryを取得した後、移動対象entryを別クエリで取得するため、AからBへの移動とBからAへの移動は異なるentry集合を先にロックできる。
- 問題: `UPDLOCK,HOLDLOCK` を追加しても、対象inventoryのentryを先にロックしてから移動元entryをロックする順序は、同時実行時に逆転し得る。
- 影響: A←B と B←A の有効な置換要求で、inventory_entryの更新ロック待ちが循環し、SQL Serverの1205が発生する可能性がある。
- 修正方針: entryロック前に同一accountのinventory親行を同一順序で更新ロックし、同一account内の置換処理を直列化する。既存のentry更新ロックとinventory_id検索用indexも維持する。
- 修正対象候補: `20_api/AstralRecordApi/AstralRecordApi/Repositories/InventoryRepository.cs`
- 修正可否: `自動修正可`
- 確信度: `高`
- 修正状態: `修正済み`

### AR-CODE-002 [高] Quest保存とアカウント削除のロック契約不一致
- 種別: `バグ/アルゴリズム`
- 対象: `20_api/AstralRecordApi/AstralRecordApi/Repositories/AccountQuestStateRepository.cs:41`
- 関連箇所: `20_api/AstralRecordApi/AstralRecordApi/Repositories/AccountRepository.cs:341`
- 根拠: Quest PUTはaccountを`UPDLOCK,HOLDLOCK`で取得してからstateと子行を置換する。一方、アカウント削除はaccountを通常の共有読み取りで取得した後、Quest子行をbulk deleteし、後でstateとaccountを更新する。
- 問題: PUTがaccount更新ロックを保持して子行を待ち、削除が子行の排他ロックを保持してaccountまたはstateの更新を待つロック待ち循環に参加できる。
- 影響: Quest保存とアカウント削除の同時実行でdeadlock、または削除と保存の競合による500が発生し得る。
- 修正方針: アカウント削除も子データ操作前に同じaccount行を`UPDLOCK,HOLDLOCK`で取得し、Quest PUTと同一の直列化プロトコルに参加させる。並行テストを追加する。
- 修正対象候補: `20_api/AstralRecordApi/AstralRecordApi/Repositories/AccountRepository.cs`
- 修正可否: `自動修正可`
- 確信度: `高`
- 修正状態: `修正済み`

### AR-CODE-005 [高] アカウント削除とinventory置換の親子ロック順不一致
- 種別: `バグ/アルゴリズム`
- 対象: `20_api/AstralRecordApi/AstralRecordApi/Repositories/AccountRepository.cs:550`
- 関連箇所: `20_api/AstralRecordApi/AstralRecordApi/Repositories/InventoryRepository.cs:371`
- 根拠: アカウント削除は`inventory_entry`を更新してから`inventory`を更新する。一方、inventory置換は同一accountの`inventory`親行を更新ロックしてから`inventory_entry`をロックする。
- 問題: 削除がentryの排他ロックを保持し、置換がinventory親行の更新ロックを保持するタイミングで、相手側のロック取得待ちが循環し得る。
- 影響: 同一accountのinventory置換とアカウント削除の同時実行でSQL Serverの1205が残る。
- 修正方針: 削除側もentry更新前に対象accountのinventory親行を`UPDLOCK,HOLDLOCK`・`inventory_id`昇順で先行ロックし、置換側と同じ順序にする。
- 修正対象候補: `20_api/AstralRecordApi/AstralRecordApi/Repositories/AccountRepository.cs`
- 修正可否: `自動修正可`
- 確信度: `高`

### AR-CODE-008 [高] inventory所有accountの共有ロック先行取得
- 種別: `バグ/アルゴリズム`
- 対象: `20_api/AstralRecordApi/AstralRecordApi/Repositories/InventoryRepository.cs:369-383`
- 関連箇所: `20_api/AstralRecordApi/AstralRecordApi/Repositories/AccountRepository.cs:633-646`
- 根拠: Round 3レビュー時点のinventory置換は`SERIALIZABLE` transaction内で対象inventoryのaccountを判定するSQLを実行してから、同一accountのinventory親行を`UPDLOCK,HOLDLOCK`で取得していた。対象判定側の共有ロックはtransaction終了まで保持され得る。一方、アカウント削除はaccount行、inventory親行の順に更新ロックを取得する。
- 問題: inventory置換が対象inventoryの共有ロックを保持したまま親行更新ロックへ進むと、アカウント削除が親行更新ロックを得て共有ロック解放を待つ経路と循環し得る。
- 影響: inventory置換とアカウント削除の同時実行でSQL Serverの1205が再発する可能性がある。
- 修正方針: SQL Serverでは対象inventoryの`account_id`をtransaction外で通常読取し、`READ COMMITTED` transaction内でaccount行を`UPDLOCK,HOLDLOCK`、同一accountのinventory親行を`inventory_id`昇順で更新ロックしてからentryを取得する。SQLiteの既存分岐は維持し、競合統合テストで確認する。
- 修正対象候補: `20_api/AstralRecordApi/AstralRecordApi/Repositories/InventoryRepository.cs`
- 修正可否: `自動修正可`
- 確信度: `高`
- 修正状態: `修正済み`
