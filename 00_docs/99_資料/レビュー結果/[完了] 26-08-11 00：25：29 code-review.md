### AR-CODE-001 [高] オーブ候補収集が Bukkit main thread で同期 HTTP を直列実行する
- 種別: `パフォーマンス`
- 対象: `10_plugin/AstralRecord/src/main/java/io/github/maaasu/astralRecord/feature/item/service/OrbService.java:524`
- 関連箇所: `10_plugin/AstralRecord/src/main/java/io/github/maaasu/astralRecord/feature/item/repository/ItemRepository.kt:183`
- 根拠: 通常インベントリの `InventoryClickEvent` から `handleInventoryOrbClick`、`openList`、`collectCandidates` が同期的に呼ばれる。`collectCandidates` は初回エンチャント時に `ItemService.findEnchantMasterById`（534行）から `ItemRepository.findEnchantMasterById`（515行）の `HttpClient.send` を実行し、さらに BAG/HOTBAR の各装備について `addCandidate`（560行）から `ItemService.findEquipmentInstanceById`（425行）、`ItemRepository.findEquipmentInstanceById`（183行）の同期 GET を cache miss 数だけ直列実行する。エンチャントマスタ cache は起動時・reload時に事前ロードされず、API request timeout の既定値は 30000 ms である。またエンチャントマスタ取得の通信 `IOException` は repository でも `ItemService` の `RuntimeException` catch でも捕捉されない。
- 問題: プレイヤーがオーブを初回クリックしただけでサーバ tick thread が API 応答待ちになり、装備数に応じた N+1 GET も発生する。API 遅延・停止時は全プレイヤーの処理を長時間停止させ、例外時は GUI 起動途中の session だけが残り得る。
- 影響: 通常操作でサーバ全体のラグ・watchdog 停止を起こし得る。API 障害を「付与候補なし」と安全に区別して扱うこともできない。
- 修正方針: 候補用装備個体と共通エンチャントマスタを非同期で取得した immutable snapshot として準備し、Bukkit main thread は cache 読み取りと GUI 描画だけを行う。起動・`/masterdata reload` で共通エンチャントマスタも原子的に差し替え、通信失敗は候補なしとは別の失敗として main thread へ戻す。cache miss を含む遅延・例外テストを追加する。
- 修正対象候補: `複数`
- 修正可否: `自動修正可`
- 確信度: `高`
- 修正状態: `修正済み`

### AR-CODE-002 [高] オーブ支払いと装備更新が非原子的・非冪等で無料適用が起きる
- 種別: `バグ/アルゴリズム`
- 対象: `10_plugin/AstralRecord/src/main/java/io/github/maaasu/astralRecord/feature/item/service/OrbService.java:1074`
- 関連箇所: `20_api/AstralRecordApi/AstralRecordApi/Models/EquipmentOperationRequests.cs:3`
- 根拠: `consumeForEquipmentOperation` はオーブ1個・素材・通貨を Plugin の memory state から先に除去するだけで、enhance/enchant/transcendence API request には支払い情報も operation ID もない。`OrbService` は1096行で operation ID を生成するが API へ送らず、API は装備更新だけを別 transaction で commit する。さらに POST が null の場合、enhance（1153行）、enchant（1238行）、transcendence（1280行）は遅延なしの GET を2回行い、到達できても旧状態なら `FAILED` として1375-1381行で receipt を返す。repair も inventory entry 保存と dirty durability flush が別 API 呼び出しである。
- 問題: API が POST を受理した後に client timeout となり、直後の GET ではまだ旧状態、receipt 返却後に POST が commit すると、装備だけ更新されオーブ・素材・通貨は戻る。また装備 commit 後かつ inventory autosave 前のプロセス停止でも、再起動後は装備更新済み・支払い未消費になる。逆順の部分保存では支払いだけが残る。enchant POST の再送は同じ抽選結果にもならない。
- 影響: 無料強化・無料エンチャント・無料状態変化、二重抽選、または支払いだけの消失が起き、プレイヤー資産と装備状態の永続整合性を保証できない。
- 修正方針: 全オーブ操作へ永続 operation ID を渡し、API 側で所有・最新条件・orb/material/gold 支払い・装備更新・確定結果を同一 DB transaction と operation ledger に保存する。同じ operation ID の再送は保存済み同一結果を返し、Plugin は transport failure 時に operation result を照会して確定する。即時 GET の旧 fingerprint だけで失敗・返却してはならない。既存構造上ひとつの transaction に統合できない場合は、再起動後も継続する durable saga/outbox と補償記録で同等の性質を持たせ、timeout・commit直後停止・保存失敗・再送の障害注入テストを追加する。
- 修正対象候補: `複数`
- 修正可否: `自動修正可`
- 確信度: `高`
- 修正状態: `修正済み`

### AR-CODE-003 [高] 非同期装備更新と戦闘耐久更新の競合で後発ダメージを失う
- 種別: `バグ/アルゴリズム`
- 対象: `10_plugin/AstralRecord/src/main/java/io/github/maaasu/astralRecord/feature/item/service/ItemService.java:552`
- 関連箇所: `10_plugin/AstralRecord/src/main/java/io/github/maaasu/astralRecord/feature/item/service/EquipmentDurabilityService.java:193`
- 根拠: `OrbService.startAsyncMutation`（1300行）は async thread から enhance/enchant/transcendence を実行し、成功時に `cacheEquipmentMutationResult` が `loadedEquipmentInstances` と `dirtyEquipmentDurability` を複数回 read/modify/write する。一方、戦闘イベントは main thread から `updateEquipmentDurability`（596行）で同じ2 mapを別々に更新し、`flushDirtyEquipmentDurability`（652行）も別の非原子的 snapshot を読む。map 自体は `ConcurrentHashMap` だが複合操作に共通の原子境界はない。
- 問題: 例として cache=90/100・pending=90 の時、async mutation が旧値から 100/110 を計算中に戦闘が85/100を putし、その後 async が100/110を putすると、flush は cache の100を永続化して後発5ダメージを失う。同様に flush と更新の競合でも古い値の確定・dirty 削除が起こり得る。
- 影響: オーブ処理中に受けた耐久消費が無償で巻き戻り、表示・cache・dirty queue・API正本が不整合になる。
- 修正方針: equipment instance 単位の lock または `ConcurrentHashMap.compute` 等で、mutation merge・耐久更新・flush snapshot/ack を同じ原子境界に置く。より単純には async thread は HTTP 結果だけを返し、全 cache/dirty 更新を main thread または単一 serial executor に集約する。barrier/latch を使い上記 interleaving を固定再現する並行テストを追加する。
- 修正対象候補: `複数`
- 修正可否: `自動修正可`
- 確信度: `高`
- 修正状態: `修正済み`

### AR-CODE-004 [中] エンチャント候補選択が transaction 外で並列操作を直列化できない
- 種別: `バグ/アルゴリズム`
- 対象: `20_api/AstralRecordApi/AstralRecordApi/Services/EquipmentService.cs:64`
- 関連箇所: `20_api/AstralRecordApi/AstralRecordApi/Repositories/EquipmentRepository.cs:47`
- 根拠: `EnchantAsync` は装備・現在 enchant の読み取り、空き slot 計算、重複除外、重み付き抽選を66-148行で済ませた後、`ApplyEnchantBatchAsync` が52行で初めて transaction を開始する。DB には equipment instance + slot/effect の UNIQUE があるが、読み取り lock・rowversion・競合時再評価はない。Plugin の null応答照合は「before fingerprint と異なる」だけを自操作成功と判断する（`OrbService.java:1238-1247`）。
- 問題: maxSlots=1 の空装備へ2リクエストが並行すると双方が slot 0 を選び、一方は UNIQUE 違反で500になる。失敗側 Plugin は他方の更新を自分の commit と誤認でき、2個のオーブを消費して効果は1個だけになる。OVERWRITE_RANDOM/FILL_ALL でも stale snapshot による候補・削除対象の取り違えが起こる。

### AR-CODE-009 [高] API 正本照合が事前保存後の同一 entry 変更を消失させる
- 種別: `バグ/アルゴリズム`
- 対象: `10_plugin/AstralRecord/src/main/java/io/github/maaasu/astralRecord/feature/inventory/service/InventoryService.java:237`
- 関連箇所: `10_plugin/AstralRecord/src/main/java/io/github/maaasu/astralRecord/feature/inventory/service/InventorySaveCoordinator.java:127`
- 根拠: `executeExclusiveAfterSave` は現在 state を149行で保存した後、155行の外部操作が戻るまで auto-save/logout-save だけを account lane で直列化し、`unresolvedExternalOperations` も保存系からしか参照されない。対して `addItemToNormalInventory`（405-445行）、`addPreparedRewardsToNormalInventory`（494-570行）、`addGold`（1798-1819行）には外部操作中の mutation guard や共通 lane がなく、mob drop（`MobDropPresentationService.java:514`）、dungeon/quest/mail/command 等から API 待機中にも同じ state を更新できる。操作完了後の `reconcileAuthoritativeEntry` は対象 ID のローカル entry を `PlayerInventoryState.java:405-417` で無条件に除去し、API から得た現在値を丸ごと追加する。たとえば事前保存時にオーブ entry 数量1、API通信中に同じ entry へ報酬1個が stack、APIが保存済み1個を消費して entry を削除、という順序では、照合がローカル数量2を削除して報酬分まで失う。状態変化の素材 entry や API が全 denomination を再構成する gold entry でも同じ競合が成立する。追加テスト `InventoryServiceOrbReconciliationTest.authoritativeAffectedEntryIsTheOnlySourceOfOrbConsumption` はローカル数量2→API数量1を常に正しい消費として検証し、数量2のうち1個が事前保存後の増分である interleaving を区別していない。
- 問題: account 保存 lane は永続化順序を守るが、API 支払い snapshot と Plugin memory mutation の順序を守らない。単一 entry の monitor 内置換は照合瞬間の同時実行しか防がず、事前保存から照合までに発生した正当な増分を API の古い基準値で上書きする。
- 影響: オーブ操作中に付与された同種オーブ・状態変化素材・ゴールド等が表示と次回保存の双方から消え、プレイヤー資産を恒久的に失う。逆方向のローカル減算が交差した場合は API 値で復活させるため、資産複製にもなり得る。
- 修正方針: operation 開始時に対象 account の entry/currency revision と事前保存 snapshot を固定し、API の affected entry 結果へその revision 後のローカル差分だけを三者マージする。あるいは全 inventory mutation を同じ account mutation lane に統合して API 確定・照合後へ順序付ける。単純に全 mutation を失敗させず、報酬等を遅延適用できる契約にし、orb/material/gold それぞれで「事前保存→同一 entry 増減→API commit→reconcile」の barrier テストを追加する。
- 修正対象候補: `複数`
- 修正可否: `自動修正可`

- 修正状態: `修正済み`
