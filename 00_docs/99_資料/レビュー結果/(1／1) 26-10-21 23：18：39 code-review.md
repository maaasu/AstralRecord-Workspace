### AR-CODE-001 [中] 実際の netsh のリダイレクト出力は UTF-8 指定でも不正 JSON になる
- 種別: `バグ/アルゴリズム`
- 対象: `60_tool/environment-cutover/ApiTls.psm1:194`
- 関連箇所: `60_tool/environment-cutover/ApiTls.psm1:205`
- 根拠: DEV-01 で同じ `netsh.exe http show sslcert ipport=0.0.0.0:444 json=enable` を新 helper 経由で読み取ると、終了コード 0 でも `message` が文字化けし終端引用符のない JSON となり、`ConvertFrom-Json` が失敗した。標準出力の元バイト列にも終端引用符が存在しない。同じ PowerShell 内で `[Console]::OutputEncoding` を UTF-8 にして直接 native capture すると有効な JSON を取得できた。追加テストの子プロセスは常に正常な UTF-8 JSON を直接書き出すため、この実際の `netsh` の挙動を検証していない。
- 問題: `ProcessStartInfo` で stdout をリダイレクトすると、`StandardOutputEncoding` でデコードする前に `netsh` が不正な JSON を生成する環境がある。
- 影響: DEV-01 と同じ出力条件では Bind の事前確認が必ず失敗し、APP-01 の切替も同じ条件なら先へ進めない。既存 binding は更新されず、機能回復もできない。
- 修正方針: 実際の `netsh` で有効な JSON が得られる取得方法を採用し、実 `netsh` を使う読み取り検査を追加する。DEV-01 では一時的に `[Console]::OutputEncoding` を UTF-8 にした直接 native capture が成功している。APP-01 でも確認し、元設定を `finally` で復元する。不正 JSON の補修や推測による更新は行わない。
- 修正対象候補: `複数`
- 修正可否: `要確認`
- 確信度: `高`
- 修正状態: `修正済み`
