### AR-CODE-001 [高] ショップ購入失敗時に支払いだけ消費され得る
- 種別: `バグ/アルゴリズム`
- 対象: `E:\AstralRecord-Workspace\10_plugin\AstralRecord\src\main\java\io\github\maaasu\astralRecord\feature\shop\service\ShopService.java:151`
- 関連箇所: `E:\AstralRecord-Workspace\10_plugin\AstralRecord\src\main\java\io\github\maaasu\astralRecord\feature\inventory\service\InventoryService.java:954` / `E:\AstralRecord-Workspace\10_plugin\AstralRecord\src\main\java\io\github\maaasu\astralRecord\feature\inventory\service\InventoryService.java:1008`
- 根拠: 一般原則。プレイヤー資産の購入処理は、支払い消費と商品付与を同一の成功単位として扱う必要がある。
- 問題: `purchase()` は `consumeGold()` で Gold を消費した後、素材消費、商品付与、`saveNow()` へ進む。素材消費や `addItemToNormalInventory()` が失敗すると `false` を返すだけで、消費済み Gold や消費済み素材を戻さない。`InventoryService.consumeGold()` / `consumeNormalItem()` は state を直接減らすため、後続の autosave / logout save で消費だけが永続化され得る。
- 影響: API 不調、装備/ルーンのインスタンス作成失敗、state 競合、予期しない付与失敗時に、購入は失敗扱いなのに通貨・素材だけ失われる。
- 修正方針: 購入を「検証 -> 全消費/付与の準備 -> state 反映 -> save」の単位に寄せる。少なくとも消費後の失敗経路では、消費済み Gold / 素材を補償してから失敗を返す。装備/ルーン付与が外部 API に依存するなら、インスタンス作成を支払い確定前に準備し、失敗時は state を変更しない。
- 修正可否: `自動修正可`
- 修正状態: `修正済み`
- 確信度: `高`

### AR-CODE-002 [高] 装備強化が支払い前に装備状態を API 反映している
- 種別: `バグ/アルゴリズム`
- 対象: `E:\AstralRecord-Workspace\10_plugin\AstralRecord\src\main\java\io\github\maaasu\astralRecord\feature\item\service\EquipmentEnhancementService.java:212`
- 関連箇所: `E:\AstralRecord-Workspace\10_plugin\AstralRecord\src\main\java\io\github\maaasu\astralRecord\feature\item\service\EquipmentEnhancementService.java:219` / `E:\AstralRecord-Workspace\10_plugin\AstralRecord\src\main\java\io\github\maaasu\astralRecord\feature\item\service\EquipmentEnhancementService.java:301`
- 根拠: 一般原則。課金・素材消費を伴う装備更新は、対価消費と装備更新の順序・失敗時補償を明示する必要がある。
- 問題: `executeEnhancement()` は成功/失敗判定後、先に `applyEnhancementResult()` を呼び、`itemService.enhanceEquipmentInstance()` または `deleteEquipmentInstance()` で装備状態を API 側へ反映する。その後で `consumeRequirements()` により素材と Gold を消費する。消費に失敗した場合、装備の強化・降格・破壊だけが先に確定し、支払い側は未確定または一部消費のまま失敗終了する。
- 影響: 消費失敗時に無料強化、素材だけ消費、Gold だけ未消費、または支払い失敗なのに装備破壊/降格が確定する。プレイヤー資産と API 上の装備状態が不整合になる。
- 修正方針: 強化前に消費を予約/確定するか、装備 API 更新と支払いを補償可能な順序にする。最小修正なら、消費を先に行い、装備更新失敗時に素材/Gold を戻す補償を入れる。より堅牢には API 側へ装備更新と対価消費を単一トランザクション endpoint として寄せる。
- 修正可否: `自動修正可`
- 修正状態: `修正済み`
- 確信度: `高`

### AR-CODE-003 [中] 装備修理 API 失敗時に Gold が戻らない
- 種別: `バグ/アルゴリズム`
- 対象: `E:\AstralRecord-Workspace\10_plugin\AstralRecord\src\main\java\io\github\maaasu\astralRecord\feature\item\service\EquipmentRepairService.java:247`
- 関連箇所: `E:\AstralRecord-Workspace\10_plugin\AstralRecord\src\main\java\io\github\maaasu\astralRecord\feature\item\service\EquipmentRepairService.java:252` / `E:\AstralRecord-Workspace\10_plugin\AstralRecord\src\main\java\io\github\maaasu\astralRecord\feature\inventory\service\InventoryService.java:954`
- 根拠: 一般原則。修理費の消費と装備耐久更新は同一成功単位で扱うべき。
- 問題: `executeRepair()` は `consumeGold()` で先に Gold を state から減らし、その後 `itemService.updateEquipmentDurability()` を呼ぶ。`updated == null` の場合はエラーメッセージを出して戻るだけで、消費済み Gold を補償しない。
- 影響: 装備耐久 API の失敗や一時障害で、修理は失敗しているのに Gold だけ失われる。`saveNow()` は呼ばれないが、state は dirty のまま残るため後続保存で消費が永続化され得る。
- 修正方針: 修理更新を先に成功確認してから Gold を消費する、または Gold 消費後の更新失敗時に `addGold()` 相当で補償する。UI 表示更新と `saveNow()` は、修理更新と支払いの両方が成功した場合だけ行う。
- 修正可否: `自動修正可`
- 修正状態: `修正済み`
- 確信度: `高`

### AR-CODE-004 [低] API キー送信時にも TLS 証明書・ホスト名検証を完全無効化できる
- 種別: `セキュリティ`
- 対象: `E:\AstralRecord-Workspace\10_plugin\AstralRecord\src\main\java\io\github\maaasu\astralRecord\infrastructure\util\ApiRequestUtil.kt:49`
- 関連箇所: `E:\AstralRecord-Workspace\10_plugin\AstralRecord\src\main\java\io\github\maaasu\astralRecord\infrastructure\util\ApiRequestUtil.kt:72` / `E:\AstralRecord-Workspace\10_plugin\AstralRecord\src\main\resources\config.yml:46` / `E:\AstralRecord-Workspace\10_plugin\AstralRecord\src\main\java\io\github\maaasu\astralRecord\infrastructure\config\ConfigProperties.java:115`
- 根拠: 一般原則。認証ヘッダを送る HTTPS クライアントで証明書検証・ホスト名検証を無効化すると、中間者攻撃に対して API キーとプレイヤーデータを保護できない。
- 問題: `api.ssl.verifyEnabled=false` で `createTrustAllSslContext()` と空の `endpointIdentificationAlgorithm` を設定し、証明書チェーン検証とホスト名検証を両方無効化する。一方で同じ request builder は `X-Api-Key` を常に付与し得る。デフォルトは `true` だが、false 設定が警告ログのみで本番利用を止めない。
- 影響: 誤設定または検証用設定の本番混入時に、API キー、Web 認証チャレンジ、プレイヤー資産系 API 通信が盗聴・改ざんされるリスクがある。
- 修正方針: `verifyEnabled=false` は debug mode か localhost / private development endpoint に限定し、本番 URL と API key が設定されている場合は起動失敗にする。必要なら自己署名 CA を truststore として明示設定する方式に置き換える。
- 修正可否: `自動修正可`
- 修正状態: `修正済み`
- 確信度: `中`
