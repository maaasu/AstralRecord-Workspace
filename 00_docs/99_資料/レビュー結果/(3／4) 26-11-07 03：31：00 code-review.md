### AR-CODE-001 [中] 遅延した予約準備が復旧済みの予約を再有効化する
- 種別: `バグ/アルゴリズム`
- 対象: `30_web/AstralRecordControl/src/AstralRecordControl.Web/Operations/ReservationService.cs:102`
- 関連箇所: `30_web/AstralRecordControl/src/AstralRecordControl.Web/Operations/ReservationService.cs:454`
- 根拠: 同じ Workflow ID の予約準備は Preparing 中に再送でき、準備結果は別の書き込みで中央台帳へ反映する。
- 問題: 復旧が Runner と中央予約を解放した後に、別の準備応答や失敗処理が中央の終端状態を上書きできる。
- 影響: 解放済みの予約が Prepared または RecoveryRequired に戻り、起動が再び妨げられる。
- 修正方針: 予約準備の確定と失敗反映の直前に最新の中央状態をトランザクション内で照合する。
- 修正対象候補: `30_web/AstralRecordControl/src/AstralRecordControl.Web/Operations/ReservationService.cs`
- 修正可否: `自動修正可`
- 確信度: `高`
- 修正状態: `修正済み`

### AR-CODE-002 [中] 復旧開始後に古い予約へ操作を登録できる
- 種別: `バグ/アルゴリズム`
- 対象: `30_web/AstralRecordControl/src/AstralRecordControl.Web/Operations/ControlOperationsService.cs:141`
- 関連箇所: `30_web/AstralRecordControl/src/AstralRecordControl.Web/Operations/ReservationService.cs:424`
- 根拠: 新規操作は Runner の snapshot を検証してから、別の書き込みで子操作を登録する。
- 問題: snapshot 取得後に同じ予約が解放処理へ進んで失敗すると、復旧と古い操作の登録が競合する。
- 影響: Runner の hold を解放した後で、その hold を前提とした操作が登録される可能性がある。
- 修正方針: 子操作の登録トランザクションで Prepared 状態と予約の所有者、fence を再確認する。
- 修正対象候補: `30_web/AstralRecordControl/src/AstralRecordControl.Web/Operations/ControlOperationsService.cs`
- 修正可否: `自動修正可`
- 確信度: `高`
- 修正状態: `修正済み`

- 関連箇所: `00_docs/30_WEB設計書/AstralRecordControl/04-操作と運用.md:45`
- 根拠: 設計書は点検後の解放時に確認結果と理由を記録すると定める。

### AR-CODE-004 [中] 遅延した通常解放が復旧済みの予約を再有効化する
- 種別: `バグ/アルゴリズム`
- 対象: `30_web/AstralRecordControl/src/AstralRecordControl.Web/Operations/ReservationService.cs:288`
- 関連箇所: `30_web/AstralRecordControl/src/AstralRecordControl.Web/Operations/ReservationService.cs:425`
- 根拠: 通常解放は Prepared 状態を読み、後続のトランザクションで Releasing を書く。
- 問題: 並行する解放と復旧が先に完了すると、古い状態を読んだ解放要求が終端状態を Releasing で上書きできる。
- 影響: 遅延した解放の通信が失敗すると、すでに解放した予約が RecoveryRequired に戻る。
- 修正方針: 通常解放への遷移前に、書き込みトランザクション内で最新の状態、解放結果、非終端の操作を照合する。
- 修正対象候補: `30_web/AstralRecordControl/src/AstralRecordControl.Web/Operations/ReservationService.cs`
