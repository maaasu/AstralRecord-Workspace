### AR-CODE-001 [高] 版数を持たない補修が新しいスナップショットを再度全解除する
- 種別: `バグ/アルゴリズム`
- 対象: `10_plugin/AstralRecord/src/main/java/io/github/maaasu/astralRecord/feature/skilltree/service/SkillTreeService.java:884`
- 関連箇所: `複数`
- 根拠: `loadInitialPlayerState` は GET で得た `loadedState.persistedVersion()` を補修要求へ渡さず POST している。一方、通常の `skillTree` snapshot は `ExpectedVersion` と現在 version の一致を必須にして競合時に保存しないが、補修側は version を確認せず unlocked node を削除して version を進める。設計書は初期ロード中の未保存 state を優先し、旧 API 値による置換をしないことを契約としている。
- 問題: 遅延した join 補修要求が、別セッションで補修後に再選択・保存された状態へ到達しても、その状態が現在の構造に有効かを確認せず全解除する。例えば v1 の不整合状態を読んだ A、A より先に v2 へ補修してメールを配信した B、その後 B が再選択を v3 snapshot として保存した場合、A の POST は同じ repairKey の既存メールを再利用しつつ v3 を空状態へ置換する。
- 影響: 補償済みのプレイヤーが選び直して保存したスキルツリーを、遅延・再試行したログイン処理だけで失う。メールは同一 repairKey のため追加されず、プレイヤーは再度選択をやり直すことになる。
- 修正方針: 補修リクエストに GET 時の expectedVersion を含め、API の Serializable transaction 内で状態 version を検証してから reset と delivery を確定する。不一致時は状態を変更せず競合として返し、Plugin は再読込・再検証して、なお不整合なら新しい version で補修する。通常 snapshot と補修の順序を入れ替えた競合テスト、および同一 repairKey の再試行がメールを一度だけ配信するテストを追加する。
- 修正対象候補: `複数`
- 修正可否: `自動修正可`
- 確信度: `高`
- 修正状態: `修正済み`

### AR-CODE-002 [中] 不正な補修リクエストを 500 として返す
- 種別: `バグ/アルゴリズム`
- 対象: `20_api/AstralRecordApi/AstralRecordApi/Controllers/AccountSkillTreeController.cs:56`
- 関連箇所: `20_api/AstralRecordApi/AstralRecordApi/Repositories/AccountSkillTreeStateRepository.cs:280`
- 根拠: `ValidateRepairRequest` は空 UUID、不正な `repairKey`、負の `expectedVersion` に対して `ArgumentException` を送出するが、`RepairInvalidState` は `KeyNotFoundException` と `DbUpdateConcurrencyException` だけを処理する。未処理例外は `Program.cs` の例外ハンドラで 500 へ変換される。一方、既存 Controller は入力検証の `ArgumentException` を `BadRequest` へ変換している。
- 問題: クライアント入力として不正な補修要求が、リクエスト不正ではなくサーバー内部障害として応答・記録される。
- 影響: 呼び出し側は修正不能な入力エラーを一時障害として再試行し、API の 4xx/5xx 契約と監視上の障害分類が崩れる。
- 修正方針: Controller で `ArgumentException` を 400 へ変換し、400 の OpenAPI 応答を宣言する。補修 request の不正な `repairKey` と負の `expectedVersion` に対する Controller レベルの 400 テストを追加する。
- 修正対象候補: `複数`
- 修正可否: `自動修正可`
- 確信度: `高`
- 修正状態: `修正済み`
