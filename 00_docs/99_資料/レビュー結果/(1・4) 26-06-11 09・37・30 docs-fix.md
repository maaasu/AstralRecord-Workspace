- 対象: `E:\AstralRecord-Workspace\00_docs\10_プラグイン設計書\feature\22-trade\3-メソッド仕様\22_3.00-メソッド仕様.md:53`

- 根拠: ユースケースとメッセージ仕様は、申請メッセージクリック時に `/trade accept` を実行すると定義している。一方で承諾処理は「承諾者宛ての最新の `PENDING` 申請」を取得すると定義している。
- 問題: 複数プレイヤーから申請を受けた場合、古い申請メッセージをクリックしても、クリックした申請ではなく最新申請を承諾する設計になり得る。クリックメッセージと承諾対象の対応が壊れる。
- 影響: プレイヤーが意図しない相手とのトレード GUI を開始する可能性があり、取引相手の誤認につながる。
- 修正方針: クリック実行コマンドに `requestId` または申請者識別子を含めるか、`/trade accept` の対象選択ルールを「クリック元申請」と一致する形に変更する。複数申請時の優先順位、期限切れ、同一相手再申請の扱いも同じ箇所に明記する。
- 修正対象候補: `E:\AstralRecord-Workspace\00_docs\10_プラグイン設計書\feature\22-trade\2-ユースケース\22_2.00-ユースケース.md` / `E:\AstralRecord-Workspace\00_docs\10_プラグイン設計書\feature\22-trade\3-メソッド仕様\22_3.00-メソッド仕様.md` / `E:\AstralRecord-Workspace\00_docs\10_プラグイン設計書\feature\22-trade\5-例外・ログ・運用\22_5.00-例外・ログ・運用.md`

### AR-DOC-002 [高] 取引成立時の片側付与失敗に対する原子性・ロールバックが未定義
- 種別: `不足` / `運用リスク`
- 対象: `E:\AstralRecord-Workspace\00_docs\10_プラグイン設計書\feature\22-trade\3-メソッド仕様\22_3.00-メソッド仕様.md:140`

- 根拠: 取引成立実行は事前に双方の受け取り先空き容量を検証し、その後 A の提示アイテムを B へ、B の提示アイテムを A へ付与すると定義している。inventory feature 側で確認できる契約は `addItemToNormalInventory` の追加処理と入りきらない場合のメッセージ返却であり、trade 用の予約・一括交換・ロールバック契約は確認できない。
- 問題: 事前検証後から付与完了までの間にインベントリ状態が変わる、または片側付与後にもう片側付与が失敗する場合の扱いが未定義。例外時に「可能な限り返却」とあるが、どの時点でどの所有者へ戻すか、付与済みアイテムを回収するか、セッション状態をどうするかが決まっていない。
