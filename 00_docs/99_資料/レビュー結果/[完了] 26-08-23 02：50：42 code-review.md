### AR-CODE-001 [中] 非同期の強制再取得が古い応答でキャッシュを巻き戻す
- 種別: `バグ/アルゴリズム`
- 対象: `10_plugin/AstralRecord/src/main/java/io/github/maaasu/astralRecord/feature/item/service/ItemService.java`
- 関連箇所: `reloadEquipmentInstances 539-565行、reloadRuneInstances 577-603行、既存の findEquipmentInstanceById 447-473行`
- 根拠: `新しい reload は API 取得を mutex の外で行い、完了時に equipment は replaceEquipmentInstanceCacheLocked、rune は loadedRuneInstances.put で無条件に公開する。一方、既存の equipment 通常取得は mutex 内で既に新しい cache が存在する場合に取得結果を破棄する競合対策を持つ。`
- 問題: `trade の強制再取得または rune の再取得が遅れて返ると、その応答が途中で行われた durability/orb mutation、別の reload、またはより新しい通常取得結果を上書きできる。equipment の dirty durability 差分だけは再計算されるが、owner・属性・他の個体情報や rune 全体の新旧判定は保護されない。`
- 影響: `取引直後の resolver/cache が API 正本より古い owner・個体情報を参照し、後続保存や再ログイン時の削除・空表示を誘発する。API の retry/idempotency が正常でも、Plugin 内の公開順序だけで一時的に誤った状態になる。`
- 修正方針: `instance 単位で reload を直列化するか、取得開始時の cache 世代・更新時刻・revision を記録し、公開直前に世代が変わっていれば応答を破棄または再取得する。equipment と rune の両方で同一の stale-response 防止契約を適用し、dirty durability とのマージもその世代判定後に行う。`
- 修正対象候補: `ItemService.java の reloadEquipmentInstances、reloadRuneInstances、および個体 cache を更新する既存 mutation/通常取得経路`
- 修正可否: `自動修正可`
- 確信度: `高`
- 修正状態: `修正済み`

### AR-CODE-002 [中] dirty durability を未検証の API 値へ差分適用して durability を誤保存し得る
- 種別: `バグ/アルゴリズム`
- 対象: `10_plugin/AstralRecord/src/main/java/io/github/maaasu/astralRecord/feature/item/service/ItemService.java`
- 関連箇所: `replaceEquipmentInstanceCacheLocked 606-645行、reloadEquipmentInstances 539-565行、InventoryService.java 2315-2354行`
- 根拠: `強制 reload は API から取得した現在値に対し、dirty 状態の pending.durabilityValue() - pending.baseDurabilityValue() を常に加算し、dirty の base を取得値へ置き換える。API 取得値が pending を作った時点の base と同一であること、またはその値を含まないことを確認する処理はない。`
- 問題: `pending 作成後に別の durability 更新・mutation が API へ反映されてから trade reload が返ると、その更新済み値へローカル差分をもう一度適用する。逆に取得応答が古い場合も、後続の flush が古い値を正本へ書き戻す。owner を loaded owner に変更して recipient 側で flush できるようにしているが、差分の適用対象の世代整合性は保証されていない。`
- 影響: `取引の retry/recovery 時に durability が過減算・過加算される、または別更新を失う。保存は成功しても誤った値が API 正本として残るため、単純な dirty フラグ保持だけでは durability の耐久性要件を満たさない。`
- 修正方針: `pending の base/revision と reload 応答の revision または API 更新時刻を比較し、同一世代の場合だけ差分を適用する。不一致時は dirty を未解決として保持して再取得・再計算するか、明示的な conflict/recovery へ遷移させる。retry で同じ結果を再送しても値が二重適用されない API/Plugin 契約もテストで固定する。`
- 修正対象候補: `ItemService.java の replaceEquipmentInstanceCacheLocked、durability dirty の flush/retry 境界、関連する durability repository 呼び出し`
- 修正可否: `要確認`
- 確信度: `中`
- 修正状態: `修正済み`
