### AR-CODE-001 [高] 角のある幅広通路でACTIVE入口のガラス横を通過できる
- 種別: `バグ/アルゴリズム`
- 対象: `10_plugin/AstralRecord/src/main/java/io/github/maaasu/astralRecord/feature/dungeon/generation/DungeonBlockPlanner.java:353`
- 関連箇所: `10_plugin/AstralRecord/src/test/java/io/github/maaasu/astralRecord/feature/dungeon/generation/DungeonBlockPlannerTest.java:75`
- 根拠: `32_0-概要.md` と `32_3-処理契約.md` は、子部屋が `ACTIVE` の間は入口全体を GLASS で閉鎖し、部屋内から退出できないことを要求している。一方 `createCorridorFootprint` は中心線の各点を X/Z 両方向へ通路幅分拡張するが、`buildRoomEntrance` は最初の境界横断点に固定幅の平面しか生成しない。既定の `corridorWidth=3` と seed 2 では、connection 1 の GLASS 底面が `(30,33)..(30,35)` であるのに、直前の曲がり角が作る `(30,36)` の AIR から親側へ到達できた。追加診断でも 20 seeds × 162 connections のうち、幅3で14件、幅5で26件、幅7で29件の迂回経路を確認した。
- 問題: 子部屋直前で中心線が曲がると、通路 footprint の角に平面外の歩行可能ブロックが残る。新規テストは平面の個数と中央3点の相対座標だけを検証し、GLASS 配置後の親子間非到達性や通路幅の境界値を検証していない。
- 影響: 攻略中の部屋から通路へ物理的に退出でき、ユーザー要件の戦闘中閉じ込めが成立しない。現行の本番マスタも幅3のため実際に発生し得る。
- 修正方針: 中心線上の固定平面ではなく、生成済み通路 footprint と子部屋の実形状から親側と子側を分断する全閉鎖座標を求める。幅1/3/5/7、直線/境界直前の曲がり、RECTANGLE/CYLINDER に対し、他ゲート解放後も ACTIVE 部屋から親部屋側へ到達できない回帰テストを追加する。
- 修正対象候補: `複数`
- 修正可否: `自動修正可`
- 確信度: `高`
- 修正状態: `修正済み`

### AR-CODE-002 [中] 保留中のカルトグラフ転送がACTIVE遷移と終了を追い越す
- 種別: `バグ/アルゴリズム`
- 対象: `10_plugin/AstralRecord/src/main/java/io/github/maaasu/astralRecord/feature/dungeon/service/DungeonService.java:1912`
- 関連箇所: `10_plugin/AstralRecord/src/main/java/io/github/maaasu/astralRecord/feature/world/service/WorldService.java:558`
- 根拠: `32_3-処理契約.md` はカルトグラフによる移動で session・participant・binding・現在地・部屋状態を再検証し、操作本人が `ACTIVE` 部屋内なら転送しないこと、終了時は保留転送の完了を待って後始末することを要求している。`teleportToClearedRoom` は `mapSnapshot` でクリック時に一度判定した後、返された Future を session に追跡せず `worldService.teleportPlayerAsync` を開始する。`WorldService` はチャンク準備後にも `TELEPORT_PREPARE_DELAY_TICKS` で実転送を遅延し、その実行直前に Dungeon 状態を再検証しない。
- 問題: クリック時には攻略済み部屋内でも、実転送までの間に AVAILABLE 部屋へ入って `ACTIVE` にしたり、セッションが ENDING に移行できる。その後も旧要求の転送がそのまま実行される。またこの Future は `entryTransfers` / `returnTransfers` のどちらにも入らないため、`completeSession` の待機対象にもならない。新規テストは既にACTIVE内にいる同期ケースだけを検証している。
- 影響: タイミング次第で攻略中の部屋からカルトグラフで別部屋へ退出できる。終了処理と重なると強制帰還や一時 World 破棄と旧転送の順序が保証されない。
- 修正方針: カルトグラフ転送を session の保留転送として追跡し、実テレポート直前に session index・participant・binding・同一World・現在地がACTIVEでないこと・移動先CLEAREDを再検証する。終了時はその Future も待機し、ACTIVE遷移後と ENDING 移行後の保留転送が実行されないテストを追加する。
- 修正対象候補: `複数`
- 修正可否: `自動修正可`
- 確信度: `高`
- 修正状態: `修正済み`

### AR-CODE-003 [高] 別接続の開削領域からACTIVE部屋を迂回退出できる
- 種別: `バグ/アルゴリズム`
- 対象: `10_plugin/AstralRecord/src/main/java/io/github/maaasu/astralRecord/feature/dungeon/generation/DungeonBlockPlanner.java:378`
- 関連箇所: `10_plugin/AstralRecord/src/test/java/io/github/maaasu/astralRecord/feature/dungeon/generation/DungeonBlockPlannerTest.java:113`
- 根拠: `32_3-処理契約.md` は、子部屋が `ACTIVE` の間は子部屋境界の開口全体を GLASS で閉じて物理退出を防ぐことを要求する。修正後の `buildRoomEntrance` は入口の `connectionFootprint` だけを候補にするが、全 connection の footprint は先に一括開削される。RECTANGLE・幅5・seed 4・connection 4では、ACTIVE閉鎖面が `(29..33, 102)` である一方、同じ部屋から出る connection 6 の幅広 footprint が `(34, 102)` を AIR にし、そこから子部屋 spawn →親部屋 spawn へ到達できた。独立診断で幅1/3/5/7×RECTANGLE/CYLINDER×100 seedsを調べ、幅5/7を中心に同様の漏れを複数確認した。
- 問題: 閉鎖面が「対象 connection の footprint」と子部屋境界の接続部に限定され、別 connection が作った同じ部屋境界の開口を cut set に含めない。また、逐次生成中の `blocks` に対し `Material.AIR` のみを候補にするため、有効な CYLINDER・幅1 定義で先行 connection のゲートと重なると `Could not resolve open room entrance` になるケースも seed 54/68/74/95 で再現した。追加テストは各構成の seed 2/112233 だけで、同一部屋の複数 connection が境界付近で重なる配置を含まない。
- 影響: 幅広通路の有効な生成結果で、攻略中プレイヤーがガラス横を通って部屋外へ退出できる。別の有効な形状・幅ではブロック計画自体が例外終了し、ダンジョン準備が失敗する。
- 修正方針: 対象 connection だけではなく、ゲート上書き前の全実歩行可能領域と子部屋形状から、子部屋内外を分断する境界開口の cut set を求める。同一部屋の入出接続が境界付近で重なる seed と、有効な全幅・形状で計画生成が成功することを回帰テストに追加する。
- 修正対象候補: `複数`
- 修正可否: `自動修正可`
- 確信度: `高`
- 修正状態: `修正済み`

### AR-CODE-004 [高] 空のACTIVE閉鎖面を許容してAVAILABLE部屋を入室不能のまま生成する
- 種別: `バグ/アルゴリズム`
- 対象: `10_plugin/AstralRecord/src/main/java/io/github/maaasu/astralRecord/feature/dungeon/generation/DungeonBlockPlanner.java:417`
- 関連箇所: `10_plugin/AstralRecord/src/test/java/io/github/maaasu/astralRecord/feature/dungeon/generation/DungeonBlockPlannerTest.java:148`
- 根拠: `32_3-処理契約.md` は親部屋クリア後に子部屋を `AVAILABLE` とし、対応する incoming ゲートを解放して進入・戦闘開始できる進行を要求する。しかし、CYLINDER・幅1・seed 54/68/74/95 の指定再現で、対象 incoming の表示ゲートとバリアを AIR とみなしても、親部屋 spawn から子部屋内の `contains` セルへは1セルも到達できなかった。各ケースの対象 connection はそれぞれ 6、8、4、5 で、いずれも `roomEntrancesByRoom` は空の `gateBlocks` を返した。
- 問題: `gateFootprint.isEmpty()` を「別 connection の閉鎖ゲートが開口を封鎖済み」として正常返却するが、その状態はACTIVE中の退出を既に防ぐだけでなく、incoming 解放後の初回入室も防ぐ。テストも `reachableAfterIncomingGateOpens == false` のとき空の閉鎖面を正常と断定し、子部屋内への到達可能性を検証していない。
- 影響: 有効な生成定義と seed で計画生成は成功するようになったが、子部屋を `AVAILABLE` から `ACTIVE` へ遷移できず、通常部屋の全攻略およびBOSS解放が永久に停止する。
- 修正方針: ACTIVE cut set の空許容とは別に、incoming ゲート解放後に親側から子部屋内へ実際に入室可能であることを必須条件にする。別 connection ゲートとの重なりを保護しつつ、入室経路を塞ぐゲート配置または通路配置を解消し、指定4 seedsで親側から任意の子部屋内セルへ到達できる回帰テストを追加する。
- 修正対象候補: `複数`
- 修正可否: `自動修正可`
- 確信度: `高`
- 修正状態: `修正済み`
