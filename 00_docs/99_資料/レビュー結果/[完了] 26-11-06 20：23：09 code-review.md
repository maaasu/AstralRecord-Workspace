### AR-CODE-001 [高] GUI 版マーカーの改行で配布前検査が必ず失敗する
- 種別: `バグ/アルゴリズム`
- 対象: `50_resourcepack/scripts/gui-assets.ps1:124`
- 関連箇所: `60_tool/deploy-debug/deploy-debug.ps1:426`
- 根拠: `Add-GuiThemeEntries` のレビュー開始時点の実装は GUI 版マーカーを `$utf8.GetBytes("1`n")` で生成していた。一方、`Publish-ResourcePacks` は同エントリーの長さが厳密に1バイトであることと、読み取った文字列が厳密に `1` であることを要求する。これは同一変更内の producer / consumer 契約の不一致である。
- 問題: 新規ビルドの `gui-theme-version.txt` は `1` と LF の2バイトになり、配布処理の `Length -ne 1` 検査で例外になる。パックの生成成功だけではこの不一致を検出できない。
- 影響: このパックを含めた通常のデバッグ配布がリソースパック公開前に必ず中断する。
- 修正方針: マーカーを改行なしの1バイト `1` として出力する。両 PowerShell でパックを再生成し、実アーカイブから版マーカーの長さと内容を読み取る consumer と同じ検査、既存のアーカイブ参照検査と決定性検査を通す。調整役が修正済みコードを作成していても、修正後成果物の検証と状態更新は修正工程で行う。
- 修正対象候補: `50_resourcepack/scripts/gui-assets.ps1`
- 修正可否: `自動修正可`
- 確信度: `高`
- 修正状態: `修正済み`

### AR-CODE-002 [中] 明るいタイトル帯で既存の金色と水色の画面名が読みにくくなる
- 種別: `バグ/アルゴリズム`
- 対象: `50_resourcepack/scripts/generate-gui-panels.py:74`
- 関連箇所: `10_plugin/AstralRecord/src/main/java/io/github/maaasu/astralRecord/shared/gui/GuiResourcePackTitle.java:128`
- 根拠: 生成されるタイトル帯は `LIGHT = #c4cec8` で塗られるが、装飾処理は元のタイトルの色を維持する。実際のタイトルとして `AdventureRecordGui.java:127` は GOLD `#ffaa00`、同144行は AQUA `#55ffff` を使う。相対輝度から算出した帯とのコントラスト比はそれぞれ1.18:1と1.32:1であり、他の WHITE も1.61:1となる。これは新たな規約違反ではなく、実際に組み合わせる色と画面名の視認性に基づく一般的な UI 品質の判断である。
- 問題: 黒い模擬ラベルを使う格子プレビューでは確認できない既存タイトル色が、実際には明るい帯と近い明度で重なる。タイトル帯を全 GUI で共用するため、冒険記録、両替所、ビルダーなど複数の画面名を読み取りにくくする。
- 影響: ユーザーが開いている画面やページを認識しにくくなり、見やすい専用 GUI という本件の目的を満たさない。
- 修正方針: 共通タイトル帯と、対応パック適用時に送信するタイトル表示色を対で調整して明確な明度差を確保する。例えば暗いスレートの帯とクリーム色の表示文字に統一し、元のサーバータイトルと非対応パック・統合版へのフォールバック表示は維持する。既存の明示色を持つ子コンポーネントも対象とし、実際の GOLD / AQUA を含む表示結果を確認する。
- 修正対象候補: `複数`
- 修正可否: `自動修正可`
- 確信度: `高`
- 修正状態: `修正済み`

### AR-CODE-003 [中] CRLF checkout で GUI 生成検査と配布ハッシュが変わる
- 種別: `バグ/アルゴリズム`
- 対象: `50_resourcepack/scripts/generate-gui-panels.py:178`
- 関連箇所: `50_resourcepack/scripts/build-resourcepack.ps1:29`
- 根拠: rebase 後の commit `d0132a359` の実 checkout で `python 50_resourcepack/scripts/generate-gui-panels.py --check` を実行すると、`Out-of-date GUI assets: assets\astralrecord\font\gui.json` で失敗した。実ファイルは1194バイト・CRLF65個だが、生成する同じ JSON はLFである。さらに `NOTICE-GUI.txt` は802バイト・CRLF16個であり、レビュー開始時点の `Add-PackEntries` は `.json` と `.mcmeta` だけをLFへ正規化していた。両版へ含めるNOTICEの改行差は、そのままアーカイブ内容とBedrockの内容fingerprintへ入る。これはREADMEが定める同じ入力からの同一バイト列と、既存ビルダーのcheckout改行正規化の契約に関わる。
- 問題: 新規JSONの検査が文字内容ではなくcheckout由来の改行差だけで失敗する。加えて通知文の内容が同じでもLF/CRLFのcheckout間で梱包バイトが変わるため、rebase前後で配布ハッシュとBedrock UUIDが変わる。
- 影響: Windowsの通常checkoutで生成物整合検査が通らず、不要なパック世代更新・キャッシュ無効化が起きる。rebase前に確認したパックと同じ意味のソースを再生成しても、検証済みハッシュへ一致しない。
- 修正方針: パネル生成検査ではJSONだけCRLFをLFへ正規化して比較し、PNGの厳密なバイト比較は維持する。梱包時はUTF-8の `.txt` も既存JSONと同じ改行正規化対象にする。実CRLF checkoutで両生成検査、PowerShell5.1 / 7 と StrictMode を有効にした配布関数経由の再生成を行い、従来のJava SHA-256 `3dde535504b6609c83ad614005832e0f63b65fd7faf1915a495ececca1294773`、Bedrock SHA-256 `3f8ea4081da681f77a33057fb44c64ace1c4dc707d111474aafd59008b07459e` と一致することを確認する。調整役が並行して修正した場合も、検証後に状態を更新する。
- 修正対象候補: `複数`
- 修正可否: `自動修正可`
- 確信度: `高`
- 修正状態: `修正済み`
