### AR-CODE-001 [高] ローカル強化と修復の投入順が同一アカウントで保証されない
- 種別: `バグ/アルゴリズム`
- 対象: `10_plugin/AstralRecord/src/main/java/io/github/maaasu/astralRecord/feature/mutation/service/LocalMutationOutbox.java:106`
- 関連箇所: `10_plugin/AstralRecord/src/main/java/io/github/maaasu/astralRecord/feature/item/service/OrbService.java:2293`
- 根拠: `LocalMutationOutbox.dispatch()` は `executor.execute(...)` で非同期に送信を開始し、`inFlightByAccount` が直列化するのは outbox 内の pending command だけである。`OrbService.executeCandidate()` は `ENHANCE` かつ outbox 接続時だけローカル経路へ入り、`REPAIR` は `startAsyncMutation()` へ進む。`pendingOrbAccounts` も従来の応答不明 recovery が `pendingOrbOperations` に登録された場合だけ設定されており、ローカル outbox の未ACK件数を判定していない。
- 問題: ローカル強化 A の結果表示・outbox保存後、outbox dispatch が account の外部操作境界を取得する前に修復 B が開始されると、B が先に `InventorySaveCoordinator` の境界と lane を取得できる。lane 自体は直列でも、プレイヤーの操作順ではなく各経路の受付順で実行されるため、A→B の順序を保証しない。
- 影響: 修復が強化より先に API へ確定し、API応答が古い強化値を返す。後続の強化が古い状態を基準に作られ、拒否・表示巻き戻し・操作結果の欠落につながる。
- 修正方針: 同一 account の全装備 mutation（ローカル outbox と従来API経路）を共通 FIFO へ投入し、ローカル outbox の pending を含めて後続操作を同じ順序で処理する。修復も即時ローカル化するか、少なくとも outbox 前後の受付境界を共通化する設計判断が必要。
- 修正対象候補: `複数`
- 修正可否: `設計判断待ち`
- 確信度: `高`
- 修正状態: `未修正`

### AR-CODE-002 [高] 修復のAPI応答が未送信ローカル強化のキャッシュを上書きする
- 種別: `バグ/アルゴリズム`
- 対象: `10_plugin/AstralRecord/src/main/java/io/github/maaasu/astralRecord/feature/item/service/ItemService.java:751`
- 関連箇所: `20_api/AstralRecordApi/AstralRecordApi/Repositories/EquipmentOrbOperationRepository.cs:232`
- 根拠: `ItemService.mergeOrbOperationResult()` は API 応答に装備があれば、操作種別や outbox の未ACK状態を確認せず `cacheEquipmentMutationResult(result.getEquipment())` を実行する。`applyLocalEquipmentInstance()` はキャッシュへ装備を置くだけで、強化の pending 世代を別管理していない。一方、API の `REPAIR` はDB上の現在の `EnhanceLevel` を変更せず、その値を含む装備を応答する。
- 問題: 初期強化値0で A（ローカル強化、base=0/target=1）を保存した直後に、A未確定のまま B（修復）がAPIで処理されると、Bの応答は強化値0となり、Plugin cache の強化値1を0へ戻す。その後の C は強化値0を基準に command を作るため、A確定後のAPI状態1に対する base 検証で `INVALID` になり得る。
- 影響: 強化を高速に連続実行した場合、後続強化が消費済み表示だけ残して確定しない、または一時的に強化値が巻き戻って見える。APIの base state 検証が不整合を検出するため、無言の二重適用にはなりにくいが、意図した操作列を保持できない。
- 修正方針: 装備個体ごとにローカル mutation の世代・期待状態を保持し、古いAPI応答で新しいローカル状態を上書きしない。共通 FIFO で順序を保証する場合も、応答マージ時に世代を確認して stale response を破棄する。
- 修正対象候補: `複数`
- 修正可否: `設計判断待ち`
- 確信度: `高`
- 修正状態: `未修正`

### AR-CODE-003 [中] ローカル強化の連続処理がメインスレッドで全outbox再書込みとforceを行う
- 種別: `パフォーマンス`
- 対象: `10_plugin/AstralRecord/src/main/java/io/github/maaasu/astralRecord/feature/mutation/service/LocalMutationOutbox.java:80`
- 関連箇所: `10_plugin/AstralRecord/src/main/java/io/github/maaasu/astralRecord/feature/item/service/OrbService.java:2383`
- 根拠: GUIクリックから `startLocalEnhancement()` が同期的に `outbox.enqueue()` を呼び、`enqueue()` は `persistLocked()` を完了してから戻る。`persistLocked()` は pending 全件を一時ファイルへ再出力し、`FileChannel.force(false)` と rename を実行する。複数回適用では `completeMutation()` から `continueBatchMutation()`、`executeCandidate()` が同期的に次回を開始するため、このI/Oが回数分繰り返される。
- 問題: API待ちは非同期でも、強化1回ごとにメインスレッドで同期ディスクI/Oとfsync相当の処理が発生する。pending件数が増えるほど毎回全件再書込みとなり、連続処理では処理量が累積する。
- 影響: 大量連続強化時に Bukkit tick が停止または遅延し、GUI入力遅延やサーバー全体のラグを発生させる。バイナリ形式だけではこの同期I/Oの待ち時間は解消しない。
- 修正方針: 追記型 journal または専用書込み executor へ移し、ローカル結果を表示する前に必要な耐久境界だけを保証する。複数回適用は一括永続化できる単位を設け、全件再書込みとforceを毎回行わない設計にする。
- 修正対象候補: `複数`
- 修正可否: `設計判断待ち`
- 確信度: `高`
- 修正状態: `未修正`

### AR-CODE-004 [中] ローカル強化と修復を混在させた連続操作のテストがない
- 種別: `テスト不足`
- 対象: `10_plugin/AstralRecord/src/test/java/io/github/maaasu/astralRecord/feature/item/service/OrbServiceLifecycleTest.java:1624`
- 関連箇所: `10_plugin/AstralRecord/src/test/java/io/github/maaasu/astralRecord/feature/mutation/service/LocalMutationOutboxTest.java:27`
- 根拠: `OrbServiceLifecycleTest.Harness` は `OrbService` を生成するが `setMutationOutbox()` を呼んでいないため、同テストの複数回強化シナリオはローカルoutbox経路ではなく従来API経路を実行する。`LocalMutationOutboxTest` はバイナリ保存・再読込・ACKを確認するが、REPAIRとの受付順、キャッシュ応答の上書き、メインスレッドでの連続I/Oは確認していない。
- 問題: 現行のテストが成功しても、A（ローカル強化）→B（修復）→C（ローカル強化）の競合、outbox dispatch未開始中の修復、連続件数増加時の書込み負荷を検出できない。
- 影響: 実サーバーの負荷やネットワーク遅延時だけ再現する順序不整合を、回帰テストで防げない。
- 修正方針: outbox と制御可能な executor を Harness に接続し、ローカル強化を保存した直後に修復を投入するテスト、stale応答で強化値が戻らないテスト、連続件数とメインスレッドI/O境界を追加する。
- 修正対象候補: `10_plugin/AstralRecord/src/test/java/io/github/maaasu/astralRecord/feature/item/service/OrbServiceLifecycleTest.java`
- 修正可否: `自動修正可`

- 修正状態: `未修正`
