### AR-CODE-001 [中] 旧日時精度の退避DBを復旧モードで検証していない
- 種別: `テスト不足`
- 対象: `60_tool/db-reset-except-release-notes/tests/db-reset-except-release-notes.integration.ps1:332`
- 関連箇所: `60_tool/db-reset-except-release-notes/Program.cs:104`
- 根拠: テストは265〜295行で保持2表を `datetime2(7)` にしてから300行で通常リセットを成功させ、330行でその退避DBを削除しています。その後333行の注入失敗時に作成される退避DBは、既に再作成済みの `datetime2(3)` スキーマから取得されます。従って350行の `--restore-backup` は本番で停止した `datetime2(7)` 退避DBを通りません。
- 問題: 本番で必要になる「旧 `datetime2(7)` の退避後に再作成が失敗し、`--restore-backup` で復旧する」経路が回帰テストされていません。
- 影響: `LoadExistingBackupAsync`、復旧モードの事前検査、または復旧時の型判定に変更が入っても、旧精度の保持データを復元できない回帰を検出できません。本番ではDBが `OFFLINE` のまま手動復旧を要します。
- 修正方針: `datetime2(7)` の8列とサブミリ秒値を投入した直後のリセットを `--fail-after-astral-record-rebuild` で失敗させ、その保持済み退避DBを `--restore-backup` で復旧するシナリオを追加する。復旧後に8列の `datetime2(3)` と変換後値、行数、マーカー・一時DBの削除、`MULTI_USER` を確認する。
- 修正対象候補: `60_tool/db-reset-except-release-notes/tests/db-reset-except-release-notes.integration.ps1`

### AR-CODE-002 [低] 精度縮小時の丸めと全8列の値を検証していない
- 種別: `テスト不足`
- 対象: `60_tool/db-reset-except-release-notes/tests/db-reset-except-release-notes.integration.ps1:282`
- 関連箇所: `60_tool/db-reset-except-release-notes/Program.cs:1071`
- 根拠: 8列は `datetime2(7)` に変更しますが、値を検証するのは `release_note.published_at_utc` だけです（313〜321行）。`lease_until_utc` と `sent_at_utc` にはNULLを入れており、他の6列も変換値・scaleを検証しません。`CONVERT(datetime2(3), ...)` は SQL Server で .1235000 を .124、.9995000 を次秒へ丸めますが、テスト値 .1234567 はこの境界を通りません。
- 問題: nullable列の非NULL値、各Outbox日時列、半ミリ秒境界と秒繰上がりの変換結果が未検証です。
- 影響: 列ごとの変換式、nullable値の変換、または将来の式変更で丸め規則が変わっても、保持データの日時が意図せず変わる回帰を検出できません。
- 修正方針: 8列すべてに非NULLの `datetime2(7)` 値を設定し、nullable列については別行でNULLも確認する。少なくとも `.1235000` と `.9995000` を使い、復元後の各列値とscale=3を明示的に比較する。READMEにも精度縮小がSQL Serverの丸めを伴うことを記載する。
