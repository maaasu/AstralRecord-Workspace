### AR-CODE-001 [高] UTC付き習得スキルACKが保存基準へ反映されない
- 種別: `バグ/アルゴリズム`
- 対象: `10_plugin/AstralRecord/src/main/java/io/github/maaasu/astralRecord/feature/skill/service/LearnedSkillService.java`
- 関連箇所: `10_plugin/AstralRecord/src/main/java/io/github/maaasu/astralRecord/feature/inventory/state/InventoryPersistence.java`
- 根拠: API が返した `updatedAt` は UTC の `Z` 付きだったが、ACK処理は offset なし専用の `LocalDateTime.parse` を使い、例外を握りつぶしていた。
- 問題: SQL保存済みの新規習得スキル version を保存基準へ反映せず dirty を残したまま snapshot 自体を完了扱いにするため、次便が `expectedVersion=null` を再送して 409 になる。
- 影響: スキル設定失敗を起点に account が block され、アイテム取得、クエスト受領、GUI操作など後続の基本操作が失敗する。
- 修正方針: API日時の共通解析を追加し、ACKの日時を反映する。不完全または解釈不能なACKは握りつぶさず保存境界へ伝播する。
- 修正対象候補: `複数`
- 修正可否: `自動修正可`
- 確信度: `高`
- 修正状態: `修正済み`

### AR-CODE-002 [高] Optional sectionの不完全ACKを成功扱いできる
- 種別: `バグ/アルゴリズム`
- 対象: `10_plugin/AstralRecord/src/main/java/io/github/maaasu/astralRecord/feature/inventory/state/PlayerStateSnapshot.java`
- 関連箇所: `10_plugin/AstralRecord/src/main/java/io/github/maaasu/astralRecord/feature/skill/service/SkillBindPresetService.java`
- 根拠: section共通検証は要求した明細が含まれることだけを確認し、余分な明細を許可していた。複数のparticipant ACK処理は形不正やID不一致で例外を上位へ返さず終了していた。
- 問題: 習得スキル、バインド、スキルツリー、冒険記録などの不完全な200 ACKでも pending snapshotを破棄でき、冒険記録では送信delta未満の累計も受領できる。
- 影響: Pluginの保存基準とSQL正本がずれ、後続保存の競合、進行消失、基本操作の継続的なblockにつながる。
- 修正方針: 送信集合とACK集合を完全一致で検証し、冒険記録の累計下限を検証する。participantの契約不一致は例外として保存境界へ伝播する。
- 修正対象候補: `複数`
- 修正可否: `自動修正可`
- 確信度: `高`
- 修正状態: `修正済み`

### AR-CODE-003 [中] Offset付きACK日時がUTCの同一時刻にならない
- 種別: `バグ/アルゴリズム`
- 対象: `10_plugin/AstralRecord/src/main/java/io/github/maaasu/astralRecord/infrastructure/util/ApiDateTimeUtil.java`
- 関連箇所: `00_docs/10_Plugin設計書/feature/03-player/3-メソッド仕様/03_3-保存.md`
- 根拠: `OffsetDateTime.toLocalDateTime()` は offset を除くだけで、`2026-09-08T17:12:53+09:00` をSQL UTC値と同じ `08:12:53` へ変換しない。
- 問題: UTC以外のoffsetを持つACKを次回の `expectedUpdatedAt` に使うと、同一瞬間でも異なる日時として送信する。
- 影響: APIの楽観ロック比較が409となり、正常保存後に後続操作がblockされる可能性がある。
- 修正方針: offset付き値をUTCの同一瞬間へ正規化してから `LocalDateTime` に変換し、offsetなし、Z、+09:00の回帰テストを追加する。
- 修正対象候補: `10_plugin/AstralRecord/src/main/java/io/github/maaasu/astralRecord/infrastructure/util/ApiDateTimeUtil.java`
- 修正可否: `自動修正可`
- 確信度: `高`
- 修正状態: `修正済み`

### AR-CODE-004 [高] 重要操作の不正200 ACKで保存済み結果をロールバックする
- 種別: `バグ/アルゴリズム`
- 対象: `10_plugin/AstralRecord/src/main/java/io/github/maaasu/astralRecord/feature/inventory/state/InventoryPersistence.java`
- 関連箇所: `10_plugin/AstralRecord/src/main/java/io/github/maaasu/astralRecord/feature/inventory/service/InventorySaveCoordinator.java`
- 根拠: `saveCriticalNow` はACK契約不一致で作成したpending/blocked snapshotも無条件で除去してfalseを返し、coordinatorはローカル変更を操作前へ戻していた。
- 問題: HTTP 200時点でSQL transactionは完了している可能性があるため、SQLは完成状態、Pluginは操作前状態となり、blockも解除される。
- 影響: アイテムや通貨の二重反映、再操作による重複消費、再ログイン時の状態反転が発生し得る。
- 修正方針: 不正200 ACKは固定結果を一度照会する。確定できなければACK不一致を他の4xx・通信失敗と区別してpending/blockedと完成ローカル状態を保持し、rollbackしない。
- 修正対象候補: `複数`
- 修正可否: `自動修正可`
- 確信度: `高`
- 修正状態: `修正済み`

### AR-CODE-005 [高] 重要操作のpre-saveが同時発生した通常変更で失敗する
- 種別: `バグ/アルゴリズム`
- 対象: `10_plugin/AstralRecord/src/main/java/io/github/maaasu/astralRecord/feature/inventory/service/InventorySaveCoordinator.java`
- 関連箇所: `10_plugin/AstralRecord/src/main/java/io/github/maaasu/astralRecord/feature/guide/service/GuideService.java`
- 根拠: `executeCriticalMutation` のpre-saveだけは `saveNow` を一回実行した直後にpending変更を検出すると失敗する一方、同クラスには差分が落ち着くまで再保存する `awaitStablePreSave` が既にある。
- 問題: snapshot capture後からACKまでにガイド、冒険記録、クエスト進行、経験値、設定変更が入ると、先行保存が成功していても `pre-save failed` になる。初回案内具付与直後の `PLAYER_LOGGED_IN` 記録もこの条件を満たす。
- 影響: 混雑や通常プレイ中のイベント発生頻度に応じて、案内具付与、クエスト、報酬、強化などの重要操作が断続的に失敗する。
- 修正方針: critical pre-saveを既存の `awaitStablePreSave` に統一し、capture中に増えた通常変更を次便まで確定してから重要操作を開始する。
- 修正対象候補: `10_plugin/AstralRecord/src/main/java/io/github/maaasu/astralRecord/feature/inventory/service/InventorySaveCoordinator.java`
- 修正可否: `自動修正可`
- 確信度: `高`
- 修正状態: `修正済み`

### AR-CODE-006 [高] 結果不明のHTTP 425が通常保存を永久ブロックする
- 種別: `仕様不整合`
- 対象: `10_plugin/AstralRecord/src/main/java/io/github/maaasu/astralRecord/feature/inventory/state/InventoryPersistence.java`
- 関連箇所: `10_plugin/AstralRecord/src/main/java/io/github/maaasu/astralRecord/feature/mutation/repository/PlayerStateRepository.java`
- 根拠: repositoryは425を結果不明として固定ACK照会と同一snapshot再送の対象にするが、最終的に425を返すとpersistenceは408/429以外の確定4xxとしてblocked snapshotへ分類する。
- 問題: 設計書が結果不明と定義する425だけで、通常保存の同一pending snapshot再試行が永久停止する。
- 影響: 混雑時の425を起点にaccountがblockされ、アイテム取得、クエスト、GUIなど基本操作を継続できなくなる。
- 修正方針: 確定4xxのblocked判定から425を除外し、pending snapshotと指数backoffを維持して通常保存から再試行する回帰テストを追加する。
- 修正対象候補: `10_plugin/AstralRecord/src/main/java/io/github/maaasu/astralRecord/feature/inventory/state/InventoryPersistence.java`
- 修正可否: `自動修正可`
- 確信度: `高`
- 修正状態: `修正済み`

### AR-CODE-007 [高] 結果照会の不正200 ACKがHTTP 425へ誤分類される
- 種別: `仕様不整合`
- 対象: `10_plugin/AstralRecord/src/main/java/io/github/maaasu/astralRecord/feature/mutation/repository/PlayerStateRepository.java`
- 関連箇所: `10_plugin/AstralRecord/src/main/java/io/github/maaasu/astralRecord/feature/inventory/state/InventoryPersistence.java`
- 根拠: POST 425後の結果照会がHTTP 200かつ構造不正の場合、private `findCompleted` は `PlayerStateAcknowledgementException` も他の照会失敗と同じく握り潰してnullを返し、最終的に元の425を投げる。
- 問題: GET 200のACK契約不一致が結果不明425へ変換され、通常保存のpending/backoff対象となる。
- 影響: 不正・不完全な200応答でaccountをblockする契約が働かず、検証不能な保存結果のまま同じsnapshotを再送し続ける。
- 修正方針: 結果照会の `PlayerStateAcknowledgementException` は握り潰さず伝播する。GET 404や通信失敗は従来どおり元の結果不明応答へ戻し、再試行を維持する回帰テストを追加する。
- 修正対象候補: `10_plugin/AstralRecord/src/main/java/io/github/maaasu/astralRecord/feature/mutation/repository/PlayerStateRepository.java`
- 修正可否: `自動修正可`
- 確信度: `高`
- 修正状態: `修正済み`
