### AR-DOC-003 [中] API 404 の扱いがリポジトリ仕様と運用方針で矛盾している
- 修正状態: 未修正
- 種別: `矛盾`
- 対象: `00_docs/10_プラグイン設計書/feature/08-inventory/3-メソッド仕様/08_3.04-リポジトリ.md:11`
- 関連箇所: `00_docs/10_プラグイン設計書/feature/08-inventory/5-例外・ログ・運用/08_5.00-例外・ログ・運用.md:23` / `00_docs/10_プラグイン設計書/feature/08-inventory/3-メソッド仕様/08_3.05-タスク・補助.md:58`
- 根拠: `InventoryRepository.findByAccountId` は `GET /api/inventory?account_id={accountId}` の `404` を `500` と同じくエラー扱いにするとしている。一方、例外・運用方針は API の `404` を「一覧取得では空レスポンス、単体取得では null」と扱うと定義している。さらに `InventoryPersistence.load(accountId)` は join 時に inventory 一覧を取得して state を構築する責務を持つため、この 404 方針の違いが join ロードの成否に直結する。
- 問題: 同じ一覧取得 404 が「エラー」と「空レスポンス」の両方として設計されている。
- 影響: 新規アカウントや未作成 inventory の join 時に、空 state として継続するのか、永続化失敗として WARN を出すのかが実装者によって分かれる。結果として初回 inventory 補完、dirty state、後続 save の振る舞いが安定しない。
- 修正方針: 一覧取得の 404 を空一覧として扱うか、エラーとして扱うかを一方に統一する。運用方針に合わせるなら `findByAccountId` の 404 は空一覧、`findEntries` の 404 は対象 inventory 未存在として空一覧または null 相当の扱いにそろえ、WARN の対象から外す条件も明記する。
- 修正対象候補: `08_3.04-リポジトリ.md`, 必要に応じて `08_5.00-例外・ログ・運用.md`
- 修正可否: `要確認`
