### AR-CODE-001 [高] 2表の退避が同一時点のスナップショットにならない
- 種別: `バグ/アルゴリズム`
- 対象: `60_tool/db-reset-except-release-notes/Program.cs:232`
- 関連箇所: `60_tool/db-reset-except-release-notes/Program.cs:195, 60_tool/db-reset-except-release-notes/README.md:54`
- 根拠: `BackupReleaseNotesAsync` は `release_note` と `release_notification_outbox` を別々の `SELECT INTO` でコピーするが、トランザクション・snapshot isolation・対象DBの排他を開始していない。`ValidateConnectivityAsync` はmasterへ接続して直ちに切断するだけである。APIは `EnableRetryOnFailure` を有効にしており、Release Note workerも稼働中は定期的にOutboxを取得・更新する。
- 問題: 2回のコピーの間に公開、通知取得、通知状態更新が入ると、親子表の組合せが単一時点の状態ではなくなる。退避件数と復元件数は同じでも、復元したOutboxが対応するRelease Noteや通知状態と整合しない状態を残し得る。
- 影響: 「公開・通知状態を保持する」という操作目的を満たせず、再作成後に通知の欠落、重複、または意図しない再送につながる。
- 修正方針: API/Webの停止を実行前提として実効的に確認した上で、保持2表を同一トランザクションの一貫性レベルで退避する。少なくとも退避開始から完了までAstralRecordへの書込みを排他する。
- 修正対象候補: `60_tool/db-reset-except-release-notes/Program.cs, 60_tool/db-reset-except-release-notes/README.md`
- 修正可否: `要確認`

### AR-CODE-002 [高] 退避後の失敗を同じコマンドで再実行すると元退避DBを復元しない
- 種別: `バグ/アルゴリズム`
- 対象: `60_tool/db-reset-except-release-notes/Program.cs:37`
- 関連箇所: `60_tool/db-reset-except-release-notes/Program.cs:214, 60_tool/db-reset-except-release-notes/README.md:56`
- 根拠: 退避DB名は実行中の `backup` 変数だけに保持される。再実行時は毎回 `BackupReleaseNotesAsync` を実行し、既存の `AstralRecord` があればその時点の2表を新しい退避DBへコピーし、存在しなければ `null` を返す。READMEは途中失敗後に「同じコマンドを再実行」と案内するが、保持された元退避DBを選択または復元する入力・探索・手順はない。
- 問題: 初回がAstralRecord削除後または復元前に失敗した場合、再実行は元退避DBを使わず、空または途中状態の新しいDBから処理を完了できる。元データは旧退避DBに残っていても、成功メッセージは新しい空/途中状態を「保持した」と報告する。
- 影響: 障害回復のために文書どおり再実行すると、Release Noteの公開・通知状態が復元されず、保持目的が失われる。
- 修正方針: 退避DB名を明示指定して復旧モードで復元できるようにするか、未完了退避DBを検出して通常実行を拒否し、元退避DBを使う復旧手順をREADMEへ明記する。
- 修正対象候補: `60_tool/db-reset-except-release-notes/Program.cs, 60_tool/db-reset-except-release-notes/README.md, 60_tool/README.md`

### AR-CODE-005 [高] 保守マーカーの所有権を判別せず別実行の隔離を解除できる
- 種別: `バグ/アルゴリズム`
- 対象: `60_tool/db-reset-except-release-notes/Program.cs:356`
- 関連箇所: `60_tool/db-reset-except-release-notes/Program.cs:414, 60_tool/db-reset-except-release-notes/Program.cs:1334`
- 根拠: `EnterApplicationOfflineAsync` は既存の `app_offline.htm` に固定の `MaintenanceFiles.Marker` が含まれていれば、そのマーカーを作成していない実行でも処理を続行する。返される `ApplicationOfflineGuard` は既存マーカーを含む全パスを保持し、`ExitApplicationOfflineAsync` は固定マーカーを含むファイルを削除する。マーカー内容には実行または退避DBを識別する値がない。
- 問題: リセットを並行実行すると、後から開始した実行も先行実行のマーカーを自分のものとして受け入れ、両方が破壊的DB操作を開始できる。先に終了した実行は、もう一方が使用中のマーカーを削除する。別のリセットが障害で残したマーカーも、対応する復旧操作かを確認せずに削除される。
- 影響: API/Webが再開した状態で別実行が再構築・復元を続け、Release Note退避・復元または再作成中のDBの整合性を損なう。
- 修正方針: 実行単位の所有IDと全リセット実行を直列化する排他制御を導入する。既存マーカーは原則として処理を拒否し、復旧時に引き継ぐ場合だけ退避DBと所有IDの対応を検証してから削除可能にする。
- 修正対象候補: `60_tool/db-reset-except-release-notes/Program.cs, 60_tool/db-reset-except-release-notes/tests/db-reset-except-release-notes.integration.ps1, 60_tool/db-reset-except-release-notes/README.md`

### AR-CODE-006 [中] リセット完了後のapplock解放失敗で正常なDBをOFFLINEに戻す
- 種別: `バグ/アルゴリズム`
- 対象: `60_tool/db-reset-except-release-notes/Program.cs:122`
- 関連箇所: `60_tool/db-reset-except-release-notes/Program.cs:113, 60_tool/db-reset-except-release-notes/Program.cs:1548`
- 根拠: 正常経路はRelease Note復元・退避DB削除・`MULTI_USER`復帰・`app_offline.htm`削除を終えた後に `ApplicationOfflineGuard.DisposeAsync` を呼ぶ。`ResetLockHandle.DisposeAsync` は `sp_releaseapplock` の実行失敗または負の結果を再送出し、外側のcatchは `rebuildStarted` がtrueであるため `IsolateFailedDatabaseAsync` を実行する。`DisposeAsync` のfinallyは接続を破棄するため、セッション所有のapplockは接続破棄時にも解放される。
- 問題: SQL接続断などで明示的なapplock解放だけが失敗した場合、DB再作成と復元はすでに完了し、保守マーカーも削除済みであるにもかかわらず、catchが正常なAstralRecordを `OFFLINE` にし、存在しないマーカーを「保持した」と案内する。
- 影響: 成功済みのリセットが一時的なロック解放通信障害だけで障害状態となり、API/Webは公開済みなのにDBだけが停止する。余計な手動復旧とプレイヤー操作停止が発生する。
- 修正方針: DB再構成完了を示す状態を明示し、applock解放時の通信失敗は接続破棄によるセッションロック解放を行ったうえで正常完了扱いまたは非破壊的な警告にする。少なくとも復元・`MULTI_USER`・マーカー削除完了後は失敗隔離処理を実行しない。
- 修正対象候補: `60_tool/db-reset-except-release-notes/Program.cs, 60_tool/db-reset-except-release-notes/tests/db-reset-except-release-notes.integration.ps1`
- 修正可否: `自動修正可`

### AR-CODE-007 [高] 任意のresume-operationで退避を省略して保持対象を削除できる
- 種別: `バグ/アルゴリズム`
- 対象: `60_tool/db-reset-except-release-notes/Program.cs:65`
- 関連箇所: `60_tool/db-reset-except-release-notes/Program.cs:411, 60_tool/db-reset-except-release-notes/Program.cs:1290`
- 根拠: `--resume-operation` は32桁16進数であることだけを検証する。`EnterApplicationOfflineAsync` は復旧モードで既存マーカーがない場合に新しい実行ID付きマーカーを作成して成功する。続く分岐は `ResumeOperationId` があるだけで `BackupReleaseNotesAsync` を呼ばず、未完了退避DBがないことだけを確認して3DBを再作成する。
- 問題: 保守マーカーが残っていない通常状態でも、任意の32桁16進数を付けた `--resume-operation` を実行すると、既存の `release_note` と `release_notification_outbox` を退避せずにAstralRecordを削除できる。実際に失敗した「退避なし」操作の隔離を引き継いでいることを確認していない。
- 影響: 誤操作または古い復旧コマンドの実行だけで、保持対象として約束したRelease Note公開・通知情報を復元不能に失う。
- 修正方針: `--resume-operation` は全対象ルートに当該実行IDと完全一致する既存マーカーがある場合だけ受け付け、1つでも存在しない場合は退避を省略せず通常の退避を行うか、明示的に停止する。統合テストでマーカーなしの任意resume-operationが再構築前に拒否されることを検証する。
- 修正対象候補: `60_tool/db-reset-except-release-notes/Program.cs, 60_tool/db-reset-except-release-notes/tests/db-reset-except-release-notes.integration.ps1, 60_tool/db-reset-except-release-notes/README.md`
