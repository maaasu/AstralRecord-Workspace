## 指摘一覧

### AR-CODE-001 [中] 保存中に再変更された entry が API の新しい楽観ロック版を受け取れない
- 種別: `バグ/アルゴリズム`
- 対象: `10_plugin/AstralRecord/src/main/java/io/github/maaasu/astralRecord/feature/inventory/service/InventoryService.java:4303`
- 関連箇所: `10_plugin/AstralRecord/src/main/java/io/github/maaasu/astralRecord/feature/inventory/state/PlayerInventoryState.java:293`
- 根拠: `00_docs/20_API設計書/feature/13-inventory/3-エンドポイント仕様/13_3.03-更新系.md` の一括置換仕様は既存 entry の `expectedUpdatedAt` と DB 正本の一致を必須とする。`InventoryAutoSaveTask` は保存をアカウント別キュー上で非同期実行し、API 応答中にも gameplay 側の state 更新が起こり得る。今回の変更で `withQuantity` / `withSlot` は正しく保存成功まで旧版を保持するが、応答処理は current entry が submitted entry と完全一致する場合しか persisted entry を反映しない。
- 問題: 保存送信後に同じ entry の数量または slot が再変更されると、`acknowledgePersistedEntries` は変更内容を守るため API 応答全体を破棄する。このとき新しい `updatedAt` まで破棄され、再変更後の entry は送信時の古い版のままとなる。次回保存ではその古い版を `expectedUpdatedAt` に送り、直前の保存で更新済みの DB 正本と不一致になる。
- 影響: オートセーブ中にアイテム取得・消費・移動が重なるプレイヤーで、次回以降の一括保存が楽観ロック不一致として拒否され、dirty state の再試行と WARN が継続する。今回追加された単体テストはローカル変更直後の版だけを確認しており、この保存応答との競合経路を検出できない。
- 修正方針: submitted と異なる current entry では数量・slot・metadata 等の current 値を維持しつつ、同じ entry ID の persisted `updatedAt` だけを反映する。entry が保存待ち中に削除・別 inventory へ移動した場合は反映しない条件を明示し、保存中の再変更後に次回 request が API 応答の版を送る回帰テストを追加する。
