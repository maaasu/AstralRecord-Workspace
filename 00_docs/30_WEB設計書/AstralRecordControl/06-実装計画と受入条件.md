# 06 実装計画と受入条件

## 実装開始の共通条件

この設計書を入力に、通常の統合入口で段階ごとに独立した実装作業を行う。設計書があるだけで未実装のAPI/サービスを利用可能と扱わない。変更する段階の03 DTO/02経路/05画面を揃える。

各段階は「成果物が存在する」「受入条件を再現できる」「新規の説明不能な警告がない」「独立レビュー済み」を完了条件とする。Contract/状態/予約/データ保全/認証境界を重点検証し、表示コピーを写すだけのテストは作らない。実サーバーを使わないfixtureと、一時sandboxサーバーの確認を分ける。

### 受入条件

- ゲーム/API/SQLを停止したfixtureでもログインし、登録済みHostの状態を取得できる。
- owner2件目作成、未登録TOTP、CookieでAgentを名乗る要求、Agent tokenで管理画面へ入る要求を拒否する。
- 旧Agent tokenと既存接続が無効化される。owner reset後の旧Cookieは次要求で拒否される。
- PCごとに異なるHostが登録され、dev-pcへdev、mc-pcへchannel1/channel2を割当可能。
- 古いconnectionEpoch/別Hostのtransfer/未知schemaを拒否する。初回失敗と長時間切断から再接続できる。
- config反映失敗では旧適用版を保持し、希望版と混同しない。Agent DB巻戻りを要復旧として止める。

## P1: Runner・基本運転・共通gate

### 実装単位

| ticket | 所有範囲 | 入出力/成果物 |
|---|---|---|
| C1-01 | Runner supervisor/ledger/log | Java直接起動、stdin/out/err、Session/stateRevision、残存プロセス照合 |
| C1-02 | Agent Inbox/Outbox、Web dispatch/UI | durable受付/完了、operationId/hash、開始期限、console、ライブ/ファイルログ |
| C1-03 | Web reservation、Agent/Runner gate、Cli | 全資源準備、fence、永続hold、ローカル緊急復旧、監査 |
| C1-04 | 既存01/02/03/16/17の入口 | 共通gate参加/継承、子処理のrun参照、停止状態確認、未対応時拒否 |

P1の変更操作有効化はC1-04完了後。共通gateを後からP4で追加する順序にはしない。未改修の旧入口が使える環境へ、変更可能なControl管理を展開しない。

### P1の実装範囲

2026-10-18実装。C1-01〜03は`30_web/AstralRecordControl`、C1-04は`60_tool/control-gate`と既存入口、配布・marker・停止確認付きRunner更新は`60_tool/control-deploy`。Web/Agent/Runnerはschema2へbackup付きtransaction migrationを行う。

JavaのStart/Stop/Restart/Kill/ConsoleCommand、Session/実行台帳、ログcursor/分割/保持、異常再起動抑止、永続予約/Host別fence、durable再送照合、ローカルOS管理者の点検・復旧、操作/保守画面を提供する。Console成功はstdin書込完了。停止timeoutでは自動Killせず、明示的な救済または終了照合までholdを保持する。

Web/Runnerの変更操作は既定無効。全HostのP1能力と固定ProgramData markerを導入確認してから有効化する。01/02/03/16/17は直接PowerShell入口もgateへ参加し、runtimeServerIdと配布pathの完全なbindingを必要とする。01/16と03停止モードの保守内Startは起動待ち段階だけ許可し、17中のStopや任意の保守内操作を許可しない。未知のPrepare結果を期限だけで解放せず、同じrunと予約で照合する。

依存チェーンの自動起動停止・一括運転・AstralReady・Bedrock/Velocityの種類別運転はP4へ割り当てる。P1では依存設定を無視して起動せず、非対応設定/操作を明示拒否する。ファイル編集・バックアップ等はP2以降のまま。

検証は.NET 10 Releaseの全project、一時HTTPSのWebSockets/LongPolling、実named pipe、専用テストプロセス、6系統のPowerShell fixtureを使用する。既存Minecraftの起動停止、実サービス登録、marker更新、実PC配布は今回の自動検証に含めない。サービスアカウント権限・実Javaの起動profile・TLS・停止方式は導入時のDev pilotで確認する。

P1最終検証は全128件成功、skipなし、ビルド警告なし。Contracts23、Authentication12、Inventory13、Agent18、Runner31、Operations16、Cli11、Integration4。実HTTPSではCLI資格情報の発行/失効・用途分離、Owner操作→Agent→Runner、保守内Start、通常Stop/Start/Console、ログと画面、Agent失効後のプロセス継続を確認した。PowerShell6系統、変更script16本の構文検査、ログ更新JSの構文検査も成功。Web/Agent/Runner/CliのWindows x64自己完結publish4種とpackage検査を通過した。独立レビューの指摘12件は修正し、対象再確認済み。

### 受入条件

- 実サーバーと無関係なテストプロセスでStart/Stop/Restart/Kill、1PC複数プロセス、Session/設定版の誤対象拒否を確認する。
- Web/Agentを停止してもRunnerがログを読み続け、プロセスが継続する。再接続で操作状態とログcursorが回復する。
- Runner異常終了後の残存プロセスをUnmanagedとし、PID再利用で他プロセスをkillしない。二重起動を拒否する。
- stdin書込境界で障害を注入し、結果不明のConsoleCommandを自動再送しない。
- 同ID同hash再送は重複実行せず、同ID異なる入力を拒否する。期限切れ命令を復帰時に開始しない。
- Web操作、予約、01/02/03/16/17直接実行が同一資源で競合し、片方が副作用前に拒否される。02の公開もEnvironment予約に含める。hold取得途中の切断で開始しない。
- stop timeoutで自動Killせず、手動停止/保守hold中にcrash restartが走らない。

## 現行環境からの導入

新規Serverで一連のbackup/restore/障害復帰を検証してから既存データを停止snapshotで移す。既存Crafty側の該当サーバー自動起動/予約/直接起動経路を停止し、Control以外から二重起動しないことを確認する。Control実行時にCraftyを必要とすることはない。

最初はDevをpilotとしてP1/P2を検証し、その後チャンネルを登録する。共有API/masterを使う場合はDevでもEnvironmentを共通登録し、本番と無関係な検証と誤認しない。PC/DNS/証明書/Java実パス/既存runtimeServerId/保存先は導入時の必須検証項目とする。

本設計の追加コミットだけで実サーバーのCrafty停止・データ移動・サービス登録は行わない。

## P2実装の検証記録

P2はControlの専用作業ツリーで実装し、一時SQLite、HTTPS Kestrel、named pipe、使い捨てfixtureプロセスだけで検証する。ファイル境界/etag/文字コード/ZIP/manifest/世代保持/保護/容量不足、復元のPrepared・OriginalMoved・Installed・Completed境界とreceipt、Owner/Agent認可、再開offsetを対象とする。大容量はNTFS sparseの20GiB fixtureを検証済み転送stageに用意し、実SHA-256照合と全5120個の4MiB HTTP rangeを通して確認する。実サービス登録、既存Minecraft、実NAS、DB/API/公開状態の復旧は行わない。

最終検証: C#は全体167件と最後の追加回帰テストを含むAgent43件の再確認により、計168件が成功。20GiBの実HTTPS全域転送、JavaScript SHA-256の独立実装との比較1件、配布前検査/gateの2スイートも成功。Web/Agent/Runner/CLIのwin-x64自己完結publishを検証し、コンパイル警告なし。独立した2観点のレビューと第2回の修正確認を実施し、12指摘を解消した。
