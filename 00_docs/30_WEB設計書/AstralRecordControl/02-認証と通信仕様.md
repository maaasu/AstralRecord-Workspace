# 02 認証と通信仕様

## 認証境界

| 接続 | 認証/認可 | 制約 |
|---|---|---|
| Browser → Webの画面/API/UI Hub | Identity Cookie、`OwnerOnly` | 単一ownerの有効状態を確認。全機能同一権限 |
| Agent → WebのAgent API/Hub | HTTPS Bearer、`AgentOnly` | 認証トークンからhostId/credentialIdを決める |
| Cli → Webのgate API | Ownerの対話認証で取得する短期Cliトークン | gateと状態照会のみ。通常のServer操作/台帳編集はOwner Cookie |
| Agent/Cli → Runner | Windows named pipeの接続ACL | Agentサービス/ローカルOS管理者に限定。通信内容だけで呼出元を信用しない |

Agentトークンで管理画面へ入れない。CookieでAgentを名乗れない。HubのhostIdやgroup名を外部入力から採用しない。公開Web/ゲームAPIの認証・管理フラグは利用しない。

## Ownerの最小認証

- ASP.NET Core Identity、owner1件、パスワード＋TOTP必須。自己登録・招待・roleは提供しない。
- WebホストのOS管理者がCliの`owner create`で対話作成。パスワード/秘密をコマンド引数へ渡さない。TOTP未登録のCookieは登録画面とログアウトだけに使い、管理APIを許可しない。
- TOTP登録完了時に使い捨て回復コードを一度表示する。通常復旧はパスワード＋回復コード。全紛失時はWeb停止中にOS管理者が`owner reset`し、旧Cookie/旧回復コードを失効して再登録する。
- CookieはSecure/HttpOnly、SameSite=Lax、絶対有効期限8時間、SlidingExpiration=false。TOTP完了時にOwnerSessionを作り、CookieへsessionIdとsecurity stampを入れる。管理APIの各要求でsessionの失効/期限とIdentity security stampを検証する。ブラウザHubも同sessionへ束縛し、失効時に切断、60秒ごとと期限到達時にも検証する。
- ログアウトは現在sessionを、パスワード/MFAの再設定と`logout-all`は全sessionを失効する。セキュリティ設定変更は5分以内の再認証を要求する。通常の起動停止では追加MFAを毎回要求しない。
- ログイン失敗はIPごと5回/分、アカウントは連続10回失敗で5分ロック。エラーはアカウント存在有無を区別しない。IPは信頼済みproxyを明示した場合だけ転送ヘッダーから取得する。
- Cookie認証の変更HTTPにはantiforgeryを必須にする。HubでBrowserから変更命令を送れない。WebSocketのOriginも固定の管理Web originだけ許可する。
- Data Protection鍵は明示保存し、WindowsではDPAPI等の保存時保護を明示する。認証DB/TOTP/回復コード/バックアップ全体を機密扱いにしACLで保護する。別PC復旧は単純な鍵コピーを保証せず、CLI再構築・全session失効・Agent再登録を手順化する。

Cliトークンは`cli login`によるパスワード＋TOTP対話で発行する256bitのランダムopaque値、有効期限15分、サーバー側はhashのみ保存する。用途はControl gateと状態照会だけとし、Agent認証とは別scheme。保守の子処理は取得済みreservationを継承し、長い処理中にトークン期限切れだけで予約を解除しない。

## Agentの登録と失効

1. ownerがHostを作成し、トークン発行操作で256bitのランダム値を一度取得する。
2. WebはSHA-256 hashとcredentialId/hostIdだけ保存する。Agentはローカル対話設定で受け取り、サービスアカウントが復号できるDPAPI等で保護する。
3. AgentはTLS証明書を通常検証したHTTPSへBearerで接続する。証明書検証の無効化・URL queryへの秘密格納をしない。
4. Hostは有効な1接続を持つ。Hello成功時に新connectionEpochを採番し、旧接続を無効化する。新接続の再照合完了まで新規操作を送らない。
5. トークン無効化/Host無効化は新規要求の拒否と既存Hub接続の切断を同時に行う。すでに開始した安全なローカル処理はjournalへ残し、失効だけでJavaを強制終了しない。

Agentは失効した接続上の新規要求を実行しない。接続generationは転送/命令の送信時に検査し、保存済みOperation自体のhashには含めない。

## 共通HTTP契約

JSONはUTF-8、camelCase、厳密enum、未知/重複キー拒否、`Content-Type: application/json`。UUID/時刻/モデルは03が正本。`protocolVersion=1`は互換性のある項目でも未定義フィールドを送らない。不一致は明示拒否し、暗黙の古い挙動へfallbackしない。

設定変更は`If-Match: "{revision}"`を必須にし、競合は409 `StaleRevision`。作成は`If-None-Match: *`。POSTによる操作/転送/Workflow作成は`Idempotency-Key: {guid}`を必須とし、同じkey/同じ入力は元のIDと状態を返す。異なる入力なら409 `OperationConflict`。操作の終端後も保持期間内は同じkeyを別用途へ使わない。

エラーはProblemDetailsに`errorCode,operationId?,traceId,retryable`を追加する。400=型/パス/未知値、401=未認証/失効、403=scheme/用途不一致、404=対象なし、409=競合/復旧必須、413=容量上限、429=回数制限、503=Host未接続。内部stack/秘密を応答しない。

Bearerはnative .NET clientのAuthorizationヘッダーで送る。WebSocket upgradeにも固定Web originをOriginヘッダーで指定する。各要求の無効化状態を照合し、所有Host以外のtransfer/operationを拒否する。Browser向けAPIへ同じ資格情報を流用しない。

## SignalR v1

Agent Hub=`/hubs/control-agent/v1`、UI Hub=`/hubs/control-ui/v1`。Hubにはbyteファイルを流さない。最大受信1MiB、commandJsonは512KiBまで、event結果summaryは8KiBまで。UI/Agentの購読はサーバー側で対象を決め、UI Hubは通知受信専用。

| 方向 / method | DTOと動作 |
|---|---|
| Agent→Web `Hello` | agentVersion,protocolVersions[],agentStoreId,maxLocalEventSeq,runnerEpoch,appliedInventoryRevision,capabilities[],localResources[] |
| Web→Agent Hello応答 | protocolVersion,connectionEpoch,controllerAckEventSeq,desiredInventoryRevision,heartbeatSeconds=10 |
| Agent→Web `Reconcile` | connectionEpoch、非終端操作/Runner Session/hold/適用revisionのsnapshot |
| Web→Agent Reconcile応答 | ackEventSeq、再照会が必要なoperationIds、inventory更新要否。照合完了後Online |
| Web→Agent `DispatchOperation` | protocolVersion,connectionEpoch,operationId,commandJson,commandSha256 |
| Agent→Web `PublishEvents` | connectionEpoch,events[]。各eventはeventSeq,operationId?,statusVersion?,eventType,occurredAtUtc,body |
| Web→Agent event応答 | ackEventSeq（連続して保存できた最大値） |
| Web→Agent `InventoryChanged` | connectionEpoch,inventoryRevision,sha256。AgentはHTTPでsnapshot取得 |
| Agent→Web `InventoryApplied` | connectionEpoch,inventoryRevision,sha256、検証結果 |
| Agent→Web `Heartbeat` | connectionEpoch,runnerEpoch,observedAtUtc,runnerAvailable,serverSnapshots[],metrics[] |
| Web→Agent `SetLogSubscription` | connectionEpoch,serverId,sessionId?,afterSequence?,enabled |
| Agent→Web `PublishLogs` | connectionEpoch,serverId,sessionId,segmentId,firstSequence,rows[],gap |
| Web→Browser `StateChanged/OperationChanged/WorkflowChanged/LogBatch` | OwnerOnlyのUI投影。受信は状態保存の代替ではない |

`Hello`でv1非対応ならIncompatible。agentStoreIdはAgent DB生成時のGuidで、WebのHostに固定する。既登録HostでstoreIdが変わる、またはmaxLocalEventSeqがWebのACK済み値より小さい場合は自動採用せず要復旧とする。DB再作成/古いbackup復元はCLI再登録・照合を要する。

P0の復旧は旧Hostを無効化し、新Host IDでAgentを対話再設定する。旧HostのstoreIdを消す/自動採用する入口は提供しない。同一論理Serverの移送・既存実行の復旧はP1以降に追加する。

inventoryは完全snapshot（schemaVersion,hostId,revision,servers[],schedules[],backupProfiles[]）。各ServerConfigは03の型。既定上限はHostごと32Server、snapshot512KiB。全件検証後Runner設定を原子的適用し、Agentに保存してからInventoryAppliedを返す。失敗時は旧適用版を維持し、希望設定との差を表示する。同一revision/hashは再適用ACK、同一revision/異なるhashは409相当の競合。

10秒heartbeat、最終受信から30秒でOffline。再接続は1,2,5,10,30,60秒上限＋20%以内jitterを継続し、初回接続失敗も対象とする。既定のSignalR再接続だけに依存しない。Online化前にinventory/操作/event/Runner状態を照合する。Offlineはプロセス停止を意味しない。

## 操作のhash、受付、再送

Webは03のOperationCommandをcompactなUTF-8 JSONとして一度作成し、文字列`commandJson`とそのbyte列のSHA-256（小文字64桁hex）を保存する。Agent/Runnerは受信文字列そのもののbyteをhash化し、parse後の再serializeを比較に使わない。JSON重複キー/未知フィールドを拒否し、envelopeとcommand内のoperationId、認証先hostIdを一致確認する。

1. Webは希望操作/入力の重複検査→必要な予約→Queuedをcommitしてから送信する。
2. Agentはhash/epoch/対象/期限を検証し、InboxへAcceptedをcommitしてから受付eventを送る。Hub到着やHTTP202だけでは実行成功にしない。
3. プロセス操作は同じcommand/hashをRunnerへ渡す。Runner ledger保存と実行直前のstate/config/Session/hold検証後に開始する。
4. statusVersionはAgentが操作ごとに単調採番する。Webは古いversionを捨て、eventSeqも連続ACKする。実行の正本はRunner/Agentのjournalで、Web表示から推測しない。
5. 同ID/同hashは既存結果を返す。同ID/異なるhashはOperationConflict。再接続で新IDを作らない。未知の実行結果はNeedsAttention。
6. ConsoleCommandはRunnerで`Dispatching`を永続化してからstdin書込し、成功後`Sent`を記録。間で障害なら送信有無不明とし自動再送しない。

開始期限の既定は対話命令60秒、予約は予定時刻＋60秒、Workflow子操作は発行時から300秒。実行開始後の通信断/開始期限超過だけで中断しない。execution timeout時は安全な中断点でFailed、部分変更/終了確認不能ならNeedsAttention＋hold保持。プロセスをtimeoutだけでkillしない。

## Agent–Runner IPC

Windows named pipe=`AstralRecordControl.Runner.v1`。リモートpipe接続は禁止し、ローカルACLでAgentサービスとOS管理者に制限する。Cliの通常保守はWeb予約を取得し、Agentを経由して操作する。Runnerの通常Executeには取得済みholdとfenceが必須。ローカル緊急復旧はOS管理者の明示モードとして監査する。

frameは`uint32 little-endian byteLength + UTF-8 JSON`、最大1MiB。requestは`protocolVersion,requestId,method,body`、responseは`requestId,ok,body,errorCode?`。IPC切断後の再照会でもoperationIdを維持する。読み取りtimeout5秒、操作要求は永続受理まで5秒、実行完了は別照会。

解放済みholdはreservationId/ownerWorkflowId/fenceの終端履歴を保持する。同じ解放の再送は成功として扱い、同じreservationIdによる再取得はReservationConflictで拒否する。新しい予約は新IDを採番し、遅延再送で過去のholdを復活させない。

| method | body / 結果 |
|---|---|
| `GetSnapshot` | P0は空object / runnerEpoch,appliedInventoryRevision,servers[],holds[]。Session詳細はP1 |
| `ApplyInventory` | inventory:{protocolVersion,hostId,revision,snapshotJson,sha256} / RunnerSnapshot。停止必要項目を検証 |
| `AcquireHold` | reservationId,ownerWorkflowId,resourceKeys[],mode / 一括検証・永続化、Runner採番fenceを返す。同じ予約/同じ集合の再取得は同値 |
| `ReleaseHold` | reservationId,ownerWorkflowId,expectedFence / 当該Runnerで一括取得した集合のfenceを照合。実行/復旧未完了なら拒否 |
| `Execute` | operationId,commandJson,commandSha256 / Runnerのledger状態。許可されたプロセスkindだけ |
| `GetExecution` | operationId / phase,version,result,Session? |
| `ReadLogs` | serverId,sessionId?,cursor?,limit / rows,nextCursor,gap |
| `InspectRecovery` | serverId / 残存PID同一性・journal照合結果。自動採用しない |

## ファイル転送

転送予約ではsource/destination Host、操作ID、Server、期限を固定する。OwnerからのuploadはsourceHostId=nullで、size/hashも作成時に必須。遠隔生成物はsourceHostIdを固定し、size/hashを両方nullでCreatedとして予約できる。AgentはExportFiles/ExportLogsでstageを生成してからprepareにsize/hashを登録しUploadingへ進める。同じ値のprepare再送は同値ACK、異なる値は409 OperationConflict。これ以降は値を変更できない。未確定Createdにはchunk/complete/downloadを許可しない。

OwnerへのdownloadはdestinationHostId=null、PC間コピーは両Hostを設定する。Agentが転送先やパスを要求時に差し替えられない。Export操作の不変commandは予約済みtransferIdを参照し、生成後のmetadata確定でcommandを書き換えない。Webが既知metadataで予約した転送はそのままUploadingで開始する。

- chunk=最大4MiB、offsetは0から連続。各chunkにX-Chunk-Sha256。同じoffset/同じhashの再送は同じACK、異なる内容は409 TransferOffsetMismatch。
- completeで総サイズ/全体SHA-256を検証しVerifiedへ変更する。検証前のデータはdownload/反映できない。Agentはdownload後も全体hashを確認する。
- 1転送の既定上限20GiB、期限2時間。期限は未開始/中継データを対象とし、実反映中は削除しない。サイズ0も明示してcomplete可能。
- Verifyは実ファイル反映ではない。ImportArtifact等の操作が予約/停止/etagを再確認し、同volume stageから反映してConsumedにする。失敗時はjournalから再照合する。
- Web中継・Agent stageは空き容量を開始前に検査し、ストリーム/範囲転送で処理する。全ファイルをメモリに載せない。Webステージ上限は設定値100GiB、超過は開始拒否。
- 転送IDは推測困難でも認可を省略しない。秘密を含むファイルはno-store、外部URLへリダイレクトしない。中継物は完了後24時間、未完了は期限後にjournalと利用中でないことを確認して削除する。

## P2の追加実装契約

- Webの`Control:EnableFileControl`とAgent/Runnerの`enableFileControl`は既定false。P1 gateの導入条件に加えて有効化し、`P2.Files`/`P2.Backups`で能力を照合する。
- P2の操作IDは作成時の`Idempotency-Key`と同じGUID。Export用転送予約のoperationIdを事前採番できる。Import/ProvisionのVerified Artifactは、操作行の保存後、dispatch前に同じoperationIdへ消費leaseを固定し、Agentの成功確定後にConsumedへ進める。
- `GET /servers/{id}/runtime`はOwnerOnlyの現在Runner状態。画面はconfig/state/Sessionを指定して通常の操作受付へ送る。ファイル一覧/読取も整合性確保のholdを使用する。
- `GET /backup-profiles[/{id}]`、POST（If-None-Match:*）、PUT（If-Match:旧revision）を提供。保存bodyは03のBackupProfile全体、POST/PUTともIdempotency-Key必須。完全inventoryに含め、Agent ACK後のprofileRevisionだけで取得する。
- `GET /servers/{id}/backups?cursor={backupId}&limit=1..100`は`{rows,nextCursor,scope:ServerFiles}`。Agent正本を照会し、Web停止中の結果も再接続後に取得する。
- protect/deleteの短縮APIは`?serverId={id}`を必須とし、bodyは`configRevision,expectedStateRevision,expectedServerSessionId?,protected=false,reason=""`。通常のServer operationに変換する。汎用operation APIも同じ機能を提供する。
- Web→Agent RPCに`ListBackups(AgentListBackupsRequest)`と`ResumeDataOperation(AgentResumeDataOperationRequest)`を追加。どちらもconnectionEpochを検証する。復元再開は同じ操作ID/hold/fenceを使い、期限切れを理由に新規操作へ置き換えない。
- 大きな読取結果はSignalRへ流さない。Agentが`POST /api/agent/v1/operations/{id}/result`へUTF-8 JSONをoctet-streamで送る。AgentOnly/epoch/Host/command hashを検証し、`X-Command-Sha256`と`X-Result-Sha256`を要求、最大16MiB、同じ操作の異なる結果は拒否。成功前に耐久spoolから送信し、イベントには小さなsummaryだけを載せる。Ownerの既存result APIが保存済みJSONをno-storeで返す。通常の1MiBメッセージ上限とは別経路。
- 転送一覧と詳細はOwnerOnlyの`GET /transfers`（最新100件）と`GET /transfers/{id}`。本文の状態フィールドは`status`。Rangeは開始/終了を明示し、複数range/suffix/4MiB超を拒否する。ブラウザはchunk hashと全体hashを照合して保存する。

## P3の追加実装契約

- Webの`Control:EnableSchedules`とAgentの`enableSchedules`は既定false。AgentはP1の管理運用markerと共通gateが有効な場合だけ`P3.Schedules`を広告する。希望inventoryのScheduleはAgentの適用ACK後に初めて実行対象となる。BackupProfileを含む完全snapshotを同期し、Schedule編集で既存profileを落とさない。
- `GET /schedules?serverId={id}`、`GET /schedules/{id}`、POST（`If-None-Match:*`）、PUT（`If-Match:旧revision`）をOwnerOnlyで提供する。更新はCSRFとIdempotency-Keyを要求し、定義revisionと適用revisionを分けて返す。詳細は直近のoccurrence履歴を含む。
- Run NowはIdempotency-KeyのGUIDをoperationIdとする要求をWebに永続化してからAgentへ渡す。応答不明でも202と`Location: /api/control/v1/schedules/{id}/requests/{operationId}`を返し、GETは`AcceptanceUnknown`または保存済みreportを返す。同じキーの再送は同じ要求・Agentの同じoccurrenceを照合し、新規IDで補償実行しない。
- Agentの`ScheduleOccurrenceChanged`/`RuntimeChanged`はローカルoutboxへ状態更新と同じtransactionで保存し、Web停止中もeventSeqと発生UTCを維持する。再接続時は適用済みSchedule report/Runner holdを照合し、Webは認証済みHost・過去の適用版・定義hash・固定UUIDを検証してACKする。重複ACK再送は保存済みhashで照合する。
- `GET /servers/{id}/metrics?fromUtc=...&toUtc=...&granularity=minute|hour`はOwnerOnly。Host/ServerのCPU・メモリ・空き容量・uptime・人数を集計し、取得不能はnullと欠測状態で返す。Java人数はローカル`127.0.0.1` status pingに限定し、TPS/MSPTは提供しない。
- Webhook送信先のPOST/PUTはOwnerの直近再認証、CSRF、Idempotency-Keyと作成/更新条件を要求する。URLはData Protectionで全体を保護し、GET/履歴に復号値を出さない。公開IPへ解決されるHTTPS/443だけを登録し、送信時もDNSを固定、リダイレクト/プロキシを無効にする。初回送信後の失敗は1/5/30分の最大3回再試行でdead-letterにする。全試行で同一eventIdを使い、受信側の重複排除を前提とする。
