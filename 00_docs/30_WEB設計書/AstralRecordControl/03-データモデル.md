# 03 データモデル

## 共通表現

- `guid`: 小文字ハイフン付きUUID文字列。空Guidは禁止。全体識別にはGuid、設定や表示の短い名前にはkeyを使う。
- `hostKey/serverKey/environmentKey`: `[a-z0-9][a-z0-9-]{0,47}`。Web全体で種別ごとに一意、作成後変更不可。
- 日時: UTCのISO 8601、保存はUTC TEXT。画面/予約入力の既定表示はAsia/Tokyo。ローカル時刻をAPIへ直接送らない。
- revision/sequence: 0以上の符号付き64bit整数。JSONも整数、JSでの比較はBigInt対応codecまたは安全整数上限チェックを使う。
- boolはSQLite INTEGER、enumは下記の厳密な文字列、JSONは検証済みTEXT。外部キーを有効化する。
- `relativePath`: `/`区切りUTF-8相対パス。絶対パス、空要素、`.`/`..`、NUL、Windows ADS、予約デバイス名を禁止。ファイル名自体の許容はWindows規則に従う。
- すべての変更対象に`createdAtUtc/updatedAtUtc`、競合し得る設定に`revision`を持たせる。DELETEは論理削除を基本にし、参照中/履歴ありのIDを別用途に再利用しない。

## Web: control.db

ASP.NET Core Identityの標準User/token/loginストアを使用する。Rolesは登録しない。単一ownerを示すSingleton行で2件目の作成を拒否する。Identity内部のパスワードhashを独自方式で置換しない。既存TOTPデータはログイン条件に使わない。

## P1の物理schemaと補助DTO

Web/Agent/Runnerの`PRAGMA user_version=2`。schema1から移行する前にSQLite backupを取り、DDLと版番号更新をtransaction内で行う。未知版や既存の未登録schemaは拒否する。元のDBを自動削除しない。

| 保存先 | P1追加 |
|---|---|
| Web control.db | `CliCredentials`、`Operations`、`Workflows`、`Reservations`、`ReservationLeases`。操作入力hashとcommand文字列/hashを区別し、操作のidempotency keyをUNIQUEにする。資源ごとの有効予約と独立したlease履歴、Host別fence、PreparedOnce、LastStepKey、ReleaseOutcomeを保持し、資源再利用や解放再送でも古いIDを識別する |
| Agent agent.db | `OperationInbox`。command文字列/hash、状態版、Runner照会結果を保持。受付/状態変化を既存`EventOutbox`へ同じtransactionで保存 |
| Runner runner.db | `Servers`に状態/Session/停止意図/復旧/再起動回数を追加。`ServerSessions`、`ExecutionLedger`、`LogSegments`、`LogLines`、`RecoveryAudit`を追加。`Holds/ReleasedHolds`を継続 |

P1の型の正本は`Contracts/Operations.cs`。`ExecutionSnapshot={operationId,commandSha256,status,statusVersion,phase,serverSessionId?,errorCode?,result,updatedAtUtc}`。phaseは`Accepted/Starting/Running/Stopping/Dispatching/Sent/Completed/Recovering/Unknown`で、状態の細分を外部結果の成功と混同しない。

`GateLease={workflowId,reservationId,resourceKeys[],fences[{hostId,fence}],status,adapterId?,runReference?}`。statusは`Preparing/Prepared/Releasing/Released/RecoveryRequired`。`RecoveryInspection={runtime,session?,processAlive,identityMatches,recoveryRequired}`は点検時点の事実であり、PIDだけで操作対象を確定しない。

`LogBatch={serverId,sessionId?,segmentId?,nextCursor,earliestAvailableCursor,gap,rows[]}`、rowは`sequence,occurredAtUtc,stream,text,truncated`。P1は1回200行まで、本文合計64KiB程度に制限する。ファイルは100MiBで分割、行はUTF-8の64KiB単位に分割し長行を明示する。30分ごとにLogRetentionDaysを過ぎた閉じたsegmentを削除し、稼働中の最新segmentを保持する。`LogCursors`は削除後も単調sequence/segmentと保持設定を残すため、定義削除後も期限管理とgap応答ができる。未完了操作は自動削除しない。

## ServerConfig v1

P0の物理schemaは各サービスの初回schema1を正本にする。WebはIdentity標準表、ControlSettings/OwnerSession、Hosts/Servers/Environments、AgentCredentials/InventoryVersions/InventoryRequests/AgentEventsと転送scope予約表を持つ。AgentはState/PendingInventory/EventOutbox、RunnerはState/Servers/Holds/ReleasedHoldsを持つ。ReleasedHoldsは解放済みreservationId/ownerWorkflowId/fenceの終端履歴で、遅延した再取得を拒否するために保持する。Operation/Workflow/転送本体等の完成形の表は、対応する実装段階でmigrationを追加する。

| 項目 | 型/必須/既定 | 契約 |
|---|---|---|
| `schemaVersion` | int / 必須 / 1 | v1以外拒否 |
| `serverId, hostId` | guid / 必須 | 台帳と一致 |
| `revision` | int64 / 必須 | 1から単調増加 |
| `kind` | enum / 必須 | `Java/Bedrock/Velocity` |
| `managedRootId, serverDirectory` | guid, relativePath / 必須 | ローカル登録root内のサーバーフォルダ |
| `executableId` | guid / 必須 | ローカル登録済みJava/Bedrock実行ファイル。絶対パス指定を受け付けない |
| `argumentList` | string[] / 必須 | shell展開なし。JavaではJVM引数、jar/argsfile、nogui等を含む |
| `stopCommand` | string / 必須 | 改行禁止、最大4096 UTF-8 bytes。種別テンプレートの値を登録時に確認 |
| `listenPort` | int? / null | 1..65535、同一Hostの管理定義と競合を検証 |
| `autoStart` | bool / false | Devはfalseを標準。MCも明示設定時だけtrue |
| `startDelaySeconds` | int / 0 | 0..900 |
| `startupTimeoutSeconds` | int / 900 | 10..3600 |
| `stopTimeoutSeconds` | int / 120 | 10..600、timeoutで自動killしない |
| `restartOnCrash` | bool / false | 手動停止/保守hold時は常に抑止 |
| `restartDelaySeconds, restartMaxCount, restartWindowSeconds` | int / 60,3,600 | 1..3600、0..20、60..86400 |
| `ignoredExitCodes` | int[] / [0] | crash判定の補助。停止意図も別に持つ |
| `dependsOnServerIds` | guid[] / [] | 循環不可。PC横断の依存起動はWeb接続中のみ |
| `dependencyReadiness` | enum / `Running` | Server単位で全依存先へ適用。`Running/AstralReady`。後者は全依存先のruntime連携が必須、非対応なら設定拒否 |
| `logRetentionDays` | int / 30 | 1..365 |

設定は完全snapshot。payload JSONのsha256は02のbyte契約で求める。Runnerは停止中反映が必要な項目と稼働中反映可能な項目を01に従い検証する。`@argsfile`/jarも管理root内とし、実行時にjunction等を再検証する。

| entity | PK | 必須項目 |

`stateRevision`はプロセス状態/Session/hold/RecoveryRequiredの変化ごとに増やす。PIDだけを再利用してSessionを復元しない。論理的なSessionは1プロセスの寿命で、起動失敗も起動要求IDとledgerへ残す。

## 状態

| 種別 | enumと意味 |
|---|---|
| Host接続 | `Offline/Reconciling/Online/Disabled/Incompatible` |
| プロセス | `Stopped/Starting/Running/Stopping/Unmanaged` |
| ゲーム準備 | `Unknown/Preparing/Ready/Failed`。プロセス状態とは独立 |
| Operation | `Queued/Accepted/Running/Succeeded/Failed/Rejected/Expired/Cancelled/NeedsAttention` |
| Workflow | `Planned/Reserving/Running/WaitingForStartup/Succeeded/Failed/RecoveryRequired/Cancelled` |
| Transfer | `Created/Uploading/Verified/Consumed/Expired/Failed` |
| Backup | `Creating/Completed/Failed/Restoring/RecoveryRequired/Deleted` |

Operationの通常遷移は`Queued → Accepted → Running → Succeeded/Failed/NeedsAttention`。未開始だけ`Rejected/Expired/Cancelled`へ進める。`NeedsAttention`は結果不明/部分変更であり、同じ操作を自動再実行しない。照合で結果が確定すればversionを増やし`Succeeded/Failed`にできる。人間が中断を確定した場合はFailed＋復旧journalを残す。

Transferは遠隔生成なら`Created → Uploading → Verified → Consumed`、既知metadataならUploadingから開始する。size/hashはprepare後不変。transferIdに紐づくoperationIdはexport開始前に事前採番可能で、対応操作が未作成の予約も期限で回収する。消費操作の開始前には対応と利用権を再検証する。

`Accepted`はAgentのInbox永続化完了。プロセス操作はRunnerのledger永続化後に副作用を開始する。OS起動と記録の間で異常停止した場合は照合してNeedsAttentionにする。`Succeeded`のConsoleCommandは「stdin書込完了」であり、ゲームコマンド成功を保証しない。

## 操作種別とpayload

`FileTarget={managedRootId:guid, relativePath:string}`、`Artifact={transferId:guid, sha256:string, sizeBytes:int64}`。後者はVerified状態・対象Host/Serverへの利用権を照合する。パスを含む全操作に04の境界検証を適用する。

| kind | payloadの必須項目（?は任意） | 前提/結果・既定timeout秒 |
|---|---|---|
| `Start` | `{}` | Stopped、設定適用済み。Session生成。900 |
| `Stop` | `{}` | 稼働Session一致。Stoppedなら同じ状態版のno-op。120 |
| `Restart` | `{}` | 正常停止完了後、新Session起動。1020 |
| `Kill` | `reason:string` | Session再照合、確認済み要求。自動再起動抑止。30 |
| `ConsoleCommand` | `command:string` | 1行4096bytes以内、Running、Session固定。30 |
| `ListFiles` | `target:FileTarget, cursor?:string, limit?:int` | 変更なし。結果は名前/種別/bytes/etag一覧、1000件上限とcursor。30 |
| `ReadFile` | `target:FileTarget` | UTF-8/既存encoding情報、etag。2MiB以内。30 |
| `WriteFile` | `target, expectedEtag:string, contentUtf8:string` | UTF-8で64KiB以下、保存前退避、原子的置換。新規時etag=`absent`。120 |
| `FileMutation` | `action, source:FileTarget, destination?:FileTarget, expectedEtag:string` | action=`CreateDirectory/Copy/Move/Delete`。Deleteは退避。120 |
| `ExportFiles` | `target:FileTarget, transferId:guid` | 単体/ZIPをstageへ作成し転送。snapshot条件は04。3600 |
| `ImportArtifact` | `artifact:Artifact, target:FileTarget, mode, expectedEtag` | mode=`File/ExtractZip`。stage検証後反映。3600 |
| `CreateBackup` | `backupId:guid, backupProfileId:guid, profileRevision:int64` | snapshot適用済みprofile、停止確認。3600 |
| `RestoreBackup` | `backupId:guid, mode, restartAfterRestore:bool` | mode=`Replace/Merge`、保護退避必須、既定再起動false。3600 |
| `ProvisionServer` | `artifact:Artifact, templateId:string, eulaAccepted:bool` | 登録済み停止Serverの空フォルダだけ。Java/Bedrock/Velocityテンプレート。3600 |
| `UpdateServer` | `artifact:Artifact, expectedCurrentSha256:string` | 停止、更新前backup、種類/版一致を検証。3600 |
| `PlayerAction` | `action, playerId:string, reason?:string` | action=`Kick/Ban/Pardon/Op/Deop/WhitelistAdd/WhitelistRemove`。Adapter別の正規コマンド/API。30 |
| `RunMaintenanceStep` | `adapterId:string, runReference:string, stepKey:string, inputJson:object` | ローカルに登録した01/03/16/17 adapterだけ。86400 |
| `PruneBackups` | `backupProfileId:guid` | profileの世代保持条件で削除対象を確定。3600 |
| `SetBackupProtection` | `backupId:guid, protected:bool` | Agent正本とWeb投影を同じ操作結果で更新。30 |
| `DeleteBackup` | `backupId:guid, reason:string` | protected/復元中/未完了を拒否。3600 |
| `QueryLogs` | `sessionId?:guid, segmentId?:string, afterSequence?:int64, search?:string, limit?:int` | Runner管理ログ読取、最大1000行。30 |
| `ExportLogs` | `sessionId:guid, transferId:guid` | Runner管理ログをArtifactへstream出力。3600 |

`FileMutation.action`等も厳密enum。空コマンド・CR/LF・NUL・長さ超過を拒否する。読取操作もoperationIdで結果を取得し、Hubで巨大な内容を返さない。書込系にユーザー指定のOS実行コマンドを含めない。

サーバー複製/PC間移送/一括操作/本体更新チェックはWorkflowとして上記単位操作へ分解する。更新取得は登録providerからHTTPSでArtifactを作り、実反映はUpdateServerで行う。Server定義の論理削除と退避済み実データの最終削除は、停止/未完了なし確認後の専用Workflowとする。

## WorkflowRequest v1

`kind,serverIds[],input`を受け、サーバー台帳から全resource集合を確定する。以下の型以外の任意実行文字列は受けない。serverIdsとinput内の対象が一致することを検証する。

| kind | input | 処理 |
|---|---|---|
| `SingleOperation` | 内部生成のOperation入力 | 単一操作用の予約/解放。外部からこのkindを直接作成しない |
| `BatchPower` | action=`Start/Stop/Restart` | 依存順/逆順に子操作を実行。最初の失敗で未開始分を停止 |
| `CloneServer` | sourceServerId,targetHostId,newServerKey,targetRootId,targetDirectory,newPort?,newRuntimeServerId?,includeWorld:bool,includePlayerData:bool | 新IDへ停止snapshotを複製、autoStart=false |
| `MoveServer` | serverId,targetHostId,targetRootId,targetDirectory | 旧Host停止/起動禁止を維持しtarget適用後に台帳所有者切替。旧定義削除ACKまで新起動禁止 |
| `DeleteServer` | serverId,preserveFiles=true,deleteBackups=false | 停止/未完了なし、必要ならtrashへ移動後に論理廃止 |
| `Update` | serverId,providerId,version,expectedCurrentSha256 | 登録provider取得→Artifact→backup→UpdateServer→検証起動 |
| `TaskChain` | steps[{stepKey,kind,payload,delaySeconds}] | 最大16step、入れ子なし、各delay0..86400。成功時だけ次へ |
| `Maintenance` | adapterId,environmentId,mode,runReference?,parameters | 固定Adapterの型別入力。01/02/03/16/17の正規引数だけ許可 |
| `AstralRecovery` | environmentId,serverIds,serverBackupIds,dbBackupReferences,filebaseRevision,definitionGenerationId,patchNumber,externalStepReferences | 全体復旧計画と正規手順の確認。任意SQLを実行しない |

MaintenanceのadapterIdは`DevUpdate/PluginUpdate/MasterReload/Distribute/PlayerPatchMigration`。parametersは各Adapterで既存設定profileId、対象Server、testMode/selectedTests、migrationMode=`Preview/Commit`等を型付けし、ファイル/資格情報の絶対パスをBrowserから受けない。未対応parameterは拒否する。

## BackupManifest v1

`schemaVersion=1, backupId, serverId, hostId, createdAtUtc, configRevision, scope=ServerFiles, consistency=Stopped, serverKind, runtimeServerId?, environmentId?, definitionGenerationId?, patchNumber?, excludedPatterns, entries[]`を持つ。entryは`relativePath,sizeBytes,sha256`。manifest自身のSHA-256をBackup行へ保存する。DB/APIは含まないことを常に表示する。

## 予約と保持

- Schedule triggerは`Once{atUtc}`、`Interval{seconds,anchorUtc}`、`Cron{expression,timeZoneId}`。cronは秒なし5フィールド、timeZoneIdの標準は`Asia/Tokyo`。Intervalは60秒以上。
- P3のoperationTemplateは同一Server/Host・最大16stepのLocalChainだけを実装する。各stepの待機は0～86400秒、kindはStart/Stop/Restart/ConsoleCommand/CreateBackup/PruneBackups。WebWorkflowとPC横断/Environment処理はP4で、Web未接続中には開始しない。再開時に新しいoccurrenceを作らない。
- occurrenceのoperationIdはUUID v5（namespace=scheduleId、name=`revision:scheduledAtUtc`）で固定する。Workflowの子operationIdはnamespace=workflowId、name=`stepKey:attempt`。04の再試行規則に従う。
- Cronの重複ローカル時刻は先のUTCだけを実行、存在しない時刻はskip。予定時刻から60秒を超えて未開始ならSkipと記録し、取り逃した停止/再起動を追走しない。
- 操作・監査90日、メトリクス1分粒度7日/1時間粒度90日、ログ30日を標準とする。非終端操作/未完了保守/未ACK eventは期限で削除しない。
- backupは既定7世代・30日。成功backupのうち最新7件と30日以内は保持し、両方を超えた世代だけ候補。protected/復元中/未完了は削除不可。

## P3の物理保存と補助契約

Web/Agent/Runnerはschema4へbackup付きtransactionで移行する。Webは`ScheduleOccurrences`、`ScheduleManualRequests`、`MetricBuckets`、`NotificationEvents`、`NotificationDestinations`、`NotificationOutbox`を追加する。Schedule定義とBackupProfileは版付きInventoryVersionsの完全snapshotに保存し、希望版とAgent適用ACKを分ける。Agentは`ScheduleApplied`、`ScheduleCursor`、`ScheduleOccurrences`、`ScheduleChildOperations`、`RuntimeObservations`を追加し、occurrence/reportとEventOutboxを同じtransactionで更新する。Runnerは終了時刻・終了コード・意図した終了かをSessionに記録する。

`ScheduleManualRequests`はRun NowのoperationId・Schedule/Host/Revision・定義snapshot・開始前の拒否コードを永続化し、通信結果が不明でも同じIDを再送できる。`ScheduleOccurrences`はAgentを実行正本とし、Webには認証済みHostと過去の適用済みinventory版・定義hashを照合したreportを投影する。予定occurrenceと子operationIdは上記UUID v5で固定する。Web/Agentの終端履歴が90日を超えたらreport本文を退役させ、IDを残して重複実行を防ぐ。Webは同一report本文のAgent eventを耐久保存・ACKしたseqをAckedAgentEventSeqに記録し、確認済みの報告だけを退役する。Agentは未ACKの報告を退役しない。NeedsAttentionや未完了は退役させない。RunnerのRecoveryAudit/DataResumeAuditは90日超で対象の復旧状態とholdが解消済みの場合に削除する。

`MetricBuckets`の主キーは`(hostId,metricKey,granularity,bucketUtcTicks)`。AgentのHost/Server sampleをWebで1分と1時間に集約し、1分は7日、1時間は90日保存する。CPU・メモリ・ディスク空き・稼働時間・Java人数は取得できた値だけ集計し、欠測を0へ置換しない。P3ではTPS/MSPTの収集元を持たない。

`NotificationEvents`はeventId、sourceHostId/sourceEventSeqまたはsourceKey、occurredAtUtc、Server/operation/Schedule参照を持つ。`NotificationDestinations`はrevision、表示名、有効状態、Data ProtectionでURL全体を保護した値を持つ。`NotificationOutbox`は`(eventId,destinationProfileId)`を主キーに同一payload・試行回数・次回時刻・送信/配信不能時刻・有限エラーコードを保存する。初回送信と3回再試行（1/5/30分）で終端とし、配信成功/不能の90日後に本文を退役する。AgentEventsはACK済みでも再送hashを残し、未ACKイベントを期限削除しない。Webの完了操作はcommand/result本文を90日後に退役し、ID/hash/statusを照合用に残す。未完了保守・要復旧予約は保持する。

## P2の物理保存と補助契約

Web/Agent/Runnerはschema3へ移行する。既存schema1/2は移行前にSQLite BackupDatabaseでWALを含めて退避し、未知版は自動採用しない。WebはTransfers/TransferChunks、Agentは操作phaseとPendingResults、RunnerはDataOperationLedgerを追加する。BackupProfileは独立表の代わりに版付きInventoryVersionsの完全snapshotへ保存し、希望版/適用ACKを一つの契約で扱う。バックアップ世代/manifest/保護/復元journalはAgentが正本で、Webは照会結果と操作履歴を投影する。

ManagedRootに`backupOnly:bool=false`を追加する。trueの登録rootはServer rootとして使用不可。UNCはbackupOnly=trueのバックアップ保存先にだけ許可し、実行ファイルと稼働Serverはローカルに限定する。保存先のデータは`control-backups/{serverId:N}/{backupId:N}`、Agentのローカルstageで完成・検証してから転送する。

BackupManifestはscope=ServerFiles/consistency=Stoppedと作成元operationId、Host/Server/config版/種類/除外/entriesを持つ。完成済み結果の再開は作成元operationIdを必ず照合し、別操作の既存世代を採用しない。空フォルダentryにはisDirectory=true,sizeBytes=0,sha256=""を使う。manifest自身のhash欄を空文字として計算し、保存済みmanifestとAgent indexを照合する。保護状態/取得状態の変更はindexだけに保存し、完成済みsnapshotのmanifestを書き換えない。大きなmanifestは通常通信の1MiB制約を適用せず、最大64MiBの厳密JSONとしてローカルで扱う。

ExportFiles payloadは`{target?:FileTarget,backupId?:guid,transferId}`で、targetとbackupIdは一方だけ。バックアップdownloadにも同じ操作を使用する。ProvisionServerのtemplateIdは登録済みServerKind（Java/Bedrock/Velocity）と一致させる。自動Provider取得や種類/版カタログは後続段階で、P2では検証済みZIPを取り込む。

RestoreJournalはoperationId/serverId/backupId/mode/phase/stage/preRestore参照を保存する。交換完了時はreceiptを耐久保存してからjournalを除き、Agentが結果記録前に停止しても二度目の復元を実行しない。失敗/不明はRunnerのdata ledgerとholdが起動を禁止する。

バックアップ一覧RPCはAgentListBackupsRequestのcursor/limit（最大100）と任意のbackupIdによる単体照会を受け、BackupPage(rows,nextCursor)を返す。先頭100件への打切りではない。BackupSummaryはdirectory予約用の登録destinationRootIdを含む。
