# 05 画面と機能

## 共通画面

実装済み画面は`/`（取得時点のsnapshot）、`/Hosts`（PC/Environment台帳・接続案内・資格情報の復旧）、`/Servers`（一覧と登録）、`/Servers/{serverId}`（希望設定の編集）、認証画面。P1では`/Servers/{serverId}/Operations`の基本運転・操作履歴・ログと`/Workflows`の予約/保守履歴・理由付き点検復旧を提供する。操作画面はowner専用・no-storeの状態GETからプロセス、Session、版、直近履歴を3秒ごとに更新する。ログもcursor付きHTTP取得で同じ間隔に追従し、新Session開始時に切り替える。ログは画面内スクロールと表示量上限を持ち、最下部を見ているときだけ新着へ追従する。コマンド入力はログの直下に置く。状態取得に失敗した間は操作を無効化し、送信中の重複操作を防ぐ。Killは「プロセスの強制終了（保存せず終了）」として表示し、理由と対象Sessionの確認を必要とする。P2では`/Servers/{id}/Files`、`/Servers/{id}/Backups`、`/Transfers`でファイル・転送・バックアップ・復元を提供する。復元は対象/ServerFiles/方式/再起動を確認し、理由付きの同一journal再開を保守履歴に表示する。P3では`/Servers/{id}/Schedules`、`/Servers/{id}/Metrics`、`/Notifications`で同一Hostの予約実行、監視、Webhook送信先と配信履歴を提供する。下表は完成形も含み、未対応機能を利用可能と表示しない。

単一ownerの個人運用を想定し、ユーザー/ロール/権限割当メニューは作らない。デスクトップとスマホの両方で操作できるRazor Pagesとし、操作画面の状態・履歴・ログはHTTPで定期取得する。ログイン画面は管理者名とパスワードだけを求め、追加の画面内チャレンジを置かない。ログイン後は明示Logout・全セッション失効・owner資格変更まで同じブラウザの管理セッションを利用する。接続済みPCがある通常画面では初期接続の案内を折り畳み、PCの状態を先に確認できるようにする。

`/Hosts`は「PCを登録→対象PCでAgentを接続」の2段階を主導線にする。登録済みカードにはHost ID、接続状態、最終報告と、対象PCの管理者PowerShellで行う`& "$env:LOCALAPPDATA\AstralRecordControl\Cli\bin\AstralRecordControl.Cli.exe" login --server-url <Control origin>`（そのWindowsユーザーで初回のみ）および同じCLIによる`agent enroll --host-id <Host ID>`を示す。CLIは既存Agentサービスから実行ファイルとデータ保存先を検出し、設定後に停止中サービスを起動する。標準外の配置でだけ`--agent-path`と必要に応じて`--data-root`を指定する。Webへの接続と設定の適用は画面を再読み込みして確認する。CLIは対象PCのowner資格を安全なローカル保存領域へ保持し、Agent資格情報を非表示で取得・配置するため、画面でトークンをコピーする操作を標準導線にしない。従来の一度限りの手動トークン発行・失効、Host設定、desired/applied版、報告rootは「設定・診断」内に残し、復旧を妨げない。Webから遠隔PCのAgent設定へ直接書き込む導線は設けない。

上部メニューは現在位置を`aria-current=page`で示すタブ風リンクとし、狭い画面では横スクロールできる。パスワード認証前には管理メニューを表示しない。初期描画からdark color-schemeを宣言する。JavaScript有効時は同一originの管理ページをfetchし、取得完了まで現在の本文を保持した後にmainだけを置換する。ヘッダーと背景は再読込せず、フェードで一度消すアニメーションも使わない。認証・API・ダウンロード・別タブは通常遷移し、JavaScript無効時も通常のリンクとフォームを使える。

管理フォームはCSRFを含むFormDataを一度だけ送信し、検証エラーや一度限り表示するAgent tokenも応答HTMLから反映する。POST本文・応答HTML・tokenを履歴やブラウザストレージに保存しない。履歴にはGETのURL・位置番号・スクロール位置だけを持ち、戻る・進むはGETで取得し直す。処理中の戻るを拒否するときは履歴の位置を戻し、前のエントリを上書きしない。通信失敗時にPOSTを自動再送しない。全取得はno-storeと同一origin Cookieを使い、認証失効時はLoginへ通常遷移する。新HTML内のCSRF・title・選択タブを反映し、共通CSS/JSの版が変わった場合はGETで全体を読み直す。POSTの直接応答は一度限りの情報を失わないよう先に表示し、次のGET移動時に全体を読み直す。

ページ置換前に旧ページのログpoll・metrics取得を中断し、ページ固有スクリプトを再初期化する。転送・保守などの処理中は画面内の移動を抑止し、完了を待つよう表示する。通常のブラウザ終了/再読み込みで操作結果が不明になった場合は保守履歴で確認する。フォームのラベルは入力欄の上に配置し、チェックボックスは横並び、操作部品は高さ44px以上を基準とする。空の検証エラー領域は表示しない。

| route | 画面・操作 |
|---|---|
| `/` | PC/Server一覧、絞込、並べ替え、表示列選択、一括起動/停止、全体要確認件数 |

| `/Servers/{serverId}` | プロセス状態とゲームready、現在Session、主要操作、保守/予約状態 |
| `/Servers/{serverId}/Console` | ライブログ、コマンド、履歴、過去ログ検索/保存 |
| `/Servers/{serverId}/Files` | フォルダ、テキスト編集、etag競合、転送/展開/退避削除 |
| `/Servers/{serverId}/Configuration` | 実行環境、引数、停止、依存、自動起動、異常再起動、希望版/適用版 |

| `/Settings`、`/Security` | 保持/環境連携、owner sessionの全失効。Settingsの完成形は後続段階 |

実装済みのダッシュボードは運用入口、登録サーバー、PC接続カードの順で表示する。登録数・接続中PC数・確認が必要なPC数を要約し、取得時刻をJSTで示す。状態は日本語の文字付きバッジとし、未接続をゲーム停止と扱わず、設定適用も推測しない。希望/適用版・内部ID・JSONは詳細画面へ置く。新規PC/Environment/Server登録フォームは一覧後のdetailsに収め、未登録時は空表ではなく登録導線を示す。サーバー表の横幅超過は表内でスクロールする。Velocityには操作・ログへのリンクを表示し、Bedrockは台帳のみで運転未対応と明示する。

各Javaサーバーの詳細画面には「設定」「操作・ログ」「予約」「監視」「ファイル」「バックアップ」の横スクロール可能なタブを表示する。Velocityは「設定」「操作・ログ」を表示し、Bedrockは設定のみとする。Velocityの実行ファイル候補にはJavaも表示し、停止コマンドの標準値は`shutdown`とする。新規登録で停止コマンドを省略すると種別に応じた標準値を保存する。操作ボタンは停止中に起動、稼働中に正常停止・再起動・強制終了・コマンド送信を有効にし、遷移中や状態不明では無効にする。VelocityはHostの`P1.Velocity`能力も確認する。受付済み・実行中・要確認の操作が残る場合も無効化し、画面再取得直後の旧状態から再送させない。操作履歴の時刻は初期描画と定期更新ともUTCと明示する。画面上の無効化は補助であり、実行時の版・Session・状態・gateの検査はサーバー側でも続ける。

GETは副作用を持たない。すべての変更は02のHTTP契約へ渡す。サーバーをまたぐ画面切替でコマンド入力や操作対象が別Serverへ流れないよう、フォームと確認内容にserverId/sessionIdを固定する。

操作フォームは押された操作種別をhidden入力へ保持してからボタンを無効化する。ブラウザが無効化後にフォームデータを収集しても操作種別を欠落させない。サーバー側も操作種別の欠落・未定義値を拒否し、起動へ補完しない。

コンソールはANSI SGRの16色・256色・RGB色と基本の文字装飾をspanへ変換し、INFO・WARN・ERROR・DEBUG等の見出しにも色を付ける。OSCやカーソル操作など非表示の端末制御は実行せず除去する。ログ文字列をHTMLとして扱わず、textContentで表示する。初期ログと追加取得ログで同じ描画処理を使い、過去行を閲覧中はスクロール位置を保持する。

## 状態と確認

- Offlineは「PCと通信できない」と表示し、最終受信UTCをJSTで併記。停止中と同じ色/文言にしない。
- プロセスRunningとゲームReadyを別表示する。API情報が古い場合は確認不能/最終取得時刻を出す。
- 希望設定保存と実適用を分け、未適用では起動ボタンを有効化しない。
- HTTP202/Acceptedは処理受付として進捗画面へ移し、Succeeded/Failed/NeedsAttentionまで追う。リロード後もoperationIdから再開する。
- 通常Start/Stopは対象を明示した1操作。Kill、復元、退避データ最終削除、移送、本番更新は対象・影響範囲・再起動有無の確認を表示する。実装詳細の内部DTOを確認画面に羅列しない。
- 結果不明は再実行ボタンより先に照合/復旧を案内する。リトライで新operationIdを作るのは、前回の終端と新規試行を明示確認した場合だけ。
- Run Nowの受付結果不明は永続要求IDと照会先を表示し、同じIDで再送する。送信先URLは表示・API応答へ復号せず、空欄更新なら保存済みの秘密を保持する。
- サーバーroot・実行環境は登録済み候補から選択し、秘密トークンは発行直後以外に表示しない。
- 制御コンソールをブラウザから離れた後もサーバーは継続する。PWAは画面導線/インストールだけを提供し、管理データや資格情報をservice workerでオフラインcacheしない。

## 対象の境界

- Java版はPaper/Purpur/Vanilla等の登録済み起動profile、ProxyはVelocityの既存構成importを対象にする。Forge/Fabric等は起動argsfileを取り込めるが、自動インストールproviderは別の対応表で明示する。
- Bedrockも実行ファイルprofileで扱う。Java用コマンド/人数取得を流用せずcapabilityで制御する。
- 本体版取得の初期providerはPaper/Purpur/Vanilla/Bedrockのうち採用する版を実装時に公式配布契約で検証する。未知providerをUIから登録して任意URLを実行できる機能にはしない。
- ユーザー別貸出、課金、招待、role、一般OSターミナル、他ゲームのSteamCMD/Hytale管理は対象外。
- 公開ステータスページはv1の必須ではない。導入する場合も認証なし情報を別DTOへ限定し、管理画面やログを公開しない。
- 既存のマスターデータ編集/プレイヤーデータ訂正を二重実装しない。ゲーム管理は既存の正規APIを呼び、認証とプロセス管理は独立を維持する。
