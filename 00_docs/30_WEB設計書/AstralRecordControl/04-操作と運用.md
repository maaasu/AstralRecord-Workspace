# 04 操作と運用

## P1実装の有効化と実行境界

P1は独立Javaプロセスの基本運転と共通gateを実装する。通常操作は`Control:EnableProcessControl=true`、Runnerの`EnableProcessControl=true`、全対象Hostの`P1.Operations/P1.LegacyGate`を満たす場合に限る。Runner本番起動は固定`%ProgramData%\AstralRecordControl\managed-operations.enabled`を要求し、Agentは同marker確認時だけP1能力を広告する。markerは導入ツールの`-EnableManagedOperations`で旧入口の改修を検査して作成する。単にWebの設定だけを変えて有効化しない。

01/02/03/16/17のBAT・直接PowerShellは`60_tool/control-gate/Control.Gate.psm1`を共通入口とする。実在するruntimeServerIdとControl Server GUID、実際の配布先/元とHost/root/相対パスのbindingを明示し、欠落/重複/曖昧対応は副作用前に拒否する。UNCのshare名からHost内パスを推定しない。全資源を先に予約し、全Hostのhold準備完了と状態確認後に変更する。02の公開もEnvironmentを予約する。

marker導入前のLegacyとManagedを区別し、markerのあるPCではcontrolGate欠落やLegacy入口を拒否する。01/16は最終run pathとworkflowIdを開始前に確定し、既存run再開時も同じleaseとrun参照を使う。子処理はleaseを継承し、子だけで解放しない。停止条件はRunner snapshotから検証し、`-ServersStopped`等の申告を停止証明として扱わない。

markerは初回の管理運用導入とTool rootを記録する。ローカル管理者が通常のTool更新を行うたびに、スクリプトのハッシュ再承認やmarker更新を要求しない。既存schema 1のhashesは旧installerとの互換記録として残す。配布パッケージの検証、実行時の設定検証、中央予約・Runner hold・停止確認はデータ整合性のため維持する。

通常の1操作用予約は終端後に照合して解放する。01/16と03停止モードは起動待ち段階のStartだけ同じworkflowId/reservationIdを継承し、保守全体が終わるまで予約を保持する。17中のStopや段階外の起動を許可しない。失敗/結果不明で新Workflowを作って再実行しない。ローカル緊急復旧は`runner inspect/recover`をOS管理者で実行し、PID・生成時刻・実行ファイル・Sessionを再照合する。通常のAgent接続権限では緊急Recoverを実行できない。

未知Prepare後の点検Abortでは、全Hostへ同じ予約IDのAcquire/Releaseまたは既知fenceのRelease再送を行い、Runnerの解放済み記録で遅延Prepareを拒否してから中央を解放する。解放はoutcomeと開始状態を永続化し、途中失敗でも同じfenceで再送できる。release応答喪失後の完了済runは既存の保護leaseを`gate inspect`で照合し、Released markerだけを回復する。Releasing/Preparedなら同じleaseでreleaseを再送し、完了した配布/公開/17のAPI要求を再実行しない。

## 共通の操作予約

中央での予約と各PCのRunnerによるholdを組み合わせる。Webのボタンを無効化するだけでは排他と扱わない。すべての変更はWorkflowを所有者に持ち、単一操作も`SingleOperation` Workflowに包む。

| resourceKey | 最終調停者 | 対象 |
|---|---|---|
| `environment:{environmentId}` | Web | 共有API配置、master seed、公開、17、全体復旧 |
| `server:{serverId}` | 対象HostのRunner | 起動停止、console、書込、backup、更新、予約実行 |
| `directory:{hostId}:{managedRootId}:{canonicalRelativePath}` | 対象HostのRunner | 配布元/先、Server以外の登録済み配置領域 |

ディレクトリ資源はprefixが交差する親子も競合とする。大文字小文字/末尾区切りをWindowsの同一パスへ正規化する。Serverのrootも自動的に資源集合へ含め、IDの異なる定義から同じ実ディレクトリを変更できないようにする。

予約modeは`Exclusive/Maintenance`。変更はどちらも排他的で、Maintenanceは保守の子操作だけを許可する持続hold。ログ/metrics/read-only設定照会は予約不要。ファイル読取は変更中の対象を避け、整合snapshotが必要なら予約を取得する。

### 取得と実行

1. Webは希望操作の入力、適用config、Browserが観測したstateRevision/Sessionを検証する。必要な全資源を確定する。
2. Web DBで全資源を一括予約する。競合時は副作用前に409で拒否し、暗黙待機/資源の途中追加はしない。
3. 対象HostのすべてがOnlineであることを確認し、hostId順にAgent経由でRunnerへAcquireHoldする。Runnerはローカル全資源を原子的に取得し、永続counterから同一hold用fenceを採番する。
4. 全Hostの取得成功後にだけ処理を開始する。取得途中で失敗し、副作用がないことを確認できるholdはReleaseして中央予約も取り消す。返答不明ならRecoveryRequiredを維持する。
5. hold取得でstateRevisionが進むため、取得前のBrowser条件を検証した後、Runnerの取得後snapshotから各子OperationのexpectedStateRevisionを確定する。Session/プロセスがhold以外の理由で変わっていれば拒否する。
6. commandのreservationFenceは対象HostのRunnerが返したfence。Runner/Agentは予約ID・ownerWorkflowId・fence・全必要資源の所属を実行直前に確認する。
7. 全子処理とjournalの終端確認後にlocal holdを解放し、全HostのACKを受けて中央予約を解放する。

中央EnvironmentのfenceはWeb採番、PCのhold fenceはそのRunnerだけが採番する。異なるauthorityの値を大小比較しない。予約ID/所有者/authority/fenceの完全一致で検証する。再起動してcounterを戻さない。

### 切断・クラッシュ・ローカル予約

Web/Agent切断、token期限、timeoutで予約を解除しない。Runner holdとAgent journalを再照合し、開始済み子プロセス/配布処理/部分変更が不明ならRecoveryRequired。`AbortAfterInspection`も副作用の巻き戻しではなく、確認した状態と理由を記録して予約を整理する操作である。

適用済みScheduleは、単一Hostで完結するStart/Stop/Restart/ConsoleCommand/CreateBackup/PruneBackupsだけをオフライン実行可能とする。AgentがローカルWorkflow/予約IDを作り、同じRunnerのgateで調停する。中央がすでに取得したholdがあれば拒否する。新しい中央保守も全Hostのhold取得前に副作用を始めないため競合しない。

ローカル予約のID/fence/eventは再接続後に中央へ投影する。共有Environmentや複数Hostの操作はWeb接続なしで開始しない。Agent停止中に予約を実行するための別実行器は作らない。

## 起動・停止・プロセス障害

### Start

1. Stopped、設定適用、root/executableの境界、configRevision/stateRevision、holdを確認する。
2. Runner ledgerへ起動意図を永続化し、serverSessionIdを先に採番する。
3. `UseShellExecute=false`、明示WorkingDirectoryとArgumentListでJavaを直接起動する。親の任意環境変数やJVM注入設定を継承せず、WindowsではOS取得の`SystemRoot/windir`を明示して通信機能を維持する。Runnerデータ領域の`process-temp/{serverId:N}`を非reparse・書込可能と確認し、`TMP/TEMP/TMPDIR`として渡す。ユーザー指定の引数は変更しない。OS shellやBATを任意実行しない。Bedrock/Velocityの運転は現段階では未対応。
4. pid/生成時刻/実行設定fingerprintをSessionへ保存し、stdinへBOMなしUTF-8で書き込む。stdout/stderrはUTF-8として非同期で継続読取する。登録実行ファイル名がjava/java.exeの場合は、元のArgumentListの前に`-Dstdout.encoding=UTF-8`と`-Dstderr.encoding=UTF-8`を既定値として付加する。同名の明示引数は元の順序のまま後から評価されるため、その場合も出力をUTF-8に揃えることを運用条件とする。長行分割でサロゲート対を切断しない。
5. プロセス存続と必要なポート確認でRunningを表示する。Astralのreadyは別の準備状態であり、起動受理だけでReadyへ進めない。

OS生成直後の記録前クラッシュは自動再起動せず照合する。親子関係・生成時間等で自分のプロセスと証明できない場合はUnmanaged/要復旧。PIDだけで別プロセスを採用・終了しない。

### Stop / Restart / Kill

Stopは対象Sessionを再照合し停止意図を先に保存、自動再起動を抑止してstopCommandを1回送る。120秒既定で終了を監視する。終了しなければNeedsAttentionとholdを保持し、Killへ自動変更しない。

Restartは同じWorkflow内でStop完了後、最新stateRevisionでStartを行う。子Operationは固定IDを使い、timeout後に別IDのRestartを追加しない。

Killは対象Server/Session/理由を確認した別命令。生成時刻/実行パス/起動記録の一致確認後にそのプロセスだけを終了し、自動再起動は抑止する。名前がjava.exeという理由だけで全プロセスを終了しない。

Stop timeout等で既存holdがある場合、通常の新WorkflowのKillを重ねない。ownerは`recover(action=KillAfterInspection)`で対象と理由を確認し、同じWorkflow/reservation/fenceを継承した救済Kill childを作る。最新Session/stateを再照合して発行し、終了確認と旧Stop journalの照合後に旧操作をFailed（明示強制停止で収束）として終端化する。救済Killが不明/失敗ならholdを維持し、成功した場合だけ解放する。

Runner異常停止後の残存JavaはUnmanaged。console/start/restartを拒否し、ログファイル閲覧と識別照合を許可する。元のコンソールや事前登録済みローカル正規停止経路があればOS管理者が停止し、なければ明示Killを検討する。終了確認後の新Startから管理下へ戻す。匿名stdioをPIDから取り戻した扱いにしない。

### 自動起動・障害復帰・依存関係

autoStartとrestartOnCrashは別設定。手動停止、保守hold、Unmanaged、RecoveryRequiredではどちらも抑止する。crashは停止意図のない異常終了として記録し、既定60秒間隔、10分以内3回まで。超過は要確認。Web未接続中の実行は上記ローカル予約規則を使う。

依存起動は有向非巡回グラフとして設定時に検証する。単一HostはAgentが順に処理し、複数HostはWeb Workflowで各Host Onlineを確認して実行する。起動条件はServer単位のdependencyReadiness（既定Running）を全依存先へ適用する。AstralReadyは依存先すべてのruntime連携がある場合だけ設定でき、現在Sessionと一致する新鮮なreadyをWebが確認する。Web未接続/欠測ではReadyを満たさず開始しない。待機上限はstartupTimeoutSeconds。停止は依存の逆順。接続不能の依存先を起動済みと推測しない。

## ログ・監視

Runnerは1行単位にserverSessionIdとsequenceを付け、UTF-8ログを100MiB単位でローテートする。巨大1行は64KiBで分割しtruncatedを表示する。Agent/ブラウザへは最大200行または64KiB/バッチ、描画遅延時もRunnerの読取を止めずgap/cursorで追いつく。古いログが消えていればearliestAvailableCursorを返す。

ANSI/Minecraft装飾は許可した装飾だけ描画し、HTMLとして実行しない。コマンド入力は監査するが、秘密設定に該当する引数はmaskする。OS資格情報の入力をコンソール機能へ流用しない。

Host/プロセスのCPU/メモリ/空き容量は10秒採取、Web保存は1分集約。人数/TPS等は種別Adapterまたは既存APIから取得し、欠測はnull。API取得失敗を0人/停止へ変換しない。

## ファイル・作成・複製・更新

Agentはすべてのパスをローカル登録rootに解決し、途中のsymlink/junction/reparse point、領域外逸脱、ZIP内の絶対パス/親参照/linkを拒否する。予約取得後、実際のopen/rename直前にも境界を再確認する。

etagはファイルのSHA-256。新規は`absent`、保存は期待etagを比較して同volumeの一時ファイルへ書き、保存前退避後に原子的置換する。既存のencoding/改行を保持する。ReadFileはencodingを返し、UTF-8以外はバイナリArtifact経由で扱う。WebのWriteFileで暗黙に文字コード変換しない。

稼働中の書込は`plugins/mods/world/実行jar/起動設定/server.properties`等を禁止し、原則停止方式とする。単なる読取は可能。稼働中に対応する設定再読込は登録済み専用Adapterだけを許可する。削除はtrashへ移し、最終削除は別の確認済み保守とする。

ZIPは検証済みstageへ展開し、既定で総展開20GiB/10万entry/圧縮比100倍を上限とする。対象volume容量の余裕も検証する。Provider取得は許可HTTPS origin・種類・版・size/hashを検証し、実行ファイルを取得しただけでは実行しない。

新規作成はServer定義→空root確保→取得/ZIP取込→EULAの明示確認→起動設定検証→適用ACK。既存フォルダ登録はローカル登録root内で、未管理プロセスがない停止状態だけを受け入れる。

複製は停止snapshotを新serverId/新rootへ転送し、ポート/runtimeServerId/固有識別設定を再指定する。プレイヤー/ワールドを含むか明示し、複製後のautoStart=false。別Hostへの移送は新Hostで検証完了まで旧Hostの定義とデータを保持し、同じ論理Serverを両Hostで同時起動しない。

本体/Plugin更新は正常停止→更新前backup→stageで種類/版/hash検証→退避交換→検証起動。失敗時は保守状態を保持して復旧する。DB/APIまで変更した後はファイルだけを自動rollbackしない。起動設定/Java選択の変更にOS全体のJava自動上書きを含めない。

## バックアップ・復元

標準profileは停止方式、7世代/30日、保存先はServer root外。取得中・失敗・保護・復元中のデータは世代削除しない。NAS保存は登録済み保存先だけを使い、まずローカルstageで完成させてから転送する。

CreateBackupはhold→元の稼働状態保存→正常停止/終了確認→stageコピー→各entryのsize/SHA-256とmanifest検証→Completed確定→profile指定かつ元が稼働なら再起動。停止timeoutは失敗し、稼働中コピーへ自動変更しない。v1は稼働中バックアップを提供しない。

RestoreBackupの`Replace`はsnapshotの状態へ戻し、snapshot外の対象ファイルを退避する。`Merge`はsnapshot内のファイルだけ復元し、その他を保持する。どちらも停止確認→退避→stage検証→同volume交換をjournal化する。既定restartAfterRestore=false。中断・破損・容量不足はRecoveryRequiredで起動禁止、入場制限も自動解除しない。

バックアップscopeはServerFilesで、SQL/API/master/公開状態は含まない。Astral全体復旧は`AstralRecovery` Workflowで対応DB backup参照、filebase版、公開世代、対象Hostを計画・表示し、承認済み既存復旧手順を順に実行する。v1で任意SQLの入力・汎用DB復元機能は作らない。Control認証DBや長期保持ManagementDBを通常のゲーム巻き戻しへ含めない。

## スケジュール・通知

Schedule定義の編集元はWeb、適用済み実行定義/occurrenceの正本は対象Agent。Webの`Control:EnableSchedules`とAgentの`enableSchedules`は既定falseで、P1 marker/gate確認と02のinventory ACK後に有効化する。Once、60秒以上のInterval、秒なし5field cron（標準`Asia/Tokyo`）と手動Run Nowを用意する。Cronの夏時間重複は先のUTCだけを実行し、存在しない時刻は発火しない。同一Host/Serverの最大16stepはWorkflow/予約IDを継承し、段間待機は0～86400秒。失敗したstepの後続を成功処理へ進めない。BackupProfileも完全snapshotで同期し、Schedule更新時に既存定義を消さない。

ローカルで安全に完結する予約だけオフライン実行可能。保守中はSkip/競合として履歴化する。予定から60秒を超えて開始できなかった実行はSkipとし、再接続後に過去のrestartをまとめて実行しない。Run NowはWebで要求IDを永続化してからAgentへ渡し、応答喪失は`AcceptanceUnknown`として同じIDの照会/再送で解決する。Update/PC間複製/Environment/既存配布WorkflowはP4で、Webと全対象Host Onlineが開始条件。

監視はAgentが約10秒ごとにHost/プロセスCPU・メモリ・ディスク空き・uptimeを採取し、Javaの`127.0.0.1` status pingから取れた場合だけ人数を付ける。Webはminuteを7日、hourを90日（2160 bucket）保持する。Agent/ゲーム応答がなければ欠測とし、0人/停止と推定しない。TPS/MSPTはP3では提供しない。

通知はWebの耐久outboxから、開始/終了/異常終了/backup結果/要復旧とSchedule実行結果を登録先Webhookへ送る。初回失敗後1/5/30分の最大3回再試行でdead-letterにし、全試行に同じeventIdを付ける。Web停止中のAgent eventはACKまで保持し、再接続後も発生UTCを保つ。通信断後の外部送信成功をWebだけでは証明できないため、受信側はeventIdで重複排除する。通知失敗をMinecraft操作失敗へ変換しない。Webhook URL全体を保護し画面/API/ログへ戻さない。公開IP宛てHTTPS/443のみ登録し、送信時はDNSを固定してリダイレクト/プロキシを無効にする。

## 既存01/02/03/16/17との連携

P1で各入口に共通gateを追加する。未改修の既存BATとWeb変更操作を同じ管理対象へ併用しない。`-ServersStopped`等は現在の確認宣言であり、プロセス停止の自動証明として使わない。

| 入口 | 必要な状態/予約 | 維持する完了条件 |
|---|---|---|
| 01/02 Dev更新 | Dev停止、入場閉鎖。01で共通API/Filebaseを更新する構成は全共有RPG停止。共有Environmentを予約 | 新しい起動Session、ready/世代確認、公開 |
| 03 マスタ再読込 | 共通API構成は全共有RPG停止。Dev専用APIで稼働中モードを使う場合は入場閉鎖、保存完了、他writer停止。Environmentと対象Server予約 | 停止モードは共有RPGの起動後にDev ready/公開。専用APIの稼働中モードはpublicationRevision増加、ready/安定 |
| 16 配布 | 配布元/先と必要なLobby/Proxyを停止、Environment予約 | 全対象の新Session/同一世代/ready後に公開 |
| 17 一括更新 | 対象ゲームは稼働/ready維持、入場閉鎖・保存完了・全員退出 | Preview既定、全候補確認後の明示Commit。同じ要求IDで結果照合 |

03のrevisionは再読込処理完了を示し、全world/NPC等activation成功の保証にはしない。Lobby/Proxyは既存のスキルツリーruntime判定だけではready確認できないため、別の起動確認Adapterを用意する。

既存run/journal/要求IDをControl Workflowへ紐付け、再開時に新runを勝手に作らない。17のCommit開始markerがあるrunは既存どおりファイルだけのRestoreを拒否する。16のWorld配布は対象のuid.dat/playerdata/stats/advancementsを保持しsession.lockをコピーしない契約で、全ファイルbackup復元とは区別する。

Webから既存処理を呼ぶのはP4だが、gateはP1で実装する。Agentはローカルに登録したadapterIdと固定入力schemaで処理を実行し、ブラウザの任意PowerShell/BAT文字列を実行しない。buildが必要な処理は開発PCで行い、MC用PCへ成果物を転送する。

## PlayerActionと既存ゲーム管理

Vanilla系は種別Adapterで正規コマンドへ変換する。playerId/reasonを型・長さ検証し、改行を入れて別コマンドを注入できないようにする。失敗時にJSONファイルを直接編集して代替しない。

AstralのBAN/whitelist等、既存APIが正本の操作はそのAPIを使う。Control ownerと既存運営主体の対応はIntegrationProfileに明示し、未設定なら該当ボタンを無効化する。ゲームAPI障害でも基本起動停止・ログ・Control認証は利用できる。

## Control自身の導入・更新・復旧

初期導入はOS管理者がサービスアカウント/ACL/ローカルroot/executableを登録し、各管理PCのCLIで一度ownerログイン→`agent enroll`によるPC接続の自動設定→Agent Hello→Server定義の順で行う。接続用資格情報は内部で発行・受け渡し・保存し、手動tokenコピーを要求しない。Web/CLIのログインは明示logout・失効・owner資格変更まで保持する。Runnerのみ起動してもWeb未登録サーバーを自動起動しない。

Web/Agent更新は対象サービス停止、SQLite整合backup、binary交換、schema migration、起動、02の再照合。Runner更新は全対象正常停止後だけ。Control更新もプログラムとProgramDataを混在コピーしない。

Webの認証DB/設定/鍵ringは暗号化backupとして別保管する。別PC移設時はOS保護鍵の復号可否を確認し、不可ならCLIでowner再構築・全session失効・Agent再登録する。古い操作DBを復元した場合は実行再開より先に各Agent/Runnerとの整合を確認し、履歴の巻き戻りで再実行しない。

P2ではバックアップ保存先の`directory:{hostId}:{destinationRootId}:control-backups/{serverId:N}`も同じ資源集合に加える。既存indexと保存先manifestはmutableな状態/保護指定以外を等値照合する。失敗したバックアップのlocal stage/保存先.incompleteは所有IDと境界を確認して掃除し、Failed記録からAgent起動時にも回収する。取込が終端失敗したWeb転送stageは24時間後の回収対象とし、NeedsAttentionの消費leaseは保持する。etagの不一致が変更前に確定した場合はRejected/StateConflictで終え、通常の再読込を妨げない。Runner受付の応答だけ失った場合はNeedsAttentionを保持して同じID/hashの実行台帳を照合する。
