# 04_5.00-例外・ログ・運用

## 1. 方針

`item` 機能は「ログ記録して処理継続」を基本とする。  
起動時の一括ロード処理ではアイテム単位の取得失敗はサーバ全体停止を引き起こさないよう、警告ログを記録してスキップする。  
パケットアダプタや操作抑止イベントハンドラでは、`runSafely` または `null` 復帰により例外漏れを防ぐ。

## 2. 主なログポイント

- `ItemRepository`
  - 取得成功: `LogId.D_5202`
  - 取得失敗（個別アイテム）: `LogId.W_5200`
  - 取得失敗（API/その他例外）: `LogId.E_5200`, `LogId.E_5201`
- `ItemService`
  - キャッシュ登録: `LogId.D_5203`
  - カテゴリ別ロード成功: `LogId.I_5202`
  - 全ロード成功: `LogId.I_5203`
  - 一括ロード失敗: `LogId.E_5202`
- `ItemStackFactory`
  - テンプレートキャッシュクリア: `LogId.D_5210`
  - （未使用）テンプレート構築デバッグ: `LogId.D_5211`
- `ItemStackPacketAdapter`
  - 登録成功: `LogId.I_5210`
  - 不明 icon Material: `LogId.W_5210`
- `ItemInteractionBlockEventHandler`
  - `runSafely` 内例外: `LogId.E_5200`
- `SetEffectRepository`
  - 取得成功: `LogId.D_5400`
  - 取得失敗（個別）: `LogId.W_5400`
  - 取得失敗（API/一覧）: `LogId.E_5400`, `LogId.E_5401`

## 3. 例外処理の境界

- `Repository`
  - HTTP 異常や `InterruptedException` を捕捉し、ログ記録後に `IOException` または `RuntimeException` で例外化する。
- `Service`
  - `loadAll` / `loadAllByCategory` / `createEquipmentInstance` などのトップレベルメソッドは例外を捕捉してログ記録し、空リスト・`null`・`0` などの安全な戻り値を返す。
- `EventHandler`
  - `runSafely` により最終的なイベント境界で例外漏れを防ぐ。
- `PacketAdapter`
  - icon Material 解決失敗時はキャッシュに `null` を保存し、以降の同一名解決を抑制する。

## 4. スレッド上の注意

- 起動時の `lootService.loadAll()` → `itemService.loadAll()` は `Bukkit.getScheduler().runTaskAsynchronously` で非同期実行される。
- API 呼び出しは同期 HTTP のため、メインスレッドからの呼び出しはコマンド経路（プレイヤー入力）以外では行わない。
- `InterruptedException` 捕捉時は `Thread.currentThread().interrupt()` を再設定している。
- `ItemStackPacketAdapter` の `onPacketSending` はネットワーク IO スレッドで動作し、ロジック中で Bukkit API への状態変更を行わない。

## 5. プレイヤー向けメッセージ

`/item` 系コマンドで使用する主要 `PlayerMsgId`:

- `P_5201`: アイテムが見つかりません: category={0}, id={1}
- `P_5209`: ロードしました: {0}/{1} ({2})
- `P_5213`: 指定IDのロード済みアイテムが見つかりません: {0}
- `P_5240`: アイテムを付与しました: {0} x{1}
- `P_5241`: インベントリに空きがありません。

`P_5063` などインベントリ初期化未完了時のメッセージは inventory 機能と共通利用する。
