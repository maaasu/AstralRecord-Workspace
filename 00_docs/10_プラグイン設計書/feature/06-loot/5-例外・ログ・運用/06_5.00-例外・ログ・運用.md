# 06_5.00-例外・ログ・運用

## 1. 方針

`loot` 機能はマスタの参照キャッシュのみを担当する。  
取得失敗時はサーバ全体を止めず、`loadAll` は例外をログ記録して `0` を返し、個別取得は警告ログ + `null` 返却または例外送出で呼び出し元へ判断を委ねる。

## 2. 主なログポイント

- `LootService`
  - 全件ロード成功: `LogId.I_5300`
  - キャッシュ登録（個別）: `LogId.D_5301`
  - 一括ロード失敗: `LogId.E_5301`
- `LootRepository`
  - 取得成功（個別）: `LogId.D_5300`
  - 取得失敗（404）: `LogId.W_5300`
  - 取得失敗（その他/例外）: `LogId.E_5300`

## 3. 例外処理の境界

- `Repository`
  - HTTP 異常時は `LogId.E_5300` を記録し `IOException` を送出する。
  - `InterruptedException` は `Thread.currentThread().interrupt()` を実行のうえ `RuntimeException` でラップして送出する。
- `Service`
  - `loadAll` は例外を捕捉して `LogId.E_5301` を記録し、`0` を返す。
  - `getLoaded` / `getLoadedLoots` / `clearCache` は内部で例外を起こさない（キャッシュ参照のみ）。

## 4. スレッド上の注意

- 起動時の `loadAll()` は `Bukkit.getScheduler().runTaskAsynchronously` で非同期実行される。
- `item` 機能の `ItemStackFactory#appendBundleLootLore` から参照される場合、`LootService.getLoaded` はメインスレッド・パケット送信スレッド双方から呼び出される可能性があるため、`LinkedHashMap` を直接参照するキャッシュ読み取りはセッション中の書き換えが発生しない前提に依存している。
  - 書き換えタイミングは起動時の `loadAll` と運用上の `clearCache` のみであり、運用中の同時更新は想定外。

## 5. プレイヤー向けメッセージ

`loot` 機能単独のプレイヤー向けメッセージは現時点で定義しない（コマンド未提供）。  
バンドル lore 上に `(未ロード)` が表示された場合は、`LootService` のロードが完了する前にアイテム生成が走ったケースであり、サーバ起動直後の一時的状態として扱う。
