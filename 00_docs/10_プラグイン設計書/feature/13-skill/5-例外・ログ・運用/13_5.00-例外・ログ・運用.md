# 13_5.00-例外・ログ・運用

## 1. 共通エラー方針

| ステータス | 想定トリガー | 対応 |
|---|---|---|
| API スキル一覧取得失敗 | API 一時障害、通信失敗 | `E_5801` を記録し、built-in 定義のみで継続する |
| API スキル詳細取得失敗 | 個別スキル詳細の欠落、通信失敗 | 対象 `skillId` のみ読込失敗として除外する |
| 実装クラス未登録 | 実装漏れ、`implementationId` 不一致 | 対象スキルのみ除外し `W_5801` を記録する |
| `params` 入力不正 | 必須キー不足、型不一致 | 対象スキルのみ除外し `W_5801` を記録する |
| 起動前条件不足 | レベル不足、MP/EN 不足、クールダウン中 | 起動元へ対応するプレイヤーメッセージを表示する |
| 実行時例外 | 実装クラス内部例外 | `E_5802` を記録する |

## 3. 運用上の方針

- `implementationId` と実装クラスの対応は plugin 側の責務とする。
- `params` の詳細構造は plugin 側で定義し、API や filebase の共通スキーマには持ち込まない。
- built-in スキル定義は API マスタ未登録でも起動できるが、通常の executor 登録と同じ検証を通す。
- 通常攻撃用 built-in は `normal_attack_melee`、`normal_attack_bow`、`normal_attack_magic` を用意する。
- `resourceType` により消費対象を切り替える。
  - `MANA`: 現在 MP を参照・消費する。
  - `ENERGY`: 現在 EN を参照・消費する。
- reload 実行時は、前回の定義一覧を丸ごと更新する。
- `SkillService` が保持するクールダウンキャッシュは `起動元 UUID + skillId` 単位で管理する。
- プレイヤー離脱時は `PlayerQuitEvent` で対象 UUID のキャッシュを解放する。
- 期限切れクールダウンは参照時に掃除する。

## 4. TPS 低下防止チェックリスト

スキルおよびスキルツリーの実装では、メインスレッドで行う処理と非同期で行う処理を次の基準で分離する。

| 観点 | 同期処理で行うもの | 非同期処理で行うもの |
|---|---|---|
| Bukkit / Paper API | `Player`、`Inventory`、`World`、サウンド、HUD、パーティクルなどサーバ状態へ触れる処理 | 原則禁止。必要な場合は結果だけをメインスレッドへ戻す |
| API / DB / ファイル IO | クリックイベント、tick、HUD描画、戦闘処理から直接呼ばない | `HttpClient#send`、DBアクセス、永続化ファイル読み書き |
| キャッシュ | 読み取り・即時のローカル状態更新 | APIからの初回ロード、dirty状態の保存 |
| クリック操作 | キャッシュ済み状態の判定、SP/Goldの即時反映、dirtyマーキング | APIへの保存リクエスト送信 |

チェック項目:

- `PlayerInteractEvent`、`InventoryClickEvent`、tick タスク内で `HttpClient#send` や repository の同期 API 通信を呼ばない。
- スキルツリー進行状態はアカウント単位でメモリキャッシュし、未ロード時は操作を保留してロード中メッセージを返す。
- ノード解放・解除はローカルキャッシュを更新して dirty とし、API には定期タスクでスナップショットを非同期一括保存する。
- API 保存失敗時は dirty を戻して次回保存へ回し、クリック処理を通信待ちにしない。
- Bukkit API が必要な表示更新、ステータス再計算、パッシブスキル再同期はメインスレッドへ戻して実行する。
- 新規実装時に「同期でよいか迷う処理」は、Bukkit API 操作以外を非同期候補として扱い、同期化する理由を設計書またはコードコメントで明示する。
