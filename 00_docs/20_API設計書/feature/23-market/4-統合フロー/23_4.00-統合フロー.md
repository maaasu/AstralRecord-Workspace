# 23_4.00-統合フロー

## 1. 出品作成フロー

1. `MarketController` が [[23_1.00-モデル定義]].マーケット出品作成リクエスト を受け取る。
2. `MarketRepository` が Serializable DB トランザクションを開始し、出品枠を判定する。
3. 全 source `inventory_entry` を ID 順に更新ロックし、GAME BAG/HOTBAR 所有・item identity を検証する。
4. `MarketPriceService` がロック取得後の状態で相場見積を作成する。
5. スタック品の場合は source ごとに `inventory_entry` から出品数量を確保する。
6. 個体品の場合は source entry を escrow の削除状態にし、`equipment_instance` または `rune_instance` の所有者・未出品・非装備状態を検証する。
7. `market_listing` と `market_listing_source` を作成する。
8. `market_price_snapshot` を作成する。
9. トランザクションを確定する。

## 2. 相場算出フロー

1. item マスタから `sellPrice` と基本価格を取得する。
2. 個体品の場合、装備/ルーン個体から評価対象属性を取得する。
3. `valuationSignature` と `rollQualityBucket` を作成する。
4. `market_transaction` を次の順で検索する。

    | 順序 | 参照範囲 |
    |---:|---|
    | 1 | 同一 `valuationSignature` |
    | 2 | 同一 `itemId` + 同一強化/状態変化 + 同一品質バケット |
    | 3 | 同一 `itemId` + 同一品質バケット |
    | 4 | 同一 `itemId` |

5. 検索結果から中央値、p25、p75、IQR を算出する。
6. 信頼度と許容価格帯を算出する。
7. `unitPrice` 指定時は `judgement` を返す。

## 3. 購入確定フロー

1. `market_listing` を更新ロック付きで取得する。
2. `ACTIVE` でなければ 409 を返す。
3. buyer と seller が異なることを検証する。
4. 購入数量が `remaining_quantity` 以下であることと、buyer/seller が異なることを検証する。
5. buyer の Gold inventory を更新ロックし、指定数量の合計額を減算する。seller へはまだ加算しない。
6. 指定数量のアイテムを buyer BAG へ移転する。個体品は source entry と instance 所有者を更新する。
7. `remaining_quantity` を減算し、0 の場合だけ `market_listing` を `SOLD` に更新する。
8. `market_transaction` を購入ごとに作成し、更新 entry ID を response 用に収集する。
9. `market_account_state` の成立取引数と Tier 情報を更新する。

## 4. 出品数制限フロー

1. `market_account_state.completed_trade_count` を取得する。
2. Tier 表から `maxListingSlotCount` を算出する（DB 物理列は互換のため `max_active_listing_count`）。
3. `market_listing` の `ACTIVE` / `SUSPENDED` / 売上未受取 `SOLD` 件数を使用済み枠として集計する。
4. 使用済み枠が上限以上なら出品を拒否する。
5. 購入成立時に seller / buyer の成立取引数を加算し、次回出品から上限を反映する。

## 5. Escrow 方針

出品中アイテムは API 管理の escrow 状態として扱う。

| 種別 | 出品時 | キャンセル/期限切れ | 購入成立 |
|---|---|---|---|
| スタック品 | source ごとに出品数量を seller inventory から減算し、出品/source レコードに数量を保持 | 未売却残数だけ seller inventory へ戻す | buyer inventory へ指定数量を付与 |
| 装備個体 | source entry を削除状態にし、出品レコードに `instanceId` を保持 | 同じ source entry を復元 | source entry を buyer BAG へ移し、`equipment_instance.account_id` を buyer へ更新 |
| ルーン個体 | source entry を削除状態にし、出品レコードに `instanceId` を保持 | 同じ source entry を復元 | source entry を buyer BAG へ移し、`rune_instance.account_id` を buyer へ更新 |

二重消費を防ぐため、出品作成・購入・キャンセルは DB トランザクションと更新ロックを使う。

## 6. 売上受取フロー

1. `SOLD` 出品を、論理削除済み receipt を含めて更新ロック付きで取得する。
2. 出品者本人を検証し、同じ `idempotencyKey` の受取済み receipt があればその結果を再生する。
3. 新規受取では約定売上が 1 以上あることを検証し、同一 listing の `market_transaction.seller_proceeds` を合算する。
4. 出品者 Gold inventory へ合算額を加算する。
5. 受取キー、金額、更新済み通貨 entry ID、受取日時を receipt として出品へ保存して論理削除し、出品枠を解放する。
6. 別のキーで受取済み出品を再度受け取ろうとした場合は 409 を返す。
