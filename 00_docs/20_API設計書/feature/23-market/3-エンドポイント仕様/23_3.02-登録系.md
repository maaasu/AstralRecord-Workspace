# 23_3.02-登録系

## マーケット相場見積

HTTPメソッド: `POST`
パス: `/api/market/price-quote`
コントローラ: `MarketController`
アクション物理名: `CreatePriceQuote`

リクエスト:

| 種別 | 名前 | 型 | 必須 | 説明 |
|---|---|---|---|---|
| Body | `accountId` | GUID |  | 所有権確認対象アカウント |
| Body | `itemCategory` | string | ✓ | item カテゴリ |
| Body | `itemId` | string | ✓ | item マスタ ID |
| Body | `instanceType` | string |  | 個体品の種別 |
| Body | `instanceId` | GUID |  | 個体 UUID |
| Body | `quantity` | int | ✓ | 数量 |
| Body | `unitPrice` | long |  | 判定対象単価 |

レスポンス:

| ステータス | 内容 | ボディ |
|---|---|---|
| 200 OK | 見積成功 | [[23_1.00-モデル定義]].相場見積レスポンス |
| 400 Bad Request | 入力不正 | `ProblemDetails` 互換 |
| 401 Unauthorized | API キー未指定または無効 | なし |
| 404 Not Found | item または個体が存在しない | なし |

処理内容:

1. item マスタを取得する。
2. 個体品の場合は装備個体を取得し、必要に応じて所有権を検証する。ルーンはスタック品として item マスタと出品数量だけを評価する。
3. 店売り価格と推奨価格を算出する。
4. 約定履歴から相場を算出する。
5. `unitPrice` が指定されている場合は価格ガード判定を行う。
6. 相場見積レスポンスを返す。

## マーケット出品作成

HTTPメソッド: `POST`
パス: `/api/market/listings`
コントローラ: `MarketController`
アクション物理名: `CreateListing`

リクエスト:

| 種別 | 名前 | 型 | 必須 | 説明 |
|---|---|---|---|---|
| Body | `operationId` | GUID | ✓ | Plugin が採番する出品作成の冪等操作 ID。同じ操作の再送では同じ値を使う |
| Body | `sellerAccountId` | GUID | ✓ | 出品アカウント UUID |
| Body | `sourceEntries` | object[] | ✓ | `inventoryEntryId` と `quantity` を持つ escrow 元一覧。合計は出品数量と一致 |
| Body | `itemCategory` | string | ✓ | item カテゴリ |
| Body | `itemId` | string | ✓ | item マスタ ID |
| Body | `instanceType` | string |  | 個体品の種別 |
| Body | `instanceId` | GUID |  | 個体 UUID |
| Body | `quantity` | int | ✓ | 出品数量 |
| Body | `currencyId` | string | ✓ | `gold` 固定。Plugin 設定済み Gold 額面を使用する |
| Body | `unitPrice` | long | ✓ | 出品単価 |
| Body | `expiresAt` | DateTime |  | 掲載期限 |
| Body | `createdBy` | GUID | ✓ | 作成者 UUID |

レスポンス:

| ステータス | 内容 | ボディ |
|---|---|---|
| 201 Created | 出品作成成功 | [[23_1.00-モデル定義]].マーケット出品レスポンス |
| 400 Bad Request | 入力不正、価格ガード不合格、出品数上限超過 | `ProblemDetails` 互換 |
| 401 Unauthorized | API キー未指定または無効 | なし |
| 404 Not Found | アカウント、item、出品元が存在しない | なし |
| 409 Conflict | 所有権競合、既に出品中、楽観ロック競合 | `ProblemDetails` 互換 |

処理内容:

1. Serializable transaction の先頭で出品者 `account` 行を更新ロックし、出品者アカウントを検証する。同一accountの player-state 保存・オーブ操作・出品作成はこの親行で直列化する。
2. 出品枠制限を検証する。使用済み出品数は `IX_market_listing_seller_status` を明示して seller/status 範囲だけを読み、個体出品判定用 `IX_market_listing_instance_active_status` を横断走査しない。

   `99a00011`／`99a00012`／`99a00013`／`99a00014`（旧スラッグは互換対象外）の所持数を CURRENCY inventory から再集計し、αは最大6、β／γ／δは各最大9として Tier 基本枠へ加算する。種類ごとの反映上限を超えた所持数は保持するが、枠には加算しない。

    | 項目 | 内容 |
    |---|---|
    | 使用済み出品枠 | `ACTIVE` / `SUSPENDED` / 売上未受取 `SOLD` の出品数 |
    | 上限 | 累計成立取引数から算出した Tier 基本枠 + GAME/CURRENCY inventory のマーケット拡張トークン有効枠 |
    | 上限超過 | 400 を返し、出品は作成しない |

3. 全 source entry を更新ロックして、seller の GAME BAG/HOTBAR 内で item／個体 identity と一致することを検証し、対象アイテムを escrow として確保する。スタックは source ごとに数量を減算し、個体品は source entry を削除状態にする。個体装備では同一 instance の全 status を一つの連続した索引rangeとしてロックし、active loadout 装備中なら拒否する。
4. ロック取得後のitemマスタ・個体値を使って相場見積を内部実行し、itemが取引不可でないこと、単価が売値を上回ること、相場乖離を検証する。売却不可フラグと売値 0 は出品対象外にしない。拒否時はtransaction全体をrollbackし、escrow変更を確定しない。
5. `market_listing` を `ACTIVE`、`remainingQuantity = quantity` で作成し、`market_listing_source` に source ごとの確保数量を保存する。
6. `market_price_snapshot` へ出品時見積を保存する。
7. `sellerAccountName` / `sellerAccountSlotIndex` を含む作成した出品を返す。
8. `operationId`、要求hash、確定した出品応答を同じSQL transactionの`market_listing_create_receipt`へ保存する。同じ`operationId`と同じ要求の再送はreceiptを再生し、異なる要求は409を返す。

## 出品作成結果照会

HTTPメソッド: `GET`
パス: `/api/market/listing-create-results/{operationId}?sellerAccountId={sellerAccountId}`
コントローラ: `MarketController`
アクション物理名: `GetCreateListingResult`

応答未受信時に、出品者が`operationId`で確定済みreceiptを照会する。未確定または存在しない操作は404、他者の照会は403、receipt不整合は409を返す。

## マーケット購入確定

HTTPメソッド: `POST`
パス: `/api/market/listings/{listingId}/purchase`
コントローラ: `MarketController`
アクション物理名: `PurchaseListing`

リクエスト:

| 種別 | 名前 | 型 | 必須 | 説明 |
|---|---|---|---|---|
| Path | `listingId` | GUID | ✓ | 出品 UUID |
| Body | `buyerAccountId` | GUID | ✓ | 購入アカウント UUID |
| Body | `quantity` | int | ✓ | 購入数量。出品残数以下、個体品は 1 |
| Body | `idempotencyKey` | string | ✓ | 二重購入防止キー。1〜100 文字 |
| Body | `updatedBy` | GUID | ✓ | 更新者 UUID |

レスポンス:

| ステータス | 内容 | ボディ |
|---|---|---|
| 200 OK | 購入成功 | [[23_1.00-モデル定義]].マーケット取引レスポンス |
| 400 Bad Request | 自分の出品購入、購入数量不正、Gold不足 | `ProblemDetails` 互換 |
| 401 Unauthorized | API キー未指定または無効 | なし |
| 404 Not Found | 出品または購入者アカウントが存在しない | なし |
| 409 Conflict | 購入可能残数不足、状態競合、二重購入競合 | `ProblemDetails` 互換 |

処理内容:

1. `listingId` の出品を更新ロック付きで取得する。
2. 出品状態が `ACTIVE` であることを検証する。
3. 購入者が出品者と異なることを検証する。
4. 購入数量が `remainingQuantity` 以下であることを検証する。
5. 購入者 Gold currency inventory を更新ロックし、購入者 Gold 不足を検証して指定数量分だけ減算する。出品者 Gold は加算しない。
6. escrow 中のアイテムを指定数量だけ購入者 BAG へ移転する。通常品は category を一意キーに含めず同一 item ID の非個体 stack に併合し、スロット未確定の stack を優先する。個体品は source entry を移し、個体所有者も更新する。
7. `remainingQuantity` を減算し、0 になった場合だけ出品を `SOLD` に更新する。
8. `market_transaction` を購入ごとに作成する。
9. seller / buyer の `market_account_state.completed_trade_count` を更新する。
10. 購入者の Gold・取得 item を含む `affectedInventoryEntryIds` を取引 receipt へ永続化し、レスポンスで返す。出品者売上は `SOLD` 後に売上受取 API で加算する。

Web購入の場合は `webOperationId` を指定する。APIは保存済み `market_web_purchase` の本人UUID・アカウント・出品・数量・固定冪等キーを検証する。通常のゲーム内購入は上記の BAG 直入れを維持する。Web購入では Gold 減算、escrowからの購入、約定記録、`player_mail_delivery` の追加、要求の `COMPLETED` 更新を同じ Serializable transaction で確定する。スタック品はメール添付として数量を保持し、個体装備は元の個体IDと強化・耐久・追加性能を保ったまま所有者を購入者へ変更する。メール既読時の player-state snapshot で添付を受け取るまで、購入品は有効な BAG entry を持たない。メールのアイコンと頭テクスチャは購入品の item master に従う。

購入確定時に出品期限 `expiresAt` を再検証し、保留中に期限切れになった購入を拒否する。

## Webマーケット購入

- `POST /api/market/web-purchases/{listingId}?actor_user_uuid={uuid}`: 本人のWeb購入要求を受付。Bodyは `operationId`、`buyerAccountId`、`quantity`。APIキーに加え `X-Donation-Web-Key` で信頼済みWebを確認し、`account.user_id` と本人UUIDを照合する。同じ操作IDと同じ内容は保存済み状態を返し、内容違いは409。ログイン中の未終了アカウントセッションがある場合は `PENDING`、なければ直ちに決済して `COMPLETED` または `FAILED` を返す。
- `GET /api/market/web-purchases/{operationId}?actor_user_uuid={uuid}`: 同じWeb鍵と本人UUIDで要求状態を照会する。本人以外の操作IDは404。
- `GET /api/market/web-purchases/pending/{accountId}`: ゲームサーバーがログイン中アカウントの保留要求を取得する。
- `POST /api/market/web-purchases/{operationId}/process`: ゲームサーバーがアカウントの事前保存境界を保持して購入を確定する。Bodyは通常購入の `buyerAccountId`、`quantity`、`idempotencyKey=web-{operationId:N}`、`updatedBy`、`webOperationId`、`preparedOnline=true`。確定応答を失った場合は同じ内容で再送し、取引receiptを再生する。

本番配置前に AstralRecord DB の `20260926_market_web_purchase.sql` migration を適用し、Web/API両方の `Donations:WebKey` を一致させる。未設定ではWeb購入を受け付けない。
11. 同じ出品・数量・`idempotencyKey` の再送は receipt を再生する。同じキーを別出品または別数量で使用した場合は 409 とする。

補足:

- Gold 額面は Plugin `GoldDenomination` と同じ `99a00001` / `99a00002` / `99a00003` / `99a00004` / `99a00005` / `99a00006` / `99a00007` を API が正本として再構成する。旧ID `gold` / `ast_gold` / `gold_coin` / `gold_ingot` / `gold_block` / `gold_diamond` / `gold_diamond_block` / `yggdrasil_star_core` は移行互換として読み込む。
