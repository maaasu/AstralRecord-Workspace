# 99_3.01-取得系

## 1. 取得系エンドポイント仕様

### Plugin 用 runtime filebase 一括取得

HTTPメソッド: `GET`
パス: `/api/master-data/runtime-filebase`
コントローラ: `MasterDataController`

責務:

API の `FileDatabase:RootPath` 配下から Plugin が実行時に使う移行対象の YAML/JSON を一括取得し、元の UTF-8 テキストのまま配信する。クライアントが任意のパスやカテゴリを指定する仕組みは設けない。

対象ディレクトリは `35.features.skilltree/nodes`、`35.features.skilltree/structures`、`45.features.shop`、`85.shared.recipe`、`51.features.quest`、`52.features.quest_board`、`42.features.gathering`、`43.features.gathering.spawner`、`41.features.mob.spawner`、`65.features.dungeon` に限定する。各カテゴリのマスタファイルだけを対象にし、schema・設計文書・編集用の採番状態は含めない。

リクエスト:

| 種別 | 名前 | 型 | 必須 | 説明 |
|---|---|---|---|---|
| Header | `X-Api-Key` | string | ✓ | 通常 API キー。Plugin の既存 API 設定を使う |

パスやカテゴリを指定する query/body は受け付けない。

レスポンス:

| ステータス | 内容 | ボディ |
|---|---|---|
| 200 OK | 全対象の取得成功 | RuntimeFilebaseResponse |
| 401 Unauthorized | API キー未指定/無効 | なし |
| 5xx | ルート設定・列挙・読取・文字コードなどの失敗 | エラー |

#### RuntimeFilebaseResponse

```json
{
  "schemaVersion": 1,
  "files": [
    { "path": "35.features.skilltree/nodes/1000.json", "content": "{\"schemaVersion\":1}" }
  ]
}
```

| フィールド | 型 | 説明 |
|---|---|---|
| `schemaVersion` | int | 配信レスポンスの契約バージョン。現在は `1` |
| `files` | array | 対象マスタの集合 |
| `files[].path` | string | `FileDatabase:RootPath` からの相対パス。区切りは `/` |
| `files[].content` | string | 元ファイルの UTF-8 YAML/JSON テキスト。内容を再生成・変換しない |

API は固定のカテゴリ許可リストからだけ走査し、返却パスが設定ルート外へ出ないことを保証する。読取対象の失敗を `files: []` の成功応答として扱わない。Plugin は起動時の非同期読込と `/masterdata reload` の準備段階で一括取得し、メモリで解析・検証してから公開する。失敗時は旧 snapshot を維持する。API に filebase を配置してから Plugin を展開し、各 Minecraft サーバーへの対象マスタ配布は行わない。既存 item/skill API と Plugin から API への SkillTree runtime snapshot 登録は継続する。

### Geyser ヘッド起動データ取得

HTTPメソッド: `GET`
パス: `/api/geyser/heads`
コントローラ: `GeyserController`
アクション物理名: `GetHeads`

責務:

Geyser Extension が起動時にロードする、マスタ定義のカスタムヘッドテクスチャと未削除登録ユーザー UUID を一度に返す。既存の `MasterDataDB.master_data_entry` を参照し、filebase を直接読み込まない。

リクエスト:

| 種別 | 名前 | 型 | 必須 | 説明 |
|---|---|---|---|---|
| Header | `X-Api-Key` | string | ✓ | API キー |

レスポンス:

| ステータス | 内容 | ボディ |
|---|---|---|
| 200 OK | 取得成功 | Geyser ヘッド起動データ |
| 401 Unauthorized | API キー未指定/無効 | なし |

#### Geyser ヘッド起動データ

物理名: `GeyserHeadsResponse`

| フィールド | 型 | 説明 |
|---|---|---|
| `textures` | string[] | item / mail / mob / skill / class の有効マスタで `icon = PLAYER_HEAD` かつ検証済み `iconTexture` を重複なく文字列昇順で返す。値は Base64 |
| `playerUuids` | GUID[] | `dbo.user.is_deleted = false` の UUID を UUID 昇順で返す。MCID、IP、BAN、権限などは返さない |

`iconTexture` は 16,384 文字以下の Base64 JSON とし、`textures.SKIN.url` が `http` または `https` の `textures.minecraft.net/texture/{1〜64桁の16進数}` である場合だけ有効とする。URL の port、userinfo、query、fragment は許可しない。無効な `iconTexture` は当該テクスチャだけを除外し、レスポンス全体は失敗させない。

Mob の `levels` に `icon` または `iconTexture` がある場合は、基底 Mob の値を継承した有効値をレベルごとに判定する。`skin.texture` は NPC 実体の外見定義であり、`textures` には含めない。

処理内容:

1. 認証パイプラインで `X-Api-Key` を検証する
2. MasterDataDB の有効な item / mail / mob / skill / class payload を取得する
3. `PLAYER_HEAD` の有効 `iconTexture` を集約・重複除外する
4. SQL Server の論理削除されていないユーザー UUID だけを取得する
5. `textures` と `playerUuids` を 200 で返す

### 疎通確認

HTTPメソッド: `GET`
パス: `/api/health`
コントローラ: `HealthController`
アクション物理名: `Get`

責務:

API サーバーへの接続可否を判定するためのレスポンスを返す。
DB やマスタデータの可用性までは保証しない（単純な「アプリケーションが応答可能か」のみ）。

リクエスト:

| 種別 | 名前 | 型 | 必須 | 説明 |
|---|---|---|---|---|
| Header | `X-Api-Key` | string | ✓ | API キー |

レスポンス:

| ステータス | 内容 | ボディ |
|---|---|---|
| 200 OK | 接続成功 | HealthCheckResponse |
| 401 Unauthorized | API キー未指定/無効 | なし |

#### HealthCheckResponse

物理名: `HealthCheckResponse`

| フィールド | 型 | 説明 |
|---|---|---|
| `status` | string | 常に `"ok"` |
| `service` | string | サービス名（`AstralRecordApi`） |
| `timestamp` | DateTime (ISO 8601, UTC) | レスポンス生成時刻 |

処理内容:

1. 認証パイプラインで `X-Api-Key` を検証する
2. `status = "ok"` / `service = "AstralRecordApi"` / `timestamp = DateTime.UtcNow` を組み立てて 200 で返す

### Seeder 実行履歴取得

HTTPメソッド: `GET`
パス: `/api/master-data/seed-runs`
コントローラ: `MasterDataController`
アクション物理名: `GetSeedRuns`

責務:

MasterDataDB Seeder の実行履歴を新しい順で取得する。

リクエスト:

| 種別 | 名前 | 型 | 必須 | 説明 |
|---|---|---|---|---|
| Header | `X-Api-Key` | string | ✓ | API キー |
| Query | `limit` | int | 省略可 | 取得件数。1〜100 に丸める。既定値は 20 |

レスポンス:

| ステータス | 内容 | ボディ |
|---|---|---|
| 200 OK | 取得成功 | Seeder 実行履歴レスポンス の配列 |
| 401 Unauthorized | API キー未指定/無効 | なし |

#### Seeder 実行履歴レスポンス

物理名: `MasterDataSeedRunResponse`

| フィールド | 型 | 説明 |
|---|---|---|
| `seedRunId` | GUID | Seeder 実行 ID |
| `triggerType` | string | 実行契機（`STARTUP` / `SEEDER_API` / `MANUAL`） |
| `status` | string | 実行状態 |
| `sourceRootPath` | string | filebase ルートパス |
| `startedAt` | DateTime (ISO 8601) | 開始日時 |
| `finishedAt` | DateTime (ISO 8601)? | 終了日時 |
| `fileCount` | int | 処理ファイル数 |
| `upsertedCount` | int | 登録・更新件数 |
| `deletedCount` | int | 削除件数 |
| `skippedCount` | int | スキップ件数 |
| `errorMessage` | string? | エラー内容 |

処理内容:

1. 認証パイプラインで `X-Api-Key` を検証する
2. `limit` を 1〜100 に丸める
3. リポジトリで Seeder 実行履歴を取得して 200 で返す

### MasterDataDB 参照状態取得

HTTPメソッド: `GET`
パス: `/api/master-data/health`
コントローラ: `MasterDataController`
アクション物理名: `GetHealth`

責務:

MasterDataDB に有効なマスタエントリが存在し、最後の Seeder 成功状態を参照できるか確認する。

リクエスト:

| 種別 | 名前 | 型 | 必須 | 説明 |
|---|---|---|---|---|
| Header | `X-Api-Key` | string | ✓ | API キー |

レスポンス:

| ステータス | 内容 | ボディ |
|---|---|---|
| 200 OK | 取得成功 | MasterDataDB 参照状態レスポンス |
| 401 Unauthorized | API キー未指定/無効 | なし |

#### MasterDataDB 参照状態レスポンス

物理名: `MasterDataHealthResponse`

| フィールド | 型 | 説明 |
|---|---|---|
| `status` | string | `ok` / `empty` / `degraded` |
| `activeEntryCount` | int | 有効マスタエントリ数 |
| `lastSeedRunId` | GUID? | 直近 Seeder 実行 ID |
| `lastSeedRunStatus` | string? | 直近 Seeder 実行状態（`RUNNING` / `SUCCEEDED` / `FAILED`） |
| `lastSucceededAt` | DateTime (ISO 8601)? | 直近成功日時 |

処理内容:

1. 認証パイプラインで `X-Api-Key` を検証する
2. リポジトリで MasterDataDB の有効エントリ数と直近 Seeder 実行結果を取得する
3. 参照状態を 200 で返す

Plugin の自動再読込監視は、初回応答を比較基準として記録する。以後、`lastSeedRunStatus = SUCCEEDED`、`lastSeedRunId != null`、`lastSucceededAt != null` を満たし、適用済み ID と異なる場合だけ既存のマスターデータ再読込を開始する。失敗・実行中・不完全な応答では再読込せず、次回取得を継続する。
