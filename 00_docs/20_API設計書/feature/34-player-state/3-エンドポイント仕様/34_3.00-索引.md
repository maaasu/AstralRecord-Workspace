# player-state endpoint 索引

| HTTPメソッド | パス | 論理名 |
|:--|:--|:--|
| POST | `/api/player-state/snapshots` | ローカル確定 player-state snapshot の原子的保存・冪等 ACK |
| GET | `/api/player-state/snapshots/{snapshotId}?accountId={accountId}` | 完成 snapshot の結果照会 |

## POST `/api/player-state/snapshots`

成功時は `200 OK` と ACK を返す。新規 apply と同一 `snapshotId` の retry は同じ ACK payload を返す。

`accountControls`は任意sectionで、account所有の選択slot（0～8）とyaw（-180以上180未満）/pitch（-90～90）の有限値を専用expectedVersionで置換する。DB世代競合・世代上限は409、所有account不一致や不正値は400、削除済みaccountは404でsnapshot全体をrollbackする。ADMIN/PLAYER共通。同snapshot再送は固定ACKだけを返し再更新せず、section未指定では旧hash・操作列を維持する。

`playTime`は任意sectionで、`{accountId, deltaSeconds}`を受け付ける。差分は0以上のInt64秒数。導入後のPLAYERモード経過時間だけを既存transaction内で`account.play_time_seconds`へ加算し、ACKへ`playTime:{accountId,totalSeconds}`を返す。APIキー認証済みPluginがPLAYER区間だけを測定して送る正本となる。保存待ちの間のADMIN→PLAYER→ADMIN切替でもPLAYER区間の差分を含むため、APIは現在・次modeで過去区間を判定せず、所有権・差分非負・累計上限・snapshot冪等性を検証する。累計負数、加算overflowは409、account不一致・負差分・不正JSONは400でsnapshot全体をrollbackする。削除済みaccountは404。section未指定では列・ACKを変更せず、旧requestのhashも変えない。同snapshot再送は以前のACKのみ返し二重加算しない。[[41_0.00-概要（API）]]を参照。

入手直後の未保存装備にローカル強化・超越・エンチャント・ルーン装着を行った場合も、`equipment.isNew=true` の完成状態として受理する。初期値への制限は設けず、支払い inventory と新規装備・stat roll・装着 child を同じ transaction で確定する。

保存前に全sectionの構造を検証する。ID重複、負数、不正slot、正規化後のeffect/group/node重複、inventory内のslot重複・スロットなしstack item重複、新規 inventory / loadout / equipment の作成属性不足は `400`。`accountProgress` の最高レベル、転生前レベル、EXPポイント端数も同時検証し、転生中は `level < rebirthOriginalLevel <= highestLevel` かつ端数0～99、転生外は端数0とする。既存親へ作成属性を送る要求も `400` とする。DBの所有権・保存済み版と照合して初めて判明する競合は `409`。

`targetVersion` はローカルモデル世代のhintであり、保存済み版との競合判定には使用しない。先行ACKで `expectedVersion` だけをリベースした結果、`targetVersion <= expectedVersion` となっても受理する。保存版はDBの現在版から進める。

`learnedSkills` は同じ外側transaction内でflushしてから `skillBindPresets` の参照先を検証する。新規習得は即座にバインド可能になる。忘却前から同じプリセット・同じslotに保存されていた対象accountの`learnedSkillId`は削除後もその位置に保持できるが、削除済みIDの新規設定・別slotへの移動・別accountのIDは拒否する。選択presetを変更する際は旧選択を解除してflushしてから新選択を保存し、一意索引への途中衝突を避ける。後続sectionが失敗した場合はこれらのflushもrollbackする。

`guideProgress` の完全 snapshot は DB にだけ存在する完了手順を競合として拒否する。`adventureRecords` の各 delta は 1 以上とし、現在 count へ加算する。`playerSettings` は account が所有する user ID と一致すること、有効行の完全 ID 集合、既存行の `expectedVersion`、新規 ID の未使用を検証する。

| status | 条件 |
|:--|:--|
| `400` | UUID、負数、duplicate ID、JSON metadata、section payload（waystone ID の空文字・空白のみ・前後空白、101文字以上、大文字小文字非区別重複を含む）が不正 |
| `404` | `accountId` が存在しない、または論理削除済み |
| `409` | snapshot ID の hash 不一致、所有権不一致（忘却前から同じslotに保持された対象accountのバインドを除く）、削除済みskill IDの新規設定・移動、entry 集合/expected timestamp/version の競合、market listing 中の equipment、受取済みまたは配信期間外の mail/login bonus |

transaction の適用順は、account lock、既存 parent の ownership と base state 検証、新規 inventory / equipment / loadout の検証と作成、対象 inventory entry の一括無効化、最終配置、optional section 更新、ACK ledger 記録である。新規親と、それを参照する entry / loadout slot は同じ要求で作成できる。Quest/Login Bonus/Guide/Adventure Record/Player Setting/Mail は同じ外側 transaction に含める。親 inventory を逐次 replace して entry 移動を削除扱いにしない。途中の child 削除 flush や section 競合は外側 transaction を commit しないため、core の素材消費・報酬と各 section を全体 rollback する。core 配列がすべて空なら inventory、entry、equipment、loadout の DB 処理と ACK query を省略する。

### 更新前ロック

管理編集との競合はuser行をaccountより先に直列化する。未退避DRAINING/RECOVERY_REQUIREDの正確なcaptured boot/session/tokenによる最終保存だけを許可し、READY/APPLYINGでは旧sessionの新しい保存も拒否する。通常lease期限後の最終保存例外は本体とskilltree sectionの両方で同じ権限・保存世代を検証する。確定済みsnapshotの同一再送は過去のACKを返すだけで新規変更をしない。詳細は[[40_0.00-概要]]を参照する。

SQL Serverでは、所持品のロック後、装備変更・ロードアウト・entry参照に含まれる装備IDをまとめて扱う。既存装備とロードアウトの出品確認範囲をSQL ServerのGUID順で取得してから、装備本体を同じ順で `UPDLOCK, HOLDLOCK` と主キーseekで取得する。出品範囲と装備・討伐・踏破のseekは、固定順の個別SQL文を128件ずつbatch化し、1件ごとのDB往復を避ける。IN句の実行計画にはlock取得順を委ねず、未存在キーのrange保護も維持する。装備の共有範囲ロックを保持したまま出品ロックへ進んだり、ロードアウト段階で別順序の出品確認を追加したりしない。保存済み版・所有権・出品中判定は従来どおり検証し、失敗時は全体をrollbackする。

討伐・踏破記録は、アカウントとマスタIDの自然キーの一意索引をseekし、読み取り時点で `UPDLOCK, HOLDLOCK` を取得する。未登録の記録も同じ範囲を保護し、共有範囲ロックから更新・insertへ同時に昇格する競合を防ぐ。外側transactionの原子性・Serializable分離レベルは維持する。

クエスト状態は、account行とquest親行の更新lockで同一accountの書込を直列化し、自然キーで既存childと照合して追加・変更・削除だけを保存する。自然キーが一致するchildのID・作成情報を保持し、未変更childの更新日時も維持する。SQL Serverのchild読込は既存の親ID先頭の自然キー一意索引をseekし、親lockで書込排他された範囲に限って `READCOMMITTED` を指定する。これにより、全childのDELETE/INSERTとSerializable子主キー範囲lockの交差を避け、異なるaccountのsnapshotを共通application lockで直列化しない。quest親のexpectedVersion検証、外側Serializable transaction、報酬inventory・後続section失敗時の全体rollbackは維持する。旧quest upsert・account clone/deleteもaccount行の更新lockを取得してからchildを書き換える。

inventory親の読込は要求中の親とpet装備親に限定し、新規親がある場合だけnatural key競合確認のため全有効親を読む。entryの読込は変更・expected・delete ID、完全置換対象inventoryの全有効entry、pet装備slot 7に限定する。移動元のexpected行と移動先の変更行は同じID集合で照合し、保存前のtimestamp・所有権、完全置換の旧baseline拒否、選択petとの整合性を維持する。SQL Serverではentry主キー・inventory先頭の有効entry索引を各枝でseekし、無関係な所持entryをscanしない。

## GET `/api/player-state/snapshots/{snapshotId}`

POST の I/O 例外または 408 / 425 / 429 / 5xx により結果が不明になったクライアントが、同じ `snapshotId` と `accountId` の確定結果を照会する。

| status | 条件 |
|:--|:--|
| `200` | 指定 account の完成台帳が存在する。`status: COMPLETED` と保存時の完全な ACK を返す |
| `400` | `snapshotId` または `accountId` が空 UUID |
| `404` | 指定 account の完成台帳が現時点では存在しない |

404 は最初の POST transaction が未完了である場合にも返り得るため、クライアントは失敗確定に使わない。同じ payload と `snapshotId` で POST を一度再送して再照会し、それでも確定結果を得られなければ結果不明として同じ保存ID・完成状態を保持する。backoff後も同一IDで回復を継続し、結果不明を理由に素材・装備を補償したり別IDで再計算したりしない。台帳の ACK は JSON 構造に加えて `snapshotId` と `accountId` の一致を検証し、不一致なら成功として返さない。
