# player-state endpoint 索引

| HTTPメソッド | パス | 論理名 |
|:--|:--|:--|
| POST | `/api/player-state/snapshots` | ローカル確定 player-state snapshot の原子的保存・冪等 ACK |
| GET | `/api/player-state/snapshots/{snapshotId}?accountId={accountId}` | 完成 snapshot の結果照会 |

## POST `/api/player-state/snapshots`

成功時は `200 OK` と ACK を返す。新規 apply と同一 `snapshotId` の retry は同じ ACK payload を返す。

保存前に全sectionの構造を検証する。ID重複、負数、不正slot、正規化後のeffect/group/node重複、inventory内のslot重複・スロットなしstack item重複、新規 inventory / loadout / equipment の作成属性不足は `400`。既存親へ作成属性を送る要求も `400` とする。DBの所有権・保存済み版と照合して初めて判明する競合は `409`。

`targetVersion` はローカルモデル世代のhintであり、保存済み版との競合判定には使用しない。先行ACKで `expectedVersion` だけをリベースした結果、`targetVersion <= expectedVersion` となっても受理する。保存版はDBの現在版から進める。

`learnedSkills` は同じ外側transaction内でflushしてから `skillBindPresets` の参照先を検証する。新規習得は即座にバインド可能になり、削除したskillへのバインドは拒否する。選択presetを変更する際は旧選択を解除してflushしてから新選択を保存し、一意索引への途中衝突を避ける。後続sectionが失敗した場合はこれらのflushもrollbackする。

`guideProgress` の完全 snapshot は DB にだけ存在する完了手順を競合として拒否する。`adventureRecords` の各 delta は 1 以上とし、現在 count へ加算する。`playerSettings` は account が所有する user ID と一致すること、有効行の完全 ID 集合、既存行の `expectedVersion`、新規 ID の未使用を検証する。

| status | 条件 |
|:--|:--|
| `400` | UUID、負数、duplicate ID、JSON metadata、section payload（waystone ID の空文字・空白のみ・前後空白、101文字以上、大文字小文字非区別重複を含む）が不正 |
| `404` | `accountId` が存在しない、または論理削除済み |
| `409` | snapshot ID の hash 不一致、所有権不一致、entry 集合/expected timestamp/version の競合、market listing 中の equipment、受取済みまたは配信期間外の mail/login bonus |

transaction の適用順は、account lock、既存 parent の ownership と base state 検証、新規 inventory / equipment / loadout の検証と作成、対象 inventory entry の一括無効化、最終配置、optional section 更新、ACK ledger 記録である。新規親と、それを参照する entry / loadout slot は同じ要求で作成できる。Quest/Login Bonus/Guide/Adventure Record/Player Setting/Mail は同じ外側 transaction に含める。親 inventory を逐次 replace して entry 移動を削除扱いにしない。途中の child 削除 flush や section 競合は外側 transaction を commit しないため、core の素材消費・報酬と各 section を全体 rollback する。core 配列がすべて空なら inventory、entry、equipment、loadout の DB 処理と ACK query を省略する。

## GET `/api/player-state/snapshots/{snapshotId}`

POST の I/O 例外または 408 / 425 / 429 / 5xx により結果が不明になったクライアントが、同じ `snapshotId` と `accountId` の確定結果を照会する。

| status | 条件 |
|:--|:--|
| `200` | 指定 account の完成台帳が存在する。`status: COMPLETED` と保存時の完全な ACK を返す |
| `400` | `snapshotId` または `accountId` が空 UUID |
| `404` | 指定 account の完成台帳が現時点では存在しない |

404 は最初の POST transaction が未完了である場合にも返り得るため、クライアントは失敗確定に使わない。同じ payload と `snapshotId` で POST を一度再送して再照会し、それでも確定結果を得られなければ結果不明として同じ保存ID・完成状態を保持する。backoff後も同一IDで回復を継続し、結果不明を理由に素材・装備を補償したり別IDで再計算したりしない。台帳の ACK は JSON 構造に加えて `snapshotId` と `accountId` の一致を検証し、不一致なら成功として返さない。
