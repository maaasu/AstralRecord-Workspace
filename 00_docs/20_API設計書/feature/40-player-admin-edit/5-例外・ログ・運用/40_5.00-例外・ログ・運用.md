# 40_player-admin-edit 例外・ログ・運用

## 認可とエラー

| HTTP | 条件 | 対応 |
|---|---|---|
| 400 | 入力・ID・数量・版の形式不正 | 明示エラーを確認して入力訂正 |
| 401 | 共通APIキー不正・未設定 | 配置設定を確認。秘密値を画面やログへ出さない |
| 403 | WebAdminでない・編集所有者が異なる | 元の操作者で再認証 |
| 404 | 対象account/session等が未存在 | 対象IDと元セッションを確認 |
| 409 | 退避未完了・版不一致・参照中entry・容量不足・マスタ不一致等 | 参加制限を保持し、安全条件を再確認 |
| 5xx・timeout | 通信または処理結果不明 | 元のsession/operation IDと正確なpayloadを保持して結果照会・同一再送 |

エラー本文は`ProblemDetails`の`status`と`title`を返す。APIの競合エラーを「反映成功」や「参加制限解除」として扱わない。Webの開始・反映・取消は要求を保護cookieに保存する確認画面を経て、次のPOSTで実行する。応答を受信する前にブラウザが閉じても、送信する操作IDと内容は前の応答で保持済みとなる。

## 導入設定

| 配置先 | 設定 | 用途 |
|---|---|---|
| API | `ApiKey:Key` | 全経路の共通APIキー。runtime登録・退避取得・ACKにも使用 |
| RPG | `api.auth.apiKey` | APIの共通APIキーと同じ値 |
| Proxy / Lobby | `api.apiKey` | APIの共通APIキーと同じ値 |
| API | `PlayerAdmin:RequiredServerIds` | Proxy・Lobby・全RPGの必須ID。空・未登録・役割不足では開始拒否 |
| Web | `AstralRecordApi:ApiKey` | APIの共通APIキーと同じ値。サーバー側だけで送信 |
| RPG | `api.serverId` | 実サーバー固有のID。account session/runtime登録と一致 |
| Proxy / Lobby | `runtime.serverId` | 登録ID。必須一覧と一致 |

管理編集・runtimeの全経路は共通APIキーで認証する。管理編集は操作者のWebAdmin権限と編集所有者を別途確認する。専用Webキー撤去の更新はAPIを先に配備してからWebを更新する。旧APIは専用ヘッダーを要求するため、新Webだけを先に更新しない。既存設定に残るWeb・runtime専用キー項目は更新後の実装では参照しない。

RPGは現在ロード済みのitem/class詳細版を登録する。新しい定義をAPIへ配置した後、RPGのロード定義と版が一致するまでは編集を開始・反映できない。名称等だけの変更でも詳細JSONの版が変わるため、同じ配置版に揃える。

導入はゲームDBとManagementDBの`20261002_player_admin_edit.sql`を通常のmigration runnerで検査・適用した後、API、全RPG/Proxy/Lobby、Webを対応版へ揃える。通常のmaintenanceで入場を閉じて実施する。`--validate-only`はSQLとmanifestの検査だけを行い、DBへ接続しない。実適用・配備は別途許可された運用作業として扱う。

## 保存待ちと復旧

退避中は新規ゲーム操作と新規account sessionを拒否する。既存の正確な保存権限による最終保存と未確定操作の回復は継続する。期限切れの復旧待ちに移った場合も、保存済みと未保存を取り違えず、未退避の既存sessionが最終保存を完了できるよう扱う。

Webは同じ操作者が再認証し、元のsession結果を照会する。通信結果不明の保留操作がある場合は、新しい訂正や取消を止め、元の要求をそのまま確認・再送する。同一operation IDと同一payloadは元receiptを返し、異なる内容は拒否する。

runtime sessionの閉鎖再送は、同account・server・boot・session・tokenが既に閉鎖済みであることを読み取り専用で確認する。再送時の新viewを反映したという意味ではなく、snapshot保存のACKでもない。RPGは別途、最終snapshotと関連保存の成功を確認してから管理編集の退避ACKを送る。

全サーバーの肯定的確認がない、bootが変わった、保存結果が不明、既存account sessionが明示終了していない場合は、反映も取消も行わない。heartbeatやTTLだけを根拠に`Closed`を書き換えたり、参加制限を削除したりしない。起動途中・保存失敗・不明操作を確認して通常の保存回復手順で完了させる。回復不能な場合は保留のまま運用担当へ引き継ぐ。

## サーバー台帳の廃止

開始時の退避対象は必須一覧だけでなく、永続台帳で有効な全登録を含める。古い登録をheartbeat期限で自動除外しない。

サーバーIDを廃止する運用では、旧プロセスの停止、最終保存receipt、旧サーバーが所有したaccount sessionの明示終了、旧bootを参照する未完了編集がないことを確認してから、許可された台帳保守で登録を無効化し必須一覧を更新する。未確認の旧サーバーを無効化して編集を通してはならない。同じIDの役割変更は登録時に拒否する。

## 監査とDB障害

ゲームDBの確定操作台帳にrequest hash、before/after、元編集sessionと操作者・理由を保持する。訂正と参加制限解除はこの台帳と同じcommitで確定する。

ManagementDB監査への投影はoperation IDを主キーとして冪等に行い、対象ユーザー・アカウント・操作者・理由・before/afterを独立して保存する。ManagementDBに到達できない場合もゲームDBの確定結果を再実行せず、未投影台帳から再試行する。

投影処理は失敗時に次を記録し再試行する。

| 項目 | 内容 |
|---|---|
| レベル | Warning |
| テンプレート | `Player admin audit projection will retry.` |
| 出力条件 | ManagementDB投影または確定台帳読取の失敗 |

未完了編集、確定receipt、未投影監査sourceはアカウントのreset/deleteで失わない。編集・投影が完了する前の下位版への戻しや台帳削除を行わない。

## 受入条件

- 参加開始と編集開始が競合しても、制限永続化後に新しい保存権限を取得できない。
- 稼働中アカウントが選択対象と違っても、critical操作・最終保存・quit futureを完了してから編集できる。
- 保存失敗・未完了future・旧boot・未終了session・期限切れで参加制限が勝手に解除されない。
- アイテムの個体ID・roll・ルーン枠・entryとレベル/EXP・クラス進行が同じ反映トランザクションで確定し、容量不足では全変更がrollbackする。
- 確認済み状態やマスタ版が変わると反映を拒否し、旧snapshotが確定訂正を上書きしない。
- 同じ要求の再送で付与や抽選を繰り返さず、ブラウザ閉鎖から元の要求と結果を確認できる。
- WebAdmin・最近の認証・antiforgery・共通APIキー・所有者検証を通さない変更は拒否する。
- ManagementDB障害でゲームの確定結果を再適用せず、復旧後に同じoperation IDの監査を一件だけ投影する。
