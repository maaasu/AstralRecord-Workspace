# 20_5.00-安全編集の導入と検証

## 導入順序

1. DBをバックアップし、`60_tool/13-db-migrate.bat`のmanifestにより`20260921_skilltree_safe_editor.sql`を適用する。既存state世代列はNULLのまま維持し、6表・カラム・制約・indexの検査成功を確認する。新規DBは同期済みinit.sqlを使う。
2. 配置先APIの`SkillTreeRuntime:MigrationKey`へruntime key・共通APIキーと異なる専用値を設定し、デプロイpreflightを通してからAPIを配置する。新テーブルがないAPI起動は許可しない。旧Pluginだけが使用中で未導入accountの従来保存は継続できる。配置後はmigration keyによるread-only runtime GETが成功することを確認する。
3. 対応Pluginを配置して起動する。server IDを重複させず、runtime keyをAPIと合わせる。ノード・構造・class・参照skillのロードとruntime登録が成功したことを確認する。
4. 非空legacy accountは下記の明示移行を行う。空stateは対応Pluginの参加時に現世代へbindする。
5. Webを配置し、本人のマイページからスキルツリー編集を開く。オンライン時は参加先のBASEワールドまたはskill_treeでのみ操作できる。正常退出後に保存済みviewを取得できたaccountはオフライン案を作成できる。

health監視によるSeeder更新成功の検知と自動reloadは維持する。APIのhealth成功は各serverへの適用完了の証明ではない。serverごとのready、boot、publication revision、実ロードgeneration、最終応答を確認する。応答切れ、互換性未対応、view不足時は編集を保留する。

## 明示移行

保持のみの移行は `60_tool/16-maintenance.bat` の `MigratePreview` / `MigrateCommit` で実行できる。対象の明示アカウント限定、またはDB全候補を設定し、入場停止中に各移行先serverの世代一致を確認してpreview/commitする。Dev用は明示アカウント限定を使用する。世代未設定の非空legacy、ノード除去、CP消費元補完は自動承認しない。配布、実行記録を使った再試行、復旧の手順は `60_tool/maintenance/README.md` を参照する。

日常のDev更新は01、本番の配布更新は16の既定Workflowが、配置・必要なseedの後に手動起動を案内し、配布前と異なる起動sessionのready・世代一致を待って移行まで継続する。起動確認済みruntime集合と移行開始時の集合が異なれば移行せず、完了前にも再確認する。未完了runとoperation IDは保持し、配置完了済みの再実行は再配布しない。停止・起動・入場制限の解除は運用者が行い、起動前や移行失敗時に更新完了を主張しない。

対象accountをオフラインにし、保存待ちがないことを確認する。migration keyを付けた管理APIから`migration-state`と旧/新`definitions`を取得し、現状のnode ID集合と消費元を確認する。非空legacyでは元の定義を運営が確認し、`confirmLegacyBaseline=true`を明示する。未知nodeを現行nodeへ読み替えない。

`migrations`へ`previewOnly=true`で、operation ID、from/to generation、expected state version、全node baseline、明示remove集合を渡す。返還一覧・保持node・接続を確認後、同じ内容の`previewOnly=false`を送信する。確定後の再送は同じoperation IDを用いる。previewはDBを変更せず、適用を意味しない。

旧状態のCPノードに消費元classが欠損している場合は、旧新定義の固定class条件が同一で、移行先class snapshotにも存在するときだけ`consumedClassAssignments`へnode IDとclass IDを明示する。previewで割当内容を確認し、同じoperation ID・割当をcommitへ渡す。既存の消費元を変更したり、定義に固定classがないノードを運営判断だけで補完したりしない。

複数accountを移行する場合は、Plugin runtime keyと分離したmigration keyを用いる。移行先serverのruntime GETで現在sessionと実ロードgenerationを確認し、`migration-candidates`を全ページ取得してから、各候補に一意なoperation IDを割り当てる。同一入力のbatchを先に`PREVIEW`で全件確認し、拒否がないbatchだけを同じoperation ID・state version・baseline・remove集合の`COMMIT`として送る。batchは最大100件で、内部では単体移行を逐次実行する。途中でsession、接続状態、state、世代が変わったaccountは個別に拒否されるため、成功済みを維持したまま拒否分だけ再取得・再実行する。DBを直接一括更新してoffline判定、snapshot互換性、移行台帳を迂回しない。

移行は保持または明示除去に限定する。保持nodeの条件/コスト変更、CPクラス廃止、経路切断がある場合は拒否し、別途仕様を伴う移行が必要。CP/PP返還は消費node削除による既存導出残高の回復であり、別途ポイント加算やGold変更を行わない。

### 互換性の判定範囲

移行が保全するのは、対象accountの解放集合・消費ポイントの種別/量・消費元class IDである。旧新の `classes` オブジェクト全体の一致は要求しない。参照する消費元/返還先class IDが移行先に存在し、保持ノードの固定class条件と保存済み消費元が一致していればよい。職業の追加、未参照職業の削除、職業名・説明・アイコン・能力値・使用可能スキル等の変更だけで保持移行を拒否しない。これは職業バランス変更全体の妥当性や残高の再配分を保証する処理ではない。

| 判定 | 維持する理由 / 許容する変更 |
|---|---|
| 保持nodeの存在・配置登録・ポイント種別/コスト・解放条件 | 消失した権利の黙認、消費量や取得条件の読み替えを防ぐ。解放条件の表示専用 `classDisplayName` は比較せず、実条件の `classId`・`playerLevel` と未知の追加条件項目は一致を要求する。未取得nodeの追加・変更、表示/効果/座標だけの変更は比較しない |
| 使用済みCPの消費元ID・固定class条件、除去時の返還先ID | 別職業へのCP付替えと返還先消失を防ぐ。職業定義全体は比較しない |
| 保持集合にrootが存在し、rootから連結していること | 実際に保持する経路の切断を防ぐ。edge全体の一致は不要で、連結を保つ追加・付替えは許容する |
| offline・有効account sessionなし・処理待ち操作なし | ログアウト保存との競合、旧世代への解放予約の後追い適用を防ぐ。未処理予約を自動取消しない |
| state version・旧世代・全node baseline・明示remove/補完集合 | 調査後に更新された進行の上書き、意図しない追加・除去・消費元変更を防ぐ |
| 移行先ready/runtime session/世代、保存snapshot hash | 実際にロードされた定義以外への移行と、同じ世代IDに対する内容のすり替えを防ぐ。旧世代と新世代のhash一致を要求するものではない |
| migration key・operation IDと入力一致・同一transaction | 管理権限の分離と二重適用防止。既存の移行記録を消して回避しない |

保持nodeの解放条件やコストを変更する移行、使用済みCPの職業廃止については、返還・再配分・既得権の扱いが別途必要になるため、この保持移行で自動承認しない。

## 旧バージョン混在・障害

- 世代記録またはaccount session履歴があるaccountは、旧PluginのGET/PUT/全player-state保存を409拒否する。sessionと世代を認識しないPluginへの参加は正常完了しない。導入済みaccountを旧Pluginで遊べるように互換解除しない。
- session期限切れや移動前のbootからは後で確定できない。完了済みsnapshot IDの照会/再送は元のACKを返すだけで再適用しない。
- reload失敗はtree/class/skillの公開を旧snapshotへ戻し、新generationとして報告しない。成功した世代変更で互換性が失われたプレイヤーは保存状態を維持して参加を停止する。
- 世代不一致は全解除/補償を行わない。同一世代の構造不整合だけ従来のrepairを許可する。未確認legacyと正式なnode廃止は上記の移行へ分離する。
- 強制終了・API障害で退出closeが確認できなければ、オフラインと推定せず編集不可。再参加と正常退出で保存済みviewを再公開する。
- account当たり有効案1件、期限7日。取消・期限切れ・再確認・失敗と適用済みを区別する。条件変更案は再送で勝手に読み替えない。

## 検証の範囲

APIのrepository/atomic snapshotテストで所有者拒否、世代差、session失効、重複要求、取消、期限、Gold-only保存権限、解放解除のGold/返還/状態/receiptの同時確定、移行preview/再送/保持条件を検証する。SQL Serverの一時DBではmigration初回/再実行/追加expectation欠落拒否、並行要求とaccount session単一所有を検証する。実行時同様にEF Core再試行strategyを有効にする。

Pluginの全JUnit、resource整合、設計トレーサビリティ、Webの認証/CSRF/要求/結果表示とgeometryを検証する。Web画面はテストデータの実Razor HTMLをローカルブラウザーで表示し、円形ノード、主要情報、広い画面、通常復帰、ドラッグ、ズーム、閉じる詳細、1440px/390px幅で確認する。

Minecraft実クライアントを伴うサーバー移動・強制再起動のend-to-end試験、実スマートフォンのピンチ入力は別環境での確認が必要。ローカルプレビューは本人の実データを変更しないfixtureであり、本番適用の証跡とはしない。
