# 14_3.02-登録系

## 1. 登録系エンドポイント仕様

### 装備インスタンス作成

HTTPメソッド: `POST`
パス: `/api/equipment/instances`
コントローラ: `EquipmentController`
アクション物理名: `CreateInstance`

責務:

MasterDataDB の `item` マスタの装備定義をもとに装備個体を生成して保存する。
ステータス乱数ロールは作成時に実値へ解決され、レスポンスには現在のエンチャント一覧も含まれる。

リクエスト:

| 種別 | 名前 | 型 | 必須 | 説明 |
|---|---|---|---|---|
| Header | `X-Api-Key` | string | ✓ | API キー |
| Header | `Content-Type` | string | ✓ | `application/json` |
| Body | (全体) | [[14_1.00-モデル定義]].装備インスタンス作成リクエスト | ✓ | 生成内容 |

レスポンス:

| ステータス | 内容 | ボディ |
|---|---|---|
| 201 Created | 作成成功 | [[14_1.00-モデル定義]].装備インスタンスレスポンス |
| 400 Bad Request | バリデーション失敗 | エラーオブジェクト |
| 401 Unauthorized | API キー未指定/無効 | なし |
| 404 Not Found | `accountId` または `equipmentId` が未存在 | なし |

処理内容:

1. 認証パイプラインで `X-Api-Key` を検証する
2. リクエストのバリデーション（必須項目）
3. `accountId` の存在確認

    | 項目 | 内容 |
    |---|---|
    | 検索対象 | `dbo.account`（`is_deleted = 0`） |
    | 未存在 | 404 を返す |

4. `equipmentId` の存在確認

    | 項目 | 内容 |
    |---|---|
    | 検索対象 | MasterDataDB の `master_data_entry`（`master_type = 'item'`） |
    | 未存在 | 404 を返す |

5. 装備個体を生成

    | 項目 | 内容 |
    |---|---|
    | `equipmentInstanceId` | `Guid.NewGuid()` |
    | `enhanceLevel` | 0 |
    | `transcendenceRank` | 0 |
    | `runeMaxSlots` | item マスタの `equipment.rune.maxSlots` を解決した値 |
    | `durabilityMax` / `durabilityValue` | item マスタの `durability.max` |
    | `statRolls` | item マスタの `stats[]` の `value` を範囲指定なら乱数解決、固定なら固定値で確定 |

6. 生成結果を 201 で返す
7. 例外時は [[14_5.00-例外・ログ・運用]].インスタンス系 のログを記録し 500 を返す

### オーブ装備操作

HTTPメソッド: `POST`
パス: `/api/equipment/orb-operations`
コントローラ: `EquipmentController`
アクション物理名: `ApplyOrb`

責務:

オーブマスタから `ENHANCE` / `REPAIR` / `TRANSCENDENCE` / `ENCHANT` の効果と条件をAPI側で解決し、オーブ1個、状態変化素材・ゴールドの支払い、抽選、装備更新、operation台帳を AstralRecord DB の単一 Serializable transaction で確定する。

リクエスト:

| 種別 | 名前 | 型 | 必須 | 説明 |
|---|---|---|---|---|
| Header | `X-Api-Key` | string | ✓ | API キー |
| Header | `Content-Type` | string | ✓ | `application/json` |
| Body | (全体) | [[14_1.00-モデル定義]].3.1 オーブ装備操作リクエスト | ✓ | 冪等操作ID、所有者、対象装備、Pluginが直近に解決したオーブentry。消費元の選択は `orbItemId` と共通消費順でAPIが行う。`orbItemId` はtrim後1～128 UTF-16 code unit |

レスポンス:

| ステータス | 内容 | ボディ |
|---|---|---|
| 200 OK | 台帳へ確定した業務結果 | `EquipmentOrbOperationResponse` |
| 400 Bad Request | バリデーション失敗 | エラーオブジェクト |
| 401 Unauthorized | API キー未指定/無効 | なし |
| 409 Conflict | 同じ `operationId` が異なる要求内容で使用済み | `result=OPERATION_CONFLICT` |

処理内容:

1. 認証パイプラインで `X-Api-Key` を検証する
2. `operationId` の台帳行を更新ロックで検索する。同一request hashなら抽選・支払いを含む保存済み業務結果を再利用し、異なる要求なら409にする。再生する現在装備、membership、enchant、stat、runeはcommit前の同じSerializable transaction snapshotから読み、対象を台帳accountが継続所有しGAME BAG/HOTBARまたはactive loadoutに保持する場合は `targetAvailable=true` と現在の `equipment`、譲渡・削除・membership欠落時はfalseと `equipment=null` を返す
3. `IX_market_listing_instance_active_status` の対象個体rangeを `UPDLOCK,HOLDLOCK` し、続けて対象装備、GAME BAG/HOTBARまたはactive loadout membershipの順に更新ロックする。`ACTIVE` / `SUSPENDED` 出品中なら支払い・装備変更なしの `NOT_ELIGIBLE` を台帳へ確定する
4. 同アカウントのGAME BAG/HOTBARにあるcategory=`orb`、itemId一致、数量1以上の通常stackを共通消費順で選ぶ。リクエストの `orbInventoryEntryId` は消費元の選択に使わない
5. オーブと装備のマスタスナップショットから効果、対象slot/rank、次強化レベル、修理量、即時次状態、共通エンチャント候補を解決する
6. 強化は成功率と失敗動作をAPIで一度だけ抽選する。エンチャントは装備ロック保持中に正の32-bit重みをlong合計し、`NextInt64`による重み付き非復元抽選を行い、`effectId` およびlegacy行の `status/type/value` 意味一致を重複除外する
7. 状態変化素材はitemIdごとに集約し、素材がオーブ自身なら必要素材数にオーブ1個を加算する。ゴールドも同transaction内で検証する
8. 業務失敗は支払い・装備変更なしで `NOT_ELIGIBLE` / `PAYMENT_UNAVAILABLE` / `NO_SLOT` / `NO_CANDIDATE` を台帳へ確定する
9. 成功はオーブを必ず1個だけ消費し、素材・ゴールド消費、装備更新、`APPLIED` payloadの台帳保存を同transactionでcommitする
10. 応答消失時は同一POST再送または次のGETで同じ業務結果を取得する。後発更新を巻き戻さないため、業務結果は固定しつつ `targetAvailable` と `equipment` は現在の所有・membershipを再検証して返す

#### 支払い entry の消費順

起点オーブを含む通常アイテム支払いはすべて `itemId` で複数entryから支払う。`BAG`、`HOTBAR` の順に inventory を処理し、各 inventory 内では `slotIndex` の大きい entry から数量を減算または削除する。`slotIndex` 未指定の entry は指定済み slot の後、同順位は `inventoryEntryId` 昇順とする。この順序は Plugin の通常アイテム消費・オーブ支払い予約と共通である。`inventoryEntryId` が明示された他の操作や CURRENCY の額面再構成には適用しない。

HTTPメソッド: `GET`

パス: `/api/equipment/orb-operations/{operationId}?account_id={accountId}`

台帳に確定済みなら200、未確定なら404、不正な空GUIDは400を返す。台帳、現在装備、membership、enchant、stat、runeの全読取は単一Serializable read transaction snapshotで行う。

### ルーン装着

HTTPメソッド: `POST`
パス: `/api/equipment/rune`
コントローラ: `EquipmentController`
アクション物理名: `EquipRune`

責務:

ルーンを装着する。`slotIndex` 未指定時は空きスロットへ自動装着し、指定時はそのスロットを更新する。

リクエスト:

| 種別 | 名前 | 型 | 必須 | 説明 |
|---|---|---|---|---|
| Header | `X-Api-Key` | string | ✓ | API キー |
| Header | `Content-Type` | string | ✓ | `application/json` |
| Body | (全体) | [[14_1.00-モデル定義]].3.5 ルーン装着 | ✓ | 装着内容 |

レスポンス:

| ステータス | 内容 | ボディ |
|---|---|---|
| 200 OK | 装着成功 | [[14_1.00-モデル定義]].装備インスタンスレスポンス（更新後） |
| 400 Bad Request | `slotIndex` が範囲外 / ルーン要件未達 | エラーオブジェクト |
| 401 Unauthorized | API キー未指定/無効 | なし |
| 404 Not Found | 装備個体 or ルーン個体未存在 | なし |

処理内容:

1. 認証検証
2. 装備個体・ルーン個体（[[15_README]]）の取得（未存在は 404）
3. ルーン要件の検証

    | 項目 | 内容 |
    |---|---|
    | `targetSlots` | 装備の `equipment.slot` が許可リストに含まれるか |
    | `requiredEnhanceLevel` | 装備の `enhanceLevel` がルーン要求を満たすか |
    | `allowedRuneIds` | 装備側ホワイトリストに ruleItemId が含まれるか（空なら無制限） |
    | 違反時 | 400 を返す |

4. スロット選択

    | 項目 | 内容 |
    |---|---|
    | `slotIndex` 指定あり | そのスロットを上書き |
    | `slotIndex` 未指定 | 0 〜 `runeMaxSlots - 1` の最小空きを使用 |
    | 空き無し（未指定時） | 400 を返す |

5. 装着レコードを upsert し、更新後レスポンスを 200 で返す

### プリセット有効化

HTTPメソッド: `POST`
パス: `/api/equipment/loadouts/{loadoutId}/activate`
コントローラ: `EquipmentLoadoutController`
アクション物理名: `ActivateLoadout`

責務:

指定プリセットを `isActive = true` にし、同一 `accountId` + `loadoutProfile` の他プリセットを `isActive = false` にする。

リクエスト:

| 種別 | 名前 | 型 | 必須 | 説明 |
|---|---|---|---|---|
| Header | `X-Api-Key` | string | ✓ | API キー |
| Path | `loadoutId` | GUID | ✓ | 対象プリセットUUID |
| Body | `updatedBy` | GUID | ✓ | 更新実行者UUID |

レスポンス:

| ステータス | 内容 | ボディ |
|---|---|---|
| 200 OK | 有効化成功 | [[14_1.00-モデル定義]].ロードアウトレスポンス |
| 401 Unauthorized | API キー未指定/無効 | なし |
| 404 Not Found | 未登録/論理削除済み | なし |

処理内容:

1. 認証検証
2. 対象プリセット取得（未存在は 404）
3. 同 `accountId` + `loadoutProfile` の他プリセットを `isActive = false` に一括更新（トランザクション）
4. 対象を `isActive = true` に更新
5. 200 で返す

## 追記: 装備耐久値更新

HTTPメソッド: `POST`
パス: `/api/equipment/durability`
コントローラ: `EquipmentController`
アクション物理名: `UpdateDurability`

装備インスタンスの `durabilityValue` を更新する。`durabilityMax` を持たない装備は更新対象外とし、存在しない装備と同じく 404 を返す。`durabilityValue` は `0..durabilityMax` に丸めて保存する。

| 種別 | 名前 | 型 | 必須 | 説明 |
|---|---|---|---|---|
| Header | `X-Api-Key` | string | ○ | API キー |
| Header | `Content-Type` | string | ○ | `application/json` |
| Body | `equipmentInstanceId` | uuid | ○ | 更新対象の装備インスタンス ID |
| Body | `durabilityValue` | int | ○ | 更新後の現在耐久値 |
| Body | `updatedBy` | uuid | ○ | 更新者アカウント ID |

| ステータス | 内容 | ボディ |
|---|---|---|
| 200 OK | 更新成功 | 装備インスタンスレスポンス |
| 401 Unauthorized | API キー未指定/無効 | なし |
| 404 Not Found | 装備インスタンス未存在、または耐久値を持たない装備 | なし |

処理内容:

1. 認証検証。
2. transaction内で装備インスタンスを更新ロックし、`updatedBy == accountId` を検証する。未存在、所有不一致、または `durabilityMax` / `durabilityValue` が null の場合は 404。
3. ロック取得後の最新 `durabilityMax` を使い、`durabilityValue` を `0..durabilityMax` に clamp する。
4. `durabilityValue` / `updatedAt` / `updatedBy` だけを更新する。事前読取した `enhanceLevel`、状態ランク、最大耐久等を全行上書きしない。
