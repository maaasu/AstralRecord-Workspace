# 24_2.00-ユースケース

## 1. Plugin からチャレンジを発行する

1. 必須項目と user UUID を検証する。
2. 対象ユーザーが存在し、削除されていないことを確認する。
3. 同じユーザーの未消費・未失効・期限内チャレンジを失効する。
4. 新しいコードを生成し、ハッシュだけを DB に保存する。
5. 平文コード、有効期限、ログイン URL を Plugin へ返す。

## 2. Web からチャレンジを消費する

1. コードから空白とハイフンを除去し、大文字へ正規化する。
2. SHA-256 ハッシュでチャレンジを検索する。
3. 未消費・未失効・期限内であることを検証する。
4. 同一行を状態条件付きで更新して消費時刻を記録する。条件に合う更新は1回だけ成功する。
5. ゲームDBの消費トランザクション内でManagementDBの `player` をupsertし、保存後に消費をcommitする。ManagementDB障害時は消費をrollbackして再試行を許可する。分散トランザクションは使わない。
6. ManagementDBに無効状態のWeb認証情報行がなければ作り、作成済みの`sessionVersion`を取得する。
7. `issueTrustedBrowser=true`かつWeb管理者の場合は、現在の`sessionVersion`に結び付けたランダムトークンを発行し、トークン本体は応答で一度だけ返す。
8. ユーザー、アカウント、Web管理フラグ、`sessionVersion`を返す。

## 3. 固定ID・パスワードでログインする

1. APIはログインID単位の永続試行回数・ロックを確認する。
2. 有効な認証行だけをPBKDF2-HMAC-SHA512で検証する。不在、無効、パスワード不正、ゲーム側で明示削除済みのユーザーはすべて同じ失敗応答にする。
3. 成功時は認証前に読んだ`sessionVersion`を応答へ入れる。並行して認証情報が更新された場合、Web Cookieは次回照合で失効する。
4. ゲームDBにユーザー行がないリセット状態ではManagementDBのMCID、permission=0、空のaccountIdsを返す。ゲームDBに削除済みユーザー行がある場合は失敗する。

## 4. 固定ID・パスワードを管理する

1. Webは保護CookieからUUID、`sessionVersion`、Minecraftコード認証日時を導出してAPIキー付きで送る。
2. 初回有効化・再有効化は5分以内のMinecraftコード認証を必須とする。変更・無効化は同認証または現在パスワードを必須とする。
3. APIは15〜128 Unicode scalarのパスワードを検査し、空白のtrimを行わず、既知の共通語・単純連番・反復・ログインIDを含む値を拒否する。
4. `sessionVersion`を条件とするCASに成功した時だけ更新し、新しい版を返す。無効化はパスワードハッシュだけを削除し、ログインIDは予約保持する。

## 5. コンソールからMCIDを指定して発行する

1. Pluginが完全一致MCIDをAPIへ送る。
2. APIは削除されていない `dbo.user` を最大2件取得する。
3. 1件だけならUUIDとMCIDを返し、Pluginが通常の発行APIを呼ぶ。
4. 0件または複数件ならコードを発行しない。

## 6. Web管理機能を認可する

1. Webは認証Cookieのuser UUIDを使ってAPIへ照会する。
2. APIはManagementDBの `player.web_admin` だけを返す。
3. `true` の場合だけ管理画面を許可する。レコードなし、`false`、API障害はすべて拒否する。
4. 直近5分以内のコード証明、または現在の`sessionVersion`に結び付いた信頼済みブラウザを確認する。信頼済みブラウザの成功時は最終利用日時を更新し、最後の利用から7日間利用がなければ失効させる。重要度による管理操作の分割は行わない。
