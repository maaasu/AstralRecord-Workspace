# 22_3.00-登録系（API）

### トレード確定

HTTPメソッド: `POST`
パス: `/api/trade/commit`
コントローラ: `TradeController`
アクション物理名: `Commit`

リクエスト:

| 種別 | 名前 | 型 | 必須 | 説明 |
|---|---|---|---|---|
| Body | `operationId` | GUID | ✓ | [[22_1.00-モデル定義（API）]].トレード確定要求の冪等キー |
| Body | `playerAAccountId` / `playerBAccountId` | GUID | ✓ | 異なる参加 account |
| Body | `playerAItems` / `playerBItems` | 明細配列 | ✓ | [[22_1.00-モデル定義（API）]].トレード item 明細 |
| Body | `playerAGold` / `playerBGold` | long | ✓ | それぞれが支払う Gold |
| Body | `updatedBy` | GUID | ✓ | 監査更新者 |

レスポンス:

| ステータス | 内容 | ボディ |
|---|---|---|
| 200 OK | 確定成功または同一要求の再送 | [[22_1.00-モデル定義（API）]].トレード確定応答 |
| 400 Bad Request | GUID、数量、Gold、個体数量が不正 | Problem Details |
| 404 Not Found | 参加 account または個体が存在しない | Problem Details |
| 409 Conflict | source entry、所有者、残高、inventory、冪等キーの競合 | Problem Details |

処理内容:

1. operation ID と要求内容を検証し、同一 ID の台帳を排他取得する

    | 項目 | 内容 |
    |---|---|
    | 同一要求 | 保存済み応答を返し、移管・Gold 更新を再実行しない |
    | 異なる要求 | `trade.idempotency_conflict` として 409 を返す |

2. 両 account の GAME BAG、提示元 entry、Gold inventory を serializable transaction でロックする

    | 項目 | 内容 |
    |---|---|
| 通常 item（ルーンを含む） | 数量を起点から減算し、受取 BAG の同一 stack に併合または新規 entry を作成する。新規 entry の `slot_index` は Plugin 再同期で確定する |
| 装備 | entry membership と装備個体 `account_id` を同じ transaction で受取 account へ変更する。移管 entry の `slot_index` は Plugin 再同期で確定する |
    | Gold | 両残高を同時に検証し、正規額面へ書き戻す |

3. affected entry ID を応答と `dbo.trade_commit` 台帳へ保存して commit する

    | 項目 | 内容 |
    |---|---|
    | Plugin 同期 | 成功後に A/B 双方が各 ID を API 正本から再同期する。再同期・保存に失敗しても同じ `operationId` の再送は保存済み応答を返すため、未完了 account だけを回復できる |
    | Plugin の応答不明 | HTTP 送信後の通信喪失・応答解析失敗・5xx は transaction 未確定を証明しないため、Plugin は session を `COMMITTING` として同じ `operationId` を再送する。API が明示した 4xx 業務拒否だけを DB 未変更として `OPEN` へ戻す |
    | 失敗 | transaction を rollback し、DB と台帳を変更しない |
