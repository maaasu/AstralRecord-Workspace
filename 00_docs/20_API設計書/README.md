# 設計書運用ルール（AstralRecord API）

このファイルは `00_docs/20_API設計書/` 配下の設計書構造ルールです。  
全 feature の設計書は本ルールに従って作成・改修します。

本ルールは [[../10_Plugin設計書/README]] と整合しつつ、API（REST）特有の表現を組み込んだものです。
プラグイン設計書と差異のある箇所は本ファイルが優先します。

## feature 一覧

| feature | 内容 |
|---|---|
| `feature/28-release-note` | Markdownリリースノートの公開登録とDiscord通知Outbox |

## 0. 編集ツールと参照記法

- 設計書の編集ツールは **Obsidian** を使用する。
- 別ファイル参照は原則 `[[参照]]`（Wikiリンク）を使用する。
- 通常の Markdown リンクより `[[参照]]` を優先する。
- 別ファイルを参照する場合は、原則としてパス付きではなくファイル名のみを使用する。
  - 例: `[[01_1.00-モデル定義]].ユーザレスポンス`
  - 非推奨: `[[../01-user/1-モデル定義/01_1.00-モデル定義]].ユーザレスポンス`
- プラグイン設計書（`00_docs/10_Plugin設計書/`）の同一機能と相互参照することがある。
  Obsidian でファイル名衝突が発生しないよう、ファイル名先頭の機能番号でプラグイン設計書と揃える。
  - 例: API 側 `user` も `01-user` とし、md ファイルも `01_*` で始める。
  - ただしファイル名の本体（`-` 以降）が衝突する場合は、API 側は接尾辞 `（API）` を付けて区別する。

## 1. ディレクトリ構造（例: 01-user）

```text
20_API設計書/
  README.md
  feature/
    01-user/
      01_README.md
      0-概要/
        01_0.00-概要.md
      1-モデル定義/
        01_1.00-モデル定義.md
      2-ユースケース/
        01_2.00-ユースケース.md
      3-エンドポイント仕様/
        01_3.00-索引.md
        01_3.01-取得系.md
        01_3.02-登録系.md
        01_3.03-更新系.md
        01_3.04-削除系.md          # 必要時
      4-統合フロー/
        01_4.00-統合フロー.md
      5-例外・ログ・運用/
        01_5.00-例外・ログ・運用.md
      9-未決事項/
        01_9.00-未決事項.md         # 必要時
```

カテゴリ番号 `3` は API 設計書では `エンドポイント仕様` に読み替える。
それ以外のカテゴリ番号はプラグイン設計書と同じ意味で扱う。

## 2. 採番ルール

- feature ディレクトリ名は `2桁採番-機能名`（例: `01-user`）
- feature 採番は対応するプラグイン feature と一致させる
  - プラグインに対応 feature がない API 専用機能の場合は、`10` 以降の空き番号を使用する
- feature 直下の README ファイル名は `機能番号_README.md`（例: `01_README.md`）
- カテゴリ番号は 1 桁運用（必要に応じて `10` 以上を使用可）
  - `0`: 概要
  - `1`: モデル定義（Request/Response DTO）
  - `2`: ユースケース
  - `3`: エンドポイント仕様
  - `4`: 統合フロー
  - `5`: 例外・ログ・運用
  - `9`: 未決事項
- md ファイル名は以下形式
  - `機能番号_カテゴリ番号.詳細番号-名称.md`
  - 例: `01_0.00-概要.md`, `01_3.01-取得系.md`
- ファイル名に `[` `]` は使用しない
- ファイル名の区切りは空白ではなく `_` を使用する
- 詳細番号はカテゴリごとに `00` 始まりで `01`, `02`... と 1 ずつ増加
- ディレクトリ内にファイルが 1 つの場合、索引ファイルは作らない

## 3. feature README.md の必須項目

1. 対象実装パス（Controller / Models / Repositories / Entities）
2. 対応プラグイン feature（プラグイン設計書側へのリンク）
3. ドキュメント一覧（推奨順）
4. 依存 feature（API 内部の依存）
5. 更新ルール（変更時に必ず更新する章）

## 4. エンドポイント仕様ルール

- 記載場所: `3-エンドポイント仕様/`
- 詳細ファイルの分割単位は HTTP メソッド区分（取得系/登録系/更新系/削除系）を基本とする。
  エンドポイント数が少ない場合は `3.00` 一本にまとめてよい。
- 論理名（日本語）は「文章」ではなく「単語連結の名詞句（体言止め）」で記載する
  - 例: `ユーザ取得`, `ユーザ登録`, `権限更新`（`ユーザを取得する` のような文章形は使わない）
- 各エンドポイントには以下の **テンプレート見出し** を必ず含める

```text
### <論理名>

HTTPメソッド: `GET`
パス: `/api/user/{uuid}`
コントローラ: `UserController`
アクション物理名: `GetUser`
```

- `アクション物理名` は実装メソッド名と一致させる
- 別ファイルで定義されたエンドポイント仕様を参照する場合は `[[ファイル名]].論理名` の形式で記載する
  - 例: `[[01_3.03-更新系]].権限更新`
- DTO（Request / Response）はモデル定義（`1-モデル定義/`）で定義し、本文では論理名で参照する
  - 例: `### ユーザレスポンス` の下に `物理名: UserResponse`
- 別ファイルで定義されたモデルを参照する場合は `[[ファイル名]].モデル論理名` の形式で記載する
  - 例: `[[01_1.00-モデル定義]].ユーザレスポンス`
- 本文では原則として `UserResponse` などの物理名ではなく日本語のモデル論理名を使用する
- リポジトリ呼び出しなど API 内部のメソッド連携を説明する場合、実装メソッド名ではなく論理名を本文に使用する

### 4.1 リクエスト記載ルール

- リクエストは **1 つの表に統合** し、`種別` 列で Path / Query / Header / Body を区別する。
- Body が複雑な場合のみ、Body 内訳を別表（`#### Body 詳細`）に分割してよい。

```text
リクエスト:

| 種別 | 名前 | 型 | 必須 | 説明 |
|---|---|---|---|---|
| Header | `X-Api-Key` | string | ✓ | API キー |
| Path | `uuid` | GUID | ✓ | 対象ユーザの UUID |
| Body | `mcid` | string | ✓ | Minecraft ID |
```

- リクエスト例（HTTP / JSON）は **テンプレートとして必須ではない**。
  実装者が読み解きにくいときのみ補助として記載する。

### 4.2 レスポンス記載ルール

- レスポンスは HTTP ステータスコードごとに表で列挙する。

```text
レスポンス:

| ステータス | 内容 | ボディ |
|---|---|---|
| 200 OK | 取得成功 | [[01_1.00-モデル定義]].ユーザレスポンス |
| 401 Unauthorized | API キー未指定または無効 | なし |
| 404 Not Found | 未登録または論理削除済み | なし |
```

- ボディが存在する場合はモデル論理名で参照する。
- 共通エラー（401 など）は [[5-例外・ログ・運用]] で集約定義し、本文では参照のみとしてよい。

### 4.3 処理内容記載ルール

- 処理内容はプラグイン設計書と同じ「番号付き手順 + 補足表」形式で記載する。
- 抽象表現だけで終わらせず、その番号内に判定条件・取得項目・委譲先・例外時挙動をまとめて記載する。
- 1 つの処理に含まれる検証内容を、別番号へ分離しない。

```text
処理内容:

1. リポジトリで対象ユーザを取得する

    | 項目 | 内容 |
    |---|---|
    | 検索キー | `uuid` |
    | 取得対象 | [[01_1.00-モデル定義]].ユーザレスポンス |
    | 論理削除済み | 取得対象外として扱い 404 を返す |
```

## 5. ログ・エラーレスポンス記載ルール

- 対象は `3-エンドポイント仕様/` および `5-例外・ログ・運用/`
- API のログ・メッセージは原則 **ハードコーディング** されている前提で、ログIDは使用しない。
  - プラグイン設計書のような `LogId.*` 採番は行わない。
  - 設計書には実際にソース上で出力される文字列テンプレートをそのまま記載する。
- ログは、ログを出力する処理番号の直下にインデントして記載する
- `ログ:` のような独立見出しは作らない
- ログは以下の表形式を使用する（`ID` 行は持たない）

```text
4. 例外時は以下ログを記録する

    | 項目 | 内容 |
    |---|---|
    | レベル | Error |
    | テンプレート | `Failed to get user {Uuid}` |
    | 出力条件 | リポジトリ呼び出しで例外発生時 |
    | 引数 | `{Uuid}` = 対象UUID |
```

- テンプレートは `_logger.LogXxx` に渡される文字列をそのまま記載する。
  - 構造化ログのプレースホルダ（`{Uuid}` 等）はバッククォートで囲んで原文どおりに残す。
  - `string.Format` や補間文字列を使う場合は最終的に出力される形を記載する。
- エラーレスポンスボディも同じ形式で記載する。
- ログレベルは .NET の `LogLevel` 表記（`Trace` / `Debug` / `Information` / `Warning` / `Error` / `Critical`）を使う。

## 6. モデル定義ルール

- Request / Response DTO は `1-モデル定義/` でまとめて定義する。
- DTO 名は論理名（日本語）と物理名（C# 型名）を併記する。
  - 例: `### ユーザレスポンス` の下に `物理名: UserResponse`
- 各 DTO は項目表を持つ。

```text
| フィールド | 型 | nullable | 説明 |
|---|---|---|---|
| `uuid` | GUID | ✗ | プレイヤーUUID |
| `accountId` | GUID | ✓ | 選択中アカウントUUID |
```

- 列挙値・固定値は項目表の `説明` 列に記載するか、`#### 列挙` セクションを別に設ける。
- DB Entity との対応は本ファイルには記載せず、`4-統合フロー/` または DB 設計書（`40_database/`）側で扱う。

## 7. 統合フロー記載ルール

- `4-統合フロー/` には Controller → Repository → DB（→ 他 feature API）の流れを記載する。
- プラグイン側の呼び出し元を併記してよい（例: プラグインの `[[01_3.04-リポジトリ]].ユーザ存在確認` から呼ばれる）。
- DB スキーマ詳細は `40_database/` 側、プラグイン側仕様は `00_docs/10_Plugin設計書/` を参照する形にし、ここでは API 視点での委譲関係のみを示す。

## 8. 運用

- 実装変更 PR では対応する設計書も更新する
- API 契約変更（DTO 追加・削除、ステータスコード変更）はプラグイン設計書 / DB 設計書 / Web 設計書も合わせて見直す
- 未確定事項は `9-未決事項/` に集約する
