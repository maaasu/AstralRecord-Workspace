# Skilltree 設計

## 役割

Skilltree は、skill や能力解放の順序、前提関係、選択分岐を定義します。ノード定義と配置・接続構造は filebase JSON を正本とし、プレイヤー別の解放状態は `account-skilltree` API / DB を正本とします。

## 設計方針

- 開始ノード、前提ノード、排他または分岐の意味を明確にします。
- 一本道だけでなく、同程度の進行度に役割の異なる選択肢を用意します。
- 後続ノードが前提ノードの役割を単純に無効化しないようにします。
- 存在しない skill や未実装の解放条件を参照しません。
- ノード効果は `effects[]` に統合し、`skill` と `status` を `type` で識別します。
- ノードの `lore` は任意項目とし、省略時はPluginとエディターでノード固有の説明を表示しません。`lore` を定義する場合は文字列配列とします。
- ノードには任意の `unlockCondition.classId` と `unlockCondition.playerLevel` を設定できます。職業レベル条件は持ちません。
- クラス条件は現在職そのもの、または `unlockClassLevel[].class` を再帰的に辿った祖先職なら成立します。複数経路のいずれかで祖先に到達できれば成立します。
- 条件不成立ノードは通常プレイヤーから非表示とし、解放済みでも効果を停止します。
- `skill` 効果はスキルの所有権ではなく使用許可を付与します。同じクラス条件では、同じスキルの使用許可を複数ノードへ重複定義しません。`unlockCondition.classId` が異なる場合に限り、同じスキルを別ノードへ定義できます。
- `nodeId` は Git 管理の `node-id-sequence.json` を高水位としてエディターが自動採番し、欠番を許容して削除済み ID を再利用しません。Plugin は採番状態を読み込みません。
- 配置は構造 JSON で `nodeId` と相対座標を直接対応させ、`positionId` は使用しません。
- edge は無向接続として端点だけを保持し、edge ID は持ちません。
- 自動配置は編集補助に限定し、採用した最終座標を必ず構造 JSON へ明示保存します。
- Plugin は JSON を読み取り専用で使用し、ゲーム内からノード定義や構造を書き換えません。

## コンテンツ設計

### PPノードの役割

プレイヤーレベルの上昇によって得られる PP を消費するノードを、スキルツリー進行の基礎とします。PP ノードは、通常の成長と比べて選択する意味が明確に感じられる、強めの恒久的な能力・使用許可・ステータス補正を与えます。効果が弱すぎる、または役割が曖昧なノードを PP の消費先にしません。今回のPP調整対象はステータス補正のみとし、新規の `skill` 効果やノード固有説明は追加しません。

PP の獲得量と残高計算は API / Plugin の契約を正本とし、本書ではノードの役割と配置を定めます。CP ノードを追加する場合も JSON 契約に従いますが、PP ノードのために定める中心・地域・再利用の方針を無断で置き換えません。

### 中心と十字方向の進行

- 中心には、すべての職業が利用できる冒険者ノードを置きます。冒険者ノードは原則として `unlockCondition.classId` を持たない PP ノードです。
- 冒険者ノードから、前後左右の十字方向へ接続を伸ばします。中心付近は全職業の基礎能力・共通の選択肢を担わせます。
- 中心から遠いほど、専門性・選択の強さ・前提関係を増やします。距離だけで効果量を機械的に決めるのではなく、接続と PP コストを含めて進行度を設計します。
- 職業・系統のノードは冒険者領域の外側から伸ばします。ソードマン、ハンター、メイジなどの専門系統は、冒険者領域を起点とする枝として読める形にします。

### 職業地域と配置構造

職業別ノードは、職業ごとに地図上の別地域を作りません。同じ方角、中心からの距離帯、外周の輪郭を共有する「職業地域」に配置します。表示条件で他職業のノードが隠れたときにも、プレイヤーから見て不自然に欠けた地図や孤立した島に見えないようにするためです。

職業地域の共有は、すべての職業で個々の座標や能力を一致させる意味ではありません。ただし、共通領域と2つの専門領域を持つ上位職の新規配置は、個別設計で例外を明記しない限り、後述の「上位職の標準円弧配置」に従います。

- 共有するもの: 方角、中心からのおおまかな距離帯、地域全体のシルエット、冒険者領域から到達する流れ。
- 一致を要求しないもの: 個々のnode ID、職業固有の能力、表示内容、許可された座標変換後の具体座標。node数、edge構造、分岐数を標準と異なる形にする場合は、個別設計で例外として明記します。
- 同一座標へ職業別ノードを重ねません。構造 JSON では職業条件の違いにかかわらず相対座標の重複が禁止されているため、同じ職業地域の中で互いに異なる座標を使います。
- 同一職業領域内のedge同士は交差・重複させません。異なる`classId`の職業領域に属する専用edge同士は、配置領域を共有するための交差を許容します。`classId`条件のないnode同士を結ぶ共通領域edgeは、職業専用edgeや領域境界edgeを含む他のいずれのedgeとも交差・重複させません。

### 上位職の標準円弧配置

この節は、共通領域と2つの専門領域を持つ上位職を新規作成または全面再設計する場合の標準配置を定めます。この規則は、特定の職業名、node ID、表示名、能力、保存済み座標を参照せず、配置構造だけを独立した契約として定めます。

この規則の追加前に定義済みの職業領域へは遡及適用しません。既存配置を全面再設計すると明示した場合だけ適用し、座標重複やedge交差を解消する局所調整だけを理由に標準構造へ移行しません。

- status nodeは、共通領域24個と専門領域48個ずつの合計120個を標準とします。能力、pointCost、表示内容、skill nodeの有無は個別設計で定めます。
- 対象領域内部を単一の幹や単一の連結成分に集約せず、四象限へ分散した4本の主円弧で構成します。必要な場合は、主円弧を補助する短い円弧を0〜2本追加できます。
- 主円弧は各22〜35 status nodeを持ち、各々を親領域の異なる地点から独立した入口edgeで接続します。補助円弧も親領域から独立した入口edgeを持たせます。
- 既存職業と同じ座標シルエットを使う場合でも、node IDの対応、内部edge、親入口を複製しません。座標は見た目の基準、edgeは対象職業の能力進行の基準として分け、別々に設計します。
- 親入口は合計4〜6本とし、4本の主円弧がそれぞれ異なる入口から到達できる構造にします。同じ職業条件のskill nodeをstatus nodeへ接続するedgeは親入口数に含めません。
- 各親入口は、親領域と対象領域で同じ象限にあるnode同士を結び、境界edgeの長さを原則6ブロック以内へ収めます。候補が複数ある場合は距離だけで決めず、親nodeの能力から入口nodeの能力へ説明できる進行を優先します。
- 親nodeの能力と直接対応する入口nodeが存在しない場合は、同じ象限で最も近いnodeを選び、個別職業節へ接続距離と採用理由を記載します。見た目の参照元で使われている入口対応を、そのまま別職業へ転用しません。
- 対象領域のstatus nodeだけを抜き出した内部グラフは4〜6個の連結成分で構成し、各成分を木構造とします。内部閉路を作らず、内部edge数をstatus node数から内部成分数を引いた値と一致させます。
- 円形に見せる部分は閉じた輪ではなく、外周に沿って連続する開いた円弧として配置します。円弧の両端をedgeで結ばず、途中の分岐と終端によって進行を作ります。
- 4本の主円弧を北東・北西・南西・南東へ1本ずつ配置します。各象限にはstatus nodeを20個以上置き、各主円弧はX/Zとも20以上の広がりを持たせます。
- 全領域のX幅とZ幅はそれぞれ55以上とし、配置済みnodeは構造原点からX/Zともに`-34`〜`34`へ収めます。他職業と地域を共有する場合は、領域全体へ同一の0.1刻みオフセットを適用して座標重複を避けます。
- 内部edge長の平均は3.3〜4.0を目安とし、局所的な調整を除いて極端な密集または間延びを作りません。円弧内の隣接node間隔を揃え、ギザギザした線や局所的に潰れた円形を残しません。
- 4本の主円弧は、能力や進行内容に応じてnode数、枝数、終端位置を変えて構いません。ただし、1本だけを小さな直線や密集した閉円環にせず、四象限を使う全体シルエットを保ちます。
- skill nodeを置く場合は、関連するstatus nodeから独立leafとして分岐させます。skill nodeの追加を理由にstatus nodeの親入口、主円弧数、内部閉路の規則を変えません。
- 補助自動配置は下書きだけに使用し、最終座標とedgeは構造JSONへ明示保存します。

標準から外れる場合は、構造JSONを編集する前に、status node数、主円弧数、補助円弧数、親入口数、内部成分数、閉路の有無、座標変換、採用理由を個別職業節へ記載します。「職業ごとに異なる配置を許容する」という一般方針だけを根拠に、標準構造から暗黙に逸脱しません。

作成後はJSON Schemaと既存の意味検証に加え、次を設計上の受け入れ条件として確認します。

- status node数、主円弧数、補助円弧数、親入口数、内部成分数が設計どおりであること。
- status node内部のedge数が「status node数 - 内部成分数」と一致し、内部閉路がないこと。
- 四象限すべてに20個以上のstatus nodeがあり、X幅・Z幅が各55以上であること。
- 主円弧ごとにX/Zの広がりが各20以上あり、対象職業だけのプレビューで大きな開いた円弧として読めること。
- 各親入口が対応する主円弧と同じ象限にあり、境界edge長が原則6ブロック以内で、親nodeと入口nodeの能力関係または近接採用理由を説明できること。
- 同一職業領域内のedge同士を交差・重複させず、共通領域edgeは他のいずれのedgeとも交差・重複させないこと。領域境界edgeは、対象職業の表示時に同時表示される共通領域・祖先職・同一職業のedgeと交差・重複させません。対象職業の表示時に隠れる別職業の専用edgeとの交差は許容します。
- 内部edge長の平均が3.3〜4.0を大きく外れず、密集した小円環や直線状の幹になっていないこと。

- root は中心 `(0, 0, 0)` に置き、その周囲に合計6個の無料PP status nodeを環状に置きます。rootから環の6nodeすべてへ接続し、環の外側から既存の後続枝へ接続します。rootは `adventurer_meditation` の使用許可を付与します。旧rootの `MAX_HEALTH / MAX_MANA / MAX_ENERGY` 各10は、テーマに沿って命脈・循環・活風の無料nodeへ移し、無料領域全体のstatus総量を維持します。
- 無料環の6nodeは、全基本能力、全職共通攻撃、物理・魔法防御、HPとMP、三資源、ENと機動の6テーマに分けます。単一職でのみ価値が高い能力に偏らせず、各nodeは直後の通常有料PP nodeより多面的な基礎パッケージとします。割合系statusは職業や装備の特徴とし、無料環では直接付与しません。
- 有料PPは十字の4方向へ小円を1個ずつ置きます。各小円は無料環から2経路へ分岐し、各経路に1PP nodeを3個置き、外端の2PP notableで再合流します。各方向は6個の1PP nodeと1個の2PP notableからなり、4方向合計28node・32PPとします。
- 二つの経路は攻撃、基本能力、耐久、HP、MP、EN、回復を混在させます。同じ能力パッケージを一本道へ連続配置せず、一方向だけを進んでも単一statusだけが伸びない構成とします。
- 1PP nodeは既存の通常・強化パッケージを再利用し、2PP notableは全職で利用できる攻撃、機動、耐久、三資源の4テーマとします。割合系statusは職業や装備の特徴としてPP nodeから外し、すべて `FLAT` の実数系statusで構成します。
- `unlockCondition.playerLevel` は設定せず、接続経路とPP残高で進行を制御します。Player Level 100以上まで拡張する前提で、今回の4小円は内周の基本領域とし、将来はnotableの先から追加クラスタへ伸ばします。
- 冒険者CP基礎幹は、PP小円の間にある北西・北東・南東・南西の斜め4方向へ、北西8node、ほか各7nodeで配置します。中央無料環から直接接続し、PP小円を中継しません。各nodeは1冒険者CPで、`classId: adventurer` を設定します。
- ソードマンCP基礎幹は、冒険者幹の4つの中継nodeから分岐する4枝に27nodeを配置します。各status nodeは1ソードマンCPで、`classId: swordsman` を設定します。

- ソードマスターはソードマン領域の4終端から、四象限に分けた4本の開いた主円弧へ接続します。共通剣技24node、剣聖48node、剣舞48nodeの能力区分を維持し、内部を4成分の木構造として配置します。剣聖は単発火力、会心、貫通、見切り、クールダウン短縮を伸ばし、剣舞は攻撃速度、ENG効率、継続火力、吸収回復を伸ばします。両枝ともskill nodeを混載せず、条件付き挙動は将来のskill実装へ残します。
- シャープシューターのstatus node 120個は定義済みですが、現行の `starter` にはnode、座標、edgeを配置しません。配置設計を確定するまでは未配置とし、ハンター領域からも接続しません。

### ノード能力・表示の再利用

同じ能力を表す既存ノードがある場合は、原則として新規の名称やアイコンを作らずに流用します。たとえば `MAX_HEALTH` を `FLAT` で `10` 増やすノードは、スキルツリー内のどの地域・職業条件で使う場合も、原則として同じ表示名、アイコン、lore、タグを使用します。

- 再利用の正本は [35-skilltree-node-catalog.md](35-skilltree-node-catalog.md) とします。ノードを追加・変更する前に必ず参照します。
- 効果種別、対象ステータスまたは skill ID、補正種別、数値、効果の組合せが同じなら、カタログの表示定義を流用します。プレイヤーへ提示する役割、職業条件、配置位置の違いだけで別名・別アイコン・別 lore・別タグにはしません。
- 数値、対象、補正種別、スキル ID、または効果の組合せが明確に異なる場合は、新しいカタログ項目を作れます。新規項目には既存項目と混同しない名前・アイコン・タグを定めます。`lore` は必要な場合だけ定義し、省略できます。
- バランス上 `pointCost` を変える必要がある場合でも、同じ能力であることを保つため、表示定義はカタログを流用し、変更理由をノード作成時に確認します。
- カタログは表示と能力の一貫性を管理する設計資料です。`nodeId`、職業条件、配置、edge を代替せず、実際のノード定義と構造は filebase JSON を正本とします。
- 正のステータス効果は、`75.shared.status` の `decimalPlaces` で整形したゲーム内表示が `+0` にならない値にします。小数表示しない `HP_REGEN` / `MP_REGEN` を直接付与する場合は、表示値を最低 `+1` とします。

### AI を含む作成時の手順

AI または作成者がスキルツリーノードを追加・変更するときは、次の順で設計します。

1. 追加したい能力を整理し、ノードカタログから同じ効果を探します。
2. 該当項目があれば表示定義を流用し、なければ新しいカタログ項目を定義します。
3. PP ノードなら、冒険者中心・十字方向・既存の職業地域との関係を確認して配置候補を作ります。
4. 職業別ノードは、対応する職業地域に置きます。共通領域と2つの専門領域を持つ上位職は、個別設計に明記した例外がなければ「上位職の標準円弧配置」を使用します。
5. 編集前に、status node数、主円弧数、補助円弧数、内部成分数、閉路の有無、座標変換、占有範囲を配置計画として確定します。親領域からの入口は、親node、入口node、象限、境界edge長、能力上の接続意図を対応表にし、座標の参照元とは独立して決めます。
6. 構造JSONへ保存した後、JSON Schemaと意味検証に加え、四象限のnode数、X/Z幅、内部edge長、境界edge長、同一職業領域内と共通領域edgeの交差、開いた円弧形状、対象職業だけを表示したプレビューを確認します。

## 開発者用エディター

- ローカル Web エディターは `60_tool/skilltree-editor/` に配置します。
- ノード定義、配置、接続の編集は同エディターから行います。
- JSON Schema と意味検証に成功したデータだけを保存し、保存前ファイルをバックアップします。
- JSON Schema が追加された場合、汎用 JSON テキスト編集と Schema 検証をフォールバックとして使用します。
- ゲーム内表示シミュレーションでは現在職とプレイヤーレベルを指定し、Plugin と同じ祖先職・レベル条件でノードと両端が可視な edge だけを表示します。

- ノードタグは`76.shared.tag`のうち`SKILLTREE_NODE`に適用できる定義を日本語名・説明付きで一覧、キャンバス、詳細、編集候補へ表示します。保存JSONにはタグIDだけを記録し、未定義または対象外のタグは保存しません。
- スキル効果は`30.features.skill`から日本語名・説明・種別を読み、一覧・キャンバスのホバー・詳細へ表示します。保存JSONには従来どおり`skillId`だけを記録します。
- キャンバスのノード表示サイズは32～140pxで変更でき、ブラウザのローカル設定へ保持します。構造JSONのブロック座標やPlugin表示サイズは変更しません。
