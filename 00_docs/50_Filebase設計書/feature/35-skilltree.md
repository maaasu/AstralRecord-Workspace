# Skilltree 設計

## 役割

Skilltree は、skill や能力解放の順序、前提関係、選択分岐を定義します。ノード定義と配置・接続構造は filebase JSON を正本とし、プレイヤー別の解放状態は `account-skilltree` API / DB を正本とします。

## 設計方針

- 開始ノード、前提ノード、排他または分岐の意味を明確にします。
- 一本道だけでなく、同程度の進行度に役割の異なる選択肢を用意します。
- 後続ノードが前提ノードの役割を単純に無効化しないようにします。
- 存在しない skill や未実装の解放条件を参照しません。
- ノード効果は `effects[]` に統合し、`skill` と `status` を `type` で識別します。
- ノードの `lore` は任意項目とし、省略時はPluginとエディターでノード固有の説明を表示しません。`lore` を定義する場合は文字列配列とします。
- ノードには任意の `unlockCondition.classId` と `unlockCondition.playerLevel` を設定できます。職業レベル条件は持ちません。
- クラス条件は現在職そのもの、または `unlockClassLevel[].class` を再帰的に辿った祖先職なら成立します。複数経路のいずれかで祖先に到達できれば成立します。
- 条件不成立ノードは通常プレイヤーから非表示とし、解放済みでも効果を停止します。
- `skill` 効果はスキルの所有権ではなく使用許可を付与します。同じクラス条件では、同じスキルの使用許可を複数ノードへ重複定義しません。`unlockCondition.classId` が異なる場合に限り、同じスキルを別ノードへ定義できます。
- `nodeId` は Git 管理の `node-id-sequence.json` を高水位としてエディターが自動採番し、欠番を許容して削除済み ID を再利用しません。Plugin は採番状態を読み込みません。
- 配置は構造 JSON で `nodeId` と相対座標を直接対応させ、`positionId` は使用しません。
- edge は無向接続として端点だけを保持し、edge ID は持ちません。
- 自動配置は編集補助に限定し、採用した最終座標を必ず構造 JSON へ明示保存します。
- Plugin は JSON を読み取り専用で使用し、ゲーム内からノード定義や構造を書き換えません。

## コンテンツ設計

### PPノードの役割

プレイヤーレベルの上昇によって得られる PP を消費するノードを、スキルツリー進行の基礎とします。PP ノードは、通常の成長と比べて選択する意味が明確に感じられる、強めの恒久的な能力・使用許可・ステータス補正を与えます。効果が弱すぎる、または役割が曖昧なノードを PP の消費先にしません。今回のPP調整対象はステータス補正のみとし、新規の `skill` 効果やノード固有説明は追加しません。

PP の獲得量と残高計算は API / Plugin の契約を正本とし、本書ではノードの役割と配置を定めます。CP ノードを追加する場合も JSON 契約に従いますが、PP ノードのために定める中心・地域・再利用の方針を無断で置き換えません。

### 中心と十字方向の進行

- 中心には、すべての職業が利用できる冒険者ノードを置きます。冒険者ノードは原則として `unlockCondition.classId` を持たない PP ノードです。
- 冒険者ノードから、前後左右の十字方向へ接続を伸ばします。中心付近は全職業の基礎能力・共通の選択肢を担わせます。
- 中心から遠いほど、専門性・選択の強さ・前提関係を増やします。距離だけで効果量を機械的に決めるのではなく、接続と PP コストを含めて進行度を設計します。
- 職業・系統のノードは冒険者領域の外側から伸ばします。ソードマン、ハンター、メイジなどの専門系統は、冒険者領域を起点とする枝として読める形にします。

### 職業地域と配置構造

ソードマン、ハンター、メイジなどの職業別ノードは、職業ごとに地図上の別地域を作りません。同じ方角、中心からの距離帯、外周の輪郭を共有する「職業地域」に配置します。表示条件で他職業のノードが隠れたときにも、プレイヤーから見て不自然に欠けた地図や孤立した島に見えないようにするためです。

職業地域の共有は、配置構造そのものを一致させる意味ではありません。各職業は、役割に合わせてノード座標、接続、分岐位置、枝の長さを別に設計できます。たとえば同じ東側の中盤地域に、ソードマンの近接・防御系、ハンターの射程・機動系、メイジの魔力・属性系を置けます。

- 共有するもの: 方角、中心からのおおまかな距離帯、地域全体のシルエット、冒険者領域から到達する流れ。
- 一致を要求しないもの: 個々のノード座標、edge、分岐、ノード数、職業固有の能力。
- 同一座標へ職業別ノードを重ねません。構造 JSON では職業条件の違いにかかわらず相対座標の重複が禁止されているため、同じ職業地域の中で互いに異なる座標を使います。

### 現行の基礎ステータスパッケージ

`starter` 構造は、全職共通・冒険者・一次職の基礎ステータス幹と、実skill解放を定義します。status 効果を持つノードは148個、将来のskill予約枠は10個、実際の `skill` effectは8件、合計166個です。

| 地域 | status node | 消費 | 解放条件 |
|:--|--:|:--|:--|
| root | 1 | PP 0 | なし |
| root直近の無料PP | 8 | PP 0 | なし |
| 有料PP | 29 | PP 29 | 通常ノードはなし。各方向の最終ノードのみPlayer Lv.20～28 |
| 冒険者基礎幹 | 29 | 冒険者CP 29 | `classId: adventurer` |
| ソードマン基礎幹 | 27 | ソードマンCP 27 | `classId: swordsman` |
| ハンター基礎幹 | 27 | ハンターCP 27 | `classId: hunter` |
| メイジ基礎幹 | 27 | メイジCP 27 | `classId: mage` |

- root は中心 `(0, 0, 0)` に置き、上下左右の各方向へ3ブロック間隔で2個ずつ、合計8個の無料PP status nodeを置きます。rootは `MAX_HEALTH / MAX_MANA / MAX_ENERGY` を各10、無料ノードはすべて複数statusの基礎パッケージとします。
- 有料PPは十字の4方向へ北8、東7、南7、西7の順で置き、すべて1PPとします。通常の有料PP status nodeに `unlockCondition.playerLevel` は設定しません。各方向の最終ノードだけを強力なstatus nodeとしてレベル制限付きにし、Player Lv.30までのPP取得量と接続順で進行を制御します。

有料PPのstatus効果はすべて `FLAT` で、同じパッケージを同じ表示定義で再利用します。通常パッケージ、強化パッケージ、最終パッケージの順に効果量を上げ、最終ノードだけに次のPlayer Lv.条件を付けます。

| 方角 | 通常パッケージ | 強化パッケージ | 最終パッケージ（条件） |
|:--|:--|:--|:--|
| 北・攻撃 | `1056, 1060, 1064, 1068`: `ATTACK +3` / `STRENGTH +2` | `1072, 1076, 1080`: `ATTACK +4` / `STRENGTH +3` / `CRITICAL_RATE +0.5` | `1084`: `ATTACK +6` / `STRENGTH +5` / `CRITICAL_RATE +1` / `CRITICAL_DAMAGE +5`（Player Lv.20） |
| 東・命中 | `1057, 1061, 1065, 1069`: `DEXTERITY +3` / `AGILITY +2` | `1073, 1077`: `DEXTERITY +4` / `AGILITY +3` / `ACCURACY +1` | `1081`: `DEXTERITY +6` / `AGILITY +5` / `ACCURACY +2` / `EVASION +1`（Player Lv.24） |
| 南・耐久 | `1058, 1062, 1066, 1070`: `VITALITY +3` / `MAX_HEALTH +25` | `1074, 1078`: `VITALITY +3` / `DEFENSE +3` / `MAX_HEALTH +20` | `1082`: `VITALITY +6` / `MAX_HEALTH +50` / `DEFENSE +5` / `MAGIC_DEFENSE +3`（Player Lv.26） |
| 西・魔力 | `1059, 1063, 1067, 1071`: `INTELLIGENCE +3` / `MAX_MANA +25` | `1075, 1079`: `INTELLIGENCE +4` / `MAX_MANA +30` / `MP_REGEN +0.2` | `1083`: `INTELLIGENCE +6` / `MAX_MANA +60` / `MP_REGEN +0.5` / `MAX_ENERGY +10`（Player Lv.28） |

通常パッケージにはレベル条件を付けず、無料ノードと接続済みの次ノードをPP残高で選べるようにします。最終パッケージは複数の基本能力・派生ステータスをまとめた高効率ノードのため、レベル条件を残します。

- 冒険者CP幹は各方向の2個目の無料PP nodeから始まる隣接レーンへ北8、東7、南7、西7で置き、各nodeを1CPとします。`classId: adventurer` は派生職でも祖先条件として成立し、消費元は冒険者CPのまま維持します。
- 各方向の冒険者CP幹の内側2node目を、3一次職それぞれの独立した入口anchorとします。転職条件となる冒険者Lv.10では9CPを得ているため、4方向を2nodeずつ開く8CPで全入口へ到達できます。残りの冒険者nodeは隣接する別レーンで継続し、一次職の基礎幹をPlayer Lv.30や冒険者幹の完走でゲートしません。
- 一次職は各方向のanchorから、他職の非表示nodeを中継せずに4本の基礎幹を直接伸ばします。各職27nodeはすべて1CPで、Class Lv.28の27CPで全取得できます。今回の27nodeはほぼ全員が取得する基礎配分であり、一次職CP幹のプレイヤーごとの差を作るビルド用status nodeは未実装です。ソードマン地域では `1202` / `1203` / `1204` / `1211` を、ハンター地域では `1207` / `1212` / `1213` を実skill解放として使用します。`1202` はシールドリチャージ、`1203` はバスティオンストライク、`1204` はフレイムラッシュ、`1211` はラストシールド、`1207` はスペルステップ、`1212` はクラッシュアロー、`1213` はヒールアローを参照します。シールドドレインはソードマンの初期配布へ移し、skilltreeには配置しません。PP側の共通ビルド差分は上記の4方向statusパッケージで担います。

### 将来skill予約枠

将来のskill用に、status nodeとは別に10個の予約枠を置きます。内訳はPP地域4、冒険者地域3、ハンター地域1、メイジ地域2です。ソードマン地域の予約枠はすべて実skill解放へ置換済みであり、`1211` は既存予約枠を再利用せずに追加した実skill nodeです。ハンターでは予約枠 `1205` を新規の `1212` へ置換してクラッシュアローを配置し、`1205` は再利用しません。ヒールアローは予約枠を再利用せず、新規の `1213` として追加します。残りのハンター予約枠 `1207` は `hunter_spell_step` へ置換済みです。メイジでは予約枠 `1208` を `mage_sparking` の使用許可へ置換します。

- 予約枠は `effects: []`、`pointCost: 0` とし、地域に対応する `pointType` と `classId` を使用します。
- 現行schemaには絶対ロック専用項目がないため、`unlockCondition.playerLevel: 2147483647` で通常プレイヤーから非表示にする暫定表現です。将来のレベル仕様変更まで含めた絶対ロックではありません。
- 予約枠はstatus幹から分かれる後続なしのleafとし、基礎幹の途中へ挟まず、解放進行を妨げません。
- 実skill IDは参照しません。実skill追加時は予約枠を削除または新しいnodeへ置換し、削除したnode IDを再利用しません。

予約枠 `1202` / `1203` / `1204` はソードマンの `administrator_shield_recharge` / `swordsman_bastion_strike` / `swordsman_flame_rush` 使用許可nodeへ置換済みです。`1211` は `swordsman_last_shield` の使用許可nodeとして `1127` から追加します。`1205` は `1212` へ置換済みで、クラッシュアローを参照します。これらはすべて対応職業CP 1、対応する `classId` とします。

ハンターでは、予約枠 `1205` の座標（`-6, 0, -36`）と `1147` からの接続を維持したまま、node `1212` を `hunter_crash_arrow` の使用許可nodeへ置換します。`1212` はハンターCP 1、`classId: hunter` とし、残りのハンター予約枠 `1206` は将来用に残します。`1207` は `hunter_spell_step` の使用許可nodeへ置換済みです。
`1213` は `hunter_heal_arrow` の使用許可nodeとして `1212` の後段（座標 `-6, 0, -39`）へ新規追加します。`1213` はハンターCP 1、`classId: hunter` とします。

### ノード能力・表示の再利用

同じ能力を表す既存ノードがある場合は、原則として新規の名称やアイコンを作らずに流用します。たとえば `MAX_HEALTH` を `FLAT` で `10` 増やすノードは、スキルツリー内のどの地域・職業条件で使う場合も、原則として同じ表示名、アイコン、lore、タグを使用します。

- 再利用の正本は [35-skilltree-node-catalog.md](35-skilltree-node-catalog.md) とします。ノードを追加・変更する前に必ず参照します。
- 効果種別、対象ステータスまたは skill ID、補正種別、数値、効果の組合せが同じなら、カタログの表示定義を流用します。プレイヤーへ提示する役割、職業条件、配置位置の違いだけで別名・別アイコン・別 lore・別タグにはしません。
- 数値、対象、補正種別、スキル ID、または効果の組合せが明確に異なる場合は、新しいカタログ項目を作れます。新規項目には既存項目と混同しない名前・アイコン・タグを定めます。`lore` は必要な場合だけ定義し、省略できます。
- バランス上 `pointCost` を変える必要がある場合でも、同じ能力であることを保つため、表示定義はカタログを流用し、変更理由をノード作成時に確認します。
- カタログは表示と能力の一貫性を管理する設計資料です。`nodeId`、職業条件、配置、edge を代替せず、実際のノード定義と構造は filebase JSON を正本とします。

### AI を含む作成時の手順

AI または作成者がスキルツリーノードを追加・変更するときは、次の順で設計します。

1. 追加したい能力を整理し、ノードカタログから同じ効果を探します。
2. 該当項目があれば表示定義を流用し、なければ新しいカタログ項目を定義します。
3. PP ノードなら、冒険者中心・十字方向・既存の職業地域との関係を確認して配置候補を作ります。
4. 職業別ノードは、対応する職業地域に置きます。地域の共有と、職業ごとに異なる配置構造を両立させます。
5. JSON Schema と意味検証、特に相対座標重複・到達可能性・表示条件を確認します。

## 開発者用エディター

- ローカル Web エディターは `60_tool/skilltree-editor/` に配置します。
- ノード定義、配置、接続の編集は同エディターから行います。
- JSON Schema と意味検証に成功したデータだけを保存し、保存前ファイルをバックアップします。
- JSON Schema が追加された場合、汎用 JSON テキスト編集と Schema 検証をフォールバックとして使用します。
- ゲーム内表示シミュレーションでは現在職とプレイヤーレベルを指定し、Plugin と同じ祖先職・レベル条件でノードと両端が可視な edge だけを表示します。
- Plugin 設定編集はリポジトリ上の `10_plugin/AstralRecord/src/main/resources/config.yml` を対象とします。稼働環境の設定と filebase へデプロイまたは同期した後、`/masterdata reload` で反映し、エディターから稼働サーバーへ直接書き込みません。
- ステータス効果は`75.shared.status`の日本語名と整形済み値を一覧・キャンバスのホバー・詳細へ表示し、編集候補も日本語名付きで提示します。保存JSONには従来どおり不変IDだけを記録します。
- ノードタグは`76.shared.tag`のうち`SKILLTREE_NODE`に適用できる定義を日本語名・説明付きで一覧、キャンバス、詳細、編集候補へ表示します。保存JSONにはタグIDだけを記録し、未定義または対象外のタグは保存しません。
- スキル効果は`30.features.skill`から日本語名・説明・種別を読み、一覧・キャンバスのホバー・詳細へ表示します。保存JSONには従来どおり`skillId`だけを記録します。
- キャンバスのノード表示サイズは32～140pxで変更でき、ブラウザのローカル設定へ保持します。構造JSONのブロック座標やPlugin表示サイズは変更しません。

## progression

ノードを標準的に解放できる段階は、タグ、接続、コストとカテゴリ設計を合わせて判断します。後続ノードを前提ノードより早い段階へ配置しません。
