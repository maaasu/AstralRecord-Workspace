# Skilltree 設計

## 役割

Skilltree は、skill や能力解放の順序、前提関係、選択分岐を定義します。ノード定義と配置・接続構造は filebase JSON を正本とし、プレイヤー別の解放状態は `account-skilltree` API / DB を正本とします。

## 設計方針

- 開始ノード、前提ノード、排他または分岐の意味を明確にします。
- 一本道だけでなく、同程度の進行度に役割の異なる選択肢を用意します。
- 後続ノードが前提ノードの役割を単純に無効化しないようにします。
- 存在しない skill や未実装の解放条件を参照しません。
- ノード効果は `effects[]` に統合し、`skill` と `status` を `type` で識別します。
- ノードには任意の `unlockCondition.classId` と `unlockCondition.playerLevel` を設定できます。職業レベル条件は持ちません。
- クラス条件は現在職そのもの、または `unlockClassLevel[].class` を再帰的に辿った祖先職なら成立します。複数経路のいずれかで祖先に到達できれば成立します。
- 条件不成立ノードは通常プレイヤーから非表示とし、解放済みでも効果を停止します。
- `skill` 効果はスキルの所有権ではなく使用許可を付与します。同じクラス条件では、同じスキルの使用許可を複数ノードへ重複定義しません。`unlockCondition.classId` が異なる場合に限り、同じスキルを別ノードへ定義できます。
- `nodeId` は Git 管理の `node-id-sequence.json` を高水位としてエディターが自動採番し、欠番を許容して削除済み ID を再利用しません。Plugin は採番状態を読み込みません。
- 配置は構造 JSON で `nodeId` と相対座標を直接対応させ、`positionId` は使用しません。
- edge は無向接続として端点だけを保持し、edge ID は持ちません。
- 自動配置は編集補助に限定し、採用した最終座標を必ず構造 JSON へ明示保存します。
- Plugin は JSON を読み取り専用で使用し、ゲーム内からノード定義や構造を書き換えません。

## パラディン専門枝

`starter` のパラディン領域は、削除済み ID `1378`、`1396`、`1417`、`1435`、`1456`、`1474` を除く `1362`〜`1487` のstatus node 120個と、skill node `1522`〜`1534` の13個で構成する。削除済み ID は再利用しない。status nodeはすべて `pointCost: 1`、`unlockCondition.classId: paladin` とし、既存ソードマンnode `1359` から共通防御領域へ入る。

| 系統 | status node | skill node | 全取得CP | 役割 |
|:--|:--|:--|--:|:--|
| 共通防御 | `1362`〜`1386`（`1378`を除く） | なし | 24 | DEFENSE、MAGIC_DEFENSE、MAX_HEALTH、VITALITY |
| Holy | `1387`〜`1437`（`1396`、`1417`、`1435`を除く） | `1523`〜`1528` | 54 | MAX_SHIELD、SHIELD_RECHARGE_REDUCTION、SUPPORT_POWER、Mana、聖属性skill向け攻撃 |

共通防御は6node円環3個、HolyとGuardianはそれぞれ6node円環6個で構成し、円環間を2nodeの短い経路で接続する。共通防御の外端からHolyを東側、Guardianを西側へ分け、両枝を外周方向へ弧状に広げる。各円環では同系統statusを5個の通常nodeと1個のnotableへまとめる。円環内の隣接node中心間隔は1〜約1.4ブロックとし、旧来の3ブロック以上という配置制約はパラディン領域へ適用しない。

Holyのskill nodeは1か所へ集約しない。パラディンシールド `1527` はMAX_SHIELD円環、ホーリーフィールド `1524` はSUPPORT_POWER円環、ホーリースマイト `1523` とホーリースマッシュ `1525` は同じ攻撃円環の反対側、ディバインチェイサー `1526` は最外周の聖域円環からそれぞれ独立leafとして分岐する。ホーリーコントロール `1528` はホーリースマイト `1523` の子nodeとし、聖柱を操作するため同skillの使用許可を前提にする。Guardianは最外周の回復・最大HP円環 `1487` からディフェンスコンバージョン `1522` とGuard系入口 `1529` を別々に分岐し、`1529`から盾攻撃側の`1530`→`1531`と、防衛制御側の`1532`→`1533` / `1534`へ分ける。Guard系はHolyと反対の西側外周へ配置する。

既存PPノードのレベル条件除去はAPIの世代移行で保持可能とする。同ID・PP種別・コスト・職業条件を維持したプレイヤーレベル条件の除去だけを例外とし、条件の新設・数値変更やCP条件変更は従来どおり互換性検証で拒否する。

パラディン領域の座標範囲はX `-33.9`〜`31.3`、Z `-32.8`〜`31.9` とし、東西へ広がる大きな外周シルエットを作る。パラディン領域内のedge同士は交差・重複させない。異なる職業領域の専用edgeとの交差は許容する。

共通魔導を含む各専門枝の全取得は72CP、全領域は120CPである。Lv100の99CPでは一方の完成形と他系統の一部まで取得できるが、両系統の全取得はできない。エレメンタルは火・氷・雷を均等に伸ばす複数属性型とする。アーケインは高い固定MP消費を持つskillを支える最大MPと攻撃statusへ集中するが、実際のMP消費量に比例してダメージを増やす未実装効果やskill自体は追加しない。

全nodeへZ方向`+0.1`のオフセットを一律適用し、個別nodeだけをずらさない。相対Yは0、座標範囲はX `-33.1`〜`30.5`、Z `-30.9`〜`28.5`とする。4象限すべてに22〜35nodeを配置し、内部edge長の平均は約3.72とする。ウィザード領域内と共通領域edgeとの交差・重複を作らず、異なる職業領域の専用edgeとの交差は許容する。

## コンテンツ設計

### PPノードの役割

プレイヤーレベルの上昇によって得られる PP を消費するノードを、スキルツリー進行の基礎とします。PP ノードは、通常の成長と比べて選択する意味が明確に感じられる、強めの恒久的な能力・使用許可・ステータス補正を与えます。効果が弱すぎる、または役割が曖昧なノードを PP の消費先にしません。今回のPP調整対象はステータス補正のみとし、新規の `skill` 効果やノード固有説明は追加しません。

PP の獲得量と残高計算は API / Plugin の契約を正本とし、本書ではノードの役割と配置を定めます。CP ノードを追加する場合も JSON 契約に従いますが、PP ノードのために定める中心・地域・再利用の方針を無断で置き換えません。

### 中心と十字方向の進行

- 中心には、すべての職業が利用できる冒険者ノードを置きます。冒険者ノードは原則として `unlockCondition.classId` を持たない PP ノードです。
- 冒険者ノードから、前後左右の十字方向へ接続を伸ばします。中心付近は全職業の基礎能力・共通の選択肢を担わせます。
- 中心から遠いほど、専門性・選択の強さ・前提関係を増やします。距離だけで効果量を機械的に決めるのではなく、接続と PP コストを含めて進行度を設計します。
- 職業・系統のノードは冒険者領域の外側から伸ばします。ソードマン、ハンター、メイジなどの専門系統は、冒険者領域を起点とする枝として読める形にします。

### 職業地域と配置構造

職業別ノードは、職業ごとに地図上の別地域を作りません。同じ方角、中心からの距離帯、外周の輪郭を共有する「職業地域」に配置します。表示条件で他職業のノードが隠れたときにも、プレイヤーから見て不自然に欠けた地図や孤立した島に見えないようにするためです。

職業地域の共有は、すべての職業で個々の座標や能力を一致させる意味ではありません。ただし、共通領域と2つの専門領域を持つ上位職の新規配置は、個別設計で例外を明記しない限り、後述の「上位職の標準円弧配置」に従います。

- 共有するもの: 方角、中心からのおおまかな距離帯、地域全体のシルエット、冒険者領域から到達する流れ。
- 一致を要求しないもの: 個々のnode ID、職業固有の能力、表示内容、許可された座標変換後の具体座標。node数、edge構造、分岐数を標準と異なる形にする場合は、個別設計で例外として明記します。
- 同一座標へ職業別ノードを重ねません。構造 JSON では職業条件の違いにかかわらず相対座標の重複が禁止されているため、同じ職業地域の中で互いに異なる座標を使います。
- 同一職業領域内のedge同士は交差・重複させません。異なる`classId`の職業領域に属する専用edge同士は、配置領域を共有するための交差を許容します。`classId`条件のないnode同士を結ぶ共通領域edgeは、職業専用edgeや領域境界edgeを含む他のいずれのedgeとも交差・重複させません。

### 上位職の標準円弧配置

この節は、共通領域と2つの専門領域を持つ上位職を新規作成または全面再設計する場合の標準配置を定めます。この規則は、特定の職業名、node ID、表示名、能力、保存済み座標を参照せず、配置構造だけを独立した契約として定めます。

この規則の追加前に定義済みの職業領域へは遡及適用しません。既存配置を全面再設計すると明示した場合だけ適用し、座標重複やedge交差を解消する局所調整だけを理由に標準構造へ移行しません。

- status nodeは、共通領域24個と専門領域48個ずつの合計120個を標準とします。能力、pointCost、表示内容、skill nodeの有無は個別設計で定めます。
- 対象領域内部を単一の幹や単一の連結成分に集約せず、四象限へ分散した4本の主円弧で構成します。必要な場合は、主円弧を補助する短い円弧を0〜2本追加できます。
- 主円弧は各22〜35 status nodeを持ち、各々を親領域の異なる地点から独立した入口edgeで接続します。補助円弧も親領域から独立した入口edgeを持たせます。
- 既存職業と同じ座標シルエットを使う場合でも、node IDの対応、内部edge、親入口を複製しません。座標は見た目の基準、edgeは対象職業の能力進行の基準として分け、別々に設計します。
- 親入口は合計4〜6本とし、4本の主円弧がそれぞれ異なる入口から到達できる構造にします。同じ職業条件のskill nodeをstatus nodeへ接続するedgeは親入口数に含めません。
- 各親入口は、親領域と対象領域で同じ象限にあるnode同士を結び、境界edgeの長さを原則6ブロック以内へ収めます。候補が複数ある場合は距離だけで決めず、親nodeの能力から入口nodeの能力へ説明できる進行を優先します。
- 親nodeの能力と直接対応する入口nodeが存在しない場合は、同じ象限で最も近いnodeを選び、個別職業節へ接続距離と採用理由を記載します。見た目の参照元で使われている入口対応を、そのまま別職業へ転用しません。
- 対象領域のstatus nodeだけを抜き出した内部グラフは4〜6個の連結成分で構成し、各成分を木構造とします。内部閉路を作らず、内部edge数をstatus node数から内部成分数を引いた値と一致させます。
- 円形に見せる部分は閉じた輪ではなく、外周に沿って連続する開いた円弧として配置します。円弧の両端をedgeで結ばず、途中の分岐と終端によって進行を作ります。
- 4本の主円弧を北東・北西・南西・南東へ1本ずつ配置します。各象限にはstatus nodeを20個以上置き、各主円弧はX/Zとも20以上の広がりを持たせます。
- 全領域のX幅とZ幅はそれぞれ55以上とし、配置済みnodeは構造原点からX/Zともに`-34`〜`34`へ収めます。他職業と地域を共有する場合は、領域全体へ同一の0.1刻みオフセットを適用して座標重複を避けます。
- 内部edge長の平均は3.3〜4.0を目安とし、局所的な調整を除いて極端な密集または間延びを作りません。円弧内の隣接node間隔を揃え、ギザギザした線や局所的に潰れた円形を残しません。
- 4本の主円弧は、能力や進行内容に応じてnode数、枝数、終端位置を変えて構いません。ただし、1本だけを小さな直線や密集した閉円環にせず、四象限を使う全体シルエットを保ちます。
- skill nodeを置く場合は、関連するstatus nodeから独立leafとして分岐させます。skill nodeの追加を理由にstatus nodeの親入口、主円弧数、内部閉路の規則を変えません。
- 補助自動配置は下書きだけに使用し、最終座標とedgeは構造JSONへ明示保存します。

標準から外れる場合は、構造JSONを編集する前に、status node数、主円弧数、補助円弧数、親入口数、内部成分数、閉路の有無、座標変換、採用理由を個別職業節へ記載します。「職業ごとに異なる配置を許容する」という一般方針だけを根拠に、標準構造から暗黙に逸脱しません。

作成後はJSON Schemaと既存の意味検証に加え、次を設計上の受け入れ条件として確認します。

- status node数、主円弧数、補助円弧数、親入口数、内部成分数が設計どおりであること。
- status node内部のedge数が「status node数 - 内部成分数」と一致し、内部閉路がないこと。
- 四象限すべてに20個以上のstatus nodeがあり、X幅・Z幅が各55以上であること。
- 主円弧ごとにX/Zの広がりが各20以上あり、対象職業だけのプレビューで大きな開いた円弧として読めること。
- 各親入口が対応する主円弧と同じ象限にあり、境界edge長が原則6ブロック以内で、親nodeと入口nodeの能力関係または近接採用理由を説明できること。
- 同一職業領域内のedge同士を交差・重複させず、共通領域edgeは他のいずれのedgeとも交差・重複させないこと。領域境界edgeは、対象職業の表示時に同時表示される共通領域・祖先職・同一職業のedgeと交差・重複させません。対象職業の表示時に隠れる別職業の専用edgeとの交差は許容します。
- 内部edge長の平均が3.3〜4.0を大きく外れず、密集した小円環や直線状の幹になっていないこと。

- メイジは27nodeの汎用幹から、魔導・炎・雷・氷の4専門円環へ分岐します。各円環はソードマンと同じ2経路・1notable構造で、全取得は56メイジCPです。`mage_arcane_flow`、`mage_sparking`、`mage_fireball`、`mage_frost_blizzard`、`mage_frost_ball` は関連する小nodeから独立したleafとして分岐します。
- パラディンは共通防御領域からHolyとGuardianへ分岐します。Guardian最外周のnode `1487` から `paladin_defense_conversion` の1CP leaf `1522` と、Guard系入口 `paladin_guard_convert` の1CP node `1529` を別方向へ分岐します。`1529`から盾攻撃側の`paladin_shield_bash` `1530`→`paladin_shield_impact` `1531`、防衛制御側の`paladin_fortress` `1532`→`paladin_guardian_protect` `1533` / `paladin_guardian_chain` `1534`へ接続し、Holy skillとは反対の西側へ配置します。Holy側の既存配置は維持し、skill nodeはstatus nodeへ混載しません。
- ウィザードはメイジ領域の4終端から、四象限に分けた4本の開いた主円弧へ接続します。共通魔導24node、エレメンタル48node、アーケイン48nodeという能力区分を維持しつつ、内部を4成分の木構造として全外周へ分散します。エレメンタルは火・氷・雷のダメージと貫通を同率で伸ばし、アーケインは最大MP、魔法攻撃力、知力、スキルダメージ、魔法防御貫通、詠唱短縮を伸ばします。120nodeはすべてstatus nodeとし、skill使用許可を混載しません。
- ファントムアーチャーは120status nodeと17skill nodeを配置します。ハンター領域の4入口・開いた4円弧を維持し、弱体・貫通・幻影射撃・回復・機動・パッシブを関連statusから独立leafへ接続します。取得経路とCPは本書の専門枝を参照します。
- ソードマスターはソードマン領域の4終端から、四象限に分けた4本の開いた主円弧へ接続します。共通剣技24node、剣聖48node、剣舞48nodeの能力区分を維持し、内部を4成分の木構造として配置します。剣聖は単発火力、会心、貫通、見切り、クールダウン短縮を伸ばし、剣舞は攻撃速度、ENG効率、継続火力、吸収回復を伸ばします。両枝のstatus nodeへskill使用許可を混載せず、既存の静寂一閃node `2402` の配置を維持し、既存スキルnode `2403`〜`2418` の配置も維持します。
- シャープシューターのstatus node 120個と継承の心得のskill node `2240` は定義済みで、現行の `starter` に配置します。`2240` は共通射撃node `2120` から独立leafとして接続し、ハンター領域からは接続しません。ファイアアローnode `2241`、アイスアローnode `2242`、ヒールアローαnode `2255`、拡散する野望node `2257`、ファントムショットnode `2258` も現行 `starter` に配置済みです。
- 冒険者の敏捷幹から `administrator_just_dodge` を独立した1CP leafとして分岐し、ハンターにも同じ効果・表示を再利用した1CP leafを配置します。skill nodeはstatus nodeへ混載せず、関連する基礎幹・専門円環の途中から独立接続します。

### ノード能力・表示の再利用

同じ能力を表す既存ノードがある場合は、原則として新規の名称やアイコンを作らずに流用します。たとえば `MAX_HEALTH` を `FLAT` で `10` 増やすノードは、スキルツリー内のどの地域・職業条件で使う場合も、原則として同じ表示名、アイコン、タグを使用します。

- 再利用の正本は [35-skilltree-node-catalog.md](35-skilltree-node-catalog.md) とします。ノードを追加・変更する前に必ず参照します。
- 効果種別、対象ステータスまたは skill ID、補正種別、数値、効果の組合せが同じなら、カタログの表示定義を流用します。プレイヤーへ提示する役割、職業条件、配置位置の違いだけで別名・別アイコン・別タグにはしません。
- 数値、対象、補正種別、スキル ID、または効果の組合せが明確に異なる場合は、新しいカタログ項目を作れます。新規項目には既存項目と混同しない名前・アイコン・タグを定めます。
- バランス上 `pointCost` を変える必要がある場合でも、同じ能力であることを保つため、表示定義はカタログを流用し、変更理由をノード作成時に確認します。
- カタログは表示と能力の一貫性を管理する設計資料です。`nodeId`、職業条件、配置、edge を代替せず、実際のノード定義と構造は filebase JSON を正本とします。
- 正のステータス効果は、`75.shared.status` の `decimalPlaces` で整形したゲーム内表示が `+0` にならない値にします。小数表示しない `HP_REGEN` / `MP_REGEN` を直接付与する場合は、表示値を最低 `+1` とします。

### AI を含む作成時の手順

AI または作成者がスキルツリーノードを追加・変更するときは、次の順で設計します。

1. 追加したい能力を整理し、ノードカタログから同じ効果を探します。
2. 該当項目があれば表示定義を流用し、なければ新しいカタログ項目を定義します。
3. PP ノードなら、冒険者中心・十字方向・既存の職業地域との関係を確認して配置候補を作ります。
4. 職業別ノードは、対応する職業地域に置きます。共通領域と2つの専門領域を持つ上位職は、個別設計に明記した例外がなければ「上位職の標準円弧配置」を使用します。
5. 編集前に、status node数、主円弧数、補助円弧数、内部成分数、閉路の有無、座標変換、占有範囲を配置計画として確定します。親領域からの入口は、親node、入口node、象限、境界edge長、能力上の接続意図を対応表にし、座標の参照元とは独立して決めます。
6. 構造JSONへ保存した後、JSON Schemaと意味検証に加え、四象限のnode数、X/Z幅、内部edge長、境界edge長、同一職業領域内と共通領域edgeの交差、開いた円弧形状、対象職業だけを表示したプレビューを確認します。

## リメイク構造（remake）

### 目的と切り替え

既存の `starter` を残し、職業ごとに `remake` へ新しい領域を作成します。初回は中心と冒険者領域を配置します。全職業の領域がそろうまで、Plugin の `skilltree.structureId` は `starter` を使用します。切り替え時のプレイヤー別解放状態の移行は別途設計します。

### 共通方針

- 職業領域の新規ノード数は、その職業の最大レベルの約4倍を目安とします。
- Path of Exile 2 のパッシブツリーを参考に、小ノード、ビルドの方向を決める主要ノード（`notable`）、長所と短所を併せ持つキーストーン（`keystone`）、次の職業領域への出口となる道標（`gateway`）を置きます。
- 輪やループで経路に選択肢を作ります。職業ノードはすべて1CPとし、主要ノードとキーストーンの価値は到達経路の長さで調整します。

### 中心とPP予約通路

中心の `(0, 0, 0)` に root のメディテーション（`1047`、0PP）を再利用します。PP領域を後で作り直すため、東西南北の軸に沿う `|x| < 2.6` または `|z| < 2.6` の帯を空けます。この帯に職業ノードを置かず、職業領域の接続も横切らせません。root から各象限の入口 `E` へ伸びる斜めの4本だけは例外です。

#### 受け入れ条件

- 新規ステータスノード240個と既存スキルノード5個の配置を追加し、構造全体で367ノード・426接続になる。
- 自己接続・重複接続・座標重複がなく、root から全ノードへ到達できる。
- 構造全体で任意の2ノード間の距離が1.7ブロック以上あり、共通の端点を持つ組を除くすべての接続が交差・重複しない。
- root 以外の全ノードが `|x| >= 2.6` かつ `|z| >= 2.6` を満たし、root から各入口への4本を除く接続がPP予約通路を横切らない。
- 各象限の効果合計とキーストーン単体の効果を出力し、冒険者の各道標から主要ノード・キーストーン・各道標・既存スキルへの最短到達コストを確認できる。[生成スクリプト](../../../99_work/skilltree-remake/generate_swordsman.py)

## 開発者用エディター

- ローカル Web エディターは `60_tool/05-master-data-editor/` に配置します。
- ノード定義、配置、接続の編集は同エディターから行います。
- JSON Schema と意味検証に成功したデータだけを保存し、保存前ファイルをバックアップします。
- JSON Schema が追加された場合、汎用 JSON テキスト編集と Schema 検証をフォールバックとして使用します。
- ゲーム内表示シミュレーションでは現在職とプレイヤーレベルを指定し、Plugin と同じ祖先職・レベル条件でノードと両端が可視な edge だけを表示します。
- Plugin 設定編集はリポジトリ上の `10_plugin/AstralRecord/src/main/resources/config.yml` を対象とします。稼働環境の設定と filebase へデプロイまたは同期した後、`/masterdata reload` で反映し、エディターから稼働サーバーへ直接書き込みません。
- ステータス効果は`75.shared.status`の日本語名と整形済み値を一覧・キャンバスのホバー・詳細へ表示し、編集候補も日本語名付きで提示します。保存JSONには従来どおり不変IDだけを記録します。
- ノードタグは`76.shared.tag`のうち`SKILLTREE_NODE`に適用できる定義を日本語名・説明付きで一覧、キャンバス、詳細、編集候補へ表示します。保存JSONにはタグIDだけを記録し、未定義または対象外のタグは保存しません。
- スキル効果は`30.features.skill`から日本語名・種別を読み、一覧・キャンバスのホバー・詳細へ表示します。説明文は表示・取得しません。保存JSONには従来どおり`skillId`だけを記録します。
- キャンバスはWebの「スキルツリー編集」画面と同じ配色・形（PPは円、CPは角丸四角、中心を結ぶ直線の接続）で描き、`notable`・`keystone`・`gateway`タグとrootを枠で区別します。ノードの大きさは最も近いノードとのブロック距離に合わせて縮め、枠を重ねません。
- キャンバスの最大ノード表示サイズは32～140pxで変更でき、ブラウザのローカル設定へ保持します。構造JSONのブロック座標やPlugin表示サイズは変更しません。

## Tier2ビルド拡充の習得導線

追加node `2433`〜`2467` のうち、退役したシャープシューター8個を除く27個をstarterへ配置し、全て既存の職業別skill nodeから接続する。各nodeは1CPで、職業条件・skill masterの習得素材条件を維持する。既存の座標と接続は変更せず、新規線分が同一職業領域または共通領域と交差・重複しない位置を使用する。この追加群の末尾は2467。採番の高水位は `node-id-sequence.json` を正本とし、退役時も巻き戻さない。

パラディンは聖域とガードコンバート、シャープシューターは継承と火氷・拡散・幻影射撃、ウィザードは元素・プリズム・維持技能、アークメイジは既存の支援陣・拘束陣・星術から分岐する。固有技能数はパラディン・ウィザード・アークメイジが各17、シャープシューターが9で、祖先職や共用弓の技能を数へ含めない。nodeの使用許可と習得済み個体は別であり、解放後も原石を消費して習得・強化する。
