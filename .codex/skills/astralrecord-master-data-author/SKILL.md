# AstralRecord マスターデータ作成

## 基本ルール

設計資料から本番向けの ファイルベース マスターデータを作成し、単独の想像で補わない。個別ワールドのアイデアは対象 YAML または明示されたワールド文脈に保持し、変更されやすい計画メモではなく安定したモチーフ/進行度コメントを使う。

## 必須コンテキスト

1. `E:\AstralRecord-Workspace\AGENTS.md` を読む。
2. `E:\AstralRecord-Workspace\40_filebase\AGENTS.md` を読む。
3. ファイルベース 設計書を読む。
   - `E:\AstralRecord-Workspace\00_docs\50_Filebase設計書\README.md`
   - 依頼されたカテゴリの `E:\AstralRecord-Workspace\00_docs\50_Filebase設計書\feature\<category>.md`
   - `E:\AstralRecord-Workspace\00_docs\50_Filebase設計書\モチーフ選定ガイド.md`
   - `E:\AstralRecord-Workspace\00_docs\50_Filebase設計書\作成時チェックリスト.md`
4. 対象ディレクトリとスキーマファイルを選ぶために `references/filebase-target-map.md` を読む。
5. マスタファイルを編集または追加する前に、対象 YAML スキーマを読む。
6. 近隣の既存 YAML を確認し、ローカルの形式、参照形式、ID 形式、希少度の命名、値の尺度を把握する。

## アイコン選択ルール

- 新規のアイテムまたはスキルを定義するときは、既存コンテンツで使用済みの `icon` を確認し、原則として再利用しない。
- ただし、モチーフや用途から特定の `icon` が明らかに適切で、別の `icon` に置き換える方が不自然な場合は、既存コンテンツで使用済みでも再利用してよい。ノクスリンゴに `apple` を使うケースが該当する。
- 単なる見た目の近さや実装都合だけでは例外にしない。例外を適用した場合は、採用理由を作業報告へ記載する。

## 並列パッケージのルール

複数担当が ファイルベース マスタを並列作成する場合、個々の YAML ファイルや相互依存する技術レイヤーではなく、整合した最小のプレイ可能なパッケージ単位で分割する。

- パッケージごとに作業ブランチと専用作業ツリーを割り当てる。並列編集担当に書き込み可能な作業ツリー、Git インデックス、チェックアウト済みブランチを共有させない。
- 編集前にパッケージ名前、所有対象のパス、予約済み ID または ID 接頭辞、共有ファイル所有者、他パッケージへの依存関係、予定する完了処理順を記録する。
- 1つの作業ツリー内で参照を検証できる独立した領域 / 戦闘 / 経済パッケージを優先する。依存関係とマージ順が明示されていない限り、モブ、素材、ドロップ報酬連鎖を担当間で分割しない。
- 複数パッケージから共有登録簿、スキーマ、設計書、共通の YAML を編集しない。所有者を1人に割り当てるか、後続の統合作業へ延期する。
- Git が変更のない状態マージと報告しても、重複 ID は意味上の競合として扱う。最新の `develop` にリベースした後、すべての `40_filebase/**/*.yml` を再走査してマスタ ID の重複を確認し、マージ前にパッケージが導入または変更したすべての参照を再検証する。

## 手順

1. 依頼内容を対象グループで分類する。
   - 領域パッケージ: ワールド、敵モブ、モブスポナー、素材、装備、消耗品、必要に応じたドロップ報酬プール/テーブル、ショップ。
   - 戦闘パッケージ: クラス、スキル、バフ、装備、敵、ドロップ報酬。
   - 経済パッケージ: 素材、消耗品、装備、レシピ、ショップ、ドロップ報酬。
2. 整合した新規マスタの最小集合を定義する。接続のない大きな一覧より、完成したプレイ可能なループを優先する。
3. 編集前に ID を確認する。
   - すべての `40_filebase/**/*.yml` から候補 `id` を検索する。
   - 小文字 snake_case の ID を使う。
   - 接頭辞は所有権またはカテゴリの明確化に役立つ場合だけ付ける。ユーザーまたは対象 YAML が示していない領域モチーフを推測しない。
4. スキーマが定めるディレクトリに YAML ファイルを追加する。1 ファイルにつき1つの論理マスタとし、ディレクトリが既存の `v1.<id>.yml` 命名を使っている場合はそれに合わせる。
5. 参照を解決可能な状態に保つ。
   - 対象スキーマに従い、`ref: item:<id>`、`ref: skill:<id>`、`ref: buff:<id>`、`ref: mob:<id>`、ドロップ報酬参照を使う。
   - 新しいモブが新しい素材をドロップする場合は、先に素材を作成する。
   - ドロップ報酬テーブルが新しいプールを参照する場合は、先にプールを作成する。
6. ファイルベース README が定める安定した `motif` と相対的な `progression` の設計コメントを追加し、カテゴリの役割、進行度、希少度、入手難度から値を導く。
7. 報告前に、変更したすべての YAML と `作成時チェックリスト.md` を再読する。
8. 並列パッケージの場合は、後続の完了処理担当が再検証できるよう、所有対象のパス、予約済み ID、依存関係、共有ファイルの判断、予定する完了処理順を報告へ含める。

## 品質基準

- 作成する各マスタは具体的なゲームプレイ目的を持たせる。
- マスタデータのプレイヤー向け文字列は、日本語 MMORPG の利用者向けに日本語で記載する。`name`、`displayName`、`title`、`label`、`description`、`lore`、メール `body`、NPC 操作 `message`、ショップ名前、クエストテキスト、その他プレイヤーに表示・送信されるテキストを含む。
- 技術的な ID、Bukkit 素材名前、列挙型値、参照接頭辞、タグ、実装識別子は、スキーマとプラグインが要求する既存の英語 / 大文字形式を保つ。
- 名前と説明文は、ユーザーが指定または対象 YAML に記録したモチーフに従い、未指定のワールド設定を追加しない。
- ユーザーが開始用の一式を明示的に求めない限り、本番追加に `test`、`sample`、`lab`、`starter` などのデバッグ名前を使わない。
- ユーザーが実装補助を求めていない限り、またはスキーマがリソース参照の存在を要求していない限り、プラグイン/API/Web/Resourcepack ファイルを変更しない。
- 必要な実装機能が不足している場合は、対応していない YAML を作らず、報告に制限を記載する。

## 報告形式

結果は日本語で記載する。

```markdown
## 作成結果
- <追加したプレイ可能なループ / マスタグループの概要>

## 並列所有情報
- パッケージ: <単独作業なら不要 / パッケージ名>
- 所有対象の paths / 予約済み IDs: <対象>
- dependencies / 完了処理 order: <なし / 内容>

## 追加・変更ファイル
- `<path>`: <内容>

## 参照整合
- <主要参照と確認結果>

## 検証
- `<command or manual check>`: 成功 / 失敗 / 未実行（理由）

## 残事項
- なし / <次に作るとよいマスタや要確認事項>
```
