# 設計駆動実装

ユーザーが設計書、仕様、設計書の機能フォルダー、または `E:\AstralRecord-Workspace\00_docs` 配下のパスから実装するよう求めた場合に、この参照を使う。

## 入力の扱い

1. 指定されたすべてのパスを絶対パスに正規化する。
2. 設計書パスが示す実装プロジェクトを特定する。
   - `00_docs/10_Plugin設計書`: 通常は `10_plugin/AstralRecord`。
   - 将来 API/Web 設計書が追加された場合: 設計書ツリーまたはユーザー依頼が示す対応プロジェクトに割り当てる。
3. 設計書ルート README、対象機能概要、挙動または契約を定義する直接参照設計書を読む。
4. 設計書内の実装パス名は意図された場所として扱うが、編集前に実際のプロジェクト配置も確認する。

## 抽出チェックリスト

依頼された実装に必要なものだけを抽出する。

- 機能の責務と対象外。
- コマンド、経路、画面、イベントハンドラー、定期実行する作業、統合入口。
- モデル、DTO、エンティティ、リポジトリ、ファイルベース キー、リソース ID、列挙型、定数、アイテム/素材 ID。
- 状態遷移、永続化ルール、冪等性、並行性、巻き戻し、移行挙動。
- 検証、権限/認証、エラー処理、ユーザーメッセージ、ログ、観測可能性。
- 設計書に記載されたテストまたは受け入れ基準。
- 未決事項と、まだ行われていない設計判断。

## 判断ルール

- 明示された設計判断を実装し、未決の判断を推測で埋めない。
- ユーザーが狭い変更を依頼した場合、設計書が大きな機能を説明していても、その範囲だけを実装する。
- 設計書とコードが一致しない場合は、既存挙動を壊さないために近隣の履歴/パターンを必要な範囲だけ確認する。重要な不一致は報告する。
- 設計がプラグイン/API/Web/データベース/Filebase/Resourcepack をまたぐ変更を要求する場合は、プロジェクトごとに判断理由を分け、各境界契約を検証する。
- ユーザーが設計書変更を求めておらず、実装が必要な文書不一致を明らかにしていない限り、設計書を更新しない。

## 検証

プロジェクト内の確認を優先する。

- プラグイン: ルート `README.md` / `references/plugin-code.md` に記載された Maven コンパイル/テストまたはモジュールを絞ったコマンド。
- API: `references/api-code.md` に従った API プロジェクトの `dotnet build` / 対象を絞ったテスト。
- Web: Web プロジェクトの `dotnet build` / ページ単位の確認。
- データベース/Filebase/Resourcepack: 利用できる場合は文書化された検証ツールまたは構文確認。

確認を利用できない場合は停止要因を説明し、手動で行った整合性確認の概要を含める。
