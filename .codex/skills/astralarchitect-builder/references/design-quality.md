# 参考建築を使う設計と品質評価

新築、再設計、完成度改善、作例収集で読む。チケットの入出力契約は `ticket-contract.md` を正本とする。以下の数値例と採点法は、このスキルの初期運用案であり、検証済みの建築法則やユーザーの好みではない。

## 参考資料の選び方

`reference-library.json` を用途タグで検索し、必要な特徴に合う少数の資料を読む。寸法・地形・用途・様式が近いものを優先し、件数や人気だけで選ばない。記載した権利情報は確認日時点の提供元の表示であり、第三者権利まで保証するものではない。

- `reference`: 参照候補。`limitations` を読んでから使う。品質の正解例ではない。
- `conditional`: 非商用限定、上流の権利、適合性などが未解決。自動収集・学習データへの採用は保留する。
- `method`: 評価・調査方法の出典。建築モデルのデータとして数えない。

公開されていること、無料で取得できること、コードがOSSであることだけで、建築データの再配布や学習利用まで許可されたと判断しない。作品、画像、コードの権利を分ける。許諾不明の作品はURLと調査メモに留める。ログイン、課金、アクセス制限を回避せず、小さな許諾済みサンプルから始める。

記録する項目:

```text
id / title / author / source_url / license_url / license_scope
checked_at / tags / format / stated_dimensions / source_revision
local_file（ある場合）/ sha256 / bytes / inspection_level
observed_features / design_inferences / limitations / intended_use
```

`stated_dimensions` は作者の表記順を保持し、幅・高さ・奥行を確認する。`inspection_level` は「説明のみ」「画像観察」「ファイル取得」「正規CLIで調査」「実ゲーム確認」を区別する。画像を見ていないのに画像観察済みとしない。取得しただけのファイルを解析済みとしない。

## 作例から設計への変換

作例全体を貼り付けず、採用する特徴と今回の制約を対応させる。外部 `.schem` / `.litematic` の一般読取・変換機能は現行スキルにはない。正規チケットの外では、公開された説明・寸法・画像から確かめられる範囲を使う。ダウンロードした作例をチケットに見せかけることは禁止。

1. **要件と観測**: 用途、雰囲気、入口、幅・奥行・高さの上限、既存構造、接続先の位置と高さ、残す水・樹木・地形を整理する。チケット調査前に座標や高さを確定しない。
2. **特徴の分解**: 輪郭、主棟と付属棟、基礎、壁面の柱と開口、屋根、材料の役割、歩行ルート、周囲とのつながりを分ける。作者説明の事実と、自分の推測を別に書く。
3. **今回の設計**: 採用する特徴と変更理由を書く。例:「切妻の輪郭を採用するが、狭い敷地に合わせ付属棟を省く」。参照元にない黄金比や寸法を読み取ったと主張しない。
4. **段階的に候補化**: 輪郭・主要な高さ・通路 → 基礎・柱・壁・屋根 → 開口と入口 → 照明・縁取り・景観の順に進める。骨格の不釣り合いを装飾で隠さない。各段階の操作は必要範囲だけにする。

短い設計メモの例（値は実チケットから決める）:

```text
用途 / 入口と接続点 / 使用可能な範囲 / 保存する地形
主な輪郭 / 屋根型 / 柱と開口の間隔 / 内部の有効空間
材料の役割: 基礎・骨組み・壁・屋根・小さなアクセント
参考IDと採用する特徴 / 今回変える特徴と理由
検証する動線と断面 / まだ観測していない部分
```

## 特徴別の初期設計案

以下は公開資料を手掛かりにした設計案であり、画像からの精密復元や実測済みルールではない。様式やユーザーの指定が異なる場合は変更する。

| 特徴 | 参照ID | 今回の設計で使う観点 | 典型的な失敗と確認 |
|:--|:--|:--|:--|
| 小さな山小屋 | BL-CABIN | 基礎・壁・切妻・入口の役割を明瞭にする。狭い範囲では主屋根を先に決める | 外観だけで完成扱いしない。内装・照明は別に確認 |
| 開放的な東屋 | BL-PAVILION | 柱、張り出す屋根、中心の居場所、周囲の通路を対応させる | 柱や座席で通路を塞がない。避難用の閉鎖住宅として扱わない |
| 既存の川を渡る橋 | BL-BRIDGE | 先に両岸の接続点と高さを調べ、床・支持・欄干を決める | 参照元のプールや地面を川に貼らない。段差をジャンプなしで通れるか確認 |
| ファンタジーの複合建築 | SC-WINDMILL | 主屋と塔の主従、入口の読みやすさ、屋根・窓・道の関係を検討する | 参照の規模や説明をそのまま小チケットへ押し込まない。内装の記述と実際の到達性を区別 |
| 円形の塔・井戸 | GR-CIRCLES | ブロック格子上の円の輪郭を考える補助資料 | 円形だけで完成した塔にはならない。高さ、入口、内径、階段は別設計 |

## 品質確認

### 必須条件

既存の安全境界、要求された用途、範囲内の編集、保存対象、入口と接続点を先に確認する。形式や差分の検査に通ったことは、美観・歩行・照明の検証結果を意味しない。必須条件に不具合があるときは、総合点で相殺しない。

### 比較する観点

GDMC の地形適応・機能・美観・物語性という評価観点を参考に、このスキルでは局所建築に合わせて次を使う。GDMC公式採点そのものではない。[主催者の評価説明](https://gendesignmc.wikidot.com/wiki:evaluation)

| 項目 | 見るところ |
|:--|:--|
| 輪郭と比例 | 遠目でも用途が読めるか。屋根・壁・付属構造の大きさが意図に合うか |
| 材料と奥行き | 材料の役割が一貫し、壁・柱・窓に必要な奥行きがあるか。無秩序な素材混在がないか |
| 機能と動線 | 接続先から入口・目的地へ到達できるか。頭上や足元の障害、橋の段差がないか |
| 地形との接続 | 基礎・橋台・道が既存地形に接続するか。水路や保存物を壊していないか |
| 細部と世界観 | 照明・開口・装飾が用途や雰囲気を支えるか。装飾が動線を塞がないか |

採点する場合は各項目0～4点とし、0=要件未達、1=大きな修正が必要、2=使用可能だが粗い、3=一貫している、4=比較例の中でよく仕上がっている、とする。未観測は `N/A` とし、点数を埋めない。各点に観測根拠と評価者を付ける。共通に観測できた項目だけを比較し、N/Aを0点や満点へ換算しない。自己採点は仮評価であり、利用者評価と分ける。

現行CLIにはカメラレンダリング、光量計算、歩行シミュレーションがない。`surface` は主に最上面、`slice` は水平断面であり、それだけで屋根の裏・内部・全方向の外観を確認済みにしない。入口、床、頭上、屋根の交点を絞って `get-block` と複数の `slice` で調べ、分かることだけ報告する。

画像や実ゲーム確認が必要なら、正面・背面・側面・斜視、入口、内部、昼夜を同じ条件で比べる。画像がなくても観測できる幾何と差分の確認を進め、視覚確認は未実施として引き継ぐ。ゲーム内撮影やワールド適用の権限をこの手順から推定しない。

低評価の原因を一つ選び、目的が分かる局所変更をして再確認する。追加装飾の量、変更ブロック数、収集件数だけを品質の指標にしない。参照追加後に評価が下がる場合はその参照や設計案を外す。

## 改善を測る比較

モデル、依頼文、元の地形、チケット範囲、使用可能な材料、作業量、画像条件を揃える。旧手順と新手順を同じ入力で別の検証用チケットに適用する。実チケットの `source.schem` をコピーして偽チケットを作ったり、比較用に現在の候補を無断でリセットしたりしない。旧手順の結果がなければ、今回を基準記録にする。

最初は利用者が承認した用途別の少数課題で試す。例:

- 川幅と岸の高さが異なる小橋: 動線、橋台、水の保持。
- 小さな山小屋: 屋根と壁の釣り合い、入口、室内の使える空間。
- 坂道沿いのファンタジー店舗: 段差接続、正面の読みやすさ、近隣との材料調和。
- 細長い敷地の東屋: 張り出し、柱間、周囲の通路。

これは評価課題の案であり、実施済みのベンチマークではない。課題を満たす実チケットが揃ってから比較する。

保存する比較記録: 課題ID、入力/元データのハッシュ、手順と参照ライブラリの版、使用モデル（確認できた範囲）、候補ハッシュ、所要作業量、同条件の画像、項目別点数と根拠、好まれた案と理由、未観測事項。

作例の調整に使う建築と、最終比較に使う建築を分ける。同じ建物の別視点・色違い・回転版は同じ組に置き、評価側へ漏らさない。小標本の結果から一般的な改善率を断言しない。

## 利用者が資料を提供する場合

最初は好きな完成例5～10件と、現在の失敗例2～3件が実務上の目安。これはモデル学習の必要件数ではない。数件でも比較理由が明確なら参照改善を始められる。

```text
作品名・作者・元URL:
利用許諾: 自作 / 作者の許可 / ライセンス / 不明
許可する使い方: この案件の参照 / 再利用する参照庫 / 外部サービスへの送信 / モデル学習
用途・様式・Minecraft版・必要MOD/リソースパック:
幅×奥行×高さと、寸法が分かる根拠:
好きな点（最大3つ）:
変えたい点・真似してほしくない点:
画像: 正面・背面・左右・斜視、必要に応じ平面・内部・昼夜
任意の3Dデータ: .schem / .litematic / ワールド（現在は直接取り込めない形式あり）
今回の依頼文・チケット絶対パス（候補編集する場合）:
旧候補・直した候補・どちらが良いか・その理由:
```

受領後は、権利とファイルの出所を確認 → 特徴カード化 → 対象に近い少数の作例を参照 → 正規チケットで候補作成 → 比較採点 → 理由を添えて参照・設計手順を更新、の順に進める。非公開ファイルをアップロード・外部公開する許可は、ローカル参照の許可と分ける。

## モデルそのものの追加学習

必要になった場合は別途、学習対象（設計文、ブロック操作、画像理解、3D生成）、対応モデル/サービス、利用資格、権利、計算環境、費用、入力と正解の対、評価用分割を決める。建築画像だけを集めても正しいブロック操作の教師データにはならない。

OpenAIの公開案内では、2026-10-22確認時点で従来のfine-tuningプラットフォームは新規利用者に開放されておらず、既存対象顧客向けにも移行期限がある。実施時に現行の提供条件を確認する。このスキルの更新によって、現在のCodexモデルを再学習したとは報告しない。[OpenAI公式案内](https://developers.openai.com/api/docs/guides/supervised-fine-tuning)
