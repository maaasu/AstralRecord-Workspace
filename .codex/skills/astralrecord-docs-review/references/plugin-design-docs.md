# プラグイン設計書の参照

`E:\AstralRecord-Workspace\00_docs\10_Plugin設計書` 配下のパスにはこの参照を使う。

## 必須コンテキスト

機能をレビューする前に次を読む。

- `00_docs/10_Plugin設計書/README.md`。
- 実装所有権が関係する場合は `00_docs/10_Plugin設計書/FEATURE_CATALOG.md`。
- `feature/01-user/01_0-概要.md` のような対象機能概要。
- レビュー対象の挙動に関係するモデル、ユースケース、メソッド契約、流れ、操作、予定仕様、未決事項の設計書。

用語、モデル、メソッド、流れ、依存関係、未決事項を定義する場合は Wiki リンクと相対 Markdown リンクの両方をたどる。設計書のみレビュー中は実装パスを調査しない。`FEATURE_CATALOG.md` のパスは所有権ラベルとしてだけ扱う。

## 確認する構造ルール

ルート設計 README を正本とする。現在想定する構造は次のとおり。

- 機能ディレクトリ: `2-digit-number-feature-name`。例: `01-user`。
- 必須の機能入口: 機能ディレクトリ直下の `<feature-number>_0-概要.md`。
- 機能レベルの `<feature-number>_README.md` は置かない。
- 任意のカテゴリ:
  - `1`: モデル定義。
  - `2`: 使用ケース。
  - `3`: メソッド仕様と処理契約。
  - `4`: 統合流れ。
  - `5`: 例外、ログ、操作。
  - `6`: 開発と拡張のガイド。
  - `8`: 受け入れ済みだが未実装の仕様。
  - `9`: 未決の判断だけ。
- Markdown のファイル名: `<feature-number>_<category-number>-<meaningful-name>.md`。
- Markdown ファイルが1つだけのカテゴリは機能ディレクトリに平坦なに置く。
- カテゴリディレクトリは複数の Markdown ファイルを含む場合だけ使う。
- H1 は `.md` を除いたファイル名と一致させる。
- ファイル名はプラグイン設計書ツリー全体で一意にし、括弧や空白を使わない。
- Wiki リンクと相対 Markdown リンクはどちらも有効。パスのない Wiki リンクは一意に解決できなければならない。
- 空のカテゴリディレクトリ、空の未決事項設計書、`.00` や `.01` のような詳細番号名前は無効。

## 機能概要のルール

機能概要は案内と責務の入口である。固定見出しを要求するのではなく、機能に必要な情報が含まれるかをレビューする。

- 目的、責務、対象外。
- 主要な境界と不変条件。
- 依存する機能と機能をまたぐ契約。
- 関連データ、設定、正本となるソース。
- 機能を理解するために必要な設計書へのリンク。
- ルートルールを超える価値がある場合だけ機能固有の変更影響。

実装所有権パスは `FEATURE_CATALOG.md` に置き、機能ごとに重複した目次 には置かない。

## 確認するメソッドの取り決め

カテゴリ `3` の設計書では次を確認する。

- 完全なメソッド一覧ではなく、外部から意味のある契約または機能をまたぐ契約に焦点を当てる。
- 文書化された契約に関係する入力、出力、事前条件、拒否条件、重要な判断、委譲、状態変更、永続化/スレッド境界、失敗挙動を必須とする。
- クラス名前、物理的なメソッド名前、イベント名前は任意。記載する場合はレビュー対象の設計と内部整合させる。ただし固定ラベルがなくても明確なテーブルまたはまとめられた契約は欠陥ではない。
- 論理名は、可能な範囲で理解しやすい日本語の名詞句にする。
- ファイル間参照には Wiki リンクまたは相対 Markdown リンクを使える。
- ログ/メッセージには必要に応じて ID、レベル/種別、実行条件、引数、意味、運用上の対応を示す。properties ファイルが正本として文書化されている場合、完全なメッセージテンプレートは要求しない。

## 確認する統合フローのルール

- 挙動が構成要素をまたぐ、またはローカル契約だけでは理解できない場合だけ統合フロー文書を要求する。
- Mermaid は参加者、分岐、非同期処理、補償、状態遷移を図で示すことが実質的に明確化する場合だけ必須とする。
- 単純な流れは説明文またはテーブルでよい。
- 図がある場合は、ラベルと順序が周辺の設計と一致するか確認する。

## 設計レビューの重点

設計レベルの問題を優先する。

- 流れはメソッド契約と機能概要に一致しているか。
- モデルフィールドは記載された使用ケースとライフサイクルに十分か。
- イベント、コマンド、サービス、リポジトリ、キャッシュ/セッション、作業、アダプター/リスナー、操作設計書の責務はきれいに分かれているか。
- 機能をまたぐ呼び出しは所有権と依存関係方向が分かるほど明示されているか。
- 失敗パス、null/見つからない場合挙動、再試行、ログ記録、プレイヤー向けメッセージ、運用上の対応が必要な場所に記載されているか。
- ログイン/ログアウト、キャッシュ/セッション、保存タイミング、クールダウン、バフ/状態効果、アイテム所有権、ドロップ報酬付与、その他ゲームプレイライフサイクルの状態遷移は明確か。
- 現在の挙動、受け入れた将来作業、未決の判断が明確に分かれているか。
- 文書が正本となる実装パスやメッセージテンプレートを重複させていないか。

## 意図が不足している場合

概要、使用ケース、流れ図、カテゴリ `8`、カテゴリ `9`、関連機能設計書から意図を集める。それでも意図した挙動を決められない場合は、無理に欠陥とせず、必要な判断を具体的に示した `未確認/質問` として報告する。
