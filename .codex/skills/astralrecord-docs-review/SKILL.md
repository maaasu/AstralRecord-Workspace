# AstralRecord 設計書レビュー

## 基本ルール

設計書だけをレビューする。ソースコード、実装ファイル、データベーススキーマファイル、生成素材、実行時出力は開いたり、そこから推測したりしない。設計書に書かれた実装パスは範囲を示すラベルとしてだけ扱う。指摘が1件以上ある場合だけ正規レビュー記録を作成する。指摘がない場合はレビュー記録を作成せず、作成しなかったことと未解決の質問をレビュー結果に記載する。

判断が設計者の意図に依存する場合は、まず設計書から意図を集める。対象はルート README、機能概要、使用ケース、モデル定義、流れ、操作注記、予定された仕様、未決事項、関連機能設計書とする。それでも意図が不明な場合は、無理に欠陥とせず質問または仮定として報告する。

選択したリポジトリルートを解決し、レビュー前に `<repo-root>\.codex\skills\_shared\review-record-format.md` を最後まで読む。その保存場所、ファイル名、本文スキーマ、状態、検証ルールは必須とする。

## Git 事前確認

レビュー記録を作成する前に、次を完了する。

1. `git rev-parse --show-toplevel` で選択したチェックアウトを解決し、`git status --short --branch` を確認する。
2. すでに `develop` ではない専用作業ツリー内にいる場合は、そのルートを `<task-root>` とする。
3. 選択したチェックアウトがメインの `develop` ワークスペースの場合、未コミット変更がレビュー対象と重なるか確認する。重なる場合は書き込み前に停止し、その変更を作業ツリーへ移すよう要求する。未コミット差分を含むかのように古い HEAD のコピーをレビューしてはならない。重ならない場合は `$astralrecord-git-worktree-develop` を準備モードで起動して `codex/review-<slug>` を作成し、対象パスをその作業ツリーに読み替えて、新しいルートを `<task-root>` とする。
4. 指摘により記録が必要な場合は `<task-root>\00_docs\99_資料\レビュー結果` にだけ保存する。作業ツリーからメインワークスペースのリテラルパスへ書き込まない。
5. 既存作業ツリーでレビューだけの依頼が終わり、記録を作成した場合は `$astralrecord-commit-current-diff` を起動し、検証済み記録だけをコミットする。指摘がなく記録を作成しなかった場合は、記録のコミットもない。要求されない限り、既存の実装作業ツリーを完了処理しない。
6. このスキルがレビュー専用作業ツリーを作成し、記録を作成した場合は、検証直後に `$astralrecord-git-worktree-develop` を完了処理モードで起動する。記録のステージとコミットは完了処理に任せる。記録を作成しなかった場合は不要だったと報告する。停止中の場合はブランチ/作業ツリーを保持して報告する。先にコミットしてから完了処理を呼んだり、`develop` への書き込みに戻ったりしない。

## 手順

1. Git 事前確認を完了し、ファイルへ書き込む前に `<task-root>` を確定する。
2. 読み替えた絶対パスから対象の設計領域を特定する。
   - `00_docs/10_Plugin設計書`: `references/plugin-design-docs.md` を読む。
   - 将来の API/Web 設計書: この一般手順を使い、`references/api-design-docs.md` や `references/web-design-docs.md` のような追加参照を探す。領域固有の参照がなければ、一般的な設計品質と文書化されたローカルルールだけをレビューする。
3. 判断前に文書化されたルールを読む。設計書ルート README、対象機能概要、対象設計書ツリー内のローカルルールファイルを確認する。
4. `00_docs/10_Plugin設計書` をレビューする場合だけ、`<task-root>\.codex\skills\astralrecord-docs-review\scripts\docs_structure_audit.py <absolute-docs-path>` を実行する。その出力は形式・構造の指摘の証拠として使い、レビュー全体の代用にはしない。他の設計書領域では、対応する領域監査スクリプトが追加されていない限り、確認範囲に `未実行（理由: docs_structure_audit.py は 10_Plugin設計書 専用）` と記載する。
5. 機能の意図と文書間契約を理解するために必要な最小限の関連設計書を読む。用語、モデル、メソッド、流れ、依存関係、未決事項を定義する Wiki リンク先の設計書は追って読む。
6. 設計上の欠陥をレビューする。
   - 概要、モデル、使用ケース、メソッド仕様、統合流れ、操作/ログ記録、未決事項の間の矛盾。
   - 仕様不足、記載どおりに実装できない、運用上安全でない、または責務記載と一致しない処理。
   - 設計が示唆する事前条件、失敗挙動、所有境界、依存関係、データライフサイクル、状態遷移、冪等性、並行性、巻き戻し、観測可能性の不足。
   - 文書化された設計書ルールに対する形式・命名違反。
7. 「指摘」と「質問」を分離する。現在の設計書が定義を要求していない設計者の意図不足を欠陥と呼ばない。
8. 範囲が非自明で、サブエージェントが利用できる場合は少なくとも1回の独立した読み取り専用確認工程を委譲する。機能をまたぐ、運用リスク、データライフサイクルの作業では、異なる観点を持つ2人目の専門担当を使う。エージェントには期待する指摘ではなく、対象設計書とローカルルールを渡す。調整役が証拠を重複排除し、正規記録の唯一の編集担当となる。
9. レビュー中に、レビュー対象の設計書から回答できる質問は解決する。許可されたレビュー資料から確認できない判断または事実だけを `## 未確認/質問` に残す。
10. 指摘に紐づく質問が必要な場合は `## 未確認/質問` の下に置き、`関連指摘` で指摘を参照する。
    - 指摘がない場合は記録を作成せず、記録の検証も実行しない。代わりに未解決の質問をレビュー結果へ記載する。
11. 指摘が1件以上ある場合は、共有形式で正規記録を1つだけ作成する。下記の docs-review 許可種別を使い、新しい指摘はすべて `修正状態: 未修正` で始め、見出しを追加しない。指摘がない場合は記録を作成しない。
    - 第1回は指摘がある場合だけ記録を作成し、絶対パスを調整役へ返す。
    - 第2回は記録がある場合にその正規記録パスを入力として受け取り、同じファイルを更新する。既存の ID/本文/作成日時/対象を保持し、新しい連番の指摘だけを追加する。2つ目の記録や空の記録を作成しない。
12. 保存したファイルを `<task-root>\.codex\skills\_shared\scripts\validate_review_record.py` で検証する。通過するまで修正する。
13. Git 事前確認で定めたレビュー専用のコミット/完了処理手順を完了する。統合実装作業手順では、コミット/完了処理の所有権を調整役に残す。

## 報告形式

レビューは日本語で記載する。記録がある場合は構成を変えずに検証済み本文を出力し、共有形式の正規本文と正確な節順を使う。指摘がない場合は記録を作成しなかったことを報告し、未解決の質問をレビュー結果に含める。重要度は `[高]`、`[中]`、`[低]`、`[情報]` のいずれかとする。

設計書レビューで使用できる `種別` は次のとおり。

`矛盾` | `不適切なロジック` | `不足` | `未確定事項` | `形式/命名` | `運用リスク`

新しい意図を作らずに `$astralrecord-docs-fix` が設計書を編集できる場合だけ `修正可否: 自動修正可` とする。共有形式のフィールド順に `修正対象候補`、`確信度`、`修正状態` を必ず含める。`確認した範囲` には `読んだソース: なし（設計書レビューのため）` を使う。

## レビュー結果ファイル

指摘が1件以上ある場合は、`<task-root>\00_docs\99_資料\レビュー結果` 配下に Markdown 記録を1つだけ保存する。指摘がない場合は記録を保存しない。指摘のない記録を作る代わりに、未解決の質問をレビュー結果へ記載する。ファイル名、メタデータ、フィールド、空値、状態遷移、検証の正本は共有形式だけとする。`<task-root>` が別作業ツリーの場合、`E:\AstralRecord-Workspace` をリテラルの保存先として使わない。

## 拡張ポイント

領域固有のルールは1階層の参照ファイルにまとめる。

- `10_Plugin設計書` 用は `references/plugin-design-docs.md`。
- 将来の API 設計書用には `references/api-design-docs.md` を追加する。
- 将来の Web 設計書用には `references/web-design-docs.md` を追加する。

新しい領域参照を追加する場合は、パスの判定方法、必須のルートファイル、文書カテゴリ、レビュー観点、形式ルールを含める。大きな設計書をスキルにコピーせず、作業手順から実際の設計書ツリーを参照させる。
