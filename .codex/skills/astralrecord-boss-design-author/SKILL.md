# AstralRecord ボス設計書の作成

## 位置づけ

- ボス設計書は実装の指示書である。実装担当（下位モデル）が判断を加えず書かれたとおりに作業すれば、設計したモデルが自分で実装した場合と同じ完成度になる状態を合格とする。
- 設計書は一時資料である。実装担当が実装の完了時に削除し、内容は Git の履歴で追う。実装後も効く判断だけを「11. 残す判断」に書き、実装担当が AIパーソナライズへ移す。
- 置き場所は `99_work/boss-design/<boss_id>.md`、1ボス1ファイル。書式は [テンプレート](references/design-template.md) に従う。

## 作成ルール

1. **判断を残さない。** 実装担当が選べる余地のある記述は不合格とする。「適度」「適宜」「必要に応じて」「いい感じ」「検討」「TBD」を使わず、選択肢を並べずに一つへ決める。
2. **数値と単位を確定する。** 時間は tick（20 tick = 1秒）、距離はブロック、割合は % か倍率で書く。座標はフィールドワールドの絶対座標で書く。範囲は形状（円・扇形・矩形・線）、寸法、基準点、向き、高さ範囲を書く。
3. **手本を名指しする。** 新しいクラスとメソッドごとに、構造をまねる既存のファイルとメソッド名を書く。手本がない処理だけ、疑似コードかコードの骨組みを書く。
4. **統合箇所をすべて判定する。** [ボス実装の統合箇所](../_shared/boss-integration-points.md) の I01〜I18 を一行ずつ「対象 / 対象外」と判定する。対象には変更ファイルと内容を、対象外には理由を書く。
5. **既存コードを確認してから名前を書く。** 設計書に書くクラス名・メソッド名・定数・パスは、作成時点の `develop` で存在を確認する。これから作るものには「新規」と書く。確認した `develop` の短縮ハッシュを「設計基準コミット」に書く。
6. **ビルドが通る段階に分ける。** 「8. 実装手順」は、各段階の終わりでビルドが通る単位に分け、順序を固定する。1段階の目安は、新規クラス1つか統合箇所数件とする。
7. **境界と失敗時の挙動を書く。** テンプレートの「9. 境界と失敗時の挙動」の全行に、挙動を一行で書く。
8. **確かめられる完了条件を書く。** 自動検証はコマンドと期待結果で書く。実機確認は「操作 → 期待結果」の表で書く。ボスギミックは恒久テストにしない（`PLUGIN_GUIDE.md` のテスト運用ルール）。
9. **下位モデルに向かない作業は切り出す。** 両版パック表示（I16）、外観モデル制作（I17）、フィールド建築（I18）は「別タスク」とし、上位モデルの担当にする。実装範囲は、別タスクが終わる前でも戦闘が成立するように書く（仮の外観、`DUST` による範囲表示など）。
10. **数値の根拠を書く。** `baseStats` と技の倍率は、[DPS指標](../../../00_docs/10_AIパーソナライズ/ゲームデザイン/DPS指標.md) と同じレベル帯の既存ボスの YAML コメントを基準にし、根拠を YAML コメントへ書く。
11. **プロジェクト規約を設計に含める。** メッセージ・ログ・パーティクル・テレポートは `astralrecord-code/references/plugin-code.md` の規則に沿う形で設計する。統合版の表示は `PLUGIN_GUIDE.md` のパーティクル表示共通ルールに沿って、技ごとに代替表示を決める。
12. **未決事項を残さない。** 「12. 確認事項」が「なし」になるまで、ユーザーに確認する。

## 手順

1. 依頼から、レベル帯、モチーフ、フィールド、参加人数、主要ギミックを確認する。ゲーム体験を左右する項目が未確定の場合は、推測で埋めずユーザーに質問する。
2. 同じレベル帯の既存ボスの YAML と制御クラス、フィールド（建築済みならチケットと座標）、統合箇所の各ファイルを `develop` で読む。
3. テンプレートを `99_work/boss-design/<boss_id>.md` へコピーし、全章を埋める。
4. 検査スクリプトを実行し、エラーを 0 にする。警告は該当箇所を読み、曖昧なら書き直す。

   ```powershell
   python .codex/skills/astralrecord-boss-design-author/scripts/check_boss_design.py 99_work/boss-design/<boss_id>.md
   ```

5. 実装担当として読み直す。「8. 実装手順」を上から順に、設計書と手本ファイルだけで各段階を書けるか確認する。手本や値を探しに行く必要がある箇所は設計書に追記する。
6. ユーザーに要点（戦闘の流れ、別タスク、残す判断）を示して承認を得る。
7. 承認後、設計書だけを `docs: <表示名>のボス設計書を追加` として、統合入口 `$astralrecord-code-version-commit-develop`（軽量品質ゲート）で `develop` へ反映する。
8. 実装の依頼方法をユーザーに案内する。下位モデルのセッションで次のように依頼する（Codex は `$`、Claude Code は `/` で同じスキルを呼ぶ）。

   ```text
   $astralrecord-boss-implement 99_work/boss-design/<boss_id>.md
   /astralrecord-boss-implement 99_work/boss-design/<boss_id>.md
   ```

## 実装後のレビュー

実装担当は既定で `develop` への反映前に停止し、作業ブランチを報告する。報告を受けたら、上位モデルが次を行う。

1. 設計書を `develop` 側（未反映ならそのまま、反映済みなら `git show <削除コミット>^:99_work/boss-design/<boss_id>.md`）から読み、差分と照合する。
2. `$astralrecord-code-review` でレビューし、指摘は `$astralrecord-code-fix` で修正する。
3. 別タスク（I16〜I18）を進め、`$astralrecord-git-worktree-develop` の完了処理で `develop` へ反映する。
