# AstralRecord 実装・版番号・コミット・develop 反映

## 目的

差分を作る作業を、並列編集可能な専用作業ツリーからdevelop反映まで一貫して扱う。差分作成中の作業ツリー分離は常に維持し、成功した完了処理後の後片付けはGit スキルに任せる。対象外の資料・ツール・検証工程だけを作業種別に応じて読み飛ばす。

## 最初の分類

1. `質問・説明・診断・読み取り専用レビュー`で差分が不要なら、このスキルを起動せず回答する。
2. ルート `AGENTS.md` の単一ライターによるファイルベース直接更新の例外は、既存契約内のデータ作成・値調整に限り、分類・準備の前に `$astralrecord-master-data-create-direct` へ渡す。キー・型・必須・列挙・参照形式・命名などの定義契約、読込・変換・成長式を変更する場合はこの統合入口を使い、[Filebase 編集サイトの同期規則](../_shared/filebase-editor-sync.md) に従う。
3. 差分が必要なら、先に [task-routing.md](references/task-routing.md) を読み、`対象`、`変更種別`、`軽量品質ゲート/標準品質ゲート`、`必要な参照`を決める。
4. ルート `AGENTS.md` に従い、対象プロジェクトの `Read Next` と対象の担当スキルだけを読む。作業ツリー管理参照は準備/完了処理でGit スキルから読む。既読資料や無関係なスキル・ガイドを読み直さない。
5. `標準品質ゲート` またはワークスペーススキルの処理の変更では [quality-gate.md](references/quality-gate.md) を読む。軽量品質ゲートでは読まない。
6. `40_filebase` の並列作業だけ [parallel-filebase.md](references/parallel-filebase.md) を読む。

## 担当スキルの選択

- 既存 `AR-CODE-*` 指摘の修正 → `$astralrecord-code-fix`
- 既存 `AR-DOC-*` 指摘の修正 → `$astralrecord-docs-fix`
- Minecraft内の職業・戦闘スキル → `$astralrecord-skill-author`
- 本番向け `40_filebase` マスタ作成 → `$astralrecord-master-data-author`
- 新しいプレイヤー用アイテムの外観、既存アイテムのモデル作成・変更 → `$astralrecord-item-model-author`。新規アイテムは原則マスターと両版のパックを同じ変更で作る。
- モブ・ボスの外観モデルの制作や立体意匠の改修 → `$astralrecord-mob-model-author`。
- `.codex/skills` の定義・参照・スクリプト・`agents/openai.yaml` → `$skill-creator`
- その他のプラグイン/API/Web/設計書に関連する実装 → `$astralrecord-code`

## 必須の作業手順

### 実行場所と引き継ぎ

- 通常の変更は [Codex Cloud の往復手順](references/cloud-workflow.md) に従い、開始時に Cloud とローカルの選択を質問せず、デスクトップアプリで対象の実行可能な環境を確認して、依頼ごとに新しい Codex Cloud チャットへ委譲する。これはユーザーが設定したこのワークスペースの継続的な既定指定であり、依頼文に毎回チャット作成の明示を求めない。アプリの権限・起動上の制約と、委譲できない場合の既存の手渡し経路は尊重する。開始側は開始ブランチの同期と成果の取り込みを担当する。Cloud 担当は指定コミットから専用の Git 作業ツリーを作り、担当検証とレビューを経て作業ブランチをプッシュする。別の Cloud チャットへの実装の再委譲を避け、独立レビューには同じ Cloud チャット内で利用可能な読み取り専用サブエージェントを使う。
- 作業場所や既存作業ツリーの明示があれば優先し、Cloud 限定の指定も尊重する。場所の指定がなければ、既存ローカル worktree の未コミット差分、マシン固有ファイル、ローカル専用ツールなどに依存する作業・工程は、こちらでローカルを選び、理由を進捗または結果に短く記す。分割できる場合は必要な工程だけをローカルで行う。Blockbench の確認と Minecraft 実機試験の扱いは [品質ゲート](references/quality-gate.md) に従う。
- Cloud 環境の未設定や起動失敗だけを理由に通常の重い作業をローカルへ移さず、実行環境の選択をユーザーへ投げ返さない。場所選択とは別の権限確認や、作業に必要な具体的な不足情報の確認は、それぞれの規則に従う。

### 各作業ツリーでの実装と完了処理

1. Cloud では往復手順で指定されたベースから準備する。ローカルのみで行う作業は、対象入力を持つ既存の専用 task worktree があれば編集分離を維持して使う。新規作業ツリーが必要なら `$astralrecord-git-worktree-develop` の準備でローカル `develop` から作業ブランチ / 作業ツリーを作る。既存の未コミット入力に依存する場合は、元の内容とステージ状態を保全し、対象入力を安全に引き継いで確認してから作業する。
2. 対象の担当スキルをその作業ツリー内で一度に一人の編集担当が実行し、最小の対象資料だけを読んで検証する。
3. 変更種別に対応するレビュー/修正を実行する。
   - 設計書だけ（`00_docs/40_Database設計書`以外） → `$astralrecord-docs-review` / `$astralrecord-docs-fix`
   - コード、設定、ワークスペーススキル/ツール、ファイルベース、リソースパック、混在 → `$astralrecord-code-review` / `$astralrecord-code-fix`
4. Cloud 担当は品質ゲート後に対象ファイルだけをコミットしてプッシュし、開始側へ結果を引き継ぐ。ローカルの並列編集または遅延マージはコミット後に完了処理待ちにする。
5. 開始側での `develop` 反映は `$astralrecord-git-worktree-develop` の完了処理に従う。リベース後、プラグイン成果物を変更した場合だけ `$astralrecord-plugin-version` を実行する。
6. 準備、品質ゲート、完了処理が停止した場合は作業ツリーを保持する。開始側の管理ファイルを更新し、停止理由と再開に必要なブランチ・コミットを報告する。

## 条件付きで省略できる工程

- 差分なし: 作業ツリー、担当、ビルド、レビュー、コミット、マージをすべて省略。
- 誤字、コメント、表示メタデータなどの軽量品質ゲート: 全体ビルド、第2回レビュー、専門担当を省略可。詳細は [quality-gate.md](references/quality-gate.md)。
- API/Web/設計書/filebase/resourcepack/スキルのみ: プラグイン版番号を省略。
- プラグインのテストソース、POM、許可された設計入力、テスト方針のパスに変更がない: テストのトレーサビリティ検証を省略。
- 対象外プロジェクトのガイド、参照、テスト方針、生成物確認は省略。

## 省略してはいけないもの

- 差分を作る作業の専用作業ツリーと、一人の編集担当による編集分離。
- 範囲を限定した差分確認、コミット前確認、必要なレビュー、リベース後の競合・影響確認。
- `40_filebase` のリベース後YAML、ID重複、変更参照の検証。
- プラグイン成果物を変更した完了処理での版番号更新。
- 開始側での処理終了時の作業ツリー管理ファイル更新。Cloud の作業ツリーは引き継ぎ記録で追跡する。

## サブエージェント方針

- 利用可能なら実装者と第1回のレビュー担当を分ける。
- 標準品質ゲートの第2回のレビュー担当は修正担当と分ける。
- 単純な一ファイル変更は独立レビュー担当一人でよい。
- 専門家は複数ファイル、複数プロジェクト、セキュリティ、並行性、データ整合性のときだけ追加する。

## 最終報告

日本語で、`実装結果`、`品質ゲート`、`ブランチ / 作業ツリー`、`Git結果`、`作業ツリー管理`、`未対応事項`を簡潔に報告する。プラグイン版番号は実施した場合だけ記載し、未実施なら理由を明記する。
