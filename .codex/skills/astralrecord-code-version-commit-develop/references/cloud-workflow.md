# Codex Cloud と開始環境の往復

通常の変更は、会話を開始したリポジトリを調整役とし、実装と品質ゲートは Codex Cloud に委譲する。GitHub を受け渡しに使い、開始環境で `develop` へ反映して完了する。

## 1. 開始環境で同期する

1. 開始側のリポジトリ、現在ブランチと HEAD、`develop` のチェックアウト先と HEAD、開始ブランチの追跡先を記録する。未コミット変更とステージ状態を確認し、対象入力が未コミットなら持ち込み方法を確認する。その他の未コミット変更は保持する。
2. 開始ブランチの設定済みリモートとブランチを使う。追跡先が未設定の場合は、同名ブランチの同期先が一意なリポジトリの `origin` と確認できるときだけ用いる。リモート、ブランチ名、または detached HEAD の対応を特定できなければ停止する。作業成果を受け渡す GitHub リポジトリと一致することを確認する。
3. 追跡先とリモートの `develop` をフェッチして比較する。リモート先端が開始 HEAD の祖先で先行コミットがあれば、開始 HEAD を追跡先の `refs/heads/<branch>` に通常の push で送る。対象は開始ブランチの先行コミットすべて。追跡先にブランチが存在しない場合は、確定した同名ブランチを作る。開始側がリモートより遅いだけならリモート先端を使用し、手元の開始ブランチはそのまま扱う。分岐、push 拒否、SHA 不一致があれば Cloud を開始せず、状況を確認する。強制 push は行わない。
4. ローカルの開始 HEAD と、GitHub にある開始ブランチおよび `develop` の SHA を区別して引き継ぐ。通常の Cloud 作業ベースは確認したリモート `develop` とする。開始ブランチが別の場合、その既存コミットを取り込み範囲に含めない。依頼が開始ブランチ固有のコミットに依存する場合は、ベースと `develop` に含めるコミットを先に確定する。

## 2. Cloud へ委譲する

- 対象の GitHub リポジトリを設定した公開済みの Codex Cloud 環境を使う。実行可能な環境と承認済みの委譲経路があれば、開始側の会話を調整役にして Cloud 作業を起動し、結果を待つ。デスクトップのタスク作成機能を使う場合は実行可能な環境を一覧で確認し、別チャットの作成が明示されているときに使う。利用できる CLI で委譲する場合は `codex cloud exec --help` で環境とブランチの指定方法を確認する。
- 現在の会話を Cloud へ移す機能や、Cloud から開始環境のファイルに触れる機能を前提にしない。委譲できない場合は、Cloud で実行できる引き継ぎ文と開始側で再開する条件を示す。環境が実行不可なら、設定の公開・再公開や GitHub 接続に必要な操作を案内する。
- 引き継ぎ文には、リポジトリ、同期済み開始ブランチと SHA、作業ベースのブランチと SHA、一意の `codex/<task-slug>`、依頼・対象範囲、必要な品質ゲートを含める。Cloud が担当するのは作業ブランチの push と結果の返却までと指定する。手元の未コミット差分やマシン固有の秘密設定を前提にしない。
- 初回は対象プロジェクトのツールチェーンと依存取得先を環境で確認する。AstralRecord プラグインの例は JDK 21、Maven、`mvn -f 10_plugin/AstralRecord/pom.xml test`。依存取得先は対象 POM を参照する。GitHub からの取得と作業ブランチへの書き込み権限も確認する。[Cloud 環境の設定](https://learn.chatgpt.com/docs/environments/cloud-environments)

## 3. Cloud で作業してプッシュする

1. 既存のクラウド側チェックアウトを使うかリポジトリを取得し、指定のブランチをフェッチする。指定ベース SHA が取得でき、同じ履歴上にあることを確認する。環境の既定ブランチや最新 HEAD への置き換えは行わない。
2. ローカルとリモートの両方で作業ブランチ名が未使用であることを確認し、`git worktree add -b <task-branch> <cloud-worktree-path> <base-sha>` で専用作業ツリーを作る。パスは Cloud 内で解決し、開始環境の固定パスを使わない。
3. [統合入口](../SKILL.md) の担当・レビュー手順と [品質ゲート](quality-gate.md) を実行する。対象だけをコミットし、検証した SHA を記録する。Blockbench が開始環境に必要な場合は、対象コミットと必要な操作を引き継ぐ。
4. 初回は `git push --force-with-lease=refs/heads/<task-branch>: <remote> HEAD:refs/heads/<task-branch>` で、リモートに同名の ref が存在しない場合だけブランチを作る。空の期待値は既存 ref の更新を拒否する。再開時は同じ作業のブランチと確認できた場合だけ通常の早送り push を使う。GitHub 連携を使う場合も既存の別作業ブランチを更新しない。リモート先端が作業 HEAD と一致することを確認し、作業ベース、成果ブランチと SHA、検証コマンドと結果、未実施の必須工程を返す。開始側が取り込むまでは成果のリモートブランチを保持する。

## 4. 開始環境の develop へ反映する

1. 開始側は Cloud の結果を受け取り、対象のリモート作業ブランチをフェッチして報告 SHA と照合する。作業ベースからのコミットと変更パスが依頼範囲内であることを確認する。対象成果がすでに `develop` に含まれる場合は状態を確認して完了する。
2. `develop` のリモートとローカルの先端を再確認する。リモートのみ先行なら [分離・競合確認](../../astralrecord-git-worktree-develop/references/unrelated-changes.md) を通してローカル `develop` を早送りする。双方に固有のコミットがある場合は自動で書き換えず停止する。ローカルのみ先行なら、その先端を統合ベースとする。
3. 取得した成果 SHA から開始環境内に専用の統合作業ツリーを作り、[Git スキルの完了処理](../../astralrecord-git-worktree-develop/SKILL.md#手順)に従って最新のローカル `develop` にリベースする。Cloud で検証したベースから契約や依存・対象範囲に影響する変更があれば、マージ前に対象の品質ゲートを再実行する。重い再検証は、共有が許可された統合 SHA を別の作業ブランチで送り Cloud に委譲する。再検証のために未共有のローカルコミットを追加公開する必要がある場合は先に確認する。開始環境が必要な Blockbench 確認は統合結果に対して行う。
4. Filebase の再検証と、必要なプラグイン版番号更新を完了する。検証した SHA と統合 HEAD の差分を確認し、再リベースや採番で変わった箇所に必要な検査を通す。マージ直前にベースが変わっていないことと未コミット差分との重複がないことを確認し、`git merge --ff-only` で開始環境の `develop` に反映する。ベースが変わった場合は再判定し、競合または検証失敗時は成果をマージしない。
5. `develop` の HEAD が統合結果と一致することを確認する。完了処理で開始側の統合ブランチ・作業ツリーを整理し、管理ファイルを更新する。Cloud の作業ブランチと取得 SHA、最終ローカル `develop` の SHA、実行した検証と未完了の項目を報告する。
