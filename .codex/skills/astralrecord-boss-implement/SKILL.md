# AstralRecord ボス設計書の実装

## 基本姿勢

- 判断は設計書が持っている。自分で考えて良くしようとせず、書かれたとおりに作る。
- 設計書に書かれていない機能・演出・リファクタリング・数値調整を加えない。
- 迷ったら作らずに止まる。推測で埋めた実装は、止まって質問するより悪い結果とみなす。

## 許可される調整と止まる条件

設計書どおりに書いてコンパイルできない場合でも、次の**機械的な調整だけ**は自分で行ってよい。

- import、ジェネリクス、`@NotNull` / `@Nullable`、`final` などの付け足し
- 行番号の違い（クラス名・メソッド名・手本ボスの行で位置を探す）
- メッセージ・ログ ID の採番（既存の最大番号の次の空き番号）
- 自分が書いたコードのタイプミスやコンパイルエラーの修正

次のいずれかに当てはまったら、**その段階の作業を止めて**、「確認事項」に記録してユーザーへ報告する。

- 設計書に書かれたクラス・メソッド・定数・パスが存在しない、またはシグネチャが違う
- 設計書の値・挙動を変えないと動かない（数値・範囲・tick・効果・遷移・対象ファイルの変更が必要）
- 設計書の章同士が矛盾している、または必要な値が書かれていない
- 設計書の「変更しないもの」や対象外の統合箇所に触る必要がある
- 同じビルドエラーを3回修正しても解消しない

## 手順

### 1. 準備

1. ルートの `AGENTS.md` を読む。作業ツリーは統合入口 `$astralrecord-code-version-commit-develop` の手順1に従う（既に専用の作業ツリーにいれば、それを使う）。
2. 設計書を最後まで読む。
3. 設計書を検査する。エラーが1件でもあれば実装を始めず、エラー内容を報告して終了する。

   ```powershell
   python .codex/skills/astralrecord-boss-design-author/scripts/check_boss_design.py <設計書のパス>
   ```

4. 「0. 概要」の設計基準コミットと現在の `develop` の差分のうち、「7. 統合箇所」の変更ファイルに関係するものを `git log --oneline <設計基準コミット>..develop -- <ファイル>` で確認する。変更があれば、該当箇所が設計書の記述と食い違っていないか読む。
5. 規約として `PLUGIN_GUIDE.md` と `.codex/skills/astralrecord-code/references/plugin-code.md` を読む。読むのは設計書が触る範囲（ログ、メッセージ、パーティクル、テレポート、Filebase）だけでよい。

### 2. 実装

1. 「8. 実装手順」を段階1から順に進める。段階を飛ばしたり、まとめたりしない。
2. 各段階では、設計書が名指しした手本のファイルとメソッドを先に読み、同じ構造・命名・書き方でまねる。
3. マスターデータは「3. マスターデータ」の YAML をそのまま配置する。値を書き換えない。
4. メッセージ・ログは「6. メッセージ・ログ・パーティクル」の表のとおりに登録し、採番した ID と用途名の対応を控えておく（報告に使う）。
5. 各段階の終わりに、その段階の「完了確認」を実行して成功させてから次へ進む。

### 3. 検証

1. プラグインのソースまたはリソースを変更した場合は、リソース検査を実行し、指摘を 0 件にする。

   ```powershell
   python .codex/skills/astralrecord-code/scripts/check_plugin_resources.py --repo-root <作業ツリー>
   ```

2. `10_plugin/AstralRecord` で `mvn -q test` を実行し、警告を含む出力を確認する。Maven・JDK が PATH にない場合は `60_tool/README.md` の `build-tools.local.json` の説明に従う。
3. `40_filebase` を変更した場合は、`$astralrecord-master-data-author` の「検証」節に従って YAML・ID 重複・参照を確認する。
4. 「10. 完了条件」の自動検証をすべて実行する。
5. 「10. 完了条件」の実機確認は、ユーザーから実機確認を指示された場合だけ行う。指示がなければ全項目を「未実施」として報告に載せる。
6. 「9. 境界と失敗時の挙動」の各行について、実装したコードの該当箇所（ファイルとメソッド）を一つずつ確認し、報告用に対応表を作る。

### 4. コミットと設計書の削除

1. 実装の差分だけをステージし、`feat: <表示名>を追加` としてコミットする（`COMMIT_RULES.md` に従い、`git add -A` は使わない）。
2. **設計書の削除は次の条件をすべて満たすときだけ行う。** 1つでも欠けていれば削除せず、設計書を残したまま報告する。
   - 「8. 実装手順」の全段階を完了した
   - 「確認事項」が0件である
   - 「3. 検証」の1〜4がすべて成功した
3. 「11. 残す判断」が「なし」以外なら、各項目を `00_docs/10_AIパーソナライズ/記録と整理.md` に従って、指定されたメモへ追記し、索引を更新する。
4. 設計書を削除する。`99_work/boss-design/` に他の設計書がなく `README.md` だけが残る場合も、`README.md` は残す。

   ```powershell
   git rm 99_work/boss-design/<boss_id>.md
   ```

5. `git grep -n "boss-design/<boss_id>"` で、削除した設計書へのリンクが残っていないことを確認する。
6. 削除と AIパーソナライズの更新を、`docs: <表示名>のボス設計書を削除` として別コミットにする。

### 5. 停止して報告

- 既定では、ここで止まって作業ツリーを保持する。`develop` への反映は、上位モデルのレビュー（`$astralrecord-boss-design-author` の「実装後のレビュー」）の後に行う。
- ユーザーが「develop まで反映」と明示した場合だけ、`$astralrecord-code-review` と `$astralrecord-git-worktree-develop` の完了処理へ進む。

日本語で次の形式にする。

```markdown
## 実装結果
- 設計書: `<パス>`（削除済み / 残置: <理由>）
- 完了した段階: <n> / <全段階数>

## 変更ファイル
- `<path>`: <変更内容>

## 採番した ID
| 用途名 | ID |
|:--|:--|

## 境界と失敗時の挙動の対応
| 状況 | 実装箇所 |
|:--|:--|

## 検証
- `<command>`: 成功 / 失敗 / 未実行（理由）
- 実機確認: 実施 / 未実施（全項目）

## ブランチ / 作業ツリー
- ブランチ: `<branch>`、コミット: `<hash> <message>`

## 確認事項
- なし / <止まった段階・設計書の該当箇所・食い違いの内容>
```
