# AstralRecord コードレビュー

## 確認する根拠

対象の成果物は読み取り専用で扱う。作業ルートの `AGENTS.md` から対象プロジェクトのガイドと、今回の判断に関係するパーソナライズの要望・機能判断を確認する。プラグインと API の実装規約は [plugin-code.md](../astralrecord-code/references/plugin-code.md) と [api-code.md](../astralrecord-code/references/api-code.md) を参照する。ワークスペーススキルのレビューでは、対象スキルと該当する `$skill-creator` の規則を読む。

依頼と確定条件を起点に、影響するコードと呼び出し元、既存テスト、スキーマや設定を照合して期待する挙動を確かめる。API・Web の公開契約はルート定義、入出力、呼び出し元、テストで確かめる。DB・Filebase の定義や戦闘バランスに関わる変更では該当箇所を確認する。

## 手順

1. 指定パス、機能、コミット範囲または作業差分を確認する。差分と変更された識別子から、影響する入口、呼び出し元、データ、設定を特定する。
2. 差分を通常の入口から追い、期待と実際を比較する。対象に合わせて境界値、失敗時の処理、状態遷移、再試行・並行性、データの互換性、認可、実行負荷、テストの前提を確認する。文書の変更も判断に必要な根拠と照合する。
3. 指摘には、成立する入力・状態・操作、期待と実際の差、その影響と確認した根拠を添える。未使用と判断する場合は登録や設定による呼び出しも確認する。一般的なエンジニアリング実務に基づく指摘は判断理由を示す。
4. 期待する挙動や成立条件を確定できない場合は、必要な判断とその理由を質問として返す。失敗の根拠と期待する挙動がそろい、確定条件の範囲で修正できる指摘を自動修正可とする。
5. 非自明な範囲では `AGENTS.md` の方針に従い、利用可能なら実装者から独立した読み取り専用レビューも行う。セキュリティ、並行性、データ整合性、複数プロジェクトでは必要に応じて異なる観点の担当を追加する。調整役が根拠を照合して結果をまとめる。

## 引き継ぎ

[レビューの共通書式](../_shared/review-record-format.md) で指摘と質問を会話または担当の返答に記載し、修正が必要な場合は `$astralrecord-code-fix` に渡す。指摘がない場合はその旨と、残る質問や検証上の制約を報告する。

再レビューは前回の指摘と修正結果を同じタスクで受け取り、該当箇所を確認して解消状況、新しい回帰、残る質問を返す。ファイル形式が明示的に必要な場合は、依頼された保存先を使う。保存先の指定がなければ作業ツリー外の一時ファイルとする。
